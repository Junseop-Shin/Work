# 테스트 도구 종합 비교 (Vitest / Jest / Testing Library / Playwright / Storybook + JUnit / pytest / Go / RSpec)

> 2026-06-08 | 테스트, Vitest, Jest, TestingLibrary, Playwright, JUnit, pytest, BDD, TestDouble

## 한 줄 요약

테스트 프레임워크는 **러너 · 어서션 · 더블** 세 책임의 조합이며, 언어 생태계마다 이 셋이 "통합형(JS) ↔ 조립형(Java)"으로 갈린다. 도구 선택의 근거는 결국 **테스트 비중 철학(피라미드 vs 트로피)** 과 **빌드 환경(Vite냐 아니냐)** 에서 나오고, 현대 도구의 공통 진보는 **auto-waiting**(flaky 제거)과 **fluent 어서션**(풍부한 실패 메시지)이다.

## 핵심 개념

### 테스트 프레임워크 = 3개 레이어의 조합

"Jest", "pytest"를 하나의 덩어리로 보면 도구 비교가 안 된다. 사실은 **3가지 책임**이 합쳐진 것:

| 레이어 | 하는 일 | 예시 |
|--------|---------|------|
| **러너(Runner)** | 테스트 파일 탐색·실행·병렬화·리포트 | Vitest, Jest, pytest, `go test` |
| **어서션(Assertion)** | `expect(x).toBe(y)` 등 단언 | Jest `expect`, Chai, AssertJ, `assert` |
| **더블(Test Double)** | mock/stub/spy 생성 | `vi.fn`, Mockito, `unittest.mock` |

**통합형 vs 조립형** — 첫 번째 큰 비교축:

- **JS (Jest/Vitest)** = 셋 다 내장(배터리 포함) → 입문 쉬움
- **Java (JUnit)** = 러너만. 어서션은 AssertJ, 목은 Mockito를 따로 끼움 → 조립식
- **Python (pytest)** = 러너 + 어서션(`assert` 재활용)은 내장, 목은 표준 `unittest.mock` → 반조립

### 테스트 분류 — 피라미드 vs 트로피 (도구 선택의 근거)

```
        E2E (느림, 비쌈, 신뢰도 높음)
       ────────
      통합 (Integration)
    ──────────────
   단위 (Unit) (빠름, 쌈, 격리)
  ────────────────────
```

- **피라미드 (Mike Cohn)**: 단위가 제일 많고 E2E는 소수. 백엔드/로직 중심에 적합.
- **테스팅 트로피 (Kent C. Dodds, 프론트엔드)**: **통합 테스트가 제일 두꺼워야** 한다. 이유 → 프론트엔드 버그는 "함수 하나가 맞나"보다 "컴포넌트들이 같이 잘 도나"에서 나오고, 단위 테스트는 리팩터링에 너무 잘 깨진다(brittle). 맨 아래엔 **정적 분석(TS/ESLint)** 을 깐다.

> 도구 선택은 이 비중 철학에서 나온다. 트로피를 믿으면 Testing Library(통합)에 무게 + Playwright는 핵심 플로우만, 피라미드를 믿으면 Vitest 단위 테스트를 잔뜩.

## JS/TS 생태계

### Vitest vs Jest — 러너 비교

둘 다 API가 거의 같다(`describe/it/expect`). **차이는 내부 구조**에 있다.

| | **Jest** | **Vitest** |
|---|---|---|
| 출신 | Facebook, 2014. CRA 시대 표준 | Vite 팀, 2021 |
| 모듈 | 기본 CommonJS, ESM 까다로움 | **ESM 네이티브** |
| 트랜스폼 | babel-jest로 별도 변환(느림) | **Vite 변환 파이프라인 재사용** (`vite.config` 그대로) |
| 속도 | 느린 편(콜드 스타트) | 빠름 (esbuild + HMR식 watch) |
| 설정 | `jest.config` 별도 | 앱 Vite 설정 공유 → 중복 없음 |

**왜 Vitest가 빠른가 (본질):** Jest는 테스트 시 babel로 코드를 *다시* 변환한다. Vitest는 이미 앱을 돌리는 Vite의 변환 결과를 **공유**하고, watch에서 바뀐 모듈만 다시 돈다. "**변환을 두 번 안 한다**"가 속도의 핵심.

**Jest는 죽었나?** 아니다. Next.js(웹팩/Turbopack), React Native 등 비-Vite 환경에선 Jest가 자연스럽다. 기준선: **빌드 도구가 Vite면 Vitest, 아니면 Jest.**

> 어서션 `expect`, 스냅샷, `toBe`(참조 동등) vs `toEqual`(구조 동등)은 둘이 사실상 동일.

### Testing Library — "유저처럼" 테스트하는 철학 레이어

러너가 아니라 Vitest/Jest 위에 얹는 **쿼리 + 철학** 레이어. 핵심 명제:

> "테스트가 실제 사용 방식을 닮을수록 신뢰도가 높다" — 구현 디테일(state 값, 내부 함수명, className)을 보지 말고 화면/접근성 트리로 테스트하라.

**쿼리 우선순위:** `getByRole`(1순위, 접근성 역할) > `getByLabelText` > `getByText` > ... > `getByTestId`(최후의 수단 — 유저는 testid를 모름).

**`getBy` / `queryBy` / `findBy` — 자주 헷갈리는 3종:**

| 접두사 | 못 찾으면 | 비동기 | 용도 |
|--------|-----------|--------|------|
| `getBy` | **에러** | X | 있어야 하는 요소 |
| `queryBy` | **null 반환** | X | **없어야 함** 단언 (`toBeNull`) |
| `findBy` | 에러(재시도) | **O (Promise)** | 비동기로 나타날 요소 |

> 함정: 부재 확인에 `getBy`를 쓰면 못 찾자마자 에러로 테스트가 죽는다. 부재는 반드시 `queryBy`.

**`user-event` vs `fireEvent`:** `fireEvent.click`은 click 이벤트 하나만 쏜다. 실제 클릭은 hover→mousedown→focus→mouseup→click 시퀀스이고 `user-event`가 이걸 재현 → 현재 권장.

**`act()` 경고(React):** 상태 업데이트가 렌더 완료 전에 단언됐다는 뜻. `findBy`/`waitFor`로 대부분 자동 해결.

### Playwright vs Cypress — E2E 비교

| | **Playwright** | **Cypress** |
|---|---|---|
| 출신 | Microsoft, 2020 | Cypress.io, 2017 |
| 실행 구조 | 브라우저 **밖**에서 제어(프로토콜) | 브라우저 **안**에서 실행 |
| 멀티 브라우저 | Chromium/Firefox/WebKit 전부 | Chromium 계열 위주 |
| 멀티 탭/도메인 | 자유로움 | 구조상 제약 큼 |
| 병렬 | 무료로 강력 | 유료 대시보드 의존 컸음 |
| 언어 | TS/JS/Python/Java/.NET | JS/TS only |
| 디버깅 | Trace Viewer(타임라인+DOM 스냅샷) | 타임 트래블 UI |

**본질 — "어디서 도느냐":** Cypress는 테스트가 **브라우저 안**에서 돌아 앱과 런타임 공유 → 디버깅 직관적이나 다른 탭/출처/파일시스템에 약함. Playwright는 **밖에서** 표준 프로토콜로 조종 → 멀티 브라우저/탭/도메인 자유, 병렬 강함.

**공통 강점 — auto-waiting:** Selenium 시절의 `sleep(2000)` 떡칠이 사라짐. "요소가 클릭 가능해질 때까지 자동 대기" → **flaky 테스트 급감**. 차세대 E2E의 핵심 진보. 신규 프로젝트는 **Playwright가 사실상 디폴트** 추세.

### Storybook — 컴포넌트 격리 & 시각 테스트

러너가 아니라 **컴포넌트를 앱에서 떼어내 독립 렌더하는 워크벤치**. 테스트 생태계와 엮이는 지점:

- **CSF(Component Story Format)**: 각 상태를 story로 선언 → 테스트 입력으로 재활용
- **play function**: story 안에서 user-event 시뮬레이션
- **비주얼 회귀(Chromatic 등)**: story 스크린샷 픽셀 비교 → "코드는 안 깨졌는데 **레이아웃이 틀어진**" 버그 포착. 로직 단언으론 못 잡는 영역.

> 자리매김: Storybook = **"보이는 것"의 테스트(시각)**, Testing Library/Playwright = **"동작하는 것"의 테스트**. 상보적.

### MSW — 레이어를 가로지르는 네트워크 모킹

전통적으론 `fetch`를 mock으로 바꿔치기(`vi.mock`) → "구현(axios냐 fetch냐)"에 테스트가 묶임. **MSW는 서비스 워커/인터셉터 레벨에서 네트워크 자체를 가로채** 가짜 응답을 준다:

- 앱 코드는 진짜 `fetch` 호출(구현 안 바꿈) → 더 현실적
- **같은 핸들러를 단위 테스트·Storybook·개발 서버·E2E에서 재사용** → mock 중복 제거

## 크로스 언어 — 다른 생태계의 테스트 도구

앞의 **러너/어서션/더블 3분할** 틀로 보면 차이가 선명하다.

### Java — JUnit + 조립식

- **JUnit 5 (Jupiter)**: 러너 + 기본 어서션(`assertEquals`)만. 모듈식(Platform/Jupiter/Vintage) 재설계.
- 실무 조합: **JUnit(러너) + AssertJ(fluent 어서션) + Mockito(목)** 끼워 맞춤.
- `@ParameterizedTest`: 입력 세트 반복(JS의 `it.each`).
- 철학: 엔터프라이즈 → 명시적·어노테이션 중심·타입 안전.

### Python — pytest vs unittest

- **unittest**: 표준 라이브러리. JUnit을 본떠 클래스 기반(`class Test(TestCase)`), `self.assertEqual` → 장황(boilerplate).
- **pytest**: 사실상 표준. 차별점 3가지:
  1. **평범한 `assert` 문** + **assertion rewriting**(실패 시 `assert a == b`를 분해해 "왜 다른지" 자동 출력) → `assertEqual` 군 불필요
  2. **fixture 시스템**: `@pytest.fixture` + 의존성 주입식. setUp/tearDown보다 조합성↑ (scope: function/module/session)
  3. **`@pytest.mark.parametrize`**: 파라미터화
- 목은 표준 `unittest.mock`(`MagicMock`, `patch`)을 가져다 씀.

### Go — `go test` (언어 내장)

- 테스트가 **언어/툴체인에 내장** → "표준 하나로 통일"이라는 Go 철학. 별도 프레임워크 설치 없음.
- 어서션 라이브러리 기본 없음 → `if got != want { t.Errorf(...) }` 수동(testify를 많이 끼움).
- **Table-driven test**: 슬라이스에 케이스를 담아 루프 → 파라미터화의 Go식 관용구.
- **벤치마크(`Benchmark*`)·퍼즈(`Fuzz*`)** 가 표준 포함.

### Ruby — RSpec / .NET — xUnit

- **RSpec(Ruby)**: BDD 스타일의 원조격. `describe`/`it`/`expect(x).to eq(y)` — JS의 Jasmine/Jest가 여기서 영향.
- **.NET**: xUnit/NUnit/MSTest 3파전, **xUnit**이 현대 표준. 생성자=setup, `IDisposable`=teardown으로 언어 기능 재활용.

### 어서션 스타일 계보

- **xUnit 계열(고전)**: `assertEqual(expected, actual)` — JUnit3, unittest. 인자 순서 헷갈림.
- **fluent 계열(현대)**: `expect(actual).toBe(...)` / `assertThat(actual).isEqualTo(...)` — Jest, RSpec, AssertJ. 읽으면 영어 문장 + 실패 메시지 풍부.

## BDD vs Fluent — 자주 뭉뚱그리는 두 개념

§ 어서션 계보에서 묶이지만 **직교하는 별개 개념**이다.

### Fluent — "어서션 작성 스타일(문법)"

테스트 전용이 아닌 일반 API 패턴. **메서드가 자기 자신/다음 객체를 반환해 점(`.`)으로 체이닝**:

```java
// AssertJ — 읽으면 영어 문장
assertThat(user.getAge()).isGreaterThan(18).isLessThan(65);
```

**이득 2가지:**
1. 가독성 — 왼→오 자연어처럼 읽힘
2. **실패 메시지 풍부** — `isGreaterThan(18)`은 도구가 "기대값·실제값·관계"를 다 알아 친절한 에러를 뱉음. 고전 `assertTrue(age > 18)`은 도구가 `false`만 봐서 "true이길 바랐는데 false"밖에 못 말함.

### BDD (Behavior-Driven Development) — "방법론"

TDD에서 파생. 문제의식 → "test"라는 단어가 개발자를 내부 함수 검증으로 빠지게 함. Dan North가 "**test 말고 behavior로 생각하자**"고 제안.

**전환: "이 함수를 테스트한다" → "이 시스템은 이렇게 *행동해야 한다*"**

```js
describe('장바구니', () => {
  it('상품을 추가하면 총액이 증가한다', () => { ... })
})
// "장바구니는, 상품을 추가하면 총액이 증가한다"
```

**Given-When-Then**: Given(전제) / When(행동) / Then(기대). 비개발자도 읽는 명세가 목표. 극단으론 **Cucumber/Gherkin**처럼 자연어(`.feature`)로 시나리오를 쓰고 코드와 연결.

### 둘의 관계 (직교 확인)

BDD 운동이 fluent 어서션을 유행시켰다 — "행위를 *문장처럼* 명세"하려면 어서션도 문장처럼 읽혀야 했기 때문. RSpec → Jasmine → Jest로 전파되며 JS의 `describe/it/expect`는 **BDD(구조) + fluent(어서션)** 한 세트로 굳음. 하지만 분리 가능:

| | 고전 구조 (`@Test` 메서드) | BDD 구조 (`describe/it`) |
|---|---|---|
| **고전 어서션** | JUnit4 + 기본 assert | (드묾) |
| **fluent 어서션** | JUnit5 + AssertJ ← Java 실무 | Jest, RSpec ← JS/Ruby |

> 정리: **fluent = 어서션을 어떻게 쓰냐(문법), BDD = 테스트를 무엇으로 보냐(행위 명세 방법론).** "영어 문장처럼 읽히게"라는 공통 동기로 자주 같이 다닐 뿐.

## Test Double 4종 — 언어 불문 핵심 (Meszaros 분류)

| 용어 | 뜻 | 예 |
|------|----|----|
| **Dummy** | 자리만 채움, 안 쓰임 | 인자 채우기용 null |
| **Stub** | 정해진 값을 **반환**만 | "이 API는 항상 200" |
| **Spy** | Stub + **호출 기록** | "이 함수 몇 번 불렸나" |
| **Mock** | 호출 **기대를 미리 설정**하고 검증 | "save가 정확히 1번 불려야 통과" |
| **Fake** | 동작하는 **경량 구현** | 인메모리 DB |

> 자주 틀림: 다 "mock"이라 뭉뚱그리지만 **상태 검증(Stub/결과 확인) vs 행위 검증(Mock/호출 검증)** 은 설계 철학이 다르다. 행위 검증 남발 → 구현에 묶인 brittle 테스트.

## 핵심 질의응답

**Q. 테스트 프레임워크는 왜 언어마다 통합형/조립형으로 갈리나?**
A. 러너·어서션·더블 3책임 중 무엇을 내장하느냐 차이다. JS는 셋 다 내장(Jest/Vitest), Java는 러너(JUnit)만 두고 AssertJ·Mockito를 조립, Python은 러너+어서션 내장에 목만 표준 라이브러리를 끌어다 쓰는 반조립.

**Q. Vitest가 Jest보다 빠른 본질적 이유는?**
A. Jest는 테스트 시 babel로 코드를 다시 변환하지만, Vitest는 앱을 돌리는 Vite의 변환 파이프라인을 그대로 공유해 변환을 두 번 하지 않는다. watch에서도 바뀐 모듈만 다시 돈다.

**Q. `getBy`/`queryBy`/`findBy`는 언제 뭘 쓰나?**
A. 있어야 하는 요소는 `getBy`(없으면 에러), 없어야 함을 단언할 땐 `queryBy`(null 반환), 비동기로 나타날 요소는 `findBy`(Promise, 재시도).

**Q. Playwright와 Cypress의 가장 근본적 차이는?**
A. 테스트가 도는 위치다. Cypress는 브라우저 *안*에서 실행돼 앱과 런타임을 공유(디버깅 직관적이나 멀티 탭/도메인 약점), Playwright는 *밖*에서 프로토콜로 조종(멀티 브라우저/탭/도메인 자유, 병렬 강함).

**Q. BDD와 fluent는 같은 건가?**
A. 직교한다. fluent는 `.isEqualTo()`처럼 어서션을 체이닝으로 쓰는 문법 스타일, BDD는 함수가 아니라 행위(behavior)를 명세하듯 테스트를 쓰는 방법론. BDD가 fluent를 유행시켜 자주 같이 보일 뿐, AssertJ는 fluent지만 BDD 구조는 아니다.

**Q. MSW가 `vi.mock` 방식 모킹보다 나은 점은?**
A. 네트워크 레벨에서 가로채 앱 코드가 진짜 `fetch`를 호출하므로 구현(axios/fetch)에 안 묶이고 더 현실적이며, 같은 핸들러를 단위·Storybook·E2E에서 재사용해 mock 중복을 없앤다.

## 주의사항 / 자주 하는 실수

- **커버리지 100%의 함정** — 커버리지는 코드가 *실행됐나*지 *검증됐나*가 아니다. 단언 없이 호출만 해도 오른다. 빈 곳 찾는 용도지 품질 지표가 아님.
- **구현 디테일 테스트** — 내부 state·private 메서드를 테스트하면 리팩터링마다 깨진다(트로피가 경계하는 지점).
- **flaky 테스트** — `sleep` 고정 대기, 테스트 간 순서 의존, 공유 상태. auto-waiting 도구로 상당수 해소.
- **mock 과다** — 다 mock하면 "내 mock을 테스트"하는 꼴. 통합 테스트는 진짜에 가깝게.
- **E2E 과다** — 느리고 flaky. 트로피대로 핵심 플로우만.
- **부재 확인에 `getBy`** — 못 찾자마자 에러로 죽음. `queryBy`를 써야 함.
