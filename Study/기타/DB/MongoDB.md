# MongoDB — 문서 DB

> 2026-06-08 | MongoDB, NoSQL, 문서DB, BSON, 임베딩, 샤딩

## 한 줄 요약

MongoDB는 **"같이 읽는 데이터는 한 문서에 통째로 담아 조인을 피하는"** 문서 DB다. schema-on-read(읽을 때 구조 해석)와 단일 문서 원자성이 핵심이고, 설계의 승패는 **임베딩 vs 레퍼런싱**에서 갈린다.

## 핵심 개념

### 왜 MongoDB — 문서 모델

RDB는 데이터를 테이블(행/열)로 쪼개 저장하고 조인으로 합친다. Mongo는 **문서(document)** 하나에 통째로 담는다:

```js
// RDB라면 users + posts + comments 3개 테이블 + 조인
{ _id: ObjectId("..."), name: "Jun",
  posts: [ { title: "Redis 정리", comments: ["good", "thanks"] } ] }
```

철학 = **"같이 읽는 데이터는 같이 저장"** → 조인 없이 문서 하나 읽으면 끝. 용어 매핑:

| MongoDB | RDB |
|---------|-----|
| 컬렉션(collection) | 테이블 |
| **문서(document)** | **행(row)** = "아이템 1개" |
| 필드(field) | 컬럼 |

### BSON vs JSONB

둘 다 "바이너리 JSON"이지만 **설계 위상이 다르다.**

| | **BSON** (MongoDB) | **JSONB** (PostgreSQL) |
|---|---|---|
| 정체 | DB 전체의 **기본 저장·전송 포맷** | 테이블의 **한 컬럼 타입** |
| 타입 | **풍부** — Date, ObjectId, Decimal128, Binary, int32/64 | JSON 표준만 — Date·ObjectId **없음**(날짜도 문자열) |
| 키 순서 | 보존 | 보존 안 함 |
| 순회 | 필드마다 길이 prefix → 스킵 빠름, **전송(wire)에도 사용** | PG 내부 저장 전용 |

→ **BSON = "DB의 네이티브 데이터 포맷"**(타입 풍부, 클라이언트↔서버 전송 겸용), **JSONB = "RDB 안의 JSON 컬럼"**(표준 JSON, 인덱싱 최적화). Mongo는 BSON으로 *전부*를 표현하고, PG는 JSONB를 *정형 데이터 옆에* 둔다. (참고: BSON은 필드명을 매 문서마다 반복 저장 — 스키마 자유의 대가)

### 임베딩(embedding) vs 레퍼런싱(referencing)

Mongo 스키마 설계의 **가장 중요한 결정**. 조인이 없는 세계의 대안:

```js
// (A) 임베딩 — 자식을 부모 문서 안에
{ title: "글", comments: [{ text: "댓글1" }] }
// (B) 레퍼런싱 — 별도 컬렉션, _id로 참조 (RDB의 FK 비슷)
{ title: "글", _id: 1 } / { text: "댓글1", postId: 1 }
```

**판단 기준 4가지:**
1. **같이 읽나** — 댓글은 글과 같이 봄 → 임베딩
2. **개수가 유한한가** — 무한정 늘면 임베딩 위험
3. **독립 조회하나** — 주문은 유저와 별개로 조회 → 레퍼런싱
4. **16MB** — Mongo 문서 하나는 **최대 16MB**. 무한정 늘어나는 배열을 임베딩하면 언젠가 터진다

→ **댓글 = 임베딩**(같이 읽고 종속, 유한), **주문 = 레퍼런싱**(독립 조회, 무한 증가). "문서가 너무 커지면 조회가 무거워진다"는 직관이 4번(16MB)과 연결.

## Aggregation Pipeline

조인이 없는 대신, **단계(stage)를 파이프로 이어** 데이터를 변형한다 (Unix 파이프 `|`처럼). SQL 절이 stage로 대응:

```js
db.orders.aggregate([
  { $match: { status: "paid" } },                              // WHERE
  { $group: { _id: "$userId", total: { $sum: "$amount" } } },  // GROUP BY + SUM
  { $sort:  { total: -1 } }                                    // ORDER BY
])
```

| SQL | stage |
|-----|-------|
| WHERE / GROUP BY / SELECT / ORDER BY / JOIN | `$match` / `$group` / `$project` / `$sort` / **`$lookup`** |

**선언적 vs 절차적:** RDB(SQL)는 *선언적*("뭘 원하는지"만, 옵티마이저가 방법 결정), Aggregation은 *절차적*("어떤 단계로 처리할지" 순서대로 직접 나열).

⚠️ **조인(`$lookup`)은 있지만 자주 쓰면 냄새** — Mongo 철학은 "임베딩으로 조인을 피한다"이므로, `$lookup`이 잦으면 **모델링이 잘못됐거나 RDB가 맞는 데이터**라는 신호. 성능: 파이프라인 **맨 앞 `$match`로 데이터를 줄여야** 한다(인덱스는 보통 첫 `$match`/`$sort`에서만 탐).

## 인덱스 & schema-on-read

오늘 PG에서 인덱스를 깊게 했으므로 **Mongo 특이점만**:

| Mongo | 발상 | PG 대응 |
|-------|------|---------|
| 단일/복합 | 좌측 prefix 동일 | B-tree |
| **멀티키**(배열) | 역색인 | **GIN** |
| 2dsphere | 공간 | GiST/PostGIS |
| text | 토큰화(약함) | FTS |
| hashed | 샤딩 키 분산 | Hash |

- **멀티키 인덱스** — 배열 필드에 인덱스 걸면 **자동으로** 원소마다 엔트리 생성(`"redis"→문서1`). PG의 GIN(`값→문서목록`)과 같은 원리. (복합 인덱스에 배열은 하나만 가능)
- **schema-on-read** — Mongo는 고정 스키마가 없다(schema-less). RDB는 쓰기 전 스키마 강제(schema-on-write)지만 Mongo는 구조를 **읽을 때 해석**. 그래서 Compass의 `Schema 탭`은 *정의된 스키마*가 아니라 **문서를 샘플링해 추론한** 통계. (원하면 `$jsonSchema`로 검증을 *옵션*으로 걸 수 있음)
- **인덱스 확인:** Compass `Indexes 탭` / `db.coll.getIndexes()` / `explain("executionStats")`(= PG의 EXPLAIN, `IXSCAN` vs `COLLSCAN`).

### ⚠️ 인덱스는 컬렉션 종속 — "매일 컬렉션 생성" 함정

**인덱스는 컬렉션마다 독립이다.** 새 컬렉션엔 `_id` 인덱스만 자동 생성되고, 나머지는 **안 따라온다.** "DB 레벨 글로벌 인덱스 설정"은 없다.

→ 매일 컬렉션이 생성되는 구조라면 생성 시 **`createIndex`를 코드로 같이** 호출해야 한다. 빠뜨리면 새 컬렉션은 조용히 풀스캔(COLLSCAN). 더 나은 대안:
- **TTL 인덱스** — `expireAfterSeconds`로 오래된 문서 자동 삭제(수동 drop 대체)
- **Time Series Collection (5.0+)** — 버킷팅·압축·인덱스 자동 관리
- **한 컬렉션 + 날짜 인덱스** — 인덱스 한 번이면 끝

> "컬렉션이 크면 무겁다"는 **인덱스 없을 때만.** 인덱스 워킹셋이 메모리(WiredTiger 캐시)에 들어가면 큰 컬렉션도 빠르다(= 오늘 PG 버퍼풀/워킹셋). 날짜별 컬렉션 분할은 *수동 파티셔닝*일 뿐.

## 트랜잭션 — 단일 문서 원자성 → 4.0 멀티문서

- **단일 문서 연산은 항상 원자적** — 한 문서(아이템) 안의 여러 필드를 동시에 바꿔도, 다른 읽기엔 "전부 바뀜" 또는 "전부 안 바뀜"만 보인다(중간 상태 없음). 그래서 **임베딩하면 트랜잭션이 필요한 상황 자체를 회피**한다.
- **4.0(2018) 멀티 문서 트랜잭션** — 임베딩으로 못 합치는 **독립 문서/컬렉션에 걸친 일관성**(계좌이체 A·B, 재고 차감+주문 생성)을 위해 추가.
- ⚠️ **트랜잭션은 안전망이지 일상 도구가 아니다** — 비싸다. 자주 쓰면 *설계가 RDB식으로 잘못됐거나, 애초에 RDB가 맞는 데이터*라는 신호(= [Shopify가 재고 예약을 MySQL ACID로 간 이유](../아티클/Shopify-재고예약-스케일링.md)).

**멀티문서 연산 예:** 계좌이체 / 재고 차감+주문 / 포인트 결제(잔액+내역) / 유저 삭제(여러 컬렉션 정리) / 카운터 동기화. 공통 = *비정규화·레퍼런싱으로 흩어진 사실이 같이 바뀌어야 하고, 일부만 성공하면 깨지는 경우.* 상당수는 임베딩으로 회피된다.

## 파티셔닝 & 샤딩

"키로 나누는" 발상은 같고, **어디에 나누냐가 갈린다:**

- **파티셔닝** = 키로 조각냄(보통 한 서버 안). 예: `logs_2026_06` 수동 컬렉션 분할.
- **샤딩** = 그 조각을 **여러 서버(샤드)에 분산** = 수평 파티셔닝 + 분산. **샤딩 ⊂ 파티셔닝.**

| | 수동 컬렉션 분할 | 샤딩 |
|---|---|---|
| 범위 | 한 서버(스케일 업) | **여러 서버**(수평 확장) |
| 앱 부담 | 라우팅 직접 구현 | **투명**(mongos가 라우팅) |
| 한계 | 한 서버 용량 못 넘음 | 서버 추가로 무한 |
| 운영 | 단순 | 복잡(config server·mongos·샤드) |

- **샤드 키** 선택이 핵심 — `createdAt`처럼 단조 증가 값을 쓰면 새 데이터가 전부 같은 샤드로 몰림(**hot shard**) → 분산 실패. 해시 키나 고르게 분산되는 복합 키를 써야 한다.
- 기준: 데이터가 **한 서버를 넘으면 샤딩**, 한 서버 내 관리 목적이면 TTL/Time Series/수동 분할. (= 오늘 PG 파티셔닝 vs Citus 샤딩)

## Cosmos DB (참고)

Azure의 글로벌 분산 멀티모델 DB. **MongoDB API**로 접속하면 Mongo 드라이버로 "Mongo처럼" 쓸 수 있지만 **엔진은 별개**(완전 호환 아님, RU 비용 모델). 시계열은 **파티션 키+TTL로 가능하지만 전용 자동화(연속집계 등)는 약해 직접 설계** 필요. 자동화가 핵심이면 TimescaleDB/Mongo TS가 우위.

## 핵심 질의응답

**Q. 댓글은 임베딩, 주문은 레퍼런싱 — 기준이 뭔가?**
A. ① 같이 읽나 ② 개수가 유한한가 ③ 독립 조회하나 ④ 16MB 한계. 댓글은 글과 같이 보고 종속·유한이라 임베딩, 주문은 독립 조회·무한 증가라 레퍼런싱. 무한정 늘어나는 배열 임베딩은 16MB에서 터진다.

**Q. BSON과 JSONB의 차이는?**
A. BSON은 MongoDB의 네이티브 저장·전송 포맷이라 Date·ObjectId·Decimal128 등 타입이 풍부하고 키 순서를 보존한다. JSONB는 PG의 한 컬럼 타입이라 JSON 표준 타입만 갖고 인덱싱(GIN)에 최적화돼 있다. 발상은 같지만 위상이 다르다.

**Q. 조인이 없는데 "유저별 주문 합계" 같은 집계는?**
A. Aggregation Pipeline로 단계를 직접 구현한다($match→$group→$sort). 조인 비슷한 $lookup도 있지만, 자주 쓰면 임베딩으로 재설계하거나 RDB가 맞는 신호다.

**Q. 배열 필드 인덱스는 PG의 무엇과 같나?**
A. GIN. Mongo에선 멀티키 인덱스라 부르고, 배열 원소마다 인덱스 엔트리를 자동 생성한다(값→문서목록 역색인).

**Q. 매일 컬렉션이 생성되는데 인덱스는 자동으로 만들어지나?**
A. 아니다. 인덱스는 컬렉션 종속이라 새 컬렉션엔 `_id`만 자동 생성되고 나머지는 안 따라온다. 생성 루틴에 `createIndex`를 같이 넣거나, TTL 인덱스/Time Series Collection으로 재설계하는 게 낫다.

**Q. 컬렉션이 너무 크면 관리 편하려고 키로 나눠 쓰는 거 아닌가?**
A. "키로 나누기" 발상은 맞지만, 컬렉션이 커서 무거운 건 인덱스가 없을 때(풀스캔)다. 인덱스 워킹셋이 메모리에 들어가면 큰 컬렉션도 빠르다. 날짜별 컬렉션은 수동 파티셔닝이며, 한 서버를 넘으면 샤딩이 진짜 해법이다.

**Q. Cosmos DB도 시계열 되나?**
A. 파티션 키+TTL로 저장·관리는 가능하지만 hypertable/연속집계 같은 전용 자동화는 약해 직접 설계해야 한다. 자동화가 핵심이면 TimescaleDB/Mongo Time Series가 낫다.

## 주의사항 / 자주 하는 실수

- **무한정 늘어나는 배열 임베딩** — 16MB 한계에서 터진다. 무한 증가 데이터는 레퍼런싱.
- **`$lookup`·트랜잭션 남발** — Mongo를 RDB처럼 쓰는 것. 모델링(임베딩)이나 DB 선택을 의심하라.
- **새 컬렉션에 인덱스 누락** — 조용히 COLLSCAN. 생성 루틴에 createIndex.
- **샤드 키를 단조 증가 값으로** — hot shard로 분산 실패.
- **schema-less를 "검증 없음"으로 방치** — 필요하면 `$jsonSchema` 검증을 옵션으로.
