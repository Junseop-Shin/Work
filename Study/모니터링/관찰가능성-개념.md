# 관찰가능성(Observability) — 개념

> 2026-06-10 | 모니터링, 관찰가능성, 메트릭, 트레이싱, SRE

## 한 줄 요약

관찰가능성은 **시스템이 내보내는 외부 신호(metric/log/trace)만으로 내부 상태를 추론**할 수 있는 시스템의 성질이다. 코드를 다시 배포하지 않고도 "예상 못 한 질문"에 사후 답할 수 있느냐가 핵심.

## 핵심 개념

### 모니터링 vs 관찰가능성

자주 섞이지만 결이 다르다.

- **모니터링(Monitoring)**: *미리 정해둔 질문*에 답함. "CPU 80% 넘으면 알려줘" → **알고 있는 문제(known-unknowns)** 감시.
- **관찰가능성(Observability)**: *미리 정하지 않은 질문*도 사후에 답할 수 있는 시스템 속성. "어제 밤 11시에 결제만 느려진 게 왜?" → **예상 못 한 문제(unknown-unknowns)** 추적.

> 어원은 제어이론: "외부 출력만 보고 내부 상태를 추론할 수 있으면 그 시스템은 observable하다." 즉 로그를 추가 배포하지 않고도 **이미 내보내는 신호만으로** 내부를 들여다볼 수 있느냐.

### 관찰가능성 3축 — Metrics / Logs / Traces

| 축 | 답하는 질문 | 형태 | 비용 | 카디널리티 |
|----|-----------|------|------|-----------|
| **Metrics** | "무엇이, 얼마나?" | 시계열 숫자(집계됨) | 매우 쌈 | 낮아야 함 |
| **Logs** | "정확히 무슨 일이?" | 타임스탬프 + 이벤트 텍스트 | 비쌈 | 높음 |
| **Traces** | "어디서 느려졌나?" | 요청의 서비스 간 경로 | 중간 | 높음 |

핵심은 **셋이 보완 관계**라는 점. 전형적 디버깅 릴레이:

```
1. Metric → 알림: "결제 API p99가 200ms→3s로 튐"        (무엇 / 감지)
2. Trace  → 느린 요청 추적: "payment→fraud-check 2.8s"  (어디 / 위치 특정)
3. Log    → fraud-check 그 시각: "DB pool exhausted"     (왜 / 원인 확정)
```

- **Metric = 감지(detection)**: 숫자로 "문제 있다"를 본다. 싸서 전부 상시 수집.
- **Trace = 위치 특정(localization)**: 수평적. 요청이 거쳐간 경로 중 **어느 구간**이 범인인지 좁힌다.
- **Log = 원인 확정(root cause)**: 수직적. 그 범인 안에서 **정확히 무슨 일**이 났는지 자백을 받는다.

Metric만으론 "느리다"는 알아도 어디/왜를 모르고, Log만 잔뜩 쌓으면 비싸고 추세를 못 본다.

### LGTM 스택

세 축(+시각화)을 Grafana 진영 도구로 채운 것:

- **L**oki → Logs
- **G**rafana → 셋을 한 화면에 묶는 **시각화 / 상관(correlation) 레이어**
- **T**empo → Traces
- **M**imir(또는 Prometheus) → Metrics

> "M=Mimir"는 Grafana Labs 자사 제품 브랜딩일 뿐, **실제 현장에서 M 자리는 대부분 Prometheus**. Mimir/Thanos/VictoriaMetrics는 Prometheus를 대체하는 게 아니라 규모가 커질 때 뒤에 붙이는 장기저장·수평확장 레이어다(PromQL 그대로). 상세 → [실전 문서](Prometheus-Grafana-Loki.md#운영-아키텍처--저장소는-어떻게-관리하나)

## 분산 트레이싱 & Tempo

### 왜 트레이싱이 따로 필요한가

모놀리식이면 스택트레이스 하나로 끝나지만, 요청 하나가 `gateway → auth → payment → fraud → DB`처럼 **여러 서비스를 건너다니면** 각 서비스 로그는 자기 조각만 안다. "전체가 3초인데 어디서?"를 답하려면 조각들을 하나로 꿰는 실이 필요하다.

### Trace / Span / Context Propagation

```
Trace (trace_id = abc123)  ← 요청 1건 전체
├─ Span: gateway   [0 ──────────── 3000ms]  (root)
│  ├─ Span: auth   [10 ─ 50ms]
│  └─ Span: payment[60 ───────── 2990ms]
│     └─ Span: fraud[100 ────── 2900ms]  ← 범인 (2.8s)
│        └─ Span: db [120 ─── 2850ms]
```

- **Span**: 작업 단위 하나(함수/쿼리). 시작·종료 시각 + 부모 span 참조 + 태그(`http.status=500`).
- **Trace**: 같은 `trace_id`를 공유하는 span 트리. 요청 1건 = trace 1개.
- **Context Propagation**(핵심): 서비스 A→B 호출 시 **HTTP 헤더(`traceparent`)에 trace_id와 부모 span_id를 실어** 보냄. B는 그걸 자기 span의 부모로 연결 → 네트워크 경계를 넘어 trace가 이어짐. 폭포수(waterfall)를 그리면 어느 구간이 길었는지 한눈에.

### OpenTelemetry(OTel) — 계측 표준

- 예전엔 벤더마다 SDK가 달라 락인이 심했음. **OpenTelemetry = 벤더 중립 계측 표준(CNCF)**. 코드에 OTel SDK로 한 번 심으면 백엔드(Tempo/Jaeger/Datadog)만 바꿔 낀다.
- traces/metrics/logs **3축을 다 포괄**하는 방향으로 확장 중. 요즘 계측의 사실상 디폴트.
- **자동 계측**: Express/gRPC/HTTP 클라이언트 등 인기 라이브러리는 코드 수정 없이 span 자동 생성.

### Tempo의 특징 — Loki와 같은 철학

- Tempo도 인덱스를 최소화한다. 사실상 **`trace_id`로만 조회**하고 trace 본문은 object storage(S3)에 통째로 저장 → 매우 쌈.
- "trace_id를 어떻게 아냐?" → **여기서 3축이 연결됨**: 메트릭의 **exemplar**(메트릭에 붙은 샘플 trace_id)나 로그의 `trace_id` 필드를 클릭 → Grafana가 Tempo로 점프. Tempo는 전체 검색이 약한 대신 싸고, 진입점은 metric/log가 준다.

### 샘플링 — 트레이싱의 함정

모든 요청을 다 저장하면 양이 폭발 → 샘플링한다.

- **Head 샘플링**: 요청 시작 때 저장/버림 결정(예: 1%). 싸지만 **에러난 요청을 버릴 수 있음**.
- **Tail 샘플링**: 요청 끝난 뒤 결과 보고 결정("느렸거나 에러난 것만 저장"). 똑똑하지만 모든 span을 일단 모아야 해 무겁고 복잡.
- 트레이드오프: 비용 vs "정작 보고 싶은(느린/에러) 요청을 놓치지 않기".

## 메트릭 타입 4종 — Counter / Gauge / Histogram / Summary

> 면접 단골. 타입을 잘못 고르면 쿼리가 의미를 잃는다. **단일 값 2개(Counter/Gauge) + 분포 2개(Histogram/Summary)**.

### Counter — 단조 증가(monotonic)

오직 증가만 하거나 0으로 리셋(재시작). 누적 총량.

```
http_requests_total   1,523,492   ← 켜진 이후 누적 요청 수
```

- 절대값 자체는 거의 안 본다("누적 152만"은 의미 없음). 항상 `rate()`로 감싸 **초당 변화율**을 본다 → **Counter는 rate와 세트**.
- 왜 누적으로 저장? "초당 값"을 직접 저장하면 scrape 한 번 놓치면 데이터가 영영 사라짐. 누적값은 **scrape를 몇 번 놓쳐도 차이로 복원** 가능.
- 대상: 요청 수, 에러 수, 처리 바이트, 완료 작업 수.

### Gauge — 임의로 오르내림

현재 상태 스냅샷.

```
node_memory_used_bytes   8,234,123,456
queue_depth                       47
active_connections               128
```

- 절대값 그대로가 의미 있음. `rate()` 씌우면 안 됨.
- 대상: 메모리/CPU 사용량, 큐 길이, 동시 접속 수, 온도.
- **Counter vs Gauge 판별**: "이 값이 줄어들 수 있나?" 줄면 Gauge, 절대 안 줄면(누적) Counter.

### Histogram — 분포를 버킷으로

평균은 거짓말을 한다(평균 100ms여도 1%가 10초일 수 있음). 분포를 봐야 한다. Histogram은 **버킷 경계(`le` = ≤)별 누적 카운트**를 내보낸다.

```
http_request_duration_seconds_bucket{le="0.1"}   8000   ← 0.1s 이하
http_request_duration_seconds_bucket{le="0.5"}   9500   ← 0.5s 이하 (누적!)
http_request_duration_seconds_bucket{le="+Inf"} 10000
http_request_duration_seconds_sum               1234.5
http_request_duration_seconds_count            10000
```

- 버킷은 **누적(cumulative)** → 분위수 계산 가능: `histogram_quantile(0.95, ...)`.
- **핵심 장점: 집계 가능.** 인스턴스 10대의 버킷을 `sum by(le)`로 합친 뒤 분위수를 내면 **전체 시스템의 진짜 p95**가 나온다(원재료가 서버에 있으니).
- 함정: 분위수 정확도가 **버킷 경계에 의존**. 내 latency 분포에 맞게 버킷을 설계해야 함.

### Summary — 클라이언트가 분위수를 직접 계산

```
http_request_duration_seconds{quantile="0.95"}  0.8
http_request_duration_seconds{quantile="0.99"}  2.1
```

- **결정적 단점: 집계 불가.** 인스턴스 A p99=2.1, B p99=1.8을 평균/합산하면 수학적으로 틀림(분위수는 합산 불가 통계량). 여러 인스턴스 전체 p99를 구할 방법이 없음.
- 미리 정한 분위수만 볼 수 있음(p95만 내보냈으면 p90은 영영 못 봄).

### Histogram vs Summary — 결론

| | Histogram | Summary |
|---|-----------|---------|
| 분위수 계산 | **서버**(쿼리 시) | 클라이언트(수집 시) |
| **여러 인스턴스 집계** | ✅ 가능 | ❌ 불가 |
| 분위수 유연성 | 사후 아무 분위수나 | 미리 정한 것만 |
| 정확도 | 버킷 경계 의존 | 정확 |

👉 **실무는 거의 항상 Histogram** — 분산 시스템에서 여러 인스턴스를 집계해 전체 분위수를 봐야 하므로. Summary는 단일 인스턴스 + 정확도가 중요한 특수 경우만.

## 대시보드 설계 방법론 — RED / USE

> 가장 흔한 실수는 "보이는 메트릭을 다 늘어놓는 것". RED/USE는 "무엇을 봐야 하는가"의 검증된 프레임.

### RED — 서비스(요청 흐름) 관점

사용자 요청을 처리하는 모든 것(API, 웹서버, 마이크로서비스)에 적용. Tom Wilkie(Grafana Labs).

| | 의미 |
|---|------|
| **R**ate | 초당 요청 수(처리량) |
| **E**rrors | 초당 실패 수(또는 비율) |
| **D**uration | 요청 지연 분포(p50/p95/p99) |

- 이 3개만으로 "서비스가 사용자에게 건강한가"를 안다. Rate=0(라우팅/LB 문제), Errors 급증(깨짐), Duration 급증(의존성 문제).
- RED는 **사용자 체감**에 집중 → **SLO/알림의 1순위 기준**.

### USE — 리소스(자원) 관점

머신 자원(CPU/메모리/디스크/네트워크)에 적용. Brendan Gregg(Netflix). **각 자원마다** U/S/E를 본다.

| | 의미 | 예 |
|---|------|----|
| **U**tilization | 사용률(일하는 시간 비율) | CPU 80% |
| **S**aturation | 포화(처리 못 해 **대기 중인** 양) | run queue, swap, I/O wait |
| **E**rrors | 에러 이벤트 수 | 디스크 read error, 패킷 드롭 |

- **핵심 통찰: Saturation이 진짜 신호.** Utilization 100%가 곧 문제는 아님(풀로 잘 쓰는 중일 수도). 진짜 위험은 **처리 능력을 초과해 줄 서서 대기**하는 양. CPU run queue가 쌓이고 swap이 시작되면 그때부터 급격히 느려진다.

### RED vs USE — 언제 무엇을

```
사용자 요청을 받는 것  →  RED  (서비스, API)
자원을 소비하는 것    →  USE  (CPU, 메모리, 디스크)
```

둘은 보완 관계. 대시보드 한 장에 같이 둔다:

```
┌─ 상단: RED (서비스 건강) ──────────┐   ← 먼저 본다 (사용자 영향)
│  [요청률] [에러율] [p95/p99 지연]   │
├─ 하단: USE (자원 상태) ────────────┤   ← 원인 파악 (왜 느린가)
│  [CPU U/S] [메모리 U/S] [디스크]    │
└─────────────────────────────────────┘
```

장애 흐름: RED에서 "p95가 튐"(증상) → USE에서 "메모리 saturation, swap 시작"(원인).

### Four Golden Signals (Google SRE)

RED에 Saturation을 더한 것: **Latency + Traffic + Errors + Saturation = RED + S**. 셋 다 같은 철학(**사용자 영향 지표를 먼저, 적게**).

## 알림 철학 — Alert Fatigue 방지

> 알림 시스템의 성공은 "얼마나 많이 잡냐"가 아니라 **"불필요한 걸 얼마나 안 울리냐"**. (Alertmanager 구현 → [실전 문서](Prometheus-Grafana-Loki.md#알림--alert-rule--alertmanager))

### 알림 피로(Alert Fatigue)

알림이 너무 많거나 부정확해 **사람이 알림을 무시하기 시작하는** 상태. "양치기 소년" 문제 — 거짓·중복 알림이 쌓이면 팀이 알림을 끄고, 정작 중요한 알림을 놓친다.

### Symptom-based alerting (증상 기반) — 핵심 철학

```
❌ Cause-based  : "CPU 90%", "메모리 80%"     → 자원마다 알림 → 노이즈 폭발
✅ Symptom-based: "에러율 1% 초과", "p99 > SLO" → 사용자가 아플 때만
```

- CPU 90%여도 사용자가 멀쩡하면 깨울 일이 아니다. 반대로 CPU는 낮은데 사용자가 에러를 겪으면 그게 진짜 장애.
- **페이저(긴급 알림)는 사용자가 실제로 아플 때만.** 자원 지표는 **알림이 아니라 대시보드**로 본다. → **알림 = RED, 대시보드 = RED + USE**.

### SLO 기반 알림 — Error Budget & Burn Rate

성숙한 조직은 고정 임계값("에러율 5%")이 아니라 **SLO 소진 속도**로 알린다.

- **SLO**: "99.9% 성공"(한 달 허용 실패 = 0.1% = **error budget**).
- **Burn rate**: error budget을 얼마나 빨리 태우는가.
  - 천천히 새면 → warning(업무시간 확인)
  - 1시간 만에 한 달 치 소진 → critical(즉시 깨움)
- **Multi-window burn rate**(빠른 창 + 느린 창 동시 충족)가 정석 — "이 속도면 SLO를 깰 것이다"가 훨씬 적게·정확하게 울린다.

## 핵심 질의응답

**Q. 메트릭으로 문제를 발견하고, 트레이스와 로그로 원인을 분석한다는 거지?**
A. 정확하다. Metric=감지, Trace=위치 특정(어느 서비스/구간), Log=원인 확정(그 안에서 무슨 일). 트레이스로 용의자를 한 명으로 추리고, 로그로 자백을 받는 그림.

**Q. LGTM을 같이 쓰면 좋은 이유는?**
A. 3축이 **공통 라벨과 `trace_id`로 서로 연결**되고, Grafana가 그 점프를 한 화면에서 중개하기 때문. metric 스파이크 클릭 → 그 시각 log → log의 trace_id 클릭 → trace 폭포수. 도구는 3개지만 사용자 경험은 하나.

**Q. 대시보드에 무엇을 넣어야 하나?**
A. 보이는 메트릭을 다 넣는 게 아니라 RED(서비스)/USE(자원) 프레임으로 추린다. 패널 8~12개가 적당. 알림은 RED/SLO(증상)에만 건다.

**Q. Histogram을 Summary보다 선호하는 이유?**
A. 여러 인스턴스를 집계해 **전체 시스템의 분위수**를 구해야 하는데, Summary는 분위수를 클라이언트가 미리 계산해 와서 합산이 불가능하다. Histogram은 버킷(원재료)이 서버에 있어 `sum by(le)` 후 분위수 계산이 된다.

## 주의사항 / 자주 하는 실수

- **로그만 잘 쌓으면 된다 ❌** — 로그는 비싸고 고카디널리티라 추세·알림에 부적합. 알림은 metric, 원인은 log로 역할이 다르다.
- **3축 = 도구 3개 따로 ❌** — 도구가 갈려도 **같은 라벨 체계**로 묶여야 점프가 된다.
- **자원 지표(CPU)에 알림 걸기 ❌** — 증상(RED/SLO)에 걸어야 노이즈가 적다. 자원은 대시보드로.
- **Utilization 100% = 장애 ❌** — 진짜 신호는 Saturation(대기 큐). 풀로 쓰는 것과 포화는 다르다.
- **메트릭 나열 대시보드 ❌** — RED/USE로 추리고 계층별로 분리.
