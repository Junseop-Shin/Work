# 언어별 동시성 모델 비교 — Node/Python/Java/Go/C#

> 2026-06-08 | 동시성, 병렬성, GIL, 이벤트루프, VirtualThread, asyncio

## 한 줄 요약

언어별 동시성의 차이는 결국 **"동시성(번갈아 다루기)과 병렬성(물리적 동시 실행)을 각각 어떤 실행 단위로 푸느냐"** 의 차이이며, 단일 스레드 이벤트 루프(Node·asyncio) / 경량 스레드 M:N 다중화(Go·Java VirtualThread) / OS 스레드 1:1(전통 Java·C#) 세 갈래로 갈린다.

## 핵심 개념

### 동시성 ≠ 병렬성 (모든 비교의 기준축)

- **동시성(Concurrency)**: 여러 일을 **번갈아** 다루는 구조. 1코어에서도 성립. "일을 다루는 것."
- **병렬성(Parallelism)**: 여러 일을 **물리적으로 동시에** 실행. 멀티코어 필요. "일을 실행하는 것."

> Rob Pike: "동시성은 일을 다루는 것, 병렬성은 일을 실행하는 것."

각 언어가 이 둘을 어떻게 푸는지가 차이의 전부다.

### 언어별 모델

#### Node.js — 싱글스레드 이벤트 루프
- 메인 JS는 **단 1스레드**. 동시성은 **이벤트 루프 + libuv**로 낸다.
- I/O를 만나면 OS/스레드풀에 떠넘기고 콜백을 큐에 등록한 뒤 즉시 다음 일로. → **대기 시간을 안 버림**(I/O-bound 최강).
- ❌ CPU 무거운 작업이 오면 단일 스레드가 막혀 전체 정지 → `worker_threads`(진짜 별도 스레드)로 우회.
- 동시성 ✅ / 병렬성 ❌(기본), worker_threads로만 ✅.

#### Python — GIL의 그늘
- **GIL(Global Interpreter Lock)**: 한 프로세스에서 **한 번에 1스레드만** 파이썬 바이트코드 실행 → 멀티스레드여도 **CPU 병렬 불가**.
- **I/O-bound** → `threading`/`asyncio`로 동시성 OK(I/O 대기 중엔 GIL 놓음).
- **CPU-bound** → 스레드 무용. **`multiprocessing`(프로세스 여러 개)** 로 GIL 우회해야 진짜 병렬.
- 동시성 ✅ / 병렬성: 스레드 ❌, 프로세스 ✅.

##### asyncio·코루틴은 멀티스레드/병렬이 아니다 (핵심 오해)
```
threading        : 스레드 여러 개 (GIL이 CPU 직렬화)
asyncio          : 스레드 1개 + 코루틴 수만 개 (한 스레드 위에서 번갈아) ← 병렬 아님
multiprocessing  : 프로세스 여러 개 (각자 GIL → 진짜 병렬)
```
- **코루틴 = "중간에 멈췄다 이어쓰는 함수"** 일 뿐 실행 주체가 아니다. **이벤트 루프(1스레드)가** 코루틴을 돌리다 `await`(I/O 대기) 만나면 다음 코루틴으로 넘어간다.
- 코루틴이 10만 개여도 **CPU 코어는 1개만**, 물리적으로 한 번에 하나만 실행.
- CPU 병렬이 필요하면 GIL 때문에 **무조건 프로세스**(또는 no-GIL 빌드, C확장). asyncio에서도 `loop.run_in_executor`로 스레드/프로세스풀에 떠넘길 순 있으나, 그건 코루틴이 병렬이 된 게 아니라 밑에서 스레드/프로세스를 빌리는 것.

##### GIL-free(free-threaded) 빌드 현황
| 버전 | 상태 |
|------|------|
| **3.13** (2024.10) | free-threaded 빌드 최초 등장, **experimental** (PEP 703) |
| **3.14** (2025.10) | **officially supported(실험 딱지 제거) = phase II** ✅, 단 여전히 별도 빌드(`python3.14t`), 기본 아님 |
| **3.15** (예정) | free-threaded용 Stable ABI(`abi3t`) 지원 |
- 기본/유일 빌드로 만드는 **phase III는 미정**(수년 전환). 일반 `python3.14`는 여전히 GIL 있음.

#### Java — 무거운 스레드 → Virtual Thread
- 전통: `Thread` = **OS 스레드 1:1**. 강력하지만 무거워(수MB) 수천 개가 한계 → 스레드풀로 아껴 씀.
- **Project Loom의 Virtual Thread (Java 21 정식)**: 수백만 개 가능한 경량 스레드. JVM이 소수 OS 스레드(캐리어)에 다중화.
- → **사실상 goroutine과 같은 발상**(M:N). 블로킹 코드를 그대로 쓰면서 고루틴급 확장성.
- 공유 메모리 + `synchronized`/`java.util.concurrent` 락 기반(Go 채널 철학의 반대편).
- 동시성 ✅ / 병렬성 ✅.

#### Go — CSP, "통신으로 공유"
- **goroutine(M:N) + channel(CSP)**. 락 대신 채널로 소유권을 넘기는 문화 + `go`/`select`/채널 1급 지원.
- 자세히는 [Go 동시성](Go-동시성.md).
- 동시성 ✅ / 병렬성 ✅(`GOMAXPROCS`).

#### C# — async/await의 원조
- `async/await` 문법을 대중화한 장본인(JS·Python·Rust가 영향받음).
- `Task` 기반: I/O는 `await`로 논블로킹, CPU 병렬은 `Task.Run`/`Parallel`/TPL로 멀티스레드.
- 동시성 ✅ / 병렬성 ✅.

### 종합 트레이드오프

| 언어 | 동시성 단위 | 병렬 가능? | 공유 방식 | I/O / CPU |
|------|------------|-----------|----------|-----------|
| **Node.js** | 이벤트 루프(콜백/Promise) | ❌ 기본1스레드 (worker_threads로 ✅) | 단일스레드라 락 거의 불필요 | I/O ⭐ / CPU ✕ |
| **Python** | asyncio·threading | ❌ 스레드(GIL) / ✅ 프로세스 | GIL이 사실상 직렬화 | I/O ⭕ / CPU는 멀티프로세스 |
| **Java** | Thread / **Virtual Thread** | ✅ | 공유메모리 + 락 | 둘 다 ⭐ |
| **Go** | **goroutine** | ✅ | **채널(CSP)** + 락 선택 | 둘 다 ⭐ |
| **C#** | Task / async-await | ✅ | 공유메모리 + 락 | 둘 다 ⭐ |

세 갈래 정리:
- **단일 스레드 이벤트 루프**: Node, Python(asyncio) — I/O 효율 ↑, CPU 병렬은 별도 우회.
- **경량 스레드(M:N)**: Go(goroutine), Java(Virtual Thread) — 블로킹 코드를 그대로 쓰며 대량 확장.
- **공유 철학**: Go만 "채널로 통신", 나머지는 대체로 "공유메모리 + 락".

### 리소스 단위 비교 — "goroutine이 왜 가벼운가"

동시성 단위 1개당 메모리와 현실적 최대 개수(자릿수 기준):

| 단위 | 1개당 초기 메모리 | 스택 | 현실적 최대 | 스케줄러 |
|------|----------------:|------|-----------:|---------|
| **OS 스레드** (Java platform, Python `threading`, C# `Thread`) | **~1MB** (512KB~8MB 예약) | 고정 | **~수천** | OS 커널 |
| **프로세스** (Python `multiprocessing`) | **~10MB+** (인터프리터 복제) | — | **~수십~수백** | OS 커널 |
| **Goroutine** (Go) | **~2KB** (동적 증감) | 가변 | **~수백만** | Go 런타임 |
| **Virtual Thread** (Java 21) | **~수백B~KB** (힙 저장, 가변) | 가변 | **~수백만** | JVM |
| **코루틴** (Python asyncio, JS Promise) | **~수백B~수KB** (객체) | 없음(콜스택 공유) | **~수십만+** | 이벤트 루프 |

#### 체감 — "1GB로 몇 개?" (대략)
- **OS 스레드**(1MB) → 약 **1,000개**. 그 이상은 메모리·컨텍스트스위칭 비용 폭발 → 스레드풀 필수.
- **Goroutine**(2KB) → 약 **50만 개**. OS 스레드 대비 **~500배** 더 빽빽.
- **코루틴/Virtual Thread** → goroutine과 비슷한 자릿수(수십만~수백만).
- **프로세스**(10MB+) → 약 **100개**.

#### 왜 이렇게 차이 나나
1. **스택 크기**: OS 스레드는 큰 스택(~1MB)을 고정 예약. goroutine은 2KB로 시작해 필요 시 증감(growable stack) → 개당 메모리 3자릿수 차이.
2. **스케줄링 비용**: OS 스레드 전환은 커널 모드 진입(레지스터 저장/복원, 캐시 영향)으로 비쌈. goroutine 전환은 유저 공간 함수 호출 수준으로 쌈.
3. **다중화(M:N)**: goroutine·Virtual Thread는 소수 OS 스레드 위에 수십만 개를 얹음. OS 스레드는 1:1이라 그 자체가 커널 자원.

→ 결론: "동시 연결 10만 개"는 OS 스레드 1:1로는 불가능(메모리·스케줄러 마비)하지만, Go·Java Virtual Thread는 단위를 막 띄워도 된다. goroutine 강점 = **개당 메모리가 OS 스레드의 ~1/500 + 전환이 커널 비경유** → "스레드를 아끼지 않고 써도 되는" 모델.

## 핵심 질의응답

**Q. Node/Python은 싱글스레드인데 어떻게 동시성을 내나?**
A. 이벤트 루프로 I/O 대기 시간을 양보한다. I/O를 떠넘기고 콜백을 등록한 뒤 다음 일을 하다가, 완료되면 콜백을 실행. 대기 시간을 안 버리는 구조.

**Q. Python asyncio·코루틴으로 멀티스레드/병렬이 되나?**
A. 안 된다. asyncio는 스레드를 늘리는 게 아니라 1스레드 위에서 코루틴을 번갈아 돌리는 동시성이다. CPU 코어 1개만 쓴다. 병렬이 필요하면 multiprocessing(또는 no-GIL 빌드).

**Q. GIL이 뭐가 문제인가?**
A. 한 번에 1스레드만 바이트코드를 실행하게 막아 멀티스레드의 CPU 병렬을 무의미하게 만든다. 그래서 CPU 작업은 프로세스로 우회해야 한다.

**Q. Python GIL-free는 몇 버전부터 안정인가?**
A. 3.13에서 실험적으로 등장, **3.14에서 공식 지원(phase II)**. 단 여전히 별도 빌드이고 기본은 아니다. 기본화(phase III)는 미정.

**Q. goroutine은 왜 그렇게 많이 띄울 수 있나?**
A. 개당 ~2KB(OS 스레드의 ~1/500)로 작고, 전환이 커널을 안 거치며, 런타임이 소수 OS 스레드에 M:N 다중화하기 때문. Java Virtual Thread도 같은 원리.

## 주의사항 / 자주 하는 실수

- **"asyncio = 멀티스레드"로 오해** — 단일 스레드 동시성이다. CPU 병렬 아님.
- **Node에서 CPU 작업을 메인 루프에** — 전체가 멈춘다. worker_threads로 분리.
- **동시성과 병렬성 혼용** — 면접에서 구분 못 하면 감점. 동시성=구조, 병렬성=실행.
- **Virtual Thread를 스레드풀로 재사용** — VT는 일회용(요청당 하나)이 설계 의도. 풀링은 안티패턴.
