# 폼 라이브러리 + 검증 비교 (RHF / Formik / React 19 Actions + zod / yup / class-validator)

> 2026-05-07 | RHF, Formik, ReactActions, useFormStatus, zod, yup, class-validator

## 한 줄 요약

폼 라이브러리는 **리렌더 격리** 사상이 핵심이다. **Formik**은 controlled + Context 폭격으로 큰 폼에서 무너지고, **RHF**는 uncontrolled + 필드 단위 구독(`watch`/`register`)으로 격리한다. **React 19 Actions**는 다른 차원 — 클라이언트 폼 라이브러리가 아니라 **서버와 폼을 통합**하는 React 자체 기능. 검증은 **zod**가 schema-first + 타입 추론으로 표준 자리를 가져갔고, **yup**은 추론 정확도에서 밀리며, **class-validator**는 NestJS DTO 진영 전용. 2026년 풀스택 TS 표준은 **RHF + zodResolver (+ 필요시 Server Action)**.

## 핵심 개념

### 왜 폼 라이브러리가 필요한가

순수 React로 폼을 짜면 두 갈래로 갈린다.

```tsx
// controlled — state가 진실의 원천
const [name, setName] = useState("")
<input value={name} onChange={e => setName(e.target.value)} />

// uncontrolled — DOM이 진실의 원천, ref로 읽음
const ref = useRef<HTMLInputElement>(null)
<input ref={ref} defaultValue="" />
const submit = () => console.log(ref.current?.value)
```

| | controlled | uncontrolled |
|---|---|---|
| 진실의 원천 | React state | DOM |
| 키 입력 시 | 매번 리렌더 | 리렌더 없음 |
| 실시간 검증 / 조건부 필드 | 쉬움 | 어려움 (값을 React가 모름) |
| 100필드 폼 | **느려짐** | **빠름** |

순수 controlled로 100필드를 짜면 글자 하나 칠 때마다 트리 전체가 reconciliation을 돈다. 순수 uncontrolled로 가면 "이메일 채워지면 버튼 활성화" 같은 시나리오가 막힌다. **이 트레이드오프를 라이브러리가 해결하는 방식의 차이**가 RHF vs Formik의 본질.

---

### RHF — uncontrolled + 필드 단위 구독으로 격리

```tsx
import { useForm } from "react-hook-form"

function Form() {
  const { register, watch, handleSubmit, formState: { errors } } = useForm()
  const name = watch("name")  // ← 이 필드만 구독, 이 컴포넌트만 리렌더

  return (
    <form onSubmit={handleSubmit(data => console.log(data))}>
      <input {...register("name", { required: true })} />
      <button disabled={!name}>Submit</button>
    </form>
  )
}
```

**동작 원리:**

1. `register("name")` — input에 `ref`를 꽂아 uncontrolled로 운영. React state에 안 넣음.
2. `watch("name")` — Proxy 기반 구독. 그 필드가 변할 때만 **이 컴포넌트만** 리렌더.
3. 다른 필드 100개는 그대로 — **격리(isolation)**.

이 격리가 RHF의 정체. **controlled의 편의성 + uncontrolled의 성능을 둘 다** 가져갔다.

```
[ Form 컴포넌트 ]
   ├─ register("name") → DOM ref
   ├─ register("email") → DOM ref
   ├─ register("password") → DOM ref
   └─ watch("name")  ← 이 컴포넌트가 구독
        ↓ name 변경 시 이 컴포넌트만 리렌더
        다른 register된 input들은 흔들리지 않음
```

### Formik — controlled + Context 폭격

```tsx
<Formik
  initialValues={{ email: "", password: "" }}
  validationSchema={schema}
  onSubmit={values => ...}
>
  {({ values, errors }) => (
    <Form>
      <Field name="email" />
      <Field name="password" />
    </Form>
  )}
</Formik>
```

**동작 원리:**

1. 모든 `<Field>`가 controlled — Formik 내부 state에 값 보관
2. 값 변경 시 Formik state 업데이트 → React Context로 전파
3. 그 Context를 구독하는 모든 `<Field>` 리렌더 → **폼 트리 전체 리렌더**
4. 거기에 `validateOnChange: true` (기본값) → 매번 **스키마 전체** 검증

작은 폼은 체감 안 되는데, 50+ 필드 동적 폼에서는 **input에 글자 칠 때 지연이 보임**. 이게 RHF가 시장 점유율 가져간 핵심 이유.

| | 리렌더 단위 | 검증 단위 (기본) |
|---|---|---|
| Formik | 폼 전체 | 스키마 전체 |
| RHF | watch한 필드만 | 변경된 필드만 |

---

### React 19 Actions — 다른 패러다임

RHF/Formik은 **클라이언트 폼 라이브러리**다. React 19 Actions는 **서버와 폼을 통합**하는 React 자체 기능.

```tsx
// app/signup/page.tsx
"use server"
async function signup(prevState: any, formData: FormData) {
  const email = formData.get("email") as string
  if (!email.includes("@")) return { error: "이메일 형식이 아닙니다" }
  await db.users.create({ email })
  redirect("/welcome")
}

// 클라이언트 컴포넌트
"use client"
import { useActionState } from "react"
import { useFormStatus } from "react-dom"

function SignupForm() {
  const [state, formAction] = useActionState(signup, { error: null })

  return (
    <form action={formAction}>
      <input name="email" />
      {state?.error && <p>{state.error}</p>}
      <SubmitButton />
    </form>
  )
}

function SubmitButton() {
  const { pending } = useFormStatus()
  return <button disabled={pending}>{pending ? "전송 중..." : "가입"}</button>
}
```

**핵심 4개:**

| API | 역할 |
|---|---|
| `<form action={fn}>` | `onSubmit` 대신 `action`. JS 없어도 동작 (progressive enhancement) |
| Server Action (`"use server"`) | 빌드 타임에 RPC 엔드포인트로 변환. `fetch` 보일러플레이트 사라짐 |
| `useActionState(fn, initial)` | 서버 액션 반환값을 state로 받음. 폼 결과/에러 표준 채널 |
| `useFormStatus()` | 부모 `<form>`의 pending을 자식에서 직접 읽음. props drilling 없이 |

**Progressive Enhancement** — `<form action="...">`은 HTML 네이티브. React 19는 `action={fn}`을 빌드 타임에 숨겨진 엔드포인트 URL로 변환해놓는다.

- **JS 로드 전 (hydration 전)** — 사용자가 빨리 클릭하면 브라우저 네이티브 form post → 서버 처리 → 페이지 새로고침으로 결과. 동작은 함.
- **JS 로드 후** — React가 가로채서 fetch 호출, 부분 업데이트.

RHF/Formik은 onSubmit이 JS 핸들러라 **JS 없으면 동작 자체가 안 됨**.

**`useFormStatus`는 왜 자식에 두는가** — 격리. 만약 부모 `<form>`에서 `pending`을 받으면 pending 변할 때마다 form 전체(모든 input 포함)가 리렌더. 자식 `SubmitButton`에서 받으면 그 컴포넌트만 리렌더. RHF의 watch 격리와 같은 사상이 React 19 자체 API 설계에도 들어가 있다.

### 폼 라이브러리 의사결정 매트릭스

| 상황 | 추천 |
|---|---|
| Next.js App Router + 단순 폼 (가입/로그인/댓글) | **React 19 Actions만** |
| 복잡한 동적 폼 (위저드, 100+필드, 실시간 검증) | **RHF + Server Action 호출** |
| Pages Router / 클라이언트 SPA / 서버 액션 못 씀 | **RHF (단독)** |
| 레거시 Formik 존재 | 유지 (마이그레이션 비용 ↑) |
| 새 프로젝트에서 Formik 선택 | ❌ 거의 없음 |

**RHF 안에서 Server Action 호출 — 가장 강력한 조합:**

```tsx
const onSubmit = handleSubmit(async (data) => {
  const result = await signupAction(data)  // server action을 그냥 함수로 호출
  if (result.error) setError("email", { message: result.error })
})
```

RHF의 클라이언트 UX(실시간 검증, 격리, watch) + Server Action의 서버 통합(자동 RPC, progressive enhancement) — 양쪽 강점만 가져옴.

## 검증 라이브러리

### 왜 별도 검증이 필요한가 — TS의 boundary 한계

TS 타입은 **컴파일 타임에만 존재**. 런타임에는 그냥 JS. 외부에서 들어오는 모든 데이터는 "TS가 약속한 타입"이 아닐 수 있다.

```ts
// 타입은 통과하지만 런타임에 거짓일 수 있는 곳들 (boundary)
const data: User = await fetch("/api/user").then(r => r.json())  // JSON은 any
const id = useParams<{ id: string }>().id                         // URL은 다 string
const formData = new FormData(form)                                // string | File | null
const cached = JSON.parse(localStorage.getItem("user")!)           // 외부 저장소
const env = process.env.PORT                                       // string | undefined
```

**더 중요한 건 보안** — 사용자가 의도적으로 잘못된 데이터를 보낼 수 있다. `age: number` 타입이라도 누군가 `age: "DROP TABLE users"`를 보내면 fetch 응답에 그게 들어옴. **TS는 악의적 입력을 막아주지 않는다** — 그냥 "내 코드 안에서 타입이 일관되는지" 검사할 뿐.

→ **시스템 경계에서 런타임 검증 필수**.

---

### zod — schema-first + 타입 추론

```ts
import { z } from "zod"

// 스키마 1번만 정의
const UserSchema = z.object({
  email: z.string().email(),
  age: z.number().int().min(18),
})

// 타입은 자동 추론 — 따로 안 짬
type User = z.infer<typeof UserSchema>
// { email: string; age: number }

// 런타임 검증
const result = UserSchema.parse(rawData)        // 실패 시 throw
const safe = UserSchema.safeParse(rawData)       // 안전 버전
if (safe.success) safe.data                      // 타입 좁혀짐 (type guard)
```

**핵심:** 스키마 → 타입 (단방향). **Single Source of Truth** 패턴.

복잡한 검증도 자연스럽다:

```ts
const SignupSchema = z.object({
  password: z.string().min(8),
  confirmPassword: z.string(),
}).refine(data => data.password === data.confirmPassword, {
  message: "비밀번호가 일치하지 않습니다",
  path: ["confirmPassword"],  // 에러를 어느 필드에 붙일지
})
```

---

### yup — 오래된 표준, 추론 정확도 한계

```ts
import * as yup from "yup"

const schema = yup.object({
  email: yup.string().email().required(),
})
type T = yup.InferType<typeof schema>  // { email: string }
```

기본 케이스는 비슷한데 **`transform`, `when`, conditional 같은 고급 케이스에서 추론이 깨지는 경우가 잦다**. Formik과 함께 자라온 역사 때문에 레거시에서 흔히 보이고, 새 프로젝트에서 yup 선택 이유는 거의 없다.

---

### class-validator — 데코레이터 / NestJS 진영

```ts
import { IsEmail, MinLength } from "class-validator"

class CreateUserDto {
  @IsEmail()
  email: string

  @MinLength(8)
  password: string
}

// NestJS 컨트롤러에서
@Post()
create(@Body() dto: CreateUserDto) {
  // ValidationPipe가 자동 검증 → 통과한 dto만 들어옴
}
```

**특이점:** zod/yup이 "스키마 객체"라면 class-validator는 **"클래스 자체가 스키마"**. NestJS DTO와 한 몸이라 데코레이터/`reflect-metadata` 런타임에 의존.

**프론트에서 쓰지 않는 이유:**
- 데코레이터 + `reflect-metadata` → 번들 비대화
- 클래스 인스턴스가 직렬화/역직렬화에 깔끔하지 않음
- NestJS 자동 파이프라인에 결합되어 떼어내기 어려움

→ class-validator는 **NestJS 서버 안에서만**, 클라이언트는 zod로 가는 게 일반적.

### 검증 라이브러리 비교

| | 출시 | 진영 | 핵심 패턴 | TS 추론 | 강점 |
|---|---|---|---|---|---|
| **Zod** | 2020 | TS-first | schema + 추론 | 1등 | RHF 표준, single source of truth |
| **Yup** | 2016 | 범용 (Formik과) | schema builder | 보통 | 오래돼서 안정적 |
| **class-validator** | 2015 | NestJS / 데코레이터 | class + 데코레이터 | 클래스 그대로 | NestJS DTO 통합 |

### RHF + zodResolver — 2026년 표준 패턴

```tsx
import { useForm } from "react-hook-form"
import { zodResolver } from "@hookform/resolvers/zod"
import { z } from "zod"

const SignupSchema = z.object({
  email: z.string().email("올바른 이메일을 입력하세요"),
  password: z.string().min(8, "8자 이상"),
  confirmPassword: z.string(),
}).refine(d => d.password === d.confirmPassword, {
  message: "비밀번호가 일치하지 않습니다",
  path: ["confirmPassword"],
})

type FormData = z.infer<typeof SignupSchema>

function SignupForm() {
  const { register, handleSubmit, formState: { errors } } = useForm<FormData>({
    resolver: zodResolver(SignupSchema),
  })

  return (
    <form onSubmit={handleSubmit(data => console.log(data))}>
      <input {...register("email")} />
      {errors.email && <p>{errors.email.message}</p>}
      <input type="password" {...register("password")} />
      {errors.password && <p>{errors.password.message}</p>}
      <button type="submit">가입</button>
    </form>
  )
}
```

**3개의 핵심:**
1. **스키마 1번 → 타입 + 검증 둘 다** — 한 군데서 관리
2. **`zodResolver`** 가 RHF에 zod 결과를 변환해서 넘김 (RHF는 검증 라이브러리 중립적)
3. **`refine`** 으로 필드 간 검증 (yup `when`보다 직관적)

## 핵심 질의응답

**Q. controlled 폼은 왜 100필드에서 느려지나?**
A. 입력마다 `setState` → 부모 컴포넌트 리렌더 → 모든 자식 리콘실리에이션. memo를 안 걸면 전체 트리가 흔들린다.

**Q. uncontrolled의 단점은?**
A. 값이 React state에 없으니 "값에 따라 UI 변경" 시나리오가 막힌다 — 실시간 검증, 조건부 필드, Submit 활성화 등.

**Q. RHF는 어떻게 둘 다 잡았나?**
A. uncontrolled로 운영하면서 `watch`로 특정 필드만 구독. 그 필드 변경 시 watch 호출한 컴포넌트만 리렌더. 다른 필드는 흔들리지 않음.

**Q. Formik이 큰 폼에서 느린 이유는?**
A. controlled + Context로 모든 Field에 값 전파 + `validateOnChange` 기본 활성. 글자 하나마다 폼 전체 리렌더 + 스키마 전체 검증.

**Q. React 19 Actions와 RHF는 경쟁 관계인가?**
A. 아니다. Actions는 서버 통합, RHF는 클라이언트 UX. **RHF의 onSubmit 안에서 Server Action을 호출**하는 패턴이 가장 강력.

**Q. `useFormStatus`는 왜 자식 컴포넌트에서 호출하는가?**
A. 격리. 부모 form에서 받으면 pending 변경 시 form 전체 리렌더. 자식에서 받으면 그 컴포넌트만.

**Q. progressive enhancement 가 의미하는 바는?**
A. JS 로드 전이나 비활성 환경에서도 form action이 네이티브 HTML form post로 동작. RHF/Formik은 JS 없으면 죽는다.

**Q. 클라이언트만 검증하면 왜 안 되나?**
A. 보안. 사용자가 개발자 도구로 disabled 풀거나 curl로 API 직접 호출하면 클라이언트 검증은 우회됨. **클라이언트 검증은 UX, 서버 검증은 보안**.

**Q. zod의 차별점은?**
A. **스키마가 타입의 source of truth**. 스키마 1번 정의 → `z.infer`로 타입 자동 추론. yup도 비슷하게 되지만 추론 정확도가 떨어진다.

**Q. yup을 써야 할 이유가 있나?**
A. 거의 없다. 레거시 Formik 코드베이스 유지가 아니면 zod.

**Q. class-validator를 프론트에서 쓰지 않는 이유?**
A. 데코레이터 + `reflect-metadata` 의존, NestJS 파이프라인 결합도가 높아 떼어내기 어려움. 프론트는 zod, NestJS 서버는 class-validator로 분리하는 게 일반적.

## 주의사항 / 자주 하는 실수

- **controlled 100필드 폼을 React.memo로 막으려는 시도** — 가능은 하지만 boilerplate 폭발. 그냥 RHF로 가라.
- **`useFormStatus`를 form 컴포넌트 안에서 직접 호출** — 동작은 안 함 (자식이어야 함). 또는 호출되더라도 리렌더 격리가 깨짐.
- **`<form action={fn}>` 의 `fn`을 클라이언트 함수로 착각** — `"use server"` 디렉티브 없으면 그냥 일반 onSubmit 핸들러로 동작. Server Action으로 만들려면 명시적으로 표시 필요.
- **클라이언트 zod 검증만 하고 서버에서 안 함** — 사용자 우회 가능. 서버에서도 같은 스키마로 한 번 더 검증 필수.
- **yup `InferType` 결과가 이상하다** — `transform`, `when`이 들어가면 추론이 자주 깨진다. 새 코드면 zod로.
- **class-validator를 모노레포 shared 패키지로** — 데코레이터 런타임 의존성 때문에 프론트 번들이 비대해짐. 백엔드 전용으로 격리.
