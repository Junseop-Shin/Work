# 프론트-백엔드 계약 동기화 (OpenAPI / GraphQL / tRPC)

> 2026-05-07 | OpenAPI, GraphQL, tRPC, BFF, 스키마공유, codegen, RSC, ServerAction

## 한 줄 요약

프론트와 백엔드가 **같은 도메인 룰을 따로 작성하면 반드시 어긋난다 (drift)**. 풀스택 TS + Pattern 1(Next + ORM)이라면 zod 스키마 하나로 양쪽 공유 가능 — 검증 룰은 1번 작성, 검증 실행은 2번. 풀스택 TS인데 백엔드 분리(NestJS 등)이면 **tRPC**가 최강 DX. 백엔드 언어가 다르면 **OpenAPI codegen**으로 백엔드를 진실의 원천 삼고 프론트 타입/zod 자동 생성. **GraphQL**은 schema-first로 스키마 자체가 계약. 어떤 도구든 본질은 같다 — **계약을 사람이 두 번 작성하지 않게 한다**.

## 핵심 개념

### 문제 정의 — 왜 계약 동기화가 문제인가

같은 도메인 룰을 양쪽에서 쓰는 일은 풀스택의 일상이다.

```
[Frontend zod 스키마]              [Backend Pydantic 스키마]
  email: z.string().email()           email: EmailStr
  password: z.string().min(8)         password: constr(min_length=10)
                                                                ↑
                                              어느 날 슬쩍 8 → 10으로 바뀜
```

**드리프트 (drift)** — 한쪽이 룰을 바꿔도 다른 쪽이 모른다. 결과:

- 프론트는 통과시켰는데 백엔드가 거절 → 사용자 혼란 ("아니 왜 내가 통과했는데?")
- 백엔드가 더 엄격해진 걸 프론트가 모르고 좋은 UX 못 줌
- QA에서 발견되면 다행, 배포 후 발견되면 비참

검증 룰만의 문제도 아니다 — 필드 추가/삭제, 타입 변경, 응답 구조 등 모든 API 계약이 동기화 대상.

**그러므로 계약 동기화는 "있으면 좋은 것"이 아니라 "스케일하면 반드시 필요한 것"**. 단지 작은 팀에선 PR 리뷰로 막는 게 비용 대비 합리적이고, 커지면 자동화로 가는 것뿐.

### Pattern 매트릭스 — Next.js를 어떻게 쓰는가

RSC/Server Action 시대에 Next.js는 세 가지 자세로 쓸 수 있다. 어떤 자세냐에 따라 동기화 전략이 갈린다.

**Pattern 1 — All-in-one (Next + ORM 직결)**

```tsx
// Server Component
import { db } from "@/db"
export default async function Posts() {
  const posts = await db.post.findMany()  // Prisma/Drizzle 직접
  return <ul>{posts.map(p => <li>{p.title}</li>)}</ul>
}
```

- Next.js + Prisma/Drizzle 바로 DB
- 별도 백엔드 없음
- 작은 풀스택 앱, 사이드 프로젝트, MVP, 스타트업 초기
- Vercel 마케팅이 보여주는 그림

**Pattern 2 — BFF (Backend for Frontend)**

```tsx
// Server Component이 외부 백엔드 API를 호출
export default async function Posts() {
  const posts = await fetch("https://api.company.com/posts", {
    headers: { Authorization: `Bearer ${getServerToken()}` },
  }).then(r => r.json())
  return <ul>{posts.map(p => <li>{p.title}</li>)}</ul>
}

// Server Action으로도
"use server"
async function createPost(data: PostInput) {
  return fetch("https://api.company.com/posts", { method: "POST", body: JSON.stringify(data) })
}
```

- 기존 백엔드(NestJS / Spring / Django / Rails)가 따로 존재
- Next.js는 **얇은 BFF 레이어** — 클라이언트에 가까운 서버
- Server Action은 "API 호출 보일러플레이트 + CORS 우회 + 토큰 관리" 도구
- 회사 백엔드 팀이 따로 있으면 거의 이 패턴

**Pattern 3 — 클라이언트 SPA (RSC 안 씀)**

- Pages Router 시절 / Vite + React / CRA
- 모든 통신은 클라이언트 fetch
- 회사 정책상 SSR 안 쓰거나, 풀스택 분리 명확한 경우

| 상황 | 추천 Pattern |
|---|---|
| 솔로/소규모 팀, 풀스택 TS, 백엔드 없음 | **1** (DB 직결) |
| 기존 백엔드 (다른 언어 포함) 있음 | **2** (BFF) |
| 마이크로서비스, 백엔드 팀 분리 | **2** (BFF) |
| 모바일 앱과 API 공유 필요 | **2** (백엔드를 공통 API로) |
| SSR 안 쓰는 정적 SPA | **3** |

**Pattern 1의 함정** — 처음엔 깔끔한데 모바일 앱 추가, 다른 팀이 데이터 접근, 외부 통합 등이 들어오면 결국 Pattern 2로 마이그레이션. 그래서 미래 확장이 보이면 처음부터 2로.

---

### Pattern × 백엔드 언어로 보는 검증 공유 가능성

| 구성 | 검증 공유 | 비고 |
|---|---|---|
| Pattern 1 (Next + ORM, TS) | ✅ 완벽 공유 | zod 천국 |
| Pattern 2, 백엔드 TS (NestJS 등) | 🟨 가능하지만 미묘 | NestJS는 class-validator 표준 → zod와 충돌 |
| Pattern 2, 백엔드 Java/Python/Go | ❌ 직접 공유 불가 | codegen 필요 |
| Pattern 3 (SPA + 외부 API) | ❌ 보통 안 함 | 백엔드 검증이 진실, 프론트는 UX만 |

**완벽한 zod single source of truth는 사실상 Pattern 1에서만 성립.** 나머지는 절충이 필요하고, 그 절충이 OpenAPI / GraphQL / tRPC 같은 도구.

## 동기화 전략

### 1. zod 스키마 직접 공유 (Pattern 1 전용)

```
packages/
  shared/
    schemas/user.ts   ← const SignupSchema = z.object({...})
  web/                ← shared/schemas import
  api/                ← shared/schemas import (또는 같은 Next.js 내부)
```

```ts
// shared/schemas/user.ts
export const SignupSchema = z.object({
  email: z.string().email(),
  password: z.string().min(8),
})
export type SignupInput = z.infer<typeof SignupSchema>

// web/components/SignupForm.tsx
const form = useForm<SignupInput>({ resolver: zodResolver(SignupSchema) })

// api/routes/signup.ts
app.post("/signup", (req, res) => {
  const data = SignupSchema.parse(req.body)  // 같은 룰
})
```

**룰 1번 작성, 검증 2번 실행** — 클라이언트 검증은 UX, 서버 검증은 보안. 중복은 코드가 아니라 실행이며, 후자는 의도된 보안 설계다.

**조건:**
- 양쪽 다 TS여야 함
- 모노레포 또는 같은 프로젝트
- 백엔드가 Next.js 내부 (Pattern 1) 또는 TS 백엔드 (Pattern 2-TS)

### 2. OpenAPI codegen — 가장 범용적인 답

```
Backend (Spring/FastAPI/NestJS/...)
  ↓ OpenAPI/Swagger 스펙 자동 생성 (코드/어노테이션에서)
openapi.json  ← 진실의 원천
  ↓ codegen (CI 또는 빌드 단계)
Frontend
  ├── TypeScript types
  ├── zod 스키마 (openapi-zod-client 등)
  └── fetch 클라이언트 (orval, openapi-typescript-codegen 등)
```

**핵심:** 백엔드가 진실의 원천, 프론트가 codegen으로 따라옴. 백엔드 언어 무관.

**도구:**
- `openapi-zod-client` — OpenAPI → zod 스키마 + typed client
- `orval` — OpenAPI → TS 타입 + React Query/SWR 훅
- `openapi-typescript-codegen` — OpenAPI → TS 타입 + fetch 클라이언트
- 백엔드 측: Spring `springdoc`, FastAPI 내장, NestJS `@nestjs/swagger`, Django DRF Spectacular

**워크플로우:**
1. 백엔드 PR에서 코드 변경 → OpenAPI 스펙도 자동 갱신
2. 프론트 CI에서 codegen 실행 → 변경된 타입/클라이언트 PR로 올라옴
3. 프론트 PR에서 컴파일 에러로 깨진 곳 발견 → 동기화 강제됨

**단점:**
- 빌드 파이프라인 복잡도 추가
- OpenAPI가 실제 동작과 어긋날 수 있음 (백엔드가 어노테이션을 빠뜨리면 거짓 진실)
- REST 스타일 강제 (RPC, GraphQL과 다름)

→ **백엔드 언어가 TS가 아닐 때 가장 흔한 답**.

### 3. GraphQL — 스키마-first, 양쪽 codegen

> 본 섹션은 동기화 전략 관점에서 짧게 다룸. GraphQL 자체의 깊이 있는 정리는 [GraphQL 기본](../백엔드/GraphQL-기본.md) 참조.

```graphql
# schema.graphql ← 진실의 원천
type User {
  id: ID!
  email: String!
}

type Query {
  user(id: ID!): User
}
```

```
schema.graphql
  ├─ Backend (Apollo Server, graphql-yoga 등)
  │    ↓ codegen
  │    리졸버 타입, 인풋 타입
  └─ Frontend
       ↓ codegen (graphql-codegen, urql)
       타입, 훅 (useUserQuery 등)
```

**장점:**
- 스키마 자체가 계약 — REST + OpenAPI보다 더 강제됨
- 프론트가 필요한 필드만 요청 (over-fetching 해결)
- 양쪽 codegen 풍성한 도구 (`@graphql-codegen`)

**단점:**
- GraphQL 자체의 학습 비용 (schema, resolver, federation 등)
- 캐싱 복잡 (Apollo Client / urql 캐시 정책)
- N+1 문제 (DataLoader 패턴 필수)
- Subscription 이외엔 HTTP 1개 엔드포인트 (디버깅이 REST보다 까다로움)

**언제 쓰나:**
- 다양한 클라이언트 (웹/모바일/외부 통합)가 같은 백엔드를 공유
- 데이터 모양이 클라이언트마다 달라 over-fetching이 큰 비용
- 페이스북, GitHub, Shopify 같은 플랫폼적 API

**검증 측면:**
- GraphQL 자체가 타입 검증을 함 (`Int`, `String!` 등)
- 비즈니스 룰 (이메일 형식, 길이) 은 별도 — 보통 백엔드에서 zod/yup/Pydantic
- 프론트는 codegen된 타입만 받고 검증은 따로 (또는 codegen으로 zod까지)

→ **계약 강제력이 가장 강한 방식**. 다만 비용도 가장 높음.

### 4. tRPC — 풀스택 TS의 끝판왕

```ts
// 서버
const userRouter = router({
  signup: publicProcedure
    .input(z.object({
      email: z.string().email(),
      password: z.string().min(8),
    }))
    .mutation(async ({ input }) => {
      return await db.users.create({ data: input })
    }),
})

// 클라이언트 — codegen 없이 타입 자동 추론
const { mutate, error } = trpc.signup.useMutation()
mutate({ email: "a@b.com", password: "12345678" })  // ← 타입 + 검증 자동
```

**핵심:** 서버 라우터 정의가 그대로 클라이언트 타입이 됨. `import type`으로 타입만 가져오기 때문에 빌드 타임에 결합, 런타임 의존성 없음.

**장점:**
- codegen 단계 자체가 사라짐 — 가장 부드러운 DX
- 서버 zod 스키마가 그대로 클라이언트 검증으로 — 진정한 single source of truth
- 자동완성, 리팩토링 (이름 변경 시 양쪽 한 번에)

**조건:**
- **백엔드도 반드시 TS** (Node.js / Bun / Deno)
- 모노레포 또는 패키지 공유 가능한 구조

**한계:**
- 다른 언어 백엔드 불가
- 외부 클라이언트 (모바일, 서드파티) 와 공유 시 OpenAPI/GraphQL 별도 노출 필요
- HTTP API로서 표준 도구 (curl, Postman) 친화도 낮음 (커스텀 RPC 형식)

→ **풀스택 TS + 모노레포 + 클라이언트가 자기 프론트뿐일 때** 최강.

---

### 5. 손 동기화 + PR 리뷰 (현실적 선택)

작은 팀, 변동 적은 도메인이면 **자동화 없이도 충분**:

- 백엔드 PR에 "API 변경" 라벨 → 프론트 담당자 자동 리뷰어 등록
- README에 API 스키마 변경 시 양쪽 PR 묶기 룰
- 핵심 룰만 공유 (예: 비밀번호 정책) 문서화

모든 걸 자동화할 필요는 없다. **자동화 비용 < 드리프트 비용**일 때만 도구를 도입.

## 동기화 전략 비교

| 전략 | 백엔드 언어 | codegen | 검증 공유 | DX | 학습 비용 |
|---|---|---|---|---|---|
| **zod 직접 공유** | TS만 | 없음 | ✅ 완벽 | 최고 | 낮음 |
| **OpenAPI codegen** | 무관 | 필요 | 🟨 부분 (codegen된 zod) | 보통 | 중 |
| **GraphQL** | 무관 | 필요 | 🟨 GraphQL 타입만 | 보통 | 높음 |
| **tRPC** | TS만 | 없음 | ✅ 완벽 | 최고 | 낮음 |
| **손 동기화** | 무관 | 없음 | ❌ 없음 | 최저 | 0 |

## 의사결정 매트릭스

| 상황 | 추천 |
|---|---|
| Next + ORM, 백엔드 없음, 풀스택 TS | **zod 직접 공유** |
| Next + 별도 NestJS 백엔드 (TS) | **tRPC** 또는 **zod 공유** |
| Next + Spring/Python/Go 백엔드 | **OpenAPI codegen** |
| 다양한 클라이언트가 한 백엔드 공유 | **GraphQL** |
| 모바일 앱 + 웹이 같은 API | **OpenAPI codegen** |
| 스타트업 초기, 작은 팀 | **손 동기화 + PR 리뷰** |
| 백엔드 팀이 OpenAPI 안 줌 | 정치적 합의가 먼저, 아니면 손 동기화 |

## 핵심 질의응답

**Q. 클라이언트만 검증하면 왜 안 되나?**
A. 사용자가 개발자 도구로 disabled 풀거나 curl로 API 직접 호출하면 우회됨. **클라이언트 검증은 UX, 서버 검증은 보안**.

**Q. 그럼 양쪽 검증은 코드 중복 아닌가?**
A. **룰 작성**은 한 번이면 되고 (zod 스키마 공유), **실행**만 두 번. Single source of truth 패턴으로 코드 중복 없이 양쪽 안전 확보.

**Q. 백엔드 언어가 다르면 zod single source of truth가 사라지나?**
A. 직접 import는 불가하지만 OpenAPI codegen으로 우회 가능. 백엔드 진실 → OpenAPI → 프론트 zod 자동 생성. zod의 가치는 줄지만 동기화는 가능.

**Q. tRPC vs OpenAPI codegen, 둘 다 풀스택 TS면 무엇?**
A. 클라이언트가 자기 프론트뿐이면 **tRPC** (codegen 단계 사라져서 DX 압도적). 모바일 앱이나 외부 클라이언트가 공유한다면 **OpenAPI** (REST 표준이 호환성 높음).

**Q. GraphQL을 단순 풀스택 TS에 도입해도 되나?**
A. 비추. GraphQL의 가치는 다양한 클라이언트가 다양한 모양으로 데이터를 요청할 때 빛난다. 단일 클라이언트면 학습 비용 + 캐싱/N+1 비용이 가치를 넘어선다.

**Q. RSC/Server Action은 DB 직결 전용인가?**
A. 아니다. **서버에서 실행되는 React + 자동 RPC**가 본질. DB에 가든, 외부 API에 가든, 파일 시스템에 가든 자유. Pattern 2 (BFF)에서도 가치 있음.

**Q. Server Action을 BFF에서 쓸 때의 가치는?**
A. fetch 보일러플레이트 제거 + 자동 RPC. API route handler 따로 안 짜도 됨. 토큰/CORS 서버에서 처리.

**Q. NestJS는 class-validator인데 Next.js는 zod, 둘 다 검증 어떻게?**
A. 동기화 자동화는 어려움. 옵션: ① NestJS DTO를 OpenAPI로 export → 프론트 zod codegen. ② 핵심 룰만 문서로 공유 + PR 리뷰. ③ NestJS도 zod로 통일 (`nestjs-zod` 같은 라이브러리).

**Q. drift를 0으로 만들 수 있나?**
A. 자동화로 drift 위험은 줄지만 0은 아니다 — codegen 도구의 버그, OpenAPI 어노테이션 누락, 비즈니스 룰의 양쪽 불일치 등이 남는다. **drift를 빨리 발견하는 시스템**(CI에서 codegen 돌려서 PR로 띄움)이 현실적 목표.

## 주의사항 / 자주 하는 실수

- **클라이언트 검증만 하고 끝내기** — 가장 흔한 보안 사고. curl 한 줄에 무너진다.
- **OpenAPI 어노테이션을 손으로 작성** — 코드와 어긋나기 시작하면 거짓 진실이 됨. 어노테이션 자동 추출 (`@nestjs/swagger`, FastAPI 내장 등) 도구를 써라.
- **codegen 결과를 git에 커밋 vs CI에서 생성** — 보통 커밋. 그래야 PR에서 변경이 보이고 프론트가 백엔드 변경에 반응한다. 안 커밋하면 drift 발견이 늦어짐.
- **GraphQL을 RPC처럼 쓰기** — Mutation에 `doSomething(input: X): Result` 만 잔뜩 만들면 GraphQL의 가치(필드 선택)를 못 누린다. 그럴 거면 tRPC.
- **tRPC를 외부 공개 API로** — tRPC 형식은 표준이 아님. 외부 클라이언트와 공유는 OpenAPI로.
- **풀스택 TS인데 OpenAPI codegen으로 가는 선택** — tRPC가 더 매끄러움. OpenAPI는 외부 호환성이 필요할 때만.
- **백엔드 팀이 다른 회사인데 OpenAPI 못 받음** — 정치 문제. 동기화 자동화는 선결 조건(스펙 제공) 합의가 먼저.
