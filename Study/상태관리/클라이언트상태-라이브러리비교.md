# 클라이언트 상태 라이브러리 비교 (Zustand / Redux / MobX / Valtio / Jotai)

> 2026-05-06 | 클라이언트상태, Zustand, Redux, MobX, Valtio, Jotai, 옵저버패턴, ContextAPI

## 한 줄 요약

클라이언트 상태 라이브러리는 모두 **옵저버 패턴 + 컴포넌트 구독 모델**의 변형이다. **Zustand**는 broadcast + selector 거름, **MobX/Valtio**는 proxy로 자동 추적, **Jotai**는 atom 단위 분리. 사상이 다른 만큼 mental model, boilerplate, 디버깅 난이도, fine-grained reactivity가 모두 갈린다. 대부분의 SPA에서 단순함과 직교성으로 **Zustand가 디폴트 답**.

## 핵심 개념

### 왜 라이브러리가 필요한가 — useState/Context의 한계

`useState`로 충분한 90%의 상태는 그대로 두는 것이 정답. 그러나 다음 상황에서 빌트인은 부족:

| 한계 | 증상 |
|------|------|
| **트리 외부 접근 불가** | API 인터셉터, 라우터 가드, 이벤트 리스너에서 못 씀 |
| **Props drilling** | 4단계 이상 깊으면 가독성 무너짐 |
| **Context는 selector가 없음** | value 일부만 바뀌어도 구독한 컴포넌트 **전체 리렌더** |
| **persist 미지원** | 새로고침 시 소실 |
| **DevTools 약함** | 시간여행 디버깅 불가 |

**Context의 결정적 함정** — selector 없음:

```tsx
const Context = createContext({ user: null, theme: 'light', notifications: [] })
// theme만 바꿔도 user/notifications만 보는 컴포넌트까지 모두 리렌더
```

`value={{ ... }}` 인라인 객체는 매 렌더마다 새 참조 → 모든 자식 리렌더. 이걸 회피하려고 useMemo + Context 분리 + state/dispatch 분리 등으로 보일러플레이트가 폭발하면, 사실상 Zustand를 직접 만들고 있는 것.

**원칙**: **로컬은 로컬에, 공유는 공유에**. 위에서부터 (`useState` → `useReducer + Context` → 라이브러리) 충분한 걸 고른다.

### 옵저버 패턴 — 모든 라이브러리의 공통 토대

```
       ┌─────────────────────┐
       │      Subject        │
       │ ─────────────────── │
       │  state              │
       │  observers: Set     │
       │                     │
       │  + subscribe(o)     │
       │  + setState(...)    │
       │      → notify()     │
       └─────────────────────┘
                │
       notify   │   notify
          ▼     ▼      ▼
       ┌────┐ ┌────┐ ┌────┐
       │Obs1│ │Obs2│ │Obs3│
       └────┘ └────┘ └────┘
```

50줄로 구현 가능한 본질:

```ts
function createStore<T>(initial: T) {
  let state = initial
  const listeners = new Set<(s: T) => void>()

  return {
    getState: () => state,
    setState: (next) => {
      state = { ...state, ...(typeof next === 'function' ? next(state) : next) }
      listeners.forEach((l) => l(state))   // ← 옵저버 패턴 핵심
    },
    subscribe: (l) => {
      listeners.add(l)
      return () => listeners.delete(l)
    },
  }
}
```

**이게 사실상 Zustand store의 본체**. 라이브러리들은 이 위에 selector / proxy 추적 / atom 그래프 같은 변형을 얹은 것.

### Observer vs Pub/Sub

| 축 | Observer | Pub/Sub |
|----|----------|---------|
| 중간 매개체 | 없음 (Subject = 채널) | broker / event bus |
| 결합도 | Observer가 Subject 직접 참조 | 발행자/수신자 익명 |
| 라우팅 | Subject 자체 | topic / channel |
| 메시지 보존 | 즉시 호출 | 큐/버퍼/persist 가능 |
| 사용 범위 | in-process | 분산 시스템까지 |

**React 상태관리는 모두 Observer** (in-process + 직접 참조 모델). Pub/Sub는 Kafka/Redis Pub/Sub/MQTT 같은 분산 메시징 영역. EventEmitter나 DOM addEventListener는 경계 케이스로 보통 Observer로 분류.

## Zustand (메인)

### 스토어의 정체 — Context가 아니다

**가장 흔한 오해**: "Zustand store는 Context API로 만들어진다."
**진실**: Zustand의 store는 **React 바깥의 vanilla JS 객체**. 모듈 스코프에 살고 있고 React 트리, Provider, Context와 무관.

```tsx
// Provider 없이 바로 사용 가능
function App() {
  return <Counter />
}

// React 컴포넌트 바깥에서도 접근 가능
useCounterStore.getState()
useCounterStore.setState({ count: 100 })
useCounterStore.subscribe(console.log)
```

React와의 다리는 **`useSyncExternalStore`** (React 18 hook). 외부 store ↔ React가 공식 제공하는 연결 메커니즘.

| | Zustand | Redux + Provider | Context API |
|---|---|---|---|
| Store 위치 | 모듈 스코프 vanilla 객체 | 모듈 스코프 vanilla 객체 | React 트리 안 |
| Provider 필요 | ❌ | ✅ (`<Provider>`) | ✅ (`<Context.Provider>`) |
| React 외부 접근 | ✅ | ✅ | ❌ |

> Redux도 사실 vanilla store + Provider. Provider는 "어떤 store를 쓸지" 알려주는 역할. Zustand는 그것마저 모듈 import로 대체.

### Selector + Object.is + 리렌더 메커니즘

```tsx
const count = useCounterStore((s) => s.count)   // selector
```

**리렌더 결정 흐름**:
1. store 어딘가가 변경됨 → 모든 listener에게 forEach로 알림
2. 각 listener가 selector 재실행
3. 이전 결과와 `Object.is` 비교
4. 같으면 React 리렌더 안 일어남, 다르면 리렌더

**O(N) listener 호출 + O(K) 리렌더** — broadcast then filter.

100명의 컴포넌트가 다른 값을 구독해도, listener 100번 forEach 호출은 마이크로초 단위. 비싼 건 React 리렌더이고 그건 1번만 일어남. 그래서 충분히 빠름.

**Selector의 함정** — 새 객체 반환:

```tsx
// ❌ 매 렌더마다 새 객체 → Object.is({}, {}) === false → 매번 리렌더
const { count, increment } = useCounterStore((s) => ({ count: s.count, increment: s.increment }))

// ✅ useShallow로 shallow 비교
import { useShallow } from 'zustand/react/shallow'
const { count, increment } = useCounterStore(
  useShallow((s) => ({ count: s.count, increment: s.increment }))
)

// ✅ 또는 selector 두 개로 분리
const count = useCounterStore((s) => s.count)
const increment = useCounterStore((s) => s.increment)
```

**거름망이 selector 결과 동등성에 의존**하기 때문에, 잘못 짜면 broadcast가 그대로 통과해 모든 컴포넌트가 리렌더됨. Zustand 디버깅에서 가장 자주 마주치는 함정.

### set 동작

```tsx
set((state) => ({ count: state.count + 1 }))   // functional updater (race-safe)
set({ count: 0 })                                // 절대값 설정
```

**핵심 디테일**:

- **`set`은 partial merge** (replace 아님). `set({ count: 1 })` 해도 다른 필드는 살아있음. Object.assign처럼 동작.
- **두 번째 인자 `true` = replace 모드** (`set({ count: 1 }, true)` → 다른 필드 사라짐). 거의 안 씀.
- **함수 형태가 race-safe**:
  ```tsx
  // ❌ 빠르게 두 번 클릭 시 둘 다 옛 count 봄
  const increment = () => set({ count: count + 1 })
  // ✅ 항상 최신 상태 기반
  const increment = () => set((s) => ({ count: s.count + 1 }))
  ```

### 미들웨어

미들웨어는 `create((set) => ...)` 외부 wrapping. 안쪽 → 바깥 순으로 set/get 통과.

```ts
create(
  devtools(           // ← 가장 바깥 (디버깅)
    persist(          // ← 저장 (storage sync)
      immer(          // ← 가장 안쪽 (set 의미를 mutate-style로 변환)
        (set, get) => ({ ... })
      ),
      { name: 'my-store' }
    )
  )
)
```

#### `persist`

```ts
persist(
  (set) => ({ count: 0, user: null, ... }),
  {
    name: 'app-storage',
    storage: createJSONStorage(() => localStorage),
    partialize: (state) => ({ count: state.count }),  // ← 일부만 저장 (실무 핵심)
    version: 1,
    migrate: (persisted, version) => { ... },
    onRehydrateStorage: () => (state) => { state._hasHydrated = true },
  }
)
```

**핵심**: `partialize`로 민감 정보(토큰)/휘발성 데이터 제외. SSR에선 hydration 플래그로 SSR/CSR 불일치 방지.

```tsx
// 흔한 SSR hydration 안전 패턴
const useHasHydrated = () => {
  const [hydrated, setHydrated] = useState(false)
  useEffect(() => setHydrated(true), [])
  return hydrated
}
```

#### `devtools`

Redux DevTools 확장과 연결. **`set`의 세 번째 인자에 action 이름 항상 지정**:

```ts
increment: () => set((s) => ({ count: s.count + 1 }), false, 'increment')
```

지정 안 하면 DevTools에서 `anonymous`로 뜸. production에선 `enabled: false`.

#### `immer`

```ts
immer((set) => ({
  todos: [],
  addTodo: (todo) => set((state) => {
    state.todos.push(todo)               // ← mutation처럼 보이지만 immer가 immutable로 변환
    state.user.lastEditedAt = Date.now()
  }),
}))
```

깊은 중첩 객체를 자주 수정할 때 유용. 평탄한 store라면 spread가 더 가독성 좋음. 번들 +5KB.

#### `subscribeWithSelector`

```ts
useStore.subscribe(
  (state) => state.count,                // selector
  (count, prev) => console.log('count:', prev, '→', count),
  { fireImmediately: false }
)
```

컴포넌트 외부(API 인터셉터, 라우터 가드)에서 selector 기반 구독. 토큰 변경 시 axios 헤더 갱신 같은 패턴에 사용.

### Slice 패턴

store가 커지면 도메인별로 분할:

```ts
type Store = CounterSlice & UserSlice

const createCounterSlice: StateCreator<Store, [], [], CounterSlice> = (set) => ({
  count: 0,
  increment: () => set((s) => ({ count: s.count + 1 })),
})

export const useStore = create<Store>()((...a) => ({
  ...createCounterSlice(...a),
  ...createUserSlice(...a),
}))
```

**핵심**: `StateCreator<Store, [], [], CounterSlice>`의 첫 제네릭이 전체 store 타입. slice 안에서도 `get()`으로 다른 slice 접근 가능. 200줄 넘어가거나 도메인 3개 이상이면 도입 검토.

slice는 "한 store 안의 논리적 그룹화"지 "독립 모듈"이 아님. 강한 결합이 자주 일어나면 별도 store 두 개로 분리가 더 깔끔.

### SSR — per-request store + Context

**함정**: 모듈 스코프 store는 서버 프로세스 시작 시 한 번만 생성 → **모든 요청이 같은 인스턴스 공유** → 사용자 데이터 누수.

```ts
// store.ts
export const useStore = create((set) => ({ user: null, ... }))
//
// 요청 A가 setUser({ name: 'Alice' }) 하면
// 요청 B의 응답에 Alice가 보일 수 있음 🔥
```

**해결**: per-request store + Context Provider:

```tsx
// store.ts — vanilla store factory
import { createStore } from 'zustand/vanilla'

export const createCountStore = (initial = 0) =>
  createStore<Store>((set) => ({
    count: initial,
    increment: () => set((s) => ({ count: s.count + 1 })),
  }))
```

```tsx
// store-provider.tsx
'use client'
const StoreContext = createContext<StoreApi<Store> | null>(null)

export function StoreProvider({ children, initialCount = 0 }) {
  const storeRef = useRef<StoreApi<Store>>(null)
  if (!storeRef.current) {
    storeRef.current = createCountStore(initialCount)
  }
  return <StoreContext.Provider value={storeRef.current}>{children}</StoreContext.Provider>
}

export function useCountStore<T>(selector: (s: Store) => T): T {
  const store = useContext(StoreContext)
  if (!store) throw new Error('useCountStore must be used within StoreProvider')
  return useStore(store, selector)
}
```

**비용**: Provider-less라는 매력은 깨짐. **이득**: SSR 안전성 + store 다중 인스턴스. App Router + 사용자 데이터를 store에 보관한다면 거의 필수.

## Redux Toolkit (RTK) — 비교

```ts
const counterSlice = createSlice({
  name: 'counter',
  initialState: { count: 0 },
  reducers: {
    increment: (state) => { state.count++ },   // immer 내장
  },
})
```

**Zustand와의 차이**:
- 명시적인 reducer/action 분리 (Flux 패턴)
- Redux DevTools 시간여행 디버깅 (압도적)
- middleware 생태계 (saga, thunk, observable)
- 번들 크기 큼 (~30KB+)
- 러닝 커브 높음

**언제 Redux**: 이미 Redux 코드베이스가 있거나, 강타입 백엔드(OpenAPI)에서 RTK Query를 자동 생성으로 쓰는 큰 팀.

**Zustand가 채택률 1위**가 된 이유: RTK가 줄여낸 boilerplate조차 더 적음 + Redux store/reducer/action 멘탈 모델 학습 비용 없음 + 서버 상태는 어차피 TanStack Query로 분리.

## MobX — 비교

OOP 친화. **proxy로 자동 dependency tracking**.

```ts
class CounterStore {
  count = 0
  constructor() { makeAutoObservable(this) }
  increment() { this.count++ }
  get doubled() { return this.count * 2 }   // 자동 computed
}

const Counter = observer(() => {           // ← observer HOC 필수
  return <div>{store.count}</div>
})
```

**핵심 개념**:

| 개념 | 의미 |
|------|------|
| `observable` | proxy로 감싸진 reactive 데이터 |
| `action` | state 변경 메서드 (자동 batching) |
| `computed` | 의존 observable에서 파생 값 (memoize) |
| `observer()` HOC | 컴포넌트를 reactive로 만듦 (빼먹으면 추적 안 됨) |
| `runInAction` | 여러 mutation을 한 번에 |

**강점**: 큰 OOP 도메인 모델링, computed 자동 memoize.
**약점**: 러닝 커브 가장 높음, decorator 빌드 설정, 번들 ~16KB, TypeScript 까다로움, 신규 도입 줄어드는 추세.

## Valtio — 비교 (회사 사용 중)

가장 단순한 mutable proxy 모델. Poimandres 팀.

```ts
import { proxy, useSnapshot } from 'valtio'

const state = proxy({ count: 0, user: { name: 'foo' } })

// 변경 = 그냥 mutation
function increment() { state.count++ }

// 컴포넌트
function Counter() {
  const snap = useSnapshot(state)         // ← snap은 immutable
  return <div>{snap.count}</div>
}
```

**핵심 영리한 디테일**:

- **`useSnapshot` 반환 = 그 시점의 immutable 스냅샷**. 렌더 안에선 immutable, 외부에선 mutable. 두 영역 분리.
- **구조 공유 (Structural Sharing)**: `state.user.name = 'bar'` 만 변경 시 `state.todos` 참조는 그대로. snapshot도 변경된 가지만 새 참조.
- **proxy 자동 추적**: `snap.count` 읽으면 그 컴포넌트가 자동으로 `count` 의존성으로 등록 → `count` 변경 시 그 컴포넌트만 리렌더.

**vs MobX**:

| | MobX | Valtio |
|---|---|---|
| 스타일 | OOP, 클래스 | 함수형, 객체 |
| Mutation | `action` 메서드 안 | 어디서든 |
| Computed | `get` getter 자동 | `derive` 명시 |
| 컴포넌트 | `observer()` HOC | `useSnapshot()` 훅 |
| 번들 | ~16KB | **~3KB** |
| 학습곡선 | 높음 | 낮음 |
| 트렌드 | 줄어드는 추세 | 늘어나는 추세 |

**언제 Valtio**: mutation이 자연스러운 도메인(Vue 출신, OOP 출신, 게임 UI), 작은 번들 + 단순 API.

## Jotai — 비교 (Recoil 후계자)

**atom 단위 분리**. React `useState`를 트리 외부로 끌어내고 의존성 그래프 구축.

```ts
import { atom, useAtom, useAtomValue, useSetAtom } from 'jotai'

const countAtom = atom(0)                                            // primitive
const doubledAtom = atom((get) => get(countAtom) * 2)                // derived (read-only)
const incrementAtom = atom(null, (get, set) => {                     // write-only
  set(countAtom, get(countAtom) + 1)
})

function Counter() {
  const [count, setCount] = useAtom(countAtom)
  const doubled = useAtomValue(doubledAtom)
  const increment = useSetAtom(incrementAtom)   // 읽기 안 함 → 리렌더 안 됨
  return <button onClick={increment}>{count} (×2 = {doubled})</button>
}
```

**핵심 인사이트**: atom은 그 자체로 값을 갖는 게 아니라 **"키 역할"**. 실제 값은 Provider(또는 default store)가 보관. → 같은 atom을 여러 Provider에서 다른 값으로 쓸 수 있음.

### atomFamily — 동적 atom

```ts
import { atomFamily } from 'jotai/utils'

const todoAtom = atomFamily((id: number) =>
  atom({ id, text: '', done: false })
)

function TodoItem({ id }) {
  const [todo, setTodo] = useAtom(todoAtom(id))   // id별 독립 atom
  return ...
}
```

**리스트의 각 아이템마다 독립 atom** → 한 항목 수정해도 다른 항목 리렌더 안 됨. 큰 리스트 성능에 압도적.

### async atom + Suspense

```ts
const userAtom = atom(async (get) => {
  const id = get(userIdAtom)
  return fetch(`/api/users/${id}`).then(r => r.json())
})

function User() {
  const user = useAtomValue(userAtom)   // ← Promise를 throw → Suspense
  return <div>{user.name}</div>
}
```

**Suspense 1급 시민**. 다만 캐싱/refetch는 약하므로 보통 **`jotai-tanstack-query`로 결합**. 서버 상태는 TanStack, 클라이언트 상태는 Jotai 라는 명확한 분리.

**강점**: fine-grained reactivity, useState 멘탈 모델 확장, async/Suspense 기본 지원, atomFamily로 리스트 성능, TypeScript 추론 우수.
**약점**: atom이 흩어져 있어 전체 state 한눈에 보기 어려움, 큰 도메인 한 덩어리로 다루기 불편.

### 📌 Recoil 짚어둘 점

Meta가 만든 atomic 상태관리 라이브러리. **2025년 초부터 사실상 maintenance mode** (거의 deprecated). 후계자 자리는 **Jotai**가 차지 — 거의 같은 atomic 모델 + 더 작고 활발한 메인테넌스 + Poimandres 생태계 통합. **신규 프로젝트에서 Recoil 도입은 비권장**. 기존 Recoil 코드는 Jotai 마이그레이션 자료가 잘 정리되어 있음.

## "선택적 호출"이 가능한가 — 진영별 차이

100명의 컴포넌트가 각자 다른 상태를 구독한다고 가정. 1개 상태 변경 시:

| 진영 | listener 호출 비용 | 리렌더 비용 | "필요한 컴포넌트만 호출"? |
|------|--------------------|------------|------------------------|
| **Zustand/Redux** | **O(N)** (전체 forEach) | O(K) | ❌ broadcast + selector 거름 |
| **MobX/Valtio** | O(K) (proxy 추적) | O(K) | ✅ 정확히 |
| **Jotai** | O(해당 atom listener) | O(K) | ✅ atom 단위 |

**입자(granularity) 비교**:

```
Zustand/Redux        ████████████████████████  (큰 store 1개, 필드는 selector)
MobX/Valtio          ████████  ████  ████      (객체 단위, 안 property는 자동)
Jotai                █  █  █  █  █  █  █  █    (atom 단위, 가장 작음)
```

| | 추적 단위 | store 분리 관행 |
|---|---|---|
| Zustand | 필드 (selector) | 큰 store 1개 + slice 패턴 |
| Redux | 필드 (selector) | 1개 store + reducer 분할 |
| MobX | property (proxy) | 객체별 sub-store + RootStore |
| Valtio | property (proxy) | 도메인별 proxy 자유 분리 |
| Jotai | atom | atom 단위 (모든 게 분리) |

**대부분의 SPA는 Zustand의 broadcast + filter로 충분**. 1000개 넘어가는 거대 트리, 실시간 업데이트 (게임 UI, 시각화)에서 proxy/atom 진영이 빛남.

## "왜 Zustand인가" — 결론

1. **단순한 mental model** — 옵저버 패턴 + selector. 신규 멤버 30분이면 이해.
2. **boilerplate 0** — `create((set) => ({ ... }))` 한 줄.
3. **번들 ~3KB** — 가장 가벼운 축.
4. **TanStack Query와 직교** — 서버 상태 / 클라이언트 상태 깔끔히 분리.
5. **proxy 마법 없음** — 디버깅 시 selector만 보면 됨.
6. **SSR 패턴 명확** — per-request store + Context.
7. **selector 함정만 알면 충분히 빠름** — 99%의 SPA에서.

## 핵심 질의응답

**Q. Zustand의 store는 Context API로 만들어진 건가?**
A. **아니다**. store는 모듈 스코프에 사는 vanilla JS 객체. React 트리 바깥. `useSyncExternalStore`로 React에 연결될 뿐. Provider 없이 동작하고, React 컴포넌트 바깥에서도 `useStore.getState()`/`setState()`로 접근 가능. 이게 Zustand의 결정적 차별점.

**Q. selector 함수를 인자로 넘기는 이유?**
A. "이 컴포넌트는 store 전체가 아니라 selector가 반환한 부분만 구독한다"고 알려주는 것. broadcast then filter — listener는 전체 호출되지만 selector 결과가 `Object.is`로 같으면 React 리렌더 트리거 안 함. 부분 구독 메커니즘.

**Q. `set((s) => ({...}))` vs `set({...})` 차이?**
A. 함수 형태는 race-safe (항상 최신 상태 기반), 객체 형태는 절대값 설정. 또한 `set`은 partial merge라 다른 필드 살아있음 (replace 아님). 두 번째 인자 `true` 주면 replace.

**Q. setState 시 모든 listener가 다 호출되나?**
A. **Zustand/Redux는 그렇다 (broadcast + filter)**. forEach로 전체 호출 → 각 컴포넌트가 selector + Object.is로 거름. **MobX/Valtio는 proxy가 의존성 추적해서 정확한 컴포넌트만 호출**. **Jotai는 atom마다 독립 listener라 해당 atom 구독자만 호출**.

**Q. selector를 잘못 쓰면?**
A. 새 객체 반환하면 매번 `Object.is({}, {}) === false` → 거름망 통과 → 매 setState마다 리렌더. `useShallow`로 감싸거나 selector 분리. **Zustand 디버깅에서 가장 흔한 함정**.

**Q. MobX/Valtio/Jotai는 store가 상태마다 분리되나?**
A. **Jotai만 진짜 atom 단위 분리**. MobX/Valtio는 객체 단위로 분리하고 그 안 property는 proxy가 자동 추적. Zustand는 관행상 큰 store 하나 + selector. **추적 입자**와 **store 경계**는 다른 차원.

**Q. Observer 패턴과 Pub/Sub 차이?**
A. Observer는 Subject가 Observer Set 직접 들고 forEach로 broadcast. Pub/Sub는 broker가 topic으로 라우팅 + 발행자/수신자 익명. React 상태관리는 모두 Observer (in-process + 직접 참조). Pub/Sub는 분산 시스템(Kafka/Redis Pub/Sub) 영역.

**Q. Context API로 글로벌 상태관리 안 되나?**
A. **선택적 구독(selector)이 없어서 자주 바뀌는 데이터엔 부적합**. value의 일부만 바뀌어도 구독한 모든 컴포넌트 리렌더. 회피 패턴(useMemo + Context 분리 + state/dispatch 분리)을 쓰다 보면 Zustand를 직접 만드는 셈. Context는 **자주 안 바뀌는 값의 의존성 주입**(theme/locale/auth/queryClient)에 적합.

**Q. 서버 상태와 클라이언트 상태를 한 라이브러리에서 다루는 게 좋나?**
A. **분리가 정답**. 서버 상태(캐시/네트워크 동기화)와 클라이언트 상태(UI 토글/폼 값)는 사상이 달라서. **TanStack Query (서버) + Zustand/Valtio/Jotai (클라이언트)** 가 가장 깔끔. Jotai는 `jotai-tanstack-query`로 결합 가능.

**Q. Zustand 발음?**
A. /ˈtsuːʃtant/, "쭈슈탄트". 독일어로 "상태(state)" 자체가 의미. `Z`는 영어 /z/가 아닌 독일어 /ts/.

## 주의사항 / 자주 하는 실수

- **Zustand selector에서 새 객체 반환** → 매번 리렌더. `useShallow` 사용 또는 selector 분리.
- **모듈 스코프 store + SSR** → 사용자 데이터 누수. per-request store + Context Provider 패턴 필수.
- **Context value `={{ ... }}` 인라인 객체** → 매 렌더 새 참조 → 모든 자식 리렌더. `useMemo` 사용.
- **Context로 자주 바뀌는 글로벌 상태 흉내** → selector 부재로 리렌더 폭탄. 라이브러리 도입 신호.
- **`persist`에 토큰/민감 정보 그대로 저장** → 로그아웃해도 storage에 남음. `partialize`로 제외.
- **devtools `set`의 action 이름 빼먹기** → DevTools에서 `anonymous`. 디버깅 시간 낭비.
- **모든 상태를 store에** → 로컬 상태도 store에 박는 안티패턴. **로컬은 로컬에**.
- **MobX `observer()` HOC 빼먹기** → 추적 활성화 안 됨, 리렌더 안 일어남.
- **Valtio에서 `useSnapshot` 결과를 mutate하려고 시도** → snapshot은 readonly. 원본 store를 mutate해야.
- **Jotai atom 정의를 컴포넌트 안에 넣기** → 매 렌더마다 새 atom. 모듈 스코프에 정의.
