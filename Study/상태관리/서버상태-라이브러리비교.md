# 서버 상태 라이브러리 비교 (TanStack Query / SWR / RTK Query)

> 2026-05-06 | 서버상태, 캐싱, TanStack Query, SWR, RTK Query, React Query

## 한 줄 요약

서버 상태는 **"내 손으로 만들지 않은 데이터의 캐시"**다. 세 라이브러리 모두 이 캐시 라이프사이클을 다루지만, **TanStack Query는 세밀한 두 축 캐시 모델 + 상태관리 라이브러리 독립성**, **SWR은 가장 가벼운 stale-while-revalidate 훅**, **RTK Query는 Redux 기반 선언형 endpoint + 태그 invalidation**으로 갈린다.

## 핵심 개념

### 왜 서버 상태 라이브러리가 필요한가

`useState` + `useEffect`로 fetch를 직접 쓰는 코드의 본질적 문제:

- **요청 중복** — 같은 데이터를 여러 컴포넌트가 각자 fetch
- **캐시 부재** — 이미 받은 데이터를 또 받음
- **stale 추적 부재** — 언제 다시 받아야 하는지 판단할 메커니즘 없음
- **레이스 컨디션** — 두 번째 요청이 첫 번째보다 먼저 도착하면 옛 데이터로 덮어씀
- **포커스/네트워크 복귀 갱신 없음** — 다른 탭에서 데이터 바뀐 거 모름
- **로딩/에러 상태 보일러플레이트**

서버 상태 라이브러리는 이 문제들을 **캐시 + observer 모델**로 한 번에 해결한다. 핵심 단어는 항상 **"캐시"**.

## TanStack Query (구 React Query)

### 캐시 라이프사이클 — 4가지 상태

이게 TanStack Query 이해의 출발점. **`staleTime`과 `gcTime`은 독립적인 두 축**이라는 게 가장 중요한 인사이트.

```
       observer 있음                  observer 없음 (inactive)
       ┌────────────┐                  ┌──────────────┐
       │   fresh    │  staleTime 지남  │   inactive   │  gcTime 지남
       │ (refetch   │ ───────────────► │  (캐시 보존,  │ ───────────────►  🗑️ 캐시 삭제
       │   안 함)   │                  │   stale 가능) │
       └────────────┘                  └──────────────┘
              │                               ▲
              │                               │
              ▼                               │
       ┌────────────┐                         │
       │   stale    │ ◄───── 컴포넌트 언마운트
       │ (트리거 시  │
       │  refetch)  │
       └────────────┘
```

| 타이머 | 의미 | 끝나면 |
|--------|------|--------|
| `staleTime` | "신선함 보장" 시간 | `fresh` → `stale` |
| `gcTime` (구 `cacheTime`) | "관찰자가 사라진 후" 캐시 보존 시간 | 캐시에서 **삭제** |

**핵심 규칙**: 컴포넌트(observer)가 살아 있는 동안엔 절대 GC 안 됨. `gcTime`은 마지막 observer가 사라진 시점부터 카운트.

### staleTime/gcTime 시나리오

```tsx
useQuery({
  queryKey: ['user', 1],
  queryFn: fetchUser,
  staleTime: 60_000,     // 1분
  gcTime: 5 * 60_000,    // 5분
})
```

| 시나리오 | 동작 |
|---------|------|
| 30초 뒤 같은 쿼리 컴포넌트 재마운트 | **fetch 안 함** (아직 fresh) |
| 언마운트 → 2분 뒤 재마운트 | 캐시 즉시 표시 + 백그라운드 refetch |
| 언마운트 → 6분 뒤 재마운트 | gcTime 지나 캐시 삭제 → 처음부터 fetch |

### 자동 refetch 트리거 (stale일 때만 의미)

| 트리거 | 기본값 | 동작 |
|--------|--------|------|
| `refetchOnMount` | `true` | 마운트 시 stale이면 refetch |
| `refetchOnWindowFocus` | `true` | 탭 활성화 시 stale이면 refetch |
| `refetchOnReconnect` | `true` | 네트워크 복귀 시 stale이면 refetch |
| `refetchInterval` | `false` | 폴링 (stale 무관) |

핵심 철학: **stale-while-revalidate** — 옛 데이터 우선 보여주고, 백그라운드에서 갱신.

### invalidate / refetch / setQueryData

| API | 동작 | 네트워크 요청 |
|-----|------|---------------|
| `invalidateQueries` | 매칭 쿼리를 stale로 마킹 + active 쿼리 즉시 refetch | ✅ active만 |
| `refetchQueries` | 매칭 쿼리를 stale 무관 무조건 refetch | ✅ 모두 |
| `setQueryData` | 캐시를 직접 덮어쓰기 | ❌ |

```tsx
// 90% 케이스 — invalidate
queryClient.invalidateQueries({ queryKey: ['comments', postId] })

// 응답을 이미 알 때 — setQueryData
const newPost = await createPost(data)
queryClient.setQueryData(['posts'], (old) => [...old, newPost])
```

`invalidateQueries`는 prefix 매칭이 기본. `['posts']`는 `['posts', 1]`, `['posts', { filter }]`까지 모두 매칭. `exact: true`로 정확 매칭 가능. **쿼리키를 계층적으로 설계**해두면 한 번에 invalidate할 수 있어 큰 강점.

### Optimistic Update + 롤백

```tsx
useMutation({
  mutationFn: toggleTodo,

  onMutate: async (newTodo) => {
    // 1) 진행 중 refetch 중단 (없으면 응답이 낙관적 업데이트를 덮어씀)
    await queryClient.cancelQueries({ queryKey: ['todos'] })

    // 2) 롤백용 스냅샷
    const previous = queryClient.getQueryData(['todos'])

    // 3) 낙관적 반영
    queryClient.setQueryData(['todos'], (old) =>
      old.map(t => t.id === newTodo.id ? newTodo : t)
    )

    return { previous }  // ← context로 onError에 전달
  },

  onError: (err, newTodo, context) => {
    queryClient.setQueryData(['todos'], context.previous)  // 롤백
  },

  onSettled: () => {
    queryClient.invalidateQueries({ queryKey: ['todos'] })  // 서버와 최종 동기화
  },
})
```

**`cancelQueries`가 필수**인 이유: 사용자가 토글한 직후 `refetchOnWindowFocus`로 시작된 refetch가 늦게 도착하면 캐시를 덮어써 낙관적 업데이트가 사라진다.

### React 19 `useOptimistic`과의 관계

React 19에 추가된 `useOptimistic`은 **별도의 임시 state + 자동 롤백** 모델. transition/form action 안에서 동작하고 끝나면 React가 정리.

| | TanStack `onMutate` | React `useOptimistic` |
|---|---|---|
| 어디에 임시 상태 | 캐시 직접 덮어씀 | 별도 임시 state |
| 롤백 | 수동 (`onError`) | 자동 (action 끝나면) |
| 어디서 쓰나 | 어떤 mutation이든 | transition/form action 안에서만 |
| 짝꿍 | TanStack Query | Server Actions / form action |

**대부분의 실무 케이스**: TanStack Query를 쓰고 있으면 `onMutate`. Server Actions 중심 코드면 `useOptimistic`. 둘 다 사용 가능 (캐시는 TanStack, 시각 피드백은 useOptimistic).

### Suspense 모드

```tsx
function UserProfile() {
  const { data } = useSuspenseQuery({  // ← data 타입이 그냥 T
    queryKey: ['user', id],
    queryFn: fetchUser,
  })
  return <div>{data.name}</div>
}

<ErrorBoundary fallback={<Error />}>
  <Suspense fallback={<Spinner />}>
    <UserProfile />
  </Suspense>
</ErrorBoundary>
```

**동작**: 데이터 없으면 promise를 throw → 가장 가까운 Suspense가 fallback 렌더. 에러는 ErrorBoundary가 잡음. **로딩/에러 분기를 트리 위로 끌어올림**.

**제약**: `enabled: false` 같은 조건부 옵션 불가. 데이터가 항상 필요한 곳에서만 사용. 한 컴포넌트에 여러 suspense 쿼리는 폭포수 가능 → `useSuspenseQueries`로 병렬화.

### Next.js 연동 — HydrationBoundary 패턴

```tsx
// app/posts/page.tsx (Server Component)
export default async function PostsPage() {
  const queryClient = new QueryClient()

  await queryClient.prefetchQuery({
    queryKey: ['posts'],
    queryFn: fetchPosts,
  })

  return (
    <HydrationBoundary state={dehydrate(queryClient)}>
      <PostsList />
    </HydrationBoundary>
  )
}
```

```tsx
// app/posts/PostsList.tsx
'use client'
export function PostsList() {
  const { data } = useSuspenseQuery({
    queryKey: ['posts'],
    queryFn: fetchPosts,
  })
  return <ul>{data.map(p => <li key={p.id}>{p.title}</li>)}</ul>
}
```

**핵심 포인트**:
- **`QueryClient`는 매 요청마다 새로** (RSC 함수 안에서 `new`). 전역 싱글톤은 사용자 데이터 누수.
- 클라이언트는 별도 싱글톤 (window 체크).
- **`staleTime > 0` 권장** — 0이면 hydration 직후 곧바로 stale → 클라이언트가 또 fetch.
- RSC는 hook 못 씀 — 그냥 `await fetch`/DB 호출 → prefetch로 캐시 주입 → HydrationBoundary 전달.

### HydrationBoundary 대체 패턴 (자체 Context)

회사 코드처럼 `HydrationBoundary` 대신 **React Context로 SSR 데이터를 주입**하는 패턴도 가능. 차이:

| | HydrationBoundary | Context 주입 |
|---|---|---|
| 데이터 전달 | dehydrated JSON | Context (promise도 가능) |
| 직렬화 | JSON 강제 (Date/Map/Set 손상) | JS object 그대로 |
| Streaming | 어려움 (await 필요) | promise 그대로 넘겨 RSC streaming과 자연스럽게 결합 |
| 표준성 | 공식 | 자체 |
| 유지비 | 0 | 있음 |

**적합 영역**: 자주 안 바뀌는 ISO 데이터(권한/설정/메타데이터) + RSC 무거운 앱이면 자체 패턴이 더 우월할 수 있음. 일반 CRUD/리스트는 공식 패턴이 답.

## SWR (Vercel)

### 한 줄 정리

가장 가벼운 stale-while-revalidate 훅. HTTP 캐시 헤더 전략을 React 훅으로 옮긴 것.

### 기본 사용

```tsx
const { data, error, isLoading, mutate } = useSWR(
  `/api/user/${id}`,                       // key (URL 그대로 관용)
  (url) => fetch(url).then(r => r.json()), // fetcher
)
```

### TanStack Query와의 차이

| | TanStack Query | SWR |
|---|---|---|
| Key | `['posts', id, { filter }]` 배열 | URL 문자열 |
| 캐시 모델 | `staleTime` + `gcTime` 두 축 | `dedupingInterval` (기본 2초) 단일 축 |
| Mutation | 별도 `useMutation` 훅 | `mutate(key, ...)` 함수 |
| Suspense | `useSuspenseQuery` | `{ suspense: true }` 옵션 |
| Infinite | `useInfiniteQuery` | `useSWRInfinite` |
| 번들 | ~13KB gzip | **~4KB gzip** |
| DevTools | 공식 강력 | 비공식, 약함 |

### Mutation 패턴

```tsx
import { mutate } from 'swr'

await mutate(
  '/api/todos',
  async (current) => {
    const res = await fetch('/api/todos', { method: 'POST', body: text })
    return [...current, await res.json()]
  },
  {
    optimisticData: [...currentTodos, { id: 'temp', text }],
    rollbackOnError: true,
    populateCache: true,
    revalidate: false,
  }
)
```

별도 mutation 훅 없이 캐시 갱신 함수 호출로 해결. 단순하지만 진행 중 상태(`isPending`) 추적은 직접 `useState`로.

### 강점/약점

**강점**: 번들 작음, API 단순, Vercel/Next.js 친화, RSC 친화.
**약점**: 세밀한 캐시 제어 부족 (staleTime/gcTime 구분 없음), DevTools 약함, 타입 추론 약함, mutation 라이프사이클 hook 부재.

## RTK Query (Redux Toolkit)

### 한 줄 정리

Redux 위에 올라간 데이터 페칭 레이어. **API endpoint를 선언하면 훅이 자동 생성**되고, **태그 기반으로 자동 invalidation**.

### 기본 사용 — 선언형 endpoint

```tsx
const api = createApi({
  reducerPath: 'api',
  baseQuery: fetchBaseQuery({ baseUrl: '/api' }),
  tagTypes: ['Post'],

  endpoints: (builder) => ({
    getPosts: builder.query<Post[], void>({
      query: () => 'posts',
      providesTags: ['Post'],
    }),
    addPost: builder.mutation<Post, Partial<Post>>({
      query: (body) => ({ url: 'posts', method: 'POST', body }),
      invalidatesTags: ['Post'],  // ← 자동으로 getPosts refetch
    }),
  }),
})

export const { useGetPostsQuery, useAddPostMutation } = api  // 훅 자동 생성

// 컴포넌트
const { data } = useGetPostsQuery()
const [addPost] = useAddPostMutation()
```

### 태그 기반 invalidation의 가치

```tsx
updatePost: builder.mutation({
  query: ({ id, ...patch }) => ({ url: `posts/${id}`, method: 'PATCH', body: patch }),
  invalidatesTags: (result, error, { id }) => [
    { type: 'Post', id },
    { type: 'Post', id: 'LIST' },
  ],
})
```

TanStack은 매 mutation마다 `invalidateQueries` 호출 코드 작성. RTK Query는 endpoint 선언에 태그 박아두면 자동 연쇄. **큰 앱에서 일관성 강점**.

### TanStack Query와의 차이

| | TanStack Query | RTK Query |
|---|---|---|
| 선언 방식 | 컴포넌트마다 인라인 | 중앙집중 endpoint |
| Invalidation | 명령형 (`invalidateQueries`) | **선언형 (태그)** |
| DevTools | 공식 | **Redux DevTools** (시간여행) |
| Code Generation | 없음 | **OpenAPI/GraphQL 지원** |
| 상태관리 통합 | 별개 | Redux store와 같은 곳 |
| 러닝 커브 | 중 | **고** (Redux + RTK + RTK Query) |

### 강점/약점

**강점**: 선언형 endpoint, 태그 자동 invalidation, OpenAPI code-gen (백엔드 강타입 환경에서 압도적), Redux DevTools.
**약점**: Redux 의존성, 러닝 커브, 유연성 떨어짐, 번들 큼.

## 세 라이브러리 한 표 요약

| | TanStack Query | SWR | RTK Query |
|---|---|---|---|
| 만든 곳 | TanStack | Vercel | Redux 팀 |
| 철학 | 강력하고 유연한 캐시 | 가볍고 단순 | Redux 통합 + 선언형 |
| API 스타일 | 명령형 | 명령형 (단순) | **선언형 (endpoint 중앙집중)** |
| 번들 크기 | 13KB | **4KB** | 12KB (+ Redux 30KB) |
| DevTools | 공식 강력 | 약함 | Redux DevTools |
| Mutation | 별도 `useMutation` | `mutate()` 함수 | 자동 생성 훅 |
| Invalidation | 명령형 | 명령형 | **선언형 (태그)** |
| Code Gen | 없음 | 없음 | **OpenAPI/GraphQL** |
| Suspense | ✅ 1급 시민 | ✅ 옵션 | 부분 |
| 러닝 커브 | 중 | 저 | 고 |

## "왜 TanStack Query인가" — 결론

| 상황 | 권장 |
|------|------|
| 새 프로젝트, 일반적인 데이터 페칭 | **TanStack Query** |
| 번들 크기 극도로 신경 + Vercel/Next.js 환경 | SWR |
| 이미 Redux 쓰는 중 + 백엔드 OpenAPI 스펙 있음 | RTK Query |
| Zustand/MobX 등 다른 상태관리 + 서버 상태 필요 | TanStack Query (독립적) |
| 세밀한 캐시 제어 필요 | TanStack Query |

**TanStack Query를 선택하는 진짜 이유**:
1. **상태관리 라이브러리와 독립적** — Zustand/Redux/MobX 어떤 거랑도 같이 사용 가능.
2. **세밀한 캐시 제어** — staleTime/gcTime 두 축 + observer 모델은 SWR/RTK Query에 없음.
3. **DevTools 압도적** — 디버깅 시간 큰 차이.
4. **선언형이 필요하면 wrapper로 만들면 됨** — RTK Query 같은 강제 선언형보다 자유도 높음.

## 핵심 질의응답

**Q. `useMutation`은 API 리페치해서 UI 새로 그리는 훅인가?**
A. 부분적으로만 맞음. 정확히는 **POST/PUT/DELETE 같은 쓰기 액션 트리거 + 라이프사이클 관리** 훅. **자동 refetch 기능 없음**. 리페치는 `onSuccess`에서 사용자가 명시적으로 `invalidateQueries` 호출해야 일어남. UI 갱신은 invalidate 받은 `useQuery` 쪽 책임.

**Q. `useQuery`와 `useMutation`의 결정적 차이?**
A. `useQuery`는 마운트되면 자동 fetch (선언형 읽기). `useMutation`은 `mutate(data)` 호출해야 실행 (명령형 트리거). 그리고 `useMutation`은 캐시를 자동으로 갱신 안 함.

**Q. React 19 `useOptimistic`이 있으면 `onMutate` 안 써도 되나?**
A. 둘은 사상 다름. `useOptimistic`은 **별도 임시 state + 자동 롤백** (transition/form action 안에서). `onMutate`는 **캐시 직접 덮어씀 + 수동 롤백**. TanStack Query 쓰고 있으면 `onMutate`가 자연스럽고, Server Actions 중심 코드면 `useOptimistic`. 같이 사용도 가능.

**Q. 회사 코드(IsoQuery 패턴)는 HydrationBoundary 패턴과 같은 건가?**
A. **목표는 같지만 메커니즘이 다른 자체 변형**. HydrationBoundary는 dehydrated JSON으로 캐시 전달, IsoQuery는 React Context로 SSR 값/promise 직접 주입. 후자는 RSC streaming과 자연스럽게 결합되고 직렬화 한계 회피하지만 유지비가 듦. ISO 데이터에 한해 더 우월할 수 있음.

**Q. `staleTime: 0`이 기본값인 이유?**
A. 안전한 디폴트. "데이터가 옛것일 수도 있음"을 가정하고 매번 백그라운드 갱신. 다만 변화가 적은 데이터(설정값/프로필)에선 요청 폭증 원인 → 명시적으로 `staleTime: Infinity` 권장.

**Q. `invalidateQueries`와 `refetchQueries` 차이?**
A. 전자는 매칭된 쿼리를 stale로 마킹하고 **active(마운트된)** 쿼리만 refetch. 후자는 stale 여부 무시하고 **무조건** refetch (inactive 포함). `refetchQueries`를 써야 할 상황이면 보통 설계 재검토 신호.

**Q. RTK Query 단독으로 Redux 도입할 가치 있나?**
A. **거의 없음**. RTK Query 단독 가치 < Redux 도입 비용. 이미 Redux 쓰고 있을 때만 자연스러운 선택.

## 주의사항 / 자주 하는 실수

- **`staleTime: 0` 기본값 인지 못 함** — 매 마운트마다 백그라운드 fetch. 변화 적은 데이터면 요청 폭증.
- **Optimistic update에서 `cancelQueries` 빼먹기** — refetch 응답이 낙관적 업데이트를 덮어쓰는 깜빡임.
- **`invalidateQueries` await 안 함** — 다음 코드가 옛 데이터 보고 동작.
- **`useSuspenseQuery`를 조건부로 사용** — `enabled: false` 같은 옵션 없음. 컴포넌트 분리로 해결.
- **Next.js에서 `QueryClient`를 모듈 최상단에 생성** — 전역 싱글톤 → SSR에서 사용자 데이터 누수.
- **HydrationBoundary 사용 시 `staleTime: 0`** — hydration 직후 곧바로 stale → 클라이언트가 또 fetch. 무용지물.
- **"SWR이 더 가볍다"로 선택** — 작은 앱이면 맞지만, 기능 늘리다 보면 결국 TanStack 같은 기능을 직접 구현하게 됨.
- **RTK Query 쓰려고 Redux 도입** — 보통 잘못된 결정.
