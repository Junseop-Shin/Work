## 1. 다섯 회차를 한 줄씩

| 회차 | 무엇을 했나 | 무엇을 보였나 |
|---|---|---|
| S23 LLMs4OL | 세 과제(타입·계층·관계)로 LLM 능력을 벤치마크 | 판정은 되지만 용어 추출과 공리는 평가 밖이다 |
| S24 CQ 기반 HITL | 오픈소스 LLM 6단계로 온톨로지·KG를 실제로 생성 | 작업을 쪼개야 동작한다. 재사용은 안 된다 |
| S25 멀티에이전트 | 계획을 문서로 외부화하고 역할을 나눔 | 설계 품질은 오르는데 질의 성능은 따라오지 않는다 |
| S26 Schema-grounded | 코드 구조와 Wikidata 스키마에 생성을 묶음 | 무엇에 묶느냐가 무엇을 잘하게 될지를 정한다 |
| S27 KGOE 가속화 | 모듈로 범위를 좁히고, 역할·출력 형식을 단계별로 제한 | 병목은 추출이 아니라 구조를 일관되게 관리하는 데 있다 |

앞의 둘이 "할 수 있나"를 물었고 뒤의 셋이 "어떻게 제약할 것인가"를 답한다. 챕터의 무게중심이
가능성에서 통제로 옮겨간다.

## 2. 다섯 회차에서 반복된 것 셋

### 한 번에 시키면 안 된다

| 회차 | 근거 |
|---|---|
| S24 | 논문 전체를 넣고 "KG를 만들어 달라"고 하면 쓸모 있는 결과가 거의 없었다. 6단계로 쪼갠 뒤 동작 |
| S25 | baseline은 해석·설계·작성이 한 단계로 압축된다. 설계 품질 1.33 대 3.33 |
| S26A | 관계 추출을 relation → entity → triple 3단계로 분해 |
| S27A | 대규모 온톨로지를 통째로 넣으면 무관한 조건이 규칙에 섞인다. GeoLink 대조군은 완전 실패 |
| S27B | 추출과 계층 추론을 분리하고 RDF 직렬화는 라이브러리에 맡긴다 |

다섯 회차 중 넷에서 같은 결론이 나왔다. **이것이 Ch.7에서 가장 강한 관찰이다.**

다만 이유는 회차마다 다르게 설명된다. S24는 출력 형식이 정해지지 않아서, S25는 계획과 구현이
압축돼서, S27A는 컨텍스트에 잡음이 섞여서라고 본다. 세 설명이 서로 배타적이지 않다.

### 전역 일관성은 지시로 안 되고 조회로 된다

| 회차 | 무슨 일이 |
|---|---|
| S24 | PROV-O 재사용을 프롬프트로 지시했는데 객체 속성 재사용 0건 |
| S25 | 중복만 유일하게 개선되지 않음. 전역 상태가 attention 범위를 넘어선다 |
| S26B | **Wikidata property 목록을 밖에 두고 임베딩으로 검색해 매칭한다.** 해결 |
| S27A | 모듈 목록을 밖에 두고 관련 모듈만 골라 넣는다 |

Ch.7에서 답을 찾은 유일한 항목이다. 규칙으로 적으면 이렇게 된다. **모델의 기억에 전역 일관성을
맡기지 말고, 조회 가능한 목록과 매칭 단계로 만들어 준다.**

S27A의 모듈 선택도 같은 장치의 변형이다. 목록에서 고른다는 점은 같고 고르는 단위가 관계가 아니라
모듈이다.

### 지표와 목표가 어긋난다

| 회차 | 어긋나는 지점 |
|---|---|
| S23 | ATOMIC의 N/T sro가 과제 설계 때문에 100%로 포화 |
| S25 | 설계 품질이 2.5배 올랐는데 SPARQL 응답률은 오히려 하락 |
| S26B | 더 풍부한 온톨로지를 만들면 좁은 테스트셋 기준으로 감점 |
| S27B | Exact Match가 0에 가깝다. 의미가 같아도 이름이 다르면 0점 |

방향은 제각각인데 원인은 하나다. **온톨로지 구축에는 정답이 하나가 아닌데 지표는 하나를
전제한다.** 이름 짓기에 정답이 없고, 범위를 넓히는 것이 옳은지 좁히는 것이 옳은지도 용도에
달렸다.

이 문제를 그나마 다룬 것이 S25의 두 지표 병기(SPARQL과 RAG)와 S27B의 두 매칭(Exact와 Fuzzy)이다.
둘 다 **엄격한 지표와 관대한 지표를 나란히 놓아 실패의 원인을 가른다.**

## 3. 사람이 남는 자리 — 다섯 회차 종합

| 회차 | 사람이 하는 일 |
|---|---|
| S23 | gold ontology를 만든 사람들 (벤치마크 전제) |
| S24 | CQ 확정, 정답 작성 |
| S25 | 없음 (LLM 심사자 5개로 대체) |
| S26 | Wikidata를 만든 사람들 + 확장 허용 정책 결정 |
| S27A | use case·작업 범위 정의, 모듈 설계, 최종 검증 |
| S27B | 데이터셋 구축, 정답 작성 |

**S25만 사람이 빠져 있다.** 정답 온톨로지도 human evaluation도 없다. 그 회차의 대표 수치(설계
품질 1.33 → 3.33)가 LLM 다섯의 채점이라는 점을 기억하고 읽어야 한다.

그리고 사람이 남는 자리가 회차마다 비슷하다. **무엇을 만들지 정하는 앞단과 맞았는지 판정하는
뒷단이다.** 가운데 공정이 자동화된다.

## 4. Ch.7이 실무 과제에 준 것

**첫째, 작업을 쪼개는 것이 선택이 아니라 전제다.** 우리 AS 파이프라인이 이미 추출 → 정규화 →
축 분류 → 적재로 나뉘어 있는데, 그것이 편의가 아니라 성능 조건이었다는 근거가 다섯 회차에 걸쳐
쌓였다.

**둘째, 표준 어휘 목록을 밖에 두는 설계가 맞다.** S26B의 Wikidata 매칭과 S27A의 모듈 선택이 같은
장치이고, 우리의 `config/manual_merges.yaml`과 자동 정규화가 그 자리에 있다. LLM에게 "일관되게
해달라"고 요구하는 대신 목록에서 고르게 한다.

**셋째, 평가 지표를 두 개 두는 것을 고려할 만하다.** 지금 AS 평가는 Top-k 하나뿐이라, 답이 안
나올 때 그래프에 없는 것인지 조회를 못 한 것인지 갈리지 않는다. S25의 SPARQL/RAG나 S27B의
Exact/Fuzzy처럼 엄격한 쪽과 관대한 쪽을 나란히 두면 개선 방향이 사전 보강인지 조회 방식인지
드러난다.

**넷째, 도메인이 전문적일수록 이름을 못 맞힌다.** S23의 WordNet 91.7 대 biomedical 16~37,
S27B의 Data 0.724 대 Finance 0.121이 같은 말을 한다. 제조 설비 용어는 후자 쪽이다. 생성보다
**기존 어휘에서 고르게 하는 쪽**이 안전하다는 근거가 된다.

**다섯째, 옮길 수 없는 것도 분명하다.** 이 챕터의 논문들은 문서 수십 편 규모다. S24는 논문 5편,
S25는 약관 2건, S27B는 3개 도메인 발췌본이다. AS 63만 건과는 자릿수가 다르고, 문서당 LLM 여러 번
호출하는 설계는 그 규모에서 성립하지 않는다.

## 5. 01 문서에 올릴 후보

Ch.7을 정리하면서 01 문서(`01-Ch4-6-무엇이-남고-무엇이-밀렸나.md`)에 얹을 것이 생겼다. Ch.8까지
보고 확정하되 지금 적어둔다.

| 후보 | 근거 |
|---|---|
| 관통선 ②에 확인 표시 | S26이 검증 지점이었고 확인됐다. 온톨로지가 허용 목록으로 돌아왔다 |
| 새 관통선: 전역 일관성은 조회로 푼다 | S24·S25에서 막히고 S26B·S27A에서 풀린다. Ch.7 전체를 관통한다 |
| 새 관통선: 한 번에 시키면 안 된다 | 다섯 회차 중 넷에서 반복. 다만 Ch.4~6에는 대응하는 관찰이 없어 Ch.7 이후에만 걸리는 선일 수 있다 |
| 관통선 ④에 사례 추가 | S25의 절반짜리 통제, S27A의 대조군 부재. 반례 쪽 사례가 늘었다 |

문서 이름도 손봐야 한다. 지금은 `01-Ch4-6-...`인데 Ch.7이 들어가면 범위가 달라진다. Ch.8까지
보고 한 번에 바꾸는 편이 낫다.

## 6. Ch.8로 넘기는 질문

| 질문 | 왜 남았나 |
|---|---|
| 모듈을 문서에서 자동으로 만들 수 있나 | S27A의 두 번째 한계. 기존 modular ontology가 있어야 한다 |
| 생성된 온톨로지의 논리적 모순을 언제 검사하나 | S27B에 그 단계가 없다. S25는 HermiT를 넣었다 |
| 관계 추출 자체는 얼마나 되나 | Ch.7은 온톨로지(스키마) 쪽이었고 Ch.8이 KG(인스턴스) 쪽이다 |
| 규모를 키우면 무엇이 먼저 무너지나 | 이 챕터의 실험은 전부 소규모다 |

S28이 REBEL 기반 관계 추출이라 세 번째 질문이 바로 이어진다.
