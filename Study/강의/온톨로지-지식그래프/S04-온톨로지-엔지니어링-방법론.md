## 한 줄 요약

S01~S03이 "온톨로지가 무엇이고, 어떻게 뽑는가"였다면 S04는 **"조직이 그것을 어떤 절차로 만들고 유지하는가"**다.
오늘 논문 **OTKM**의 출발점은 기존 KM 방법론이 뒤섞어 다루던 두 과정을 분리하는 것 —
**지식 메타프로세스**(KM 시스템을 *만드는* 과정)와 **지식 프로세스**(만들어진 시스템을 *쓰는* 과정).
전자를 타당성→킥오프→정제→평가→적용·진화 **5단계**로 정식화하고, 각 단계마다 **산출물**과 **결정**을 못 박는다.
Swiss Life 사례가 이 5단계를 그대로 밟는데, **자동 추출에 실패해 수작업으로 회귀**하고
**평가 단계를 밟지 못한 채 조직 개편으로 종료**된다.

# 01 Introduction

## 1. 온톨로지 엔지니어링 방법론이란

**문제** — 온톨로지를 비체계적으로 구축할 경우

- 재사용성이 낮음
- 품질이 일관되지 않음
- 협업이 어려움

**해결** — **체계적 절차 + 재사용 + 전용 도구**를 갖춘 **온톨로지 공학(ontology engineering)**이 요구됨

| 요소 | 내용 |
|---|---|
| 체계적 절차 | 요구사항 → 설계 → 구현 → 평가 |
| 재사용 | 디자인 패턴 및 기존 온톨로지의 적극적 재사용 |
| 반복 개발 | 도메인 전문가 참여 기반의 반복적(iterative) 개발 |
| 도구 | 전용 도구를 통한 품질 및 생산성 확보 |

**강의 흐름에서의 위치**

```
S01 기초·실사례 → S02 설계 원칙(Gruber·FAIR) → S03 텍스트 자동 추출 → S04 엔지니어링 방법론
```

> S02가 "좋은 온톨로지의 **속성**"(명료성·일관성·확장성…)이었다면, S04는 "그 속성을 확보하기 위한
> **절차**"다. 같은 목표를 원칙으로 접근하느냐 프로세스로 접근하느냐의 차이다.

## 2. 오늘 소개할 논문

### 주논문 — On-To-Knowledge Methodology (OTKM)

**핵심: 지식관리(KM)를 위한 온톨로지 개발 방법론**

- 지식 프로세스 vs 지식 메타프로세스를 분리하고, 온톨로지를 지식관리(KM)의 **'접착제(glue)'**로 활용
- 메타프로세스 **5단계**(타당성 → 킥오프 → 정제 → 평가 → 적용·진화)를 제시

| | |
|---|---|
| 저자 | York Sure, Steffen Staab & Rudi Studer |
| 출처 | *Handbook on Ontologies*. Berlin, Heidelberg: Springer Berlin Heidelberg (2004) |
| 피인용 | 516 |

### 참고논문 ① — LOT: An Industrial Oriented Ontology Engineering Framework

**핵심: 산업 프로젝트를 위한 경량 온톨로지 개발 방법론**

- 요구사항 → 구현 → 발행 → 유지보수의 **4단계 반복 사이클** + 각 단계별 전용 도구 지원
- 웹 발행(FAIR)·재사용·애자일을 강조 — **전통 방법론의 한계를 보완**

### 참고논문 ② — Modular Ontology Modeling

**핵심: 온톨로지 재사용 난관을 해결하기 위한 '모듈 기반 그래픽 모델링' 방법론(MOMo)과 지원 도구(CoModIDE) 제안**

- 문제 해결: 온톨로지의 복잡성과 재사용성 부족 문제를 **'모듈화'와 '디자인 패턴'**으로 해결
- 방법론: 그래픽 다이어그램을 의사소통 수단으로 활용하여 전문가 협업을 돕고,
  CoModIDE를 통해 모델링부터 코드 생성까지 지원

> **세 논문 모두 온톨로지를 "한 번 만드는 모델"이 아니라, 요구사항부터 유지보수까지 관리되는
> 실무 방법론으로 바라봄**

# 02 On-To-Knowledge Methodology (OTKM)

## 3. 연구 배경 및 동기 ① — 지식관리(KM)의 부상과 온톨로지의 필요성

- 제품 복잡도 증가, 세계화, 가상 조직, 고객 지향의 심화
  → 기업 내부 및 여러 협력 기업 간의 **체계적인 지식 관리 요구**
- 정보기술(IT)이 **조력자(enabler)** 역할
- IT 기반 지식관리(KM)는 **조직 기억(organizational memory)**을 중심으로 구축

**조직 기억** = 조직 내 지식을 축적하고 연결하며 구성원이 문제 해결에 재사용할 수 있게 만든 구조

| | 지식 유형 | 정의 | 예 |
|---|---|---|---|
| 1 | **비형식 지식** (Informal) | 문서화되지 않은 노하우, 경험, 개인의 아이디어 | — |
| 2 | **준형식 지식** (Semi-formal) | 약간의 구조를 갖춘 정보 | 이메일, 게시판 글 |
| 3 | **형식 지식** (Formal) | 명확하게 구조화된 정보 | 데이터베이스, 매뉴얼, 보고서 |

**기존의 문서 중심(document-centric) 접근의 한계**

- 보고서, 파일 단위로 저장·검색 → **지식의 재사용과 재검색이 어려움**

**온톨로지는 특정 도메인의 공유된 형식적 개념화를 제공**

- 흩어진 지식을 구조화하고 상호연결을 가능하게 함
  → **지식 구조화와 모델링 문제**에 대한 적절한 해답

## 4. 연구 배경 및 동기 ② — 초기 KM 방법론의 한계 (ex. CommonKADS)

**서로 다른 두 프로세스를 혼동함**

| | 프로세스 | 정의 | 예 |
|---|---|---|---|
| 1 | **지식 메타프로세스** (Knowledge Meta Process) | 새로운 지식관리 솔루션을 **도입하고 유지하는** 과정 | 지식 식별, 요구사항 분석, 온톨로지 구축, 유지보수 |
| 2 | **지식 프로세스** (Knowledge Process) | 이미 구축된 지식관리 솔루션을 **사용하는** 과정 | 지식 생성, 지식 수집, 검색, 접근, 활동 |

- 이 둘을 구분하지 않으면 시스템 개발, 지식 선별, 지식 생성, 유지보수 **역할이 불명확**해짐

> **OTKM의 출발점은 기존 KM 방법론이 섞어 다루던 두 과정을 분리하는 것**

```
┌─────────────────────┐              ┌─────────────────────┐
│   지식 메타프로세스    │  ←─────────→  │    지식 프로세스      │
│ KM 시스템 도입·구축   │   피드백 루프   │ 구축된 KM 시스템     │
│   (온톨로지 셋업)     │              │     운영·사용        │
└─────────────────────┘              └─────────────────────┘
```

- 두 프로세스는 **직교(orthogonal)**하며 서로 피드백한다
- **온톨로지가 둘을 연결**한다

## 5. Implementation and Invention of KM Applications

KM 애플리케이션을 **구현 및 발명**하려면 **세 프로세스를 함께** 고려해야 함 *(Fig. 6.2)*

| | 프로세스 | 내용 |
|---|---|---|
| ① | **지식 메타프로세스** | KM 시스템을 도입 및 구축하는 과정 → 온톨로지의 초기 설계/셋업 (**본 논문의 핵심**) |
| ② | **인간적 이슈** (Human Issues) | KM의 성공은 사람의 수용에 크게 좌우 + 조직 문화·동기가 중요. 초기 단계엔 **'quick wins'** 권장 |
| ③ | **소프트웨어 공학** (Software Engineering) | KM 애플리케이션은 다른 프로세스에 맞춰 구현되어야 함. 특히 지식 프로세스에서 나오는 요구사항을 반영 |

- **실무에서 IT는 KM의 10~30%만 커버** → 인간·조직 요소가 절대적
- 이후 본 논문은 **지식 메타프로세스**에 집중하고, 나머지와의 연결점을 다룸

## 6. 지식 메타프로세스 — 5단계

**각 단계의 구성**

- 각 단계 = 여러 **하위단계(sub-step)** + 종료 시 주요 **결정(decision)** + 특정 **산출물(outcome)**
- **산출물이 곧 다음 단계로 진행할지의 의사결정 근거**가 됨
  - 예) Kickoff → 산출물 = ORSD(요구사항 명세서) + 준형식 온톨로지 기술
    → 결정 = "요구사항을 충분히 포착했나"
- **정제 – 평가 – 적용·진화**는 반복(iterative) 사이클로 수행
- 온톨로지 개발은 본질적으로 **순환적(cyclic)** — 이후 단계에서 공백이 발견되면 되돌아감

**전체 구조**

| # | 단계 | 산출물 (outcome) | 결정 (decision) |
|---|---|---|---|
| ① | **Feasibility study** — 타당성 검토 | CommonKADS Worksheets | Go / No Go? |
| ② | **Kickoff** — 킥오프 | ORSD + Semi-formal ontology description | Sufficient requirements? |
| ③ | **Refinement** — 정제 | Target ontology | Meets requirements? |
| ④ | **Evaluation** — 평가 | Evaluated ontology | Roll-out? |
| ⑤ | **Application & Evolution** — 적용·진화 | Evolved ontology | Changes? |

**하위단계 14개**

| 단계 | 하위단계 |
|---|---|
| ① 타당성 검토 | 1 Problems & opportunities · 2 Focus of KM application · 3 (OTK-) Tools · 4 People |
| ② 킥오프 | 5 Capture requirements specification in ORSD · 6 Create semi-formal ontology description |
| ③ 정제 | 7 Refine semi-formal ontology description · 8 Formalize into target ontology · 9 Create Prototype |
| ④ 평가 | 10 Technology-focussed evaluation · 11 User-focussed evaluation · 12 Ontology-focussed evaluation |
| ⑤ 적용·진화 | 13 Apply ontology · 14 Manage evolution and maintenance |

- 다이어그램상 ①~⑤ 전체가 **Ontology Development**로 묶이고,
  오른쪽에 **Human Issues**와 **Software Engineering**이 별도 축으로 붙는다 (5절의 세 프로세스)

### 6.1 ① 타당성 검토 (Feasibility Study)

- **목적**: 온톨로지 개발 전, **적용 가치와 실행 가능성**을 판단하는 단계
- KM 시스템은 **조직에 자연스럽게 통합될 때** 제대로 작동함
- 성공 여부는 기술뿐만 아니라 **조직, 사용자, 비용, 프로젝트 조건**에 의해 결정됨
- 따라서 **타당성 검토를 초기에 실시**
  - 목적: **문제/기회 영역**(problem/opportunity areas)과 잠재 해법을 식별
- 최종적으로 **경제적·기술적·프로젝트 타당성** 검토
  → 가장 유망한 **초점 영역(focus area)**과 **목표 해법(target solution)** 결정

### 6.2 ② 킥오프 (Kickoff)

- 이 단계에서 **실제 온톨로지 개발이 시작**됨

**ORSD (Ontology Requirements Specification Document)**

- 온톨로지가 지원할 내용, 계획된 응용 영역, **가치 있는 지식 소스 목록**을 기술
- 개념·관계의 **포함/제외**와 온톨로지의 **계층 구조 결정**을 이끄는 지침

**그 외**

- 이 초기 단계에서 **재사용 가능한 기존 온톨로지를 탐색**
- **산출물**: ORSD + **준형식(semi-formal) 기술**
  - 명명 노드 + (무)명명·(무)방향 엣지의 그래프 (마인드맵, 설명 텍스트 연결)
- **결정**: 요구사항을 **'충분히'** 포착했는지
  - '충분히' = **현 시점엔** 더 포착/분석할 필요 없음
  - → 이후 공백 발견이 가능하므로 **순환적(cyclic)**

### 6.3 ③ 정제 (Refinement)

- **목적**: 온톨로지 명세(ORSD)에 따라 **target 온톨로지** 산출

**모델링 접근 3가지**

| | 접근 | 내용 |
|---|---|---|
| ① | **Top-down** | 일반 개념·관계부터 모델링 후 세분화 (수작업, 고품질, 상위 온톨로지 재사용) |
| ② | **Bottom-up** | 자동 문서 분석으로 개념을 준자동 추출 (텍스트 기반 지식 획득) |
| ③ | **Middle-out** | 핵심 개념 먼저 식별 → 일반화·특수화로 나머지 계층 확보 |

> **Bottom-up이 곧 [S03A](S03A-용어-추출-P-Mod.md)·[S03B](S03B-비분류-관계-학습.md)에서 배운 텍스트 자동 추출이다.**
> S03에서 하나의 연구 주제였던 것이, 여기서는 방법론 안의 **선택지 하나**로 들어와 있다.
> 그리고 뒤의 Swiss Life 사례(9.1절)에서 이 선택지는 **실패하고 Top-down 수작업으로 회귀**한다.

**형식화: 준형식 기술 → 목표 온톨로지**

```
준형식 기술   →   is-a 분류체계   →   + 기타 관계·속성   →   목표 온톨로지
 (마인드맵)        (taxonomy)         (경쟁 질문 기반)        (target)
```

- 이 단계도 **자체 순환**
- 전문가 재인터뷰, 시각화(마인드맵)로 전문가가 속성·관계 추가, 온톨로지 약속 문서화
- **산출물**: target 온톨로지
- **결정** = kickoff 요구사항 충족 여부
  - 첫 온톨로지는 프로토타입을 만들 만큼의 **'flesh'**를 가져야 함 → 평가용 첫 프로토타입으로 활용

> **is-a 분류체계** = '하위 개념이 상위 개념의 한 종류'가 되는 계층 구조.
> 예) 대학원생은 학생의 한 종류이고, 학생은 사람의 한 종류이다.

### 6.4 ④ 평가 (Evaluation)

- **목적**: 구축된 온톨로지가 목표한 요구사항을 얼마나 잘 충족하는지 **검증**

**세 가지 유형의 평가**

| | 유형 | 묻는 것 | 내용 |
|---|---|---|---|
| ① | **기술 중심** (technology-focussed) | 애플리케이션이 잘 돌아가는가? | 아래 세부 참조 |
| ② | **사용자 중심** (user-focussed) | — | 최종 목적인 **'사용자 만족도'**를 측정 |
| ③ | **형식적 평가** (formally evaluate ontologies) | 온톨로지가 논리적으로 올바른가? | 철학적 혹은 구조적 논리에 기반하여 온톨로지의 정합성을 검증 — Ex. 대학교 → 학생 (대학은 학생이다? → X) |

**① 기술 중심 평가의 두 갈래**

1. **온톨로지 속성 평가**: 온톨로지의 **문법적 정확성**(Syntax, 언어 준수 여부)과 **논리적 일관성**(Semantics)을 확인
2. **기술적 속성 평가**: 온톨로지를 활용하는 **도구와 애플리케이션 자체의 성능**을 측정

   | 지표 | 정의 |
   |---|---|
   | **상호 운용성** (Interoperability) | 서로 다른 시스템, 데이터 포맷 간에 의미를 공유할 수 있는 능력 |
   | **처리 속도** (Turn-around ability) | 사용자의 요청에 시스템이 얼마나 신속하게 결과를 반환하는지 |
   | **확장성** (Scalability) | 데이터의 양, 다루는 개념과 관계의 수가 증가하더라도 작동하는 능력 |

- **산출물**: 평가된 온톨로지
- 보통 **'평가–정제–평가'를 여러 차례 반복** 후 배포
- **결정**: 목표 응용에 필요한 모든 평가 기준을 충족하는가

> 이 3분류는 Ch.3(S07 구조적·품질 평가 OQuaRE / S08 기능적·의미적 평가 CQ 기반)에서
> 본격적으로 다뤄질 내용의 원형이다. 여기서는 "평가에 종류가 있다"는 수준까지만 나온다.

### 6.5 ⑤ 적용 · 진화 (Application & Evolution)

**적용 (Application)**: 온톨로지를 **운영 시스템(productive system)**에서 사용

- 온톨로지 기반 시스템의 실제 활용
- 이 활용 과정은 **지식 프로세스**에서 상세히 다룸 (7절)

**진화 (Evolution)**: 본질적으로 **'조직적 프로세스(organizational process)'**

- 시간이 지나면서 업무 환경, 용어, 조직 구조, 사용자 요구가 바뀜
- 온톨로지의 **update / insert / delete에 엄격한 규칙 필요**
- 절차: **변경을 수집 → 응용에 미칠 모든 영향을 충분히 테스트 → 새 버전으로 전환**
- **누가·어떻게·어느 주기로** 유지보수하는지 명확화 (**책임자 지정**)

- **산출물**: 진화된 온톨로지
- **결정**: **다음 진화 사이클을 언제 시작**할지

## 7. 지식 프로세스 (Knowledge Process) — 운영 단계

지식관리(KM) 응용이 조직에 구축된 뒤, **지식이 순환하는 4단계** *(Fig. 6.4)*

| | 단계 | 내용 |
|---|---|---|
| ① | **생성·가져오기** (Create/Import) | 문서·메타데이터를 **회사 규약(KM 인프라)**에 맞게 생성·변환 |
| ② | **포착** (Capture) | 지식 항목의 **중요도·연결성을 관계형 메타데이터로 표현** (공용 어휘에 연결) |
| ③ | **검색·접근** (Retrieve/Access) | 작업자가 필요한 정보를 찾기 위해 시스템에 질의 · **온톨로지 구조를 바탕으로** 적절 지식에 접근 |
| ④ | **지식 처리 및 활용** (Processing) | 검색된 항목을 단순히 나열하지 않고, 작업자가 수행 중인 **업무 맥락에 맞게 가공·활용** |

- 다이어그램상 **Ontology가 이 순환의 한가운데** 놓인다 (Creation → Import → Capture → Retrieval/Access → Use)

# 사례 : Swiss Life 스킬 관리

## 8. 사례 개요

- **목적**: 직원의 **역량(skills)**을 명시화
- **통합 대상**: 기존 역량 데이터베이스와 문서(예: 개인 홈페이지)를 통합 및 확장

**2가지 측면을 다룸**

1. 명시적인 역량을 통해 **인트라넷에서 고급 전문가 검색** 가능
2. **향후 경력 경로 탐색** 가능 (현재의 역량 프로필 ↔ 직무 프로필 매칭)

**두 가지 도전 → 온톨로지로 해결**

| | 도전 | 상황 | 해결 |
|---|---|---|---|
| ① | **다국어** (multilingual) | 스위스 국제기업 → 내부 4개 공용어(독·영·불·이) | 온톨로지가 **언어별 외부 표현** 제공 |
| ② | **동의어** (synonymy) | 같은 개념의 여러 표기 — 예) 'WinWord' = 'MS Word' | 온톨로지가 **동의어 표현** 허용 |

**역량 관리 애플리케이션** *(Fig. 6.5)*

- 모든 직원은 분산되고 이질적인 수많은 소스로부터 개인 데이터를
  **하나의 일관된 개인 홈페이지로 통합** 가능
  (Contact data · Skills tree · Function/role · Skill profile)

## 9. 사례 ① 타당성 검토 (Feasibility Study)

- **목적**: 지식 관리 시스템을 조직에 성공적으로 도입하기 위한 첫 번째 단계

| | 활동 | 내용 |
|---|---|---|
| ① | **성공 요인 분석 및 요구사항 식별** | 조직 내 기존 환경을 분석하고 새로운 시스템이 해결해야 할 **문제점이나 기회 영역**을 파악 · 조직의 **업무 프로세스에 어떻게 자연스럽게 녹아들 것인지**를 결정 |
| ② | **이해관계자(Stakeholders) 선정** | **인사팀(Human Resources)**과 **각 부서의 관리자급**이 주요 이해관계자로 선정 |
| ③ | **도메인 전문가(Domain Experts) 구성** | 각 부서의 **온톨로지 전문가**를 지정 (가급적 각 부서 **교육팀** 소속) |

## 10. 사례 ② 킥오프

### 10.1 과제 설정과 도구

- **과제**: 3개 부서(민간 보험·인사·IT)별로, 총 **3개의 트리**로 구성된 부서용 역량 온톨로지를 개발
  - 하나의 루트 노드(`skills`) 사이에 **교차링크로 결합**
- **워크숍**: 도메인 전문가 3명 × 2회 (1회차 = 온톨로지 개념 소개)
- **지식 소스 예시**: 스위스 데이터처리협회 서적(IT 직군을 온톨로지처럼 체계화)
  → IT 트리 수작업 구축의 훌륭한 기반
- **도구 선택 결정**: 정보추출 도구의 **준자동 추출 실패** → 직접 **'수작업' 구축** 후
  마인드매핑 도구 **MindManager** 사용

> **6.3절의 Bottom-up이 여기서 무너진다.** 방법론은 세 가지 모델링 접근을 나란히 놓지만,
> 실제 산업 사례에서는 준자동 추출이 실패하고 수작업 + 마인드매핑으로 회귀했다.
> [S03-1 자동 구축의 천장](S03-1-자동구축의-천장.md)에서 정리한 것과 같은 지점이다.

### 10.2 초기 난제와 결과

**초기 난제 ① — 개념 vs 인스턴스 경계**

- 예) Java는 'jdk1.3'으로 인스턴스화? 아니면 jdk1.3도 개념 계층?

| | 정의 | 예 |
|---|---|---|
| **개념** (Concept) | 특정 도메인 내에서 공통된 특성을 가진 **추상적인 범주** | '프로그래밍 언어', '운영체제' — 계층 구조에서 상위 수준에 위치하며 공통 속성을 정의 |
| **인스턴스** (Instance) | 개념에 속하는 **구체적인 실체**(개별 항목) | 'Java'라는 언어 안에 있는 'JDK 1.3'처럼 특정 버전이나 실제 제품명 등 더 이상 일반화하기 어려운 구체적 대상 |

**경계를 나누는 것이 중요한 이유**

| | 이유 | 내용 |
|---|---|---|
| **추론의 효율성** | 구체적인 것(예: 특정 소프트웨어 버전)을 개념으로 설정하면 **계층 구조가 복잡**해짐 |
| **유연성 부족** | 인스턴스를 개념으로 오인하여 계층에 포함될 경우, 새로운 데이터(예: 새 버전)가 나올 때마다 **계층 전체를 수정** |

**초기 난제 ② — 온톨로지 크기**

- 각 트리의 **최적 깊이·너비**는? → 도메인에 따라 다르며 **도메인 전문가가 결정**

**결과**

- 세 트리의 **준형식적(semi-formal) 온톨로지 기술서** 확보
- 단일 스킬 온톨로지로 통합 준비 완료, 결합 시 큰 변화 없음

## 11. 사례 ③ 정제 — 형식화 · 통합

- **목적**: 준형식적(semi-formal) 온톨로지 기술서를 바탕으로 **하나의 타겟 온톨로지 통합**
- **형식화 과정에서 중요한 측면**
  1. 각 스킬을 식별할 수 있는 **고유 이름 부여**
  2. 스킬의 **계층 구조 결정**

**계층 순위 지정을 위한 시도**

**1. 스킬 분류는 is-a가 아니라 `HASSUBTOPIC`** (더 약한 관계)

| 관계 | 성격 |
|---|---|
| **is-a** (Taxonomy) | 객체 지향 프로그래밍이나 논리학에서 사용하는 상속 개념 — 하위 개념은 상위 개념의 속성과 관계를 **완벽하게 물려받아야** 함 |
| **HASSUBTOPIC** | 기술 역량(Skills) 체계는 엄격한 논리적 상속보다 단순히 **'더 작은 단위의 주제'를 포함하는 느슨한 관계**가 더 적합 |

- 다만, 초기 프로토타입에서 **분류 간 관계가 누락되어 타협됨**

**2. 개념 간 "연관 관계(associative relation)" 라는 관계 유형을 추가**

- 계층적 스킬 트리 **외부의 관계**를 표현

**3. 통합 및 중복 제거**

- 세 개의 스킬 온톨로지를 하나로 통합하고, 도메인 온톨로지 부분 **내부 및 상호 간의 불일치를 제거**
- 몇 가지 중복 발생
  - 예) IT 부서와 개인 보험 부서가 공유하는 'Trofit'(Swiss Life 앱)을
    각기 다른 관점(**개발 vs 사용자**)으로 사용

**4. 개인 역량 등급 매기기**

- 기본 지식(basic knowledge) · 실무 경험(practical experience) · 역량(competency) · 최고 전문가(top specialist)
- **직원 자가 평가** (타사 Credit Suisse, ABB, IBM 경험상 신뢰도 높음)

**결과**

- 대상 기술 온톨로지(target skills ontology)는 **약 700개의 개념**으로 구성
  → 직원들은 이를 사용하여 자신의 **skill profile**을 표현할 수 있게 됨

## 12. 사례 ④ 어플리케이션 · 진화

- **평가**: 내부 구조조정으로 **사례 전체가 종료** → **프로토타입과 온톨로지 평가는 생략됨**

**그럼에도 skill 관리 어플리케이션 진화를 위해 고려한 점**

1. 직원에게 요구되는 역량은 **'움직이는 목표'** → **인사부서 전문가가 지속 평가/유지보수** 필요
2. 온톨로지 일관성을 유지하기 위해 각 온톨로지(도메인)마다 제안 통합 여부·방식을 결정하는
   **지정 ontology manager**가 요구됨
   - 신규 스킬은 주로 직원이 **제안**(새 스킬 + 스킬 트리 내 위치)
     → 전문가가 이름/위치 **변경 및 삭제를 결정**

> **5단계를 제시한 논문의 사례가 정작 ④평가를 밟지 못했다.** 조직 개편이라는,
> 방법론 바깥의 사유로 끝났다는 점이 오히려 5절의 "IT는 KM의 10~30%만 커버,
> 인간·조직 요소가 절대적"과 결론 ①(인간적 이슈 우세)을 실증한다.

# 03 Conclusion

## 13. 결론

**OTKM = 온톨로지 기반 지식관리 시스템의 도입 및 유지를 위한 프로세스 지향적 방법론**

**핵심 아이디어**

- 지식 메타프로세스(온톨로지 셋업·구축) + 지식 프로세스(운영·사용) **분리**
- 온톨로지를 지식관리(KM)의 **'접착제(glue)'**로 활용
- 메타프로세스 **5단계** (타당성 → 킥오프 → 정제 → 평가 → 적용·진화) 제시

**배운 점**

| | | 내용 |
|---|---|---|
| ① | **인간적 이슈 우세** | 여러 프로세스가 KM을 이끌지만 **'인간적 이슈(Human Issues)'가 다른 것을 지배**할 수 있음 |
| ② | **실용적 지침** | 산업 현장의 도메인 전문가용 지침은 **반드시 실용적**이어야 함 |
| ③ | **대면 + 도구** | 협업 온톨로지 공학은 **물리적 대면과 고급 도구 지원을 둘 다** 요구 |
| ④ | **브레인스토밍** | 온톨로지 엔지니어링 초기 단계, 특히 **모델링에 익숙하지 않은 도메인 전문가**에게 매우 유용 |
