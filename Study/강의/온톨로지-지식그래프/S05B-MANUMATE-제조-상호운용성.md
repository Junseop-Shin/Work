## 한 줄 요약

MANUMATE는 [S05A](S05A-Wikidata-운영-사례.md)의 반대편 극단이다 — **수십 클래스 · 폐쇄 · 현장 스케일**.
제조 현장에 ERP·MES·SCADA·PLM·PAC가 각각 최적화된 채 흩어져 있고,
같은 것을 서로 다른 이름으로 부르는 **의미적 상호운용성(Semantic Interoperability)** 문제를 푼다.
해법의 골격은 **참조 온톨로지 → [특수화] → 응용 온톨로지 → [정보 적용] → 각 시스템**이라는 3+2 구조이고,
특징적인 건 **응용 온톨로지가 제품 하나마다 생겼다가 출하되면 사라지는 일회용 객체**라는 점이다.
실증은 브라질 우유 포장재 공장 — 케이스 A는 작업자의 **암묵지를 명시화**했고,
케이스 B는 **공정 간 값을 자동 전파**했다.

# 03 MANUMATE

## 1. 논문의 성격과 실증 대상

| | |
|---|---|
| **Wikidata** | 거대 지식그래프 **운영기** |

| **사용 도구** | **OWL**(표현) + **SWRL**(규칙) + **Pellet**(추론기) + **Owlready2**(Python 구현) |

## 2. 배경 — Industry 4.0과 수많은 시스템

**제조 현장의 다양한 소프트웨어**

| 층 | 시스템 |
|---|---|
| **기업 모델링** | GRAI · CIMOSA · MO2GO · ARIS |
| **운영 / 제어** | **ERP**(전사자원) · **MES**(제조실행) · **SCADA**(감시제어) · **PLM**(수명주기) · **PAC**(자동화) |

> **각각은 개별 기능엔 최적 — 함께 쓰면 문제 발생 · 통합이 Industry 4.0의 핵심 기둥**

## 3. 문제 정의 — 시스템 간 "말 안 통함"

- 시스템마다 다른 **제조사 · 아키텍처 · 용어(taxonomy)**

| 문제 | 자료의 서술 |
|---|---|
| **의미(Semantic) 문제** | 같은 정보/변수가 **다른 부품에 적용되는** 경우 |
| **구문(Syntactic) 문제** | 다른 정보/변수가 **같은 부품에 적용됨** |

= **의미적 상호운용성(Semantic Interoperability) 문제**

> 💡 강의가 든 예 —
> Etch의 "recipe" = Litho의 "program" = CMP의 "process file"
> 같은 "온도"도 챔버 벽/척 온도인지 시스템마다 다르게 해석

> **읽다가 걸린 곳** — 통상 semantic/syntactic 구분은 *의미 차이 vs 형식·포맷 차이*로 가르는데,
> 이 표는 둘 다 **"적용 대상의 불일치"**로 서술해서 경계가 흐리다.
> **원논문을 대조해보니 슬라이드가 원문을 그대로 옮긴 것이었다** — 어긋남은 원논문 쪽에 있다.
> → [S05-06-1 6.5절](S05-06-1-세-논문을-잇는-파이프라인.md)

## 4. Knowledge Level의 자동화 공백

*(Figure 1 — Elements for an integrated manufacturing system, Pereira et al., 2021)*

| 층 | 무엇이 있나 | 상태 |
|---|---|---|
| **Understanding Level** | 사람 (경영 · 의사결정) | 채워져 있음 |
| **Knowledge Level** | **[ A ]** | **비어 있음 `?`** |
| **Information Level** | ERP · MES · SCADA 1~N · Control 1~N | 시스템은 있으나 잇는 **[ B ]가 비어 있음 `?`** |
| **Data Level** | Sensor 1 ~ N | 채워져 있음 |

- **세로축 = Vertical Integration** — 층과 층 사이 (Data → … → Understanding)
- **가로축 = Horizontal Integration** — Process 1 ↔ Process 2 ↔ … ↔ Process N

> **Knowledge 층이 비어 있음 — 정보를 지식으로 승격시키는 지능의 부재**

## 5. 두 가지 통합 — 수직 & 수평

| | 방향 | 내용 |
|---|---|---|
| **수직 통합** (Vertical) | 층을 올라감 | 데이터 → 정보 → 지식 → 이해 (**DIKW 승격**) |
| **수평 통합** (Horizontal) | 옆으로 번짐 | 공정 → 공정 · 기업 → 기업 |

**DIKW** = Data → Information → Knowledge → Wisdom

> [S04 3절](S04-온톨로지-엔지니어링-방법론.md)의 조직 기억 3층위와 나란히 놓으면 축이 다르다.
>
> | | 사다리 | 재는 것 |
> |---|---|---|
> | **DIKW** (여기) | Data → Information → Knowledge → Wisdom | **가공·해석의 정도** |
> | **OTKM 3층위** (S04) | 비형식 → 준형식 → 형식 | **형식화의 정도** |
>
> 둘 다 "올린다"는 말을 쓰지만 올리는 축이 다르다. 우리 과제로 보면
> 명장의 판단은 DIKW 축에서는 이미 **Knowledge**인데, OTKM 축에서는 아직 **비형식**이다.
> **머릿속에서는 지식인데 기계에게는 데이터조차 아니다** — 이 두 축을 겹쳐 봐야 그 간극이 보인다.

## 8. 레이어 ① 참조 온톨로지 (Reference)

**일반적이고 재사용 가능한 지식 모델 3종 — 이 단계는 '틀'만, 구체값 없음**

| 모델 | 담는 것 | 포장재 공장 예 |
|---|---|---|
| **Product** | 일반 제품 스키마 | 비닐 층 · 평량 · 알루미늄 |
| **Process** | 제조 공정 · 상호작용 | 코팅 · 인쇄 · 커팅 |
| **Materials** | 재료 모델 | 카톤지 · 알루미늄 · 잉크 |

> 💡 강의가 든 반도체 예 —
> Product = 일반 디바이스 스펙 틀 · Process = 일반 공정 흐름(Litho→Etch)
> Materials = 재료 라이브러리(포토레지스트·타겟·가스) — **여러 제품이 공유**

## 9. 레이어 ② 요구사항 (Requirements)

**실제 생산 제약 · 정보 주입 5종**

| 요구사항 | 내용 |
|---|---|
| **Production process** | 공정 제약 (코팅기 속도 · 커팅 위치) |
| **Standards** | 기술 · 품질 표준 (인쇄 품질 · 열 차단 · 무오염) |
| **Availability** | **그 시점 가용 설비** (MES가 공유) |
| **Product portfolio** | 생산 가능한 제품군 |
| **Customers** | 고객 요구사항 |

> `Availability`가 들어 있는 게 특징이다. 나머지 넷은 비교적 고정된 제약인데
> 이것만 **시점에 따라 변하는 런타임 상태**다. 즉 이 프레임워크는 정적 설계가 아니라
> **주문이 들어온 그 순간의 공장 상태를 입력으로 받는다.**

## 10. 프로세스 [A] 특수화 — 핵심 엔진

*(Figure 3 — MANUMATE Ontology Specialization Process)*

| | 내용 |
|---|---|
| **입력** | 참조 온톨로지 (**Merge**) + 요구사항 (**Reconcile**) |
| **3단계 처리** | Context Alignment → Ontology Mapping → Consistency Reasoning |
| **출력** | **응용 온톨로지** (Application Ontology) |
| **활용 관계** | `subclass`(하위클래스) · `sub-relation`(하위관계) · `instance-of`(개체화) |

| 순서 | 처리 | 하는 일 |
|---|---|---|
| 입력 A | ① 참조 온톨로지 → **Ontology Merge** | 참조 3종을 하나로 병합 |
| 입력 B | ② 요구사항 → **Semantic Reconciliation** | 현실 제약을 의미적으로 맞춤 |
| 1 | **Context Alignment** | **두 갈래가 여기서 만남** |
| 2 | **Ontology Mapping** | 개념 간 대응 관계 확정 |
| 3 | **Consistency Reasoning** | Pellet 검증 → **③ 응용 온톨로지** 산출 |

> 활용 관계 셋이 곧 **"일반을 구체로 내리는 세 가지 방법"**이다 —
> 클래스를 좁히거나(`subclass`), 관계를 좁히거나(`sub-relation`), 개체로 떨어뜨리거나(`instance-of`).
> [S04-1 3절](S04-1-OTKM이-정하지-않은-것들.md)에서 다룬 **개념/인스턴스 경계**가
> 여기서는 *경계*가 아니라 *단계*로 쓰인다.

### 10.1 일관성 추론 (Consistency Reasoning) — 자동 검증

| | 내용 |
|---|---|
| **무엇** | **Pellet 추론기**로 모순 없는지 자동 검증 |
| **효과** | 사람이 놓치는 **논리적 모순을 기계가 사전 차단** |
| **기반** | 시맨틱 규칙(**SWRL**) 기반 검증 |

> 💡 강의가 든 반도체 예 — "부식방지 코팅인데 일반 PE 지정" 같은 모순을 추론기가 자동 검출

> **이 절이 온톨로지를 쓰는 값어치가 실제로 나오는 자리다.**
> [S04-1 2.5절](S04-1-OTKM이-정하지-않은-것들.md)에서 "CQ가 추론·제약이면 OWL로 올린다"고 했는데,
> 여기가 정확히 그 조건이다 — 사람이 검수할 수 없는 조합 폭발을 추론기가 대신 본다.
> SKOS로는 절대 못 하는 일이다.

## 11. 레이어 ③ 응용 온톨로지 (Application)

| | 내용 |
|---|---|
| **정의** | 특정 제품 **하나**를 위한 유일·특수화된 온톨로지 = 최종 제품의 **'가상 표현'** |
| **생명주기** | 생성(제품 필요 시) → 사용(제조 중) → **폐기(제조 끝)** |
| **특징** | 제품마다 생성·폐기 — **재사용하지 않음** |

> 💡 강의가 든 반도체 예 — 특정 Lot의 트래블러 + 레시피 + 스펙 + 제약을
> 하나의 논리 객체로; **출하되면 소멸**

> **온톨로지를 일회용 객체로 쓴다.** 이게 이 논문에서 가장 낯선 지점이다.
> [S04 6.5절](S04-온톨로지-엔지니어링-방법론.md)의 OTKM ⑤ 적용·진화는 온톨로지를
> **영속적으로 유지보수하는 자산**으로 전제했다 — 버전 규칙, 책임자 지정, 진화 사이클.
> MANUMATE의 응용 온톨로지에는 그런 게 없다. 제품과 함께 죽기 때문이다.
>
> 다만 **영속적인 층은 따로 있다** — 참조 온톨로지(레이어 ①)다.
> 즉 **유지보수 대상은 참조 온톨로지, 일회용은 응용 온톨로지**로 갈라놓은 설계다.
> 18절 비교표의 "생명주기: 영속적 vs 일회성"은 정확히는 **응용 온톨로지 층에 대한 서술**이다.

## 13. 실증 케이스 A — 부식방지 패키지 (수직 통합)

*(Figure 8 — Application ontology and Information application for case study A)*

**처리 흐름**

```
고객(부식방지 주문) → ERP(주문 입력) → 생산계획자(MES 입력) → 코팅 작업자(특수 PE 코팅)
```

**핵심 — 암묵지의 명시화**

- 작업자의 **"부식방지 = 특수 PE 코팅"** 지식을 온톨로지로 명시화

**응용 온톨로지 구조**

| 개체 (클래스) | 속성 | 상위와의 관계 | 분배 대상 |
|---|---|---|---|
| `carton_pack1` (CartonPackage) | `has_package_type: anti_corrosive` | — (최종 포장) | **ERP** |
| `coated_reel1` (CoatedReel) | `has_package_type: anti_corrosive` | ↑ `has_sub_product` | **MES** |
| `coat_proc1` (Coat) | — | ↑ `has_final_product` | **Coating SCADA / PLC** |
| `paper_reel1` (PaperReel) | — | ↑ `has_raw_material` | |
| `pe1` (Polyethylene) | **`has_pe_type: anti_corrosive`** | ↑ `has_raw_material` | |

위로 갈수록 완제품, 아래로 갈수록 원료다.
**작업자의 암묵지가 맨 아래 `pe1`의 `has_pe_type`에 값으로 박혀 있다.**

**결과** — 정보가 ERP / MES / SCADA / PLC 로 **자동 분배 · 사람 개입 불필요**

> **우리 과제와 정면으로 겹치는 절이다.** [S04-1 1절](S04-1-OTKM이-정하지-않은-것들.md)에서
> "비형식 지식에는 매핑할 소스 자체가 없다"고 정리했는데, 이 사례는 그 비형식 지식
> (작업자만 아는 `부식방지 → 특수 PE`)을 온톨로지 관계로 못박아 **파이프라인에 태울 수 있게** 만들었다.
>
> **다만 논문은 그 명시화를 누가 어떻게 했는지는 말하지 않는다.**
> 결과물(`has_pe_type: anti_corrosive`)만 보여줄 뿐, 작업자에게서 그걸 끌어낸 과정이 없다.
> S04 Swiss Life에서 "워크숍 3명 × 2회"였던 그 자리가 여기서는 아예 비어 있다.
> **암묵지 → 온톨로지 구간은 이 논문에서도 여전히 공백이다.**

## 14. 실증 케이스 B — 인쇄·커팅 의존성 (수평 통합)

*(Figure 10 — Application ontology and information application used in the case study B)*

| | 내용 |
|---|---|
| **의존성** | `Print(has_print_image · has_offset)` ↔ `Cut(has_tool_thickness)` |
| **값 자동 전파** | **`offset = tool_thickness`** — 인쇄 여백을 커팅 툴 두께와 동일하게 |
| **이유** | 커팅 칼 두께가 **이미지 일부를 잘라먹을 수 있음** |

| 개체 (클래스) | 속성 | 값 |
|---|---|---|
| `print_proc1` (Print) | `has_print_image` | `milk.jpg` |
| | **`has_offset`** | **`5`** ← 전파받은 값 |
| `cut_proc1` (Cut) | **`has_tool_thickness`** | **`5`** → 전파하는 값 |

**`cut_proc1.has_tool_thickness` → `print_proc1.has_offset`** 로 값이 넘어간다.
두 공정은 서로 다른 설비이고 다른 SCADA/PLC가 붙는데, 값 하나가 이어져 있다.

> 💡 강의가 든 팹 유사 구조 —
> Litho 오버레이 → Etch 정렬 마진 · CMP 제거량 → Deposition 목표 두께

### 14.1 다중 상속의 의미

| **PrintedReel = 커팅의 원료** | **PrintedReel = 인쇄의 산물** |
|---|---|
| **Material**로서의 정체성 | **Product**로서의 정체성 |
| 다음 공정(Cut)의 **입력** | 이전 공정(Print)의 **출력** |

> **하나의 개체가 두 정체성을 동시에 — 관계형 스키마보다 유연**
> (증착 웨이퍼가 곧 다음 공정 투입물)

> [S04-1 2.3절](S04-1-OTKM이-정하지-않은-것들.md)에서 `is-a` · `part-of` · `broader`를 갈랐는데,
> 여기는 또 다른 축이다 — **관계의 종류가 아니라 소속의 개수**.
> `PrintedReel ⊑ Product` 이면서 `PrintedReel ⊑ Material`이다.
> 관계형 스키마에서는 테이블을 둘로 쪼개거나 플래그 컬럼을 두어야 하는 자리이고,
> 이게 제조 도메인에서 OWL을 쓸 실질적 이유 중 하나다 — **중간 산출물은 거의 항상 원료이자 제품이다.**

## 15. 구현 — Owlready2 (Python)

| | 내용 |
|---|---|
| **Owlready2** | OWL 온톨로지를 **Python 객체처럼** 다루는 라이브러리 |
| **Python 인스턴스 vs 온톨로지 개체** | Python은 **한 클래스만** / 온톨로지는 **여러 클래스 동시 소속** (`PrintedReel`) |
| **산업 연동** | HTTP API(`requests`) · MySQL · **OPC-UA** · **STEP7**(`python-snap7`) |

> 💡 강의가 든 반도체 예 — '원료이면서 제품'인 다중 정체성을 자연스럽게 표현

> 산업 연동 목록이 실무적으로 중요하다. **OPC-UA와 STEP7(Siemens PLC)이 들어 있다** —
> 온톨로지가 사무실 문서에 머물지 않고 **PLC까지 내려간다**는 뜻이다.
> 12절의 "각 시스템의 언어로 번역"이 구현 층위에서 이 라이브러리들로 실현된다.

## 16. MANUMATE의 한계 (논문이 인정)

| 한계 | 내용 |
|---|---|
| **Ontology Merge의 어려움** | 3개 참조 온톨로지 병합이 자명치 않음 → **수작업 필요** → 재사용성 저하 |
| **모델링의 높은 진입장벽** | 일반 프로그래밍과 사고방식 다름(다중 클래스 소속) → **새 전문 직군 필요** |
| **미탐구 영역** | Digital Twin · CPS(사이버물리시스템) 결합은 향후 과제 |
| **그럼에도 불구하고** | 암묵지를 **OWL/XML로 표준화** → 신뢰성 있고 자동화된 정보 교환 |

> 첫 번째 한계가 [S04 10.1절](S04-온톨로지-엔지니어링-방법론.md)의 Swiss Life와 같은 자리다 —
> **자동화하려던 지점에서 수작업으로 되돌아온다.** 2004년 사례에서는 준자동 용어 추출이,
> 여기서는 참조 온톨로지 병합이 그랬다. 20년이 지나도 **"합치는 일"은 여전히 사람이 한다.**

## 18. 종합 비교표

| 구분 | **Wikidata** | **MANUMATE** |
|---|---|---|
| **설계 목적** | 데이터 공유·질의 | 시스템 통합(상호운용) |
| **거버넌스** | 개방형 대중 협업 | 폐쇄형 전문가 설계 |
| **재사용** | 표준 + SPARQL 엔드포인트 | 참조 온톨로지 특수화 |
| **온톨로지** | 경량 · **넓고 얕음** | 경량 · **좁고 깊음** |
| **핵심 기술** | RDF reification · SPARQL | OWL + SWRL · Pellet |
| **생명주기** | 영속적 | 일회성 (제품 후 폐기) |
| **성숙도** | **대규모 실서비스** | **개념 증명 (PoC)** |

- **Wikidata** — 기존 시스템 위에 RDF/SPARQL 시맨틱 계층을 얹어
  세계 최대급 지식을 질의 가능하게 만든 **운영 사례**
- **MANUMATE** — 제조 현장의 시맨틱 상호운용성 문제를
  참조→특수화→응용 구조로 푸는 **개념 프레임워크**

> **두 칸이 눈에 걸린다.**
>
> **① 온톨로지 행 — 둘 다 '경량'이다.** 수억 statement의 Wikidata도 경량이다.
> 규모와 무게가 다른 축이라는 뜻이다. Wikidata는 공리를 거의 안 걸고 넓게 펼쳤고(질의가 목적),
> MANUMATE는 좁은 범위에 공리를 걸었다(추론이 목적). **무게 = 공리의 밀도**다.
>
> **② 성숙도 행이 결론을 좌우한다.** Wikidata는 월 1억 쿼리를 받는 실서비스이고
> MANUMATE는 PoC다. 그래서 MANUMATE의 "된다"는 **"이 구조로 풀 수 있다"**까지이지
> **"이 규모로 굴러간다"**는 아니다. 16절이 인정한 한계(병합 수작업·진입장벽)가
> 실서비스 문턱에서 어떻게 될지는 이 논문이 답하지 않는다.
