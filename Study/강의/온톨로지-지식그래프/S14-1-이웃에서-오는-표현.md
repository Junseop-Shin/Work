# 부록 S14-1 — 이웃에서 오는 표현

> **성격** — [본편](S14-GNN-기반-KG-표현.md)을 읽으며 갈라져 나온 것들이다. 1절은 이 회차에
> 처음 나오는 용어를 모은 것이고, 2~7절이 강의 밖에서 나온 것, 8절이 자료 대조다.

이 회차는 처음 보는 말이 많다. message passing, self-loop, basis, composition operator, encoder와
decoder. 같은 이름이 두 논문에서 다른 것을 가리키는 경우도 있어 먼저 갈라놓는다.

그다음이 이번 회차의 본론이다. encoder가 붙으면서 S13에는 없던 문제가 두 개 생기는데, 슬라이드가
둘 다 한 줄씩만 언급하고 지나간다. 3절과 4절이 그것을 편 것이다.

---

## 1. 용어 정리

### 한눈에

| 용어 | 뜻 | 나오는 곳 |
|---|---|---|
| message passing | 이웃의 표현을 변환해 가져와 내 표현을 만드는 절차 | 본편 5절 |
| layer | 정보가 퍼지는 거리. K layer면 K홉 이웃까지 닿는다 | 본편 5절 |
| normalization (c) | 이웃 수로 나눠 크기를 맞추는 상수. 학습되지 않는다 | 본편 5·20절 |
| self-loop | 이전 layer의 자기 표현을 다음 layer로 넘기는 항 | 본편 5·7절 |
| encoder | 그래프에서 embedding을 만드는 부분 | 본편 3·11·14절 |
| decoder · task head | embedding을 점수나 확률로 바꾸는 부분 | 본편 3·14절 |
| basis | 여러 relation이 나눠 쓰는 공용 부품 | 본편 9·35절 |
| block decomposition | 행렬 대부분을 0으로 고정하는 파라미터 절감 | 본편 10절 |
| target edge masking | 맞혀야 할 엣지를 encoder에게 가리는 처리 | 본편 15절 |
| composition operator (φ) | 이웃 entity와 relation을 합치는 연산 | 본편 27절 |
| 방향별 filter | original · inverse · self-loop 셋을 구분하는 행렬 | 본편 28절 |
| inverse relation | 역방향 엣지를 별도 relation type으로 둔 것 | 본편 7절 |
| MRR | 정답 순위의 역수를 평균한 값 | 본편 17절 |

### message passing과 layer

이름이 거창한데 세 단계다.

```
① 이웃마다 메시지를 만든다      message = W · h_이웃
② 그 메시지들을 다 더한다        Σ
③ 활성함수를 통과시킨다          h_나 = σ(Σ)
```

한 번 돌면 1홉 이웃의 정보가 들어온다. 층을 하나 더 쌓으면 내 이웃이 이미 자기 이웃 정보를
담고 있으므로 2홉까지 닿는다. **층 수가 곧 정보가 퍼지는 거리다.**

### normalization이 학습되지 않는다는 것

`c_i,r`은 relation r로 이어진 이웃 수 같은 값이다. 이웃이 1,000개인 노드와 3개인 노드가 그냥
합만 하면 스케일이 달라지므로 나눠준다.

문제는 이 값이 상수라는 점이다. 이웃 1,000개를 전부 같은 무게로 평균 내므로 그중 중요한 이웃이
있어도 골라낼 방법이 없다. 본편 20절에서 R-GCN이 MUTAG와 BGS에서 지는 원인으로 저자들이 지목한
것이 이것이고, 슬라이드가 5절 주석과 20절 해석에서 같은 얘기를 두 번 한다.

> attention을 쓰는 계열이 바로 이 지점을 겨냥한다. 이웃마다 가중치를 학습하면 고정 상수 문제가
> 사라진다. 강의에는 안 나오지만 계보상 인접한 자리다.

### self-loop — 두 논문에서 위치가 다르다

| | self-loop의 자리 |
|---|---|
| R-GCN | 이웃 합과 **별개로 더하는 항** `W_0 h_i` |
| CompGCN | 방향 filter 세 개 중 **하나** `W_S` |

하는 일은 같다. 이웃 message만 더하면 자기 자신의 이전 표현이 사라지므로 내 정보를 함께 넘긴다.
식에서 놓이는 위치가 달라 두 식을 나란히 볼 때 헷갈리기 쉽다.

### basis — 같은 이름의 다른 장치

| | 공유하는 것 | relation마다 학습하는 것 | 나오는 곳 |
|---|---|---|---|
| R-GCN basis | 변환 **행렬** V_b | 조합 계수 a_rb | 본편 9절 |
| CompGCN basis | relation **벡터** z_b | 조합 계수 | 본편 35절 |

형태는 같다. 공용 부품 B개를 두고 관계마다 계수만 배운다. 그런데 R-GCN에서 공유되는 것은
"이 관계로 오는 정보를 어떻게 변환할까"이고 CompGCN에서 공유되는 것은 "이 관계가 무슨 뜻인가"다.

**공유의 효과가 파라미터 절감보다 크다.** 사례가 셋뿐인 rare relation도 다른 관계들이 만들어
놓은 basis를 그대로 쓰므로 백지에서 시작하지 않는다. 같은 이유로 block decomposition은 rare
relation 문제에 답하지 못한다. 파라미터만 줄고 관계끼리 정보를 주고받지 않는다.

### composition operator (φ)

이웃 entity 벡터와 relation 벡터를 하나로 합치는 연산이다. CompGCN에만 있다.

```
R-GCN     message = W_r · h_u              relation 은 행렬을 고르는 번호
CompGCN   message = W_λ(r) · φ(h_u, h_r)   relation 도 벡터를 갖고 먼저 합성된다
```

φ 자리에 들어가는 뺄셈·곱셈·circular correlation이 **S13에서 본 TransE·DistMult·HolE의 연산과
같다.**

### entity / node / graph classification

- **entity classification**(R-GCN)과 **node classification**(CompGCN)은 같은 과제다. 노드 하나의
  타입이나 클래스를 맞힌다. 논문마다 부르는 이름이 다를 뿐이다
- **graph classification**은 다른 과제다. 그래프 하나를 통째로 분류한다. CompGCN에만 있다

## 2. S13에서 무엇이 바뀌었나

한 줄로 하면 **벡터를 저장하는 대신 계산한다.**

```
S13     Seoul 벡터 = 임베딩 표의 Seoul 행           저장된 값
S14     Seoul 벡터 = f(이웃들의 벡터, 관계들)        계산된 값
```

S13 방식의 약점이 여기서 드러난다. 엔티티마다 벡터가 독립적으로 학습되므로 학습 데이터에
100번 나오는 엔티티는 100번 갱신되지만 3번 나오는 엔티티는 3번만 갱신된다.

GNN은 자기 등장 횟수가 적어도 이웃이 있으면 표현이 생긴다. 본편 22절이 뽑은 문장이 그 말이다.

> DistMult는 entity마다 독립 embedding을 학습하지만, R-GCN encoder는 이웃 구조로부터 embedding을
> 구성한다. 등장이 드문 entity에서 이득이 크다.

다만 본편 22절의 Figure 4를 보면 **이득이 특정 degree 구간에 몰려 있다.** degree가 아주 낮은
왼쪽 끝에서는 두 모델이 붙어 있고 DistMult가 살짝 위인 구간도 있다. 이웃이 거의 없으면 모아올
정보도 없으니 당연한 결과인데, 위 문장만 읽으면 반대로 이해하기 쉽다. 이웃이 적은 것과 자기
등장이 적은 것은 다른 얘기다.

같은 구분이 entity classification 쪽에도 적용된다. 본편 12절의 "label이 없는 node도 message
passing에는 참여한다"가 라벨 176개짜리 데이터셋에서 학습이 되는 이유다. 채점 대상은 176개인데
그래프 전체가 정보를 나른다.

## 3. encoder가 만든 새로운 누출

본편 15절의 마지막 항목을 슬라이드는 한 줄로 지나간다.

> 예측 대상 edge를 encoder가 그대로 보지 않도록 target edge masking 또는 edge dropout이
> **필요할 수 있음**

"필요할 수 있음"이라고 적혀 있지만 이건 선택이 아니다. 구조를 따라가면 바로 보인다.

```
(연구자 A, 소속, ?) 를 맞히려고 한다
   ↓
encoder 는 그래프 전체를 보고 e(연구자 A) 를 만든다
   ↓
그런데 (연구자 A, 소속, 연구실 B) 엣지가 그 그래프 안에 있다
   ↓
e(연구자 A) 에 이미 답이 들어 있다. decoder 는 읽기만 하면 된다
```

학습이 아니라 복사다. S13의 모델에는 이 문제가 원리적으로 없었다. encoder가 없어 triple 하나를
받아 점수를 냈고, 학습 집합과 평가 집합을 나누면 그것으로 끝이었다.

**두 종류의 누출을 구분해야 한다.**

| | 어디서 생기나 | 대응 | 논문 표에서 보이나 |
|---|---|---|---|
| 데이터셋 누출 | 역관계 쌍이 학습과 평가에 나뉘어 들어감 | FB15k-237 · WN18RR로 교체 | 보인다 (데이터셋 이름) |
| 아키텍처 누출 | 맞힐 엣지를 encoder가 본다 | target edge masking · edge dropout | 안 보인다 |

[S13 부록 5절](S13-1-기호와-좌표-사이.md#5-충돌하는-지점)에서 다룬 것은 앞쪽이다. 뒤쪽은 encoder가
생기면서 새로 나타났고, **벤치마크를 바꿔도 사라지지 않는다.** 구현 단계의 문제라 논문 표만 봐서는
이 처리를 했는지 알 수 없다.

실무 함의가 둘이다. GNN을 쓰면 이 처리를 직접 해야 하고, 평가 결과가 지나치게 좋으면 모델을
칭찬하기 전에 이것부터 의심해야 한다.

## 4. 방향을 살린 encoder와 대칭만 아는 decoder

R-GCN은 방향에 공을 들인다.

- canonical relation과 inverse relation을 **별도 relation type**으로 정의한다 (본편 7절)
- 그래서 relation 수가 두 배가 되고 파라미터 문제가 그만큼 커진다 (본편 8절)
- 슬라이드가 "방향과 self-loop를 분리해야 subject와 object의 **역할 차이를 보존**할 수 있다"고
  명시한다

그런데 decoder는 DistMult다. 본편 14절 슬라이드 주석이 직접 적어뒀다.

```
f(s, r, o) = e_sᵀ R_r e_o ,  R_r = diag(r)     대각행렬이므로 대칭 관계만 표현 가능
```

[S13 20절](S13-KG-임베딩-기초.md)에서 확인한 그대로다. `Σ h_i r_i t_i = Σ t_i r_i h_i`이므로
`(A, 소속, B)`와 `(B, 소속, A)`의 점수가 **항상 같다.**

**encoder가 힘들여 보존한 방향 정보를 decoder가 마지막 단계에서 쓰지 못한다.**

정확히 하면 완전히 버리는 것은 아니다. encoder가 방향을 구분해 만든 `e_A`와 `e_B`는 서로 다른
벡터이고, 그 벡터들 안에는 방향 정보가 녹아 있다. 그러나 **점수 단계에서 한 triple의 방향을
뒤집었을 때 점수가 달라져야 하는데 달라지지 않는다.** FB15k-237의 관계 상당수가 반대칭인데
그것들을 decoder가 원리적으로 구분하지 못한다.

### 왜 그런 decoder를 골랐나

본편 21절의 실험 설계 때문이다. baseline과 decoder를 같은 모델로 두어야 성능 차이를 encoder의
기여로 읽을 수 있다. DistMult를 baseline으로 쓰기로 한 순간 decoder도 DistMult여야 한다.

**엄밀한 실험 설계를 위해 표현력을 희생한 셈이다.** R-GCN의 link prediction 수치가 낮은 이유
가운데 하나가 여기 있고, 그것을 알면서도 그렇게 설계했다고 보는 편이 자연스럽다.

### CompGCN이 넘는 지점

본편 34절 Table 4를 이 관점으로 다시 보면 다르게 읽힌다.

| encoder | DistMult decoder | ConvE decoder |
|---|---|---|
| CompGCN (Mult) | 0.338 | 0.353 |
| CompGCN (Corr) | 0.335 | **0.355** |

같은 encoder인데 decoder만 바꿔서 0.017~0.020이 오른다. ConvE는 DistMult와 달리 대칭 제약이
없다. **CompGCN 대표 수치 0.355의 이득 일부는 composition operator가 아니라 decoder 교체에서
온다.**

이것이 본편 34절의 "composition은 독립적인 만능 선택이 아니라 encoder–decoder 조합의 일부"라는
문장의 구체적인 내용이다. 그리고 5절에서 볼 실험 설계 문제와 이어진다.

## 5. 실험 설계가 대비된다

### R-GCN은 변인을 하나로 묶었다

본편 21절이다. decoder를 DistMult로 고정하고 entity 벡터를 어디서 얻는지만 바꿨다.

```
A. entity 벡터 = 자유 파라미터   → DistMult → 0.191
B. entity 벡터 = encoder 출력    → DistMult → 0.248
```

decoder도 같고 relation 대각벡터도 양쪽 다 학습한다. 그러니 차이 +29.8%를 encoder의 기여로
읽을 수 있다. [S13 부록 5절](S13-1-기호와-좌표-사이.md#5-충돌하는-지점)에서 지적한 "옵티마이저가
다른데 모델 비교라고 한다"와 정확히 반대 방향의 설계다.

### CompGCN은 분리하지 못한다

최적 composition operator가 decoder마다 다르다. TransE decoder면 Mult, DistMult decoder면 Mult,
ConvE decoder면 Corr다. 강의도 그렇게 적었는데, 뒤집으면 **composition이 얼마나 기여했는지를
단독으로 말할 수 없다**는 뜻이 된다.

한 가지는 읽을 수 있다. 같은 ConvE decoder 열 안에서 encoder 없이 0.325, R-GCN 붙이면 0.342,
CompGCN(Corr) 붙이면 0.355다. **열 안에서는 비교가 성립한다.** 다만 이 열은 CompGCN이 자기
논문에서 만든 표라, R-GCN 쪽 구현이 원논문과 같은 조건인지는 알 수 없다.

두 논문을 나란히 놓으면 배울 것이 이것이다. 새 부품을 넣었을 때 그 부품의 기여를 재려면 나머지를
전부 고정해야 한다. R-GCN은 그렇게 했고 CompGCN은 부품을 두 개 동시에 바꿨다.

## 6. 온톨로지가 후보를 줄인다

본편 16절 마지막 항목이 지나가듯 적혀 있다.

> 실무에서는 relation의 domain/range로 부적합한 type을 후보에서 제외할 수 있음

[S13 부록 7절](S13-1-기호와-좌표-사이.md#7-온톨로지가-임베딩에-줄-수-있는-것)에서 "타입 제약을
negative sampling에 쓰면 학습 효율이 오른다"를 가설로 적어뒀다. 강의가 비슷한 아이디어를 다른
자리에 놓는다. **학습이 아니라 추론이다.**

| | 언제 | 무엇이 바뀌나 | 난이도 |
|---|---|---|---|
| negative sampling에 타입 제약 | 학습 | 오답의 난이도. 모델이 배우는 내용 | 학습 코드를 고쳐야 한다 |
| 후보 필터링에 domain/range | 추론 | 채점 대상 집합. 모델은 그대로 | SPARQL 한 번이면 된다 |

추론 쪽이 훨씬 싸다. 모델을 건드리지 않고 온톨로지만 있으면 바로 쓸 수 있다. 효과도 크다.
`(연구자 A, 소속, ?)`에서 후보가 14,951개인데 `소속`의 range가 `Organization`이면 후보가 수백 개로
준다.

**대신 논문 수치를 그대로 옮겨 쓸 수 없게 된다.** 논문은 전체 엔티티를 후보로 놓고 잰다.
domain/range 필터를 걸면 같은 모델이라도 순위 지표가 크게 오른다. Hits@10 0.535는 필터가 없는
조건의 값이다. 우리 조건의 기대치를 논문에서 가져오면 안 된다는 뜻이고,
[S13 부록 6절](S13-1-기호와-좌표-사이.md#6-지표가-재는-것과-실무가-원하는-것)에서 적은 "지표와
실무 판단이 다른 질문에 답한다"의 또 다른 사례다.

온톨로지와 임베딩의 관계를 정리하면 세 자리가 나온다.

```
학습 전   타입 제약으로 어려운 오답 만들기          가설. 확인 필요
학습 후   추론 시 domain/range 로 후보 거르기       강의가 언급. 바로 쓸 수 있다
결과에서  학습된 표현에서 규칙 추출하기             S13 18절 DistMult
```

가운데가 가장 실행하기 쉽다. 온톨로지를 이미 갖고 있다면 모델을 무엇으로 고르든 붙는다.

## 7. 제조 KG에 대면

[S13 부록 8절](S13-1-기호와-좌표-사이.md#8-제조-kg에-대면-남는-것)의 다섯 항목이 GNN 계열에서
어떻게 움직이는지 본다.

**새 엔티티 문제는 설정에 달렸다.** S13의 가장 큰 걸림돌이 transductive 제약이었다. 본편 11절이
답을 준다. 입력 graph에서 각 node는 "feature 또는 학습 가능한 초기 vector"로 시작한다.

| 초기 입력 | 새 노드 | |
|---|---|---|
| node feature (타입 · 속성) | 처리 가능 | 이웃만 붙으면 표현이 나온다 |
| 학습 가능한 초기 vector | 불가 | 노드마다 자리를 학습하므로 S13과 같다 |

**우리가 고를 수 있는 문제다.** 제조 KG는 설비 타입, 공정 구분, 자재 분류 같은 feature가 있으므로
앞쪽을 고를 여지가 있다. 온톨로지를 이미 만들어뒀다면 클래스가 그대로 feature가 된다. 새 설비가
들어와도 타입과 엣지만 있으면 표현이 나온다.

**관계 수 문제는 우리 쪽에서 덜 심각하다.** R-GCN의 파라미터 폭증은 relation 1,345개 규모에서
나온다. 현장 KG의 관계가 30~50개면 basis decomposition이 애초에 필요 없다. 이 회차 내용의
상당 부분이 우리 조건에서는 안 걸리는 문제다.

**high-degree hub는 확실히 걸린다.** 제조 KG에는 hub가 많다. 공통 자재, 공통 설비 클래스, 모든
로트가 거치는 공정. 본편 20절에서 R-GCN이 MUTAG와 BGS에서 진 조건이 그대로 재현된다.

**라벨 희소 조건은 오히려 맞는다.** 본편 18절 데이터셋들의 라벨 비율이 0.04% 수준이다. 현장
KG도 라벨은 극소수이고 구조는 많다. **S13의 link prediction보다 entity classification 쪽이 우리
문제에 가까울 수 있다.** 설비나 불량의 타입을 이웃 구조로 채우는 용도라면 그렇다.

**설명 불가는 그대로 남고 나빠진다.** S13 부록 8절 다섯 번째 항목에 판정 경로와 설명 경로가
어긋나면 안 된다고 적었다. GNN은 여러 홉의 이웃을 합쳐 표현을 만들므로 어떤 이웃이 결과를
만들었는지가 S13보다 더 불투명하다.

**여기에 하나가 추가된다.** 3절의 아키텍처 누출이다. 사내 평가에서 성능이 잘 나왔다고 도입을
결정하기 전에, 맞히려는 엣지를 encoder가 보고 있지 않은지 확인해야 한다. 이건 데이터셋을 바꿔서
해결되는 문제가 아니라 파이프라인 구현을 봐야 하는 문제다.

## 8. 자료 대조

인사이트가 아니라 확인 사항이라 한 절로 눌러 담는다.

| 걸린 것 | 내용 |
|---|---|
| 같은 모델의 수치가 다르다 | FB15k-237 filtered MRR이 DistMult 0.191(R-GCN) ↔ .241(CompGCN), TransE 0.233 ↔ .294. [S13 부록 5절](S13-1-기호와-좌표-사이.md#5-충돌하는-지점)에서 본 문제가 회차를 넘어 반복된다 |
| 두 행이 섞인 것으로 보인다 | CompGCN이 인용한 R-GCN 행이 MRR .248(R-GCN 행)인데 H@10 .417·H@1 .151은 R-GCN+ 행 값이다. 원논문 대조 필요 |
| 논문 서술과 표가 어긋난다 | CompGCN이 "5개 지표 중 4개에서 우수"라고 쓰는데 MR은 RotatE, H@10은 SACN이 낫고 H@3는 동률이다. **강의가 이미 본편에서 짚었다** |

세 번째 줄이 눈에 띈다. S13에서 우리가 부록으로 뺐던 종류의 작업을 이 회차는 강의가 본편에서
하고 있다.

## 9. 정리

| | 내용 |
|---|---|
| 두 논문이 합의하는 것 | relation type을 무시하면 의미가 다른 이웃이 같게 집계된다 |
| | 관계마다 독립 파라미터를 두면 rare relation이 학습되지 않는다. 공유가 필요하다 |
| | 표현을 이웃에서 계산하면 등장이 드문 엔티티에서 이득이 있다 |
| 갈리는 것 | relation을 행렬로 둘 것인가(R-GCN) 벡터로 둘 것인가(CompGCN) |
| | 실험 설계. R-GCN은 decoder를 고정해 encoder 기여를 분리했고 CompGCN은 부품 둘을 함께 바꿨다 |
| | 파라미터를 줄이는 두 방식. basis는 관계끼리 공유하고 block은 공유하지 않는다 |
| 이 회차에서 새로 생긴 것 | encoder가 맞힐 엣지를 보는 아키텍처 누출. 벤치마크를 바꿔도 사라지지 않는다 |
| | 방향을 보존한 encoder와 대칭만 표현하는 decoder의 어긋남 |
| 미해결로 남는 것 | 고정 normalization 때문에 hub가 많은 그래프에서 성능이 떨어진다 |
| | 여러 홉을 합친 표현이라 근거 추적이 S13보다 어렵다 |
| 확인할 것 | CompGCN Table 3의 R-GCN 행이 두 행을 섞은 것인지 |
