## 1. RDF · RDFS · OWL이 층으로 쌓이는 이유

세 가지가 경쟁 관계가 아니라 **표현력을 한 단계씩 올리는 층**이다. 아래층 문법을 그대로 쓰면서
어휘를 더한다.

| 층 | 더해지는 것 | 못 하는 것 |
|---|---|---|
| RDF | 주어·서술어·목적어 트리플 | 관계의 뜻과 제약을 적을 수 없다 |
| RDFS | 클래스 계층(subClassOf), domain/range | AND·OR·NOT·개수 제약이 없다 |
| OWL | 논리 연산자, 기수 제약, 배타성 | 표현력이 커질수록 추론 비용이 커진다 |

본편 2절의 예시가 그 순서를 보여준다. `(naPINN, written_by, 김한결)`만 있으면 naPINN이
무엇인지 알 수 없는데, RDFS가 `written_by`의 domain을 Paper로 선언하면 naPINN이 Paper라는
결론이 따라 나온다.

Ch.4에서 이미 다룬 것이고, 이 회차가 도입부에서 다시 꺼내는 이유는 LLM이 만들어야 하는 출력이
어느 층인지가 논문마다 다르기 때문이다. 첫째 논문은 OWL 모듈을, 둘째 논문은 RDFS 수준의
클래스 계층과 domain/range를 만든다.

## 2. 모듈이란 무엇이고 OWL import와 어떻게 다른가

OWL에는 `owl:imports`로 다른 온톨로지를 통째로 가져오는 장치가 있다. 그런데 이 회차의 모듈은
그것과 다르다.

| | 무엇인가 |
|---|---|
| owl:imports | 파일 단위로 전체를 가져온다. 경계가 파일이다 |
| 이 논문의 module | use case를 중심으로 관련 class·property·axiom만 모은 **부분집합**. 경계가 의미다 |

핵심은 **경계를 사람이 정한다**는 점이다. Person module, Organization module처럼 도메인의 핵심
개념을 중심으로 묶는데, 어느 크기가 적절한지에 대한 기준이 없다는 것이 본편 14절의 첫 번째
한계다.

모듈이 하는 일은 하나다. LLM에게 주는 컨텍스트를 좁힌다. [S26-2 1절](S26-2-무엇에-묶느냐가-정한다.md)에서
적은 "온톨로지가 허용 목록으로 돌아왔다"와 같은 자리이고, 여기서는 그 목록을 더 작게 자른다.

## 3. GeoLink 벤치마크

해양학 분야의 온톨로지 정렬 벤치마크다. 두 온톨로지(GeoLink Base Ontology와 GeoLink Modular
Ontology)를 정렬하는 과제이고 클래스가 40~150개다.

이 벤치마크가 특별한 것은 **complex alignment**를 다룬다는 점이다. 클래스 하나를 클래스 하나에
잇는 단순 정렬이 아니라, 여러 클래스와 속성의 조합을 규칙으로 잇는다.

```
Align(A:River, B:Stream) if
  A:flowsThrough(x, y) AND A:Wetland(y) AND B:flowsThrough(u, v) AND B:Ecosystem(v)
```

본편 13절에서 온톨로지 전체를 프롬프트에 넣은 대조군이 완전히 실패한 이유가 이 복잡성이다.
규칙 본문에 무관한 조건이 섞이면 규칙 자체가 성립하지 않는다.

## 4. Pydantic과 구조화 출력

Pydantic은 파이썬에서 데이터 형식을 선언하고 검사하는 라이브러리다. 클래스로 스키마를 적으면
들어온 값이 그 형식에 맞는지 자동으로 확인한다.

```python
class OntologyElement(BaseModel):
    name: str
    domain: str
    range: str
```

LLM에게 이 스키마를 주고 그 형식으로만 출력하게 하면 **출력이 깨지지 않는다.** 필드가 빠지거나
타입이 틀리면 그 자리에서 걸린다.

S26A의 CodeKGC가 Python class로 스키마를 인코딩한 것과 발상이 비슷한데, 쓰임이 다르다. CodeKGC는
모델이 구조를 더 잘 이해하게 하려고 썼고, 여기서는 출력이 유효한지 검사하려고 쓴다.

## 5. RDF 직렬화를 LLM에게 맡기지 않는 이유

둘째 논문의 설계에서 눈여겨볼 지점이다. 최종 Turtle 파일을 LLM이 쓰지 않고 rdflib이 만든다.

이유는 S24에서 확인된 것과 같다. 거기서 LLM이 만든 KG가 SPARQL 엔진에서 바로 동작하지 않아 수동
수정이 필요한 경우가 있었다. 문법을 지키는 일은 라이브러리가 확실하게 한다.

정리하면 역할 분담이 이렇다.

| | 맡는 일 |
|---|---|
| LLM | 무엇을 클래스로 볼지, 어느 것이 어느 것의 부모인지 판단 |
| Pydantic | 출력이 형식에 맞는지 검사 |
| rdflib | 그 결과를 올바른 Turtle로 쓰기 |

## 6. entailment — 논리의 함의와 LLM의 판단

논리학에서 함의(entailment)는 전제가 참이면 결론도 반드시 참이라는 관계다. `모든 사과는
과일이다`와 `이것은 사과다`에서 `이것은 과일이다`가 함의된다.

둘째 논문의 Entailment LLM은 그 관계를 **판정하는** 역할이다. 두 클래스의 정의와 설명을 비교해
`Apple은 Fruit에 포함되는가?`를 답한다.

여기서 구분할 것이 있다. **논리적 함의는 추론기가 계산하는 것이고, 이 논문의 Entailment LLM은
자연어 설명을 읽고 추측하는 것이다.** 이름은 같지만 보장 수준이 다르다. 본편 9절의 세 번째
한계가 이 지점이다. 최종 온톨로지에 논리적 모순이 있는지 검사하는 단계가 없다.

[S25-1 3절](S25-1-읽는-데-필요한-것들.md)의 HermiT처럼 실제 추론기를 붙이면 이 간극이 메워지는데,
둘째 논문은 그 단계를 두지 않았다.

## 7. Exact Match와 Fuzzy Match

| | 언제 맞았다고 보나 |
|---|---|
| Exact Match | 생성한 이름이 정답과 문자열까지 100% 일치 |
| Fuzzy Match | 임베딩 유사도가 임계값을 넘으면 맞은 것으로 본다 |

본편 8절에서 Exact가 0.000~0.102이고 Fuzzy가 0.121~0.724다. 일곱 배 이상 벌어진다.

**Exact가 0에 가까운 것은 성능이 아니라 이름 짓기의 문제다.** 정답이 `Employee`인데 모델이
`Staff`나 `Worker`를 내놓으면 의미가 같아도 0점이다. 클래스 이름에는 정답이 하나가 아니다.

그래서 이 논문의 실질 지표는 Fuzzy다. 대신 Fuzzy는 계층과 논리 일관성을 못 본다는 한계가 따라
붙는다(본편 9절).

이 대비가 S25의 SPARQL과 RAG 두 지표와 같은 구조다. 엄격한 쪽은 이름 불일치에 걸리고 관대한
쪽은 구조를 못 본다.

## 8. Finance 도메인만 유독 낮은 것을 어떻게 읽나

Fuzzy 기준으로 Data 0.724, Logistics 0.431, Finance 0.121이다. 같은 파이프라인인데 여섯 배
차이가 난다.

논문은 이유를 자세히 적지 않는다. 짐작할 수 있는 것은 도메인 어휘의 성격이다. Data 도메인의
개념(`DataAsset`, `Employee`, `Policy`)은 일상 영어에 가깝고, 금융 문서는 전문 용어와 규제
용어가 많아 정답 이름 자체가 특수하다.

S23에서 본 것과 같은 모양이다. 거기서도 WordNet(일반 어휘)은 91.7이고 biomedical은 16~37이었다.
**도메인이 전문적일수록 LLM이 정답 이름을 맞히기 어렵다**는 것이 Ch.7에서 두 번 확인된다.
