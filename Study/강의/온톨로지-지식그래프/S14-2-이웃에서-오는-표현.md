# 부록 S14-2 — 이웃에서 오는 표현

> **성격** — 본편([S14A](S14A-R-GCN-관계별-메시지-전달.md) · [S14B](S14B-CompGCN-합성-기반-관계-표현.md))을
> 읽으며 갈라져 나온 것들이다. 강의 밖에서 나온 해석이 1~8절, 자료 대조가 9절이다.
> 용어와 식 읽기는 [S14-1](S14-1-읽는-데-필요한-것들.md)에 있다.

1절이 이 회차 전체를 하나로 꿰는 관점이고, 3절과 4절은 encoder가 붙으면서 새로 생긴 문제 둘이다.
슬라이드가 둘 다 한 줄씩만 언급하고 지나간다.

## 1. 어느 축에서 공유할 것인가

이 회차 전체가 한 질문의 변주다. **같은 부품을 어디까지 재사용할 것인가.**

CNN이 통한 이유가 필터를 위치를 넘어 재사용한 것이었다. GCN은 그것을 노드 축으로 옮겼다. 그런데
R-GCN이 관계 타입을 도입하면서 **관계 축에서는 공유를 포기한다.** 관계마다 행렬이 따로다.

| 축 | GCN | R-GCN | CompGCN |
|---|---|---|---|
| 노드 | 공유 | 공유 | 공유 |
| 관계 | 구분 자체가 없음 | 관계마다 행렬 (basis로 부분 회복) | 관계는 벡터, 행렬은 방향 3개뿐 |
| 방향 | 구분 없음 | 역관계를 별도 relation type으로 | 필터 3개로 고정 |

이 관점으로 보면 본편의 순서가 하나의 이야기가 된다.

```
S14A 2절    GCN 은 관계를 구분 못 한다          공유를 너무 많이 한다
S14A 8절    관계마다 행렬을 두니 터진다          공유를 너무 안 한다
S14A 9·10절 basis 와 block                   공유를 다시 늘리는 두 방법
S14B 5절    CompGCN update equation          공유 단위를 행렬에서 벡터로 낮춘다
S14B 12절   relation basis vector            그 벡터마저 공유한다
```

**공유를 늘리면 사례가 적은 것도 배워지고 표현력이 준다. 줄이면 반대다.** 이 회차는 그 다이얼을
어디에 둘지의 문제이고, 두 논문은 서로 다른 위치를 골랐다.

S13과도 이어진다. [S13 7절](S13-KG-임베딩-기초.md)의 RESCAL이 관계마다 k×k 행렬을 둬서 터졌고
TransE가 관계당 벡터 하나로 줄여 이겼다. 같은 다이얼이다. 그러니까 R-GCN → CompGCN의 이동은
RESCAL → TransE의 이동을 GNN 위에서 다시 한 것으로 읽을 수 있다.

## 2. S13에서 무엇이 바뀌었나

한 줄로 하면 **벡터를 저장하는 대신 계산한다.**

```
S13     Seoul 벡터 = 임베딩 표의 Seoul 행           저장된 값
S14     Seoul 벡터 = f(이웃들의 벡터, 관계들)        계산된 값
```

S13 방식의 약점이 여기서 드러난다. 엔티티마다 벡터가 독립적으로 학습되므로 100번 나오는 엔티티는
100번 갱신되지만 3번 나오는 엔티티는 3번만 갱신된다. GNN은 자기 등장 횟수가 적어도 이웃이 있으면
표현이 생긴다.

다만 S14A 22절의 Figure 4를 보면 **이득이 특정 degree 구간에 몰려 있다.** degree가 아주 낮은 왼쪽
끝에서는 두 모델이 붙어 있고 DistMult가 살짝 위인 구간도 있다. 이웃이 거의 없으면 모아올 정보도
없으니 당연한데, "등장이 드문 entity에서 이득이 크다"는 문장만 읽으면 반대로 이해하기 쉽다.
이웃이 적은 것과 자기 등장이 적은 것은 다른 얘기다.

같은 구분이 entity classification에도 적용된다. S14A 12절의 "label이 없는 node도 message passing에는
참여한다"가 라벨 176개짜리 데이터셋에서 학습이 되는 이유다. 채점 대상은 176개인데 그래프 전체가
정보를 나른다.

## 3. encoder가 만든 새로운 누출

S14A 15절의 마지막 항목을 슬라이드는 한 줄로 지나간다.

> 예측 대상 edge를 encoder가 그대로 보지 않도록 target edge masking 또는 edge dropout이
> **필요할 수 있음**

"필요할 수 있음"이라고 적혀 있지만 선택이 아니다. 구조를 따라가면 바로 보인다.

```
(연구자 A, 소속, ?) 를 맞히려고 한다
   ↓
encoder 는 그래프 전체를 보고 e(연구자 A) 를 만든다
   ↓
그런데 (연구자 A, 소속, 연구실 B) 엣지가 그 그래프 안에 있다
   ↓
e(연구자 A) 에 이미 답이 들어 있다. decoder 는 읽기만 하면 된다
```

학습이 아니라 복사다. S13의 모델에는 이 문제가 원리적으로 없었다. encoder가 없어 triple 하나를
받아 점수를 냈고, 학습 집합과 평가 집합을 나누면 그것으로 끝이었다.

**두 종류의 누출을 구분해야 한다.**

| | 어디서 생기나 | 대응 | 논문 표에서 보이나 |
|---|---|---|---|
| 데이터셋 누출 | 역관계 쌍이 학습과 평가에 나뉘어 들어감 | FB15k-237 · WN18RR로 교체 | 보인다 (데이터셋 이름) |
| 아키텍처 누출 | 맞힐 엣지를 encoder가 본다 | target edge masking · edge dropout | 안 보인다 |

[S13 부록 5절](S13-1-기호와-좌표-사이.md#5-충돌하는-지점)에서 다룬 것은 앞쪽이다. 뒤쪽은 encoder가
생기면서 새로 나타났고 **벤치마크를 바꿔도 사라지지 않는다.** 구현 단계의 문제라 논문 표만 봐서는
이 처리를 했는지 알 수 없다.

실무 함의가 둘이다. GNN을 쓰면 이 처리를 직접 해야 하고, 평가 결과가 지나치게 좋으면 모델을
칭찬하기 전에 이것부터 의심해야 한다.

## 4. 방향을 살린 encoder와 대칭만 아는 decoder

R-GCN은 방향에 공을 들인다. canonical relation과 inverse relation을 **별도 relation type**으로
정의하고(S14A 7절), 그 대가로 relation 수가 두 배가 되어 파라미터 문제가 커진다(S14A 8절).
슬라이드가 "방향과 self-loop를 분리해야 subject와 object의 **역할 차이를 보존**할 수 있다"고 명시한다.

그런데 decoder는 DistMult다. S14A 14절 슬라이드 주석이 직접 적어뒀다.

```
f(s, r, o) = e_sᵀ R_r e_o ,  R_r = diag(r)     대각행렬이므로 대칭 관계만 표현 가능
```

[S13 20절](S13-KG-임베딩-기초.md)에서 확인한 그대로다. `Σ h_i r_i t_i = Σ t_i r_i h_i`이므로
`(A, 소속, B)`와 `(B, 소속, A)`의 점수가 **항상 같다.**

**encoder가 힘들여 보존한 방향 정보를 decoder가 마지막 단계에서 쓰지 못한다.**

정확히 하면 완전히 버리는 것은 아니다. encoder가 방향을 구분해 만든 `e_A`와 `e_B`는 서로 다른
벡터이고 그 안에 방향 정보가 녹아 있다. 그러나 **한 triple의 방향을 뒤집었을 때 점수가 달라져야
하는데 달라지지 않는다.** FB15k-237의 관계 상당수가 반대칭인데 그것들을 decoder가 원리적으로
구분하지 못한다.

### 귀납 편향이 두 층에 생겼다

S13에서 귀납 편향은 한 곳이었다. 점수함수뿐이었다. S14에서는 두 곳이다.

| | 어디에 있나 | 무슨 가정을 담나 |
|---|---|---|
| encoder | 이웃을 모으는 방식 | 이웃이 그 노드를 설명한다 |
| decoder | triple을 채점하는 연산 | 이 연산이 이 관계 성질을 표현한다 |

**둘이 서로 어긋날 수 있다는 것이 이 절의 내용이다.** 모델을 고를 때 한쪽만 보면 안 된다.

### 왜 그런 decoder를 골랐나

S14A 21절의 실험 설계 때문이다. baseline과 decoder를 같은 모델로 두어야 성능 차이를 encoder의
기여로 읽을 수 있다. DistMult를 baseline으로 쓰기로 한 순간 decoder도 DistMult여야 한다.

**엄밀한 실험 설계를 위해 표현력을 희생한 셈이다.** R-GCN의 link prediction 수치가 낮은 이유
가운데 하나가 여기 있고, 그것을 알면서도 그렇게 설계했다고 보는 편이 자연스럽다.

## 5. 실험 설계가 대비된다

### R-GCN은 변인을 하나로 묶었다

S14A 21절이다. decoder를 DistMult로 고정하고 entity 벡터를 어디서 얻는지만 바꿨다.

```
A. entity 벡터 = 자유 파라미터   → DistMult → 0.191
B. entity 벡터 = encoder 출력    → DistMult → 0.248
```

decoder도 같고 relation 대각벡터도 양쪽 다 학습한다. 그러니 차이 +29.8%를 encoder의 기여로 읽을
수 있다. [S13 부록 5절](S13-1-기호와-좌표-사이.md#5-충돌하는-지점)에서 지적한 "옵티마이저가
다른데 모델 비교라고 한다"와 정확히 반대 방향의 설계다.

### CompGCN은 부품 둘을 함께 바꿨다

S14B 11절 Table 4를 4절의 관점으로 다시 보면 다르게 읽힌다.

| encoder | DistMult decoder | ConvE decoder |
|---|---|---|
| CompGCN (Mult) | 0.338 | 0.353 |
| CompGCN (Corr) | 0.335 | **0.355** |

같은 encoder인데 decoder만 바꿔서 0.017~0.020이 오른다. ConvE는 DistMult와 달리 대칭 제약이 없다.
**CompGCN 대표 수치 0.355의 이득 일부는 composition operator가 아니라 decoder 교체에서 온다.**

최적 operator가 decoder마다 달라진다는 것도 같은 얘기다. 강의는 "composition은 encoder–decoder
조합의 일부"라고 적었는데, 뒤집으면 composition이 얼마나 기여했는지를 단독으로 말할 수 없다는
뜻이 된다.

한 가지는 읽을 수 있다. 같은 ConvE 열 안에서 encoder 없이 0.325, R-GCN 0.342, CompGCN(Corr)
0.355다. **열 안에서는 비교가 성립한다.** 다만 이 표는 CompGCN이 자기 논문에서 만든 것이라
R-GCN 쪽 구현이 원논문과 같은 조건인지는 알 수 없다.

두 논문을 나란히 놓으면 배울 것이 이것이다. 새 부품의 기여를 재려면 나머지를 전부 고정해야 한다.

## 6. 이웃이 나를 설명한다는 가정

> 강의 밖 내용이다.

GCN의 전제를 한 줄로 하면 "이웃을 보면 그 노드를 알 수 있다"이다. **이것은 사실이 아니라 가정이다.**

잘 맞는 경우가 있다. 논문 인용은 같은 분야끼리 이어지고, 소셜 네트워크는 비슷한 사람끼리 연결된다.

안 맞는 경우도 있다.

- **위장이 있는 경우.** 사기 계정은 일부러 정상 계정과 연결된다. 이웃을 평균 내면 신호가 지워진다
- **상보적 관계.** 부품과 완제품은 같은 종류가 아니다. 이웃을 닮아야 할 이유가 없다

이 구분에 이름이 있다. 이웃이 나를 닮는 성질을 homophily, 안 닮는 것을 heterophily라 부르고,
GCN 계열은 앞쪽을 전제로 설계됐다.

> S14A 20절에서 R-GCN이 MUTAG·BGS에서 지는 것을 저자들은 hub와 고정 normalization으로 설명한다.
> 이 가정이 안 맞는 데이터셋일 가능성도 함께 볼 만한데 확인하지는 못했다.

제조 KG로 옮기면 걸리는 자리가 보인다. **불량 로트의 이웃은 대부분 정상 로트다.** 같은 라인,
같은 설비, 같은 자재를 공유하니까. message passing이 불량 신호를 이웃 평균으로 지워버릴 수 있다.
hub 문제와는 다르다. hub는 이웃이 너무 많아 생기는 문제이고 이것은 이웃이 나와 다른 종류라서
생기는 문제다.

반대로 잘 맞는 자리도 있다. 설비 타입을 맞히는 일이 그렇다. 같은 부품을 갖고 같은 공정에 속한
설비는 실제로 같은 타입일 가능성이 높다.

**도입 전에 물어볼 질문 하나로 정리된다. 우리가 맞히려는 라벨이 이웃과 같은 값을 갖는 경향이
있는가.** 기존 KG에서 잴 수 있다. 라벨이 있는 노드들에 대해 이웃의 라벨과 일치하는 비율을 세면
된다. 이 값이 낮으면 GNN을 붙일 이유가 약해진다.

## 7. 온톨로지가 후보를 줄인다

S14A 16절 마지막 항목이 지나가듯 적혀 있다.

> 실무에서는 relation의 domain/range로 부적합한 type을 후보에서 제외할 수 있음

[S13 부록 7절](S13-1-기호와-좌표-사이.md#7-온톨로지가-임베딩에-줄-수-있는-것)에서 "타입 제약을
negative sampling에 쓰면 학습 효율이 오른다"를 가설로 적어뒀다. 강의가 비슷한 아이디어를 다른
자리에 놓는다. **학습이 아니라 추론이다.**

| | 언제 | 무엇이 바뀌나 | 난이도 |
|---|---|---|---|
| negative sampling에 타입 제약 | 학습 | 오답의 난이도. 모델이 배우는 내용 | 학습 코드를 고쳐야 한다 |
| 후보 필터링에 domain/range | 추론 | 채점 대상 집합. 모델은 그대로 | SPARQL 한 번이면 된다 |

추론 쪽이 훨씬 싸다. 모델을 건드리지 않고 온톨로지만 있으면 된다. 효과도 크다.
`(연구자 A, 소속, ?)`에서 후보가 14,951개인데 `소속`의 range가 `Organization`이면 수백 개로 준다.

**대신 논문 수치를 우리 조건의 기대치로 쓸 수 없게 된다.** 논문은 전체 엔티티를 후보로 놓고 잰다.
필터를 걸면 같은 모델이라도 순위 지표가 크게 오른다. Hits@10 0.535는 필터 없는 조건의 값이다.
[S13 부록 6절](S13-1-기호와-좌표-사이.md#6-지표가-재는-것과-실무가-원하는-것)에서 적은 "지표와
실무 판단이 다른 질문에 답한다"의 또 다른 사례다.

온톨로지와 임베딩이 만나는 자리를 정리하면 셋이다.

```
학습 전   타입 제약으로 어려운 오답 만들기          가설. 확인 필요
학습 후   추론 시 domain/range 로 후보 거르기       강의가 언급. 바로 쓸 수 있다
결과에서  학습된 표현에서 규칙 추출하기             S13 18절 DistMult
```

가운데가 가장 실행하기 쉽다. 온톨로지를 이미 갖고 있다면 모델을 무엇으로 고르든 붙는다.

## 8. 제조 KG에 대면

[S13 부록 8절](S13-1-기호와-좌표-사이.md#8-제조-kg에-대면-남는-것)의 다섯 항목이 GNN 계열에서
어떻게 움직이는지 본다.

**새 엔티티 문제는 설정에 달렸다.** S13의 가장 큰 걸림돌이 transductive 제약이었다. S14A 11절이
답을 준다.

| 초기 입력 h^(0) | 새 노드 | |
|---|---|---|
| node feature (타입 · 속성) | 처리 가능 | 이웃만 붙으면 표현이 나온다 |
| 학습 가능한 초기 vector | 불가 | 노드마다 자리를 학습하므로 S13과 같다 |

**우리가 고를 수 있는 문제다.** 제조 KG는 설비 타입, 공정 구분, 자재 분류 같은 feature가 있으므로
앞쪽을 고를 여지가 있다. 온톨로지를 이미 만들어뒀다면 클래스가 그대로 feature가 된다.

**관계 수 문제는 우리 쪽에서 덜 심각하다.** R-GCN의 파라미터 폭증은 relation 1,345개 규모에서
나온다. 현장 KG의 관계가 30~50개면 basis decomposition이 애초에 필요 없다. 2절의 다이얼을 굳이
공유 쪽으로 돌릴 이유가 없다는 뜻이다.

**high-degree hub는 확실히 걸린다.** 공통 자재, 공통 설비 클래스, 모든 로트가 거치는 공정.
S14A 20절에서 R-GCN이 진 조건이 그대로 재현된다.

**라벨 희소 조건은 오히려 맞는다.** S14A 18절 데이터셋들의 라벨 비율이 0.04% 수준이다. 현장 KG도
라벨은 극소수이고 구조는 많다. **S13의 link prediction보다 entity classification 쪽이 우리 문제에
가까울 수 있다.**

**설명 불가는 그대로 남고 나빠진다.** GNN은 여러 홉의 이웃을 합쳐 표현을 만들므로 어떤 이웃이
결과를 만들었는지가 S13보다 더 불투명하다.

**여기에 두 개가 추가된다.** 3절의 아키텍처 누출을 파이프라인에서 직접 막아야 하고, 6절의 질문에
먼저 답해야 한다. 맞히려는 라벨이 이웃과 같은 값을 갖는 경향이 있는가.

## 9. 자료 대조

인사이트가 아니라 확인 사항이라 한 절로 눌러 담는다.

| 걸린 것 | 내용 |
|---|---|
| 같은 모델의 수치가 다르다 | FB15k-237 filtered MRR이 DistMult 0.191(R-GCN) ↔ .241(CompGCN), TransE 0.233 ↔ .294. [S13 부록 5절](S13-1-기호와-좌표-사이.md#5-충돌하는-지점)의 문제가 회차를 넘어 반복된다 |
| 두 행이 섞인 것으로 보인다 | CompGCN이 인용한 R-GCN 행이 MRR .248(R-GCN 행)인데 H@10 .417·H@1 .151은 R-GCN+ 행 값이다. 원논문 대조 필요 |
| 논문 서술과 표가 어긋난다 | CompGCN이 "5개 지표 중 4개에서 우수"라고 쓰는데 MR은 RotatE, H@10은 SACN이 낫고 H@3는 동률이다. **강의가 이미 본편에서 짚었다** |

세 번째 줄이 눈에 띈다. S13에서 우리가 부록으로 뺐던 종류의 작업을 이 회차는 강의가 본편에서
하고 있다.

## 10. 정리

| | 내용 |
|---|---|
| 이 회차를 꿰는 것 | 같은 부품을 어느 축에서 재사용할 것인가. 노드 · 관계 · 방향 |
| | 공유를 늘리면 rare한 것이 배워지고 표현력이 준다. 두 논문이 다른 위치를 골랐다 |
| 두 논문이 합의하는 것 | relation type을 무시하면 의미가 다른 이웃이 같게 집계된다 |
| | 표현을 이웃에서 계산하면 등장이 드문 엔티티에서 이득이 있다 |
| 갈리는 것 | relation을 행렬로 둘 것인가(R-GCN) 벡터로 둘 것인가(CompGCN) |
| | 실험 설계. R-GCN은 decoder를 고정했고 CompGCN은 부품 둘을 함께 바꿨다 |
| 이 회차에서 새로 생긴 것 | encoder가 맞힐 엣지를 보는 아키텍처 누출. 벤치마크를 바꿔도 사라지지 않는다 |
| | 귀납 편향이 encoder와 decoder 두 층에 생겼고 서로 어긋날 수 있다 |
| 미해결로 남는 것 | 고정 normalization 때문에 hub가 많은 그래프에서 성능이 떨어진다 |
| | 이웃이 나를 설명한다는 가정이 안 맞는 그래프에서는 어떻게 되는가 |
| | 여러 홉을 합친 표현이라 근거 추적이 S13보다 어렵다 |
