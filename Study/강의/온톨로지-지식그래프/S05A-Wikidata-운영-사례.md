# 01 온톨로지 Recap

## 2. 온톨로지의 4가지 구성 요소

| 요소 | 정의 | 예 |
|---|---|---|
| **클래스** (Class) | 개념 / 범주 (종류) | `Wafer`, `Lot`, `Process` |
| **인스턴스** (Individual) | 클래스의 실제 개체 | `Lot_A1234`, `Wafer_07` |
| **속성** (Property) | 클래스 간 관계 · 값 | `Lot —contains→ Wafer` |
| **공리** (Axiom) | 항상 참인 논리 규칙 | "Litho 공정은 Mask 공정 이후에 진행된다" |

> **[S01 2절](S01-기본개념과-실사례.md)의 4요소와 구성이 다르다.**
>
> | | S01 | S05 recap |
> |---|---|---|
> | | 개체 · 범주 · **속성** · **관계** | 클래스 · 인스턴스 · **속성** · **공리** |
>
> **관계가 빠지고 공리가 들어왔다.** 관계는 속성(Object Property)에 흡수됐다 — 3절에서 바로 그렇게 정리된다.
> 관점의 차이로 읽힌다. S01은 *"그래프가 무엇으로 이루어지는가"*(구성 요소)이고,
> S05는 *"OWL로 무엇을 쓸 수 있는가"*(표현 수단)에 가깝다.
> **공리가 4요소에 들어오는 순간 추론이 시야에 들어온다.**

## 3. 속성의 두 종류

| | 연결하는 것 | 예 |
|---|---|---|
| **Object Property** (객체 속성) | 개체 ↔ 개체 | `Wafer —is_processed_by→ Etch Step` |
| **Data Property** (데이터 속성) | 개체 → 값 (문자 / 숫자) | `Wafer —has_thickness→ "775 Å"` |

> [S04-1 2.4절](S04-1-OTKM이-정하지-않은-것들.md)에서 `skos:broader`에 상속이 없는 이유로
> "개체 ↔ 개체를 잇는 관계라 물려받을 자리가 없다"고 정리했다. **그게 바로 Object Property다.**
> Data Property는 값으로 끝나므로 그래프의 잎(leaf)이 된다.

|---|---|

**아래(RDF)가 기반, 위로 갈수록 표현력·기능이 추가된다.**

| 층 | 하는 일 | 예 | 제조 도메인 예 |
|---|---|---|---|
| **RDF** | 지식을 트리플로 — (주어, 술어, 목적어) | `(Berlin, capital_of, Germany)` | `Wafer_07, has_thickness, "775Å"` |
| **OWL** | 종류의 계층 · 공리 | `Dog ⊑ Animal` (개는 동물의 하위) | `TestWafer ⊑ Wafer` |
| **SPARQL** | 그래프 조회 질의 (그래프판 SQL) | `SELECT ?x WHERE { ?x type Cat }` | 결함 있는 Wafer 모두 조회 |
| **SWRL** | if-then 규칙으로 자동 도출 | `hasParent(x,y) ∧ hasBrother(y,z) → hasUncle(x,z)` | Lot이 hold+스크랩 → 다음 공정 진입 금지 |

> **두 가지 짚어둘 것.**

> | **W3C 시맨틱 웹 스택** (여기) | **표현 수단**의 층 — 아래가 위를 떠받친다 |
> | **Ontology Learning Layer Cake** (S03A) | **추출 공정**의 층 — Terms → … → Rules 순서로 뽑는다 |

## 8. 문제의식 — 왜 시맨틱 기술이 필요했나

**내부 저장은 MySQL의 JSON 문자열(blob)**

- MediaWiki 기반 — **백과사전 텍스트엔 적합, 데이터 분석·질의엔 부적합**
- 오류·누락·편향을 찾고 외부와 비교하려면 강력한 질의가 필수

**WMF의 선택 — RDF + SPARQL**

| | 선택지 | 결과 |
|---|---|---|
| 후보 | 자체 개발 · NoSQL | 탈락 |
| **채택** | **RDF + SPARQL** | 성숙한 시맨틱 표준 · 무료 오픈소스 도구 풍부 |

- 저장은 JSON, 공유·질의 계층은 RDF/SPARQL — **두 세계를 다리로 연결**
- **저장은 JSON 그대로, 공유·질의 계층만 시맨틱으로** (레거시를 안 건드리는 현실적 선택)

## 9. Wikidata의 데이터 모델

**Item과 Property가 모두 1급 객체 + 전역 ID (언어 중립적)**

| 주어 | 속성 | 목적어 |
|---|---|---|
| Germany (**`Q183`**) | speed limit (**`P3086`**) | 100 km/h |

- `Q183`(Germany), `P3086`(speed limit) — **Property도 자체 문서 페이지를 가진다**
- 각 항목은 언어별 **Label · Description · Also known as**를 가짐
  - Q183 → 한국어 라벨 "독일", 설명 "중앙유럽의 국가", 별칭 "도이칠란트 · 독일연방공화국"
  - P3086 → 한국어 라벨 "제한 속도", 별칭 "속도 제한 · 최대속도 · 최고 속도"

> **Property가 1급 객체라는 게 요점이다.** 전역 ID가 언어 중립적이라
> "제한 속도"와 "speed limit"이 같은 `P3086`을 가리킨다.
>
> [S04-1 2.5절](S04-1-OTKM이-정하지-않은-것들.md)에서 SKOS가 하던 일 — **대표 이름 하나 + 다른 이름들** — 을
> Wikidata는 별도 층으로 얹지 않고 **데이터 모델 자체에 넣었다.** ID는 `Q183`, 사람이 읽는 이름은 라벨.
> 명장 어휘가 여섯 갈래로 흩어지던 문제를 구조적으로 막는 방식이다.

## 10. Requirements ① — 트리플 하나로 안 되는 정보

**복합 값 (compound value)**

- `100 km/h` = 숫자 100 + 단위 km/h → **단순 리터럴이 아님**

**한정어 (Qualifier) — '문장에 대한 문장'**

- 독일 속도제한 100은 조건이 붙음: **"정착지 밖 포장도로에서만 유효"** (`P3005`)

→ **메타 정보를 담을 구조가 필요함**

## 11. Requirements ② — 내장 주석 (Reference & Rank)

| | **Reference (출처)** | **Rank (순위)** |
|---|---|---|
| 무엇 | 각 문장이 **하나 이상의 출처**를 가짐 | `preferred` / `normal` / `deprecated` |
| 용도 | 문헌 정보 · 참조 URL 등 | 여러 값 중 **무엇을 쓸지 필터링** |

- 인구는 연도별 여러 값 → **최신값을 `preferred`로 표시**
- "명왕성은 행성"처럼 틀린 문장 → **`deprecated`로 남겨둠**

> `deprecated`로 **남겨둔다**는 게 핵심이다. 틀린 문장을 지우지 않는다.
> 과거에 그렇게 알려졌다는 사실 자체가 정보이고, 지우면 "왜 이 값이 없지"라는 재입력이 반복된다.

## 12. Reification (구체화)

> **문장 자체를 노드로 만들고, 조건·출처·순위를 거기에 매단다**
> → 하나의 속성이 **여러 RDF 속성으로 분화**

| 접두사 | 잇는 것 |
|---|---|
| `wdt:P3086` | **단순화된 값 직접 연결** (최고 rank만) → 쉬운 질의 |
| `p:P3086` | 주어 → **문장 노드** (조건·출처 접근 통로) |
| `psv:P3086` | 문장 노드 → **완전한 복합 값** |
| `pq:P3005` | 문장 노드 → **한정어(조건)** |
| `prov:wasDerivedFrom` | 문장 노드 → **출처** |

| 출발 | 경로 | 도착 | 용도 |
|---|---|---|---|
| Germany | `wdt:P3086` | 100 | 단순 값 — **쉬운 질의** |
| Germany | `p:P3086` | **문장 노드** (statement node) | 조건·출처 접근 통로 |
| 문장 노드 | `psv:` | 값노드 [100 + km/h] | 완전한 복합 값 |
| 문장 노드 | `pq:` | 조건 (P3005) | 한정어 |
| 문장 노드 | `prov:` | 출처 | reference |

**같은 사실에 두 경로가 난다** — `wdt:`로 바로 값에 닿거나, `p:`로 문장 노드를 거쳐 조건·출처까지 가거나.

## 13. 쉬운 건 쉽게, 복잡한 건 가능하게

- **단순 질의는 `wdt:` 만 사용** — 요약값만 빠르게, 복잡한 인코딩을 무시할 수 있음
- **정밀 질의는 `p:` / `psv:` / `pq:` 까지** — 조건·출처·복합값 전체를 파고들 수 있음

> 같은 사실을 **두 벌로 저장**한다는 뜻이다. Summary 2번이 이를 **"중복을 감수하고 유연성 확보"**라고
> 명시한다. 정규화 원칙을 의도적으로 깨는 설계이고, 깨는 대가로 얻는 게
> **"초심자도 쓸 수 있는 질의"**다. 20절 Lessons의 `Merging Views in RDF`가 같은 말이다.

| 구간 | 응답 시간 |

## 18. 사용 로그 분석 — Robotic vs Organic

| **Robotic (로봇형)** | **Organic (유기형)** |
|---|---|
| **소수 소스**의 **대량** 트래픽 | **다수 소스**의 **소량** 트래픽 |
| 봇 · 스크립트 | → **진짜 사람의 정보 요구** |

> **진짜 사람(Organic) 쿼리 비율 = 0.6%**

- **구분 없이 분석하면** — 진짜 사용자 니즈가 봇 트래픽에 **완전히 묻힘**
- **봇 하나가 통계를 좌우** — "auxiliary matcher" 봇: **2,040만 → 540만 건**으로 급변
- 예를 들면 — **MES 로그도 자동 스크립트 / 사람 조회를 분리해야 진짜 패턴이 보임**

### 18.1 SPARQL 기능 사용 패턴

여섯 구간(I1~I6)에서 측정한 기능별 사용률(%). 두 집단이 갈리는 항목만 추리면 이렇다.

| 기능 | Organic | Robotic | |
|---|---|---|---|
| `DISTINCT` | 18.7 ~ 64.2 | 4.2 ~ 15.0 | **사람 우세** |
| `OPTIONAL` | 40.4 ~ 56.5 | 11.3 ~ 29.7 | **사람 우세** |
| `ORDER BY` | 12.8 ~ 46.5 | 6.8 ~ 17.8 | **사람 우세** |
| `LIMIT` | 31.2 ~ 51.5 | 11.5 ~ 21.5 | **사람 우세** |
| `Subquery` | 0 ~ 13.3 | 0 ~ 0.34 | **사람 우세** |
| `GROUP BY` | 5.1 ~ 19.9 | 0.2 ~ 0.5 | **사람 우세** |
| `Service lang` | 40.5 ~ 55.0 | 4.3 ~ 9.4 | **사람 우세** |
| `VALUES` | 3.0 ~ 11.0 | 11.9 ~ 36.7 | **봇 우세** |
| `BIND` | 4.0 ~ 9.9 | 9.6 ~ 23.0 | **봇 우세** |
| `UNION` | 1.9 ~ 12.8 | 7.6 ~ 18.9 | **봇 우세** |
| `JOIN` | 82.5 ~ 91.7 | 61.2 ~ 88.3 | (둘 다 높음) |

| | 쓰는 기능 | 성격 |
|---|---|---|
| **Organic (사람)** | LIMIT · DISTINCT · OPTIONAL · ORDER BY · 서브쿼리 · 집계 | **탐색적 · 분석적** |
| **Robotic (봇)** | BIND · UNION · VALUES | **정형화된 배치 요청** |
