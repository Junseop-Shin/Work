## 1. 역량 질문(CQ)이 왜 설계의 출발점인가

온톨로지를 만들 때 "무엇을 클래스로 둘 것인가"부터 시작하면 끝이 없다. 세상의 모든 것을 담을
수는 없으니 **어디서 멈출지를 정해줄 기준**이 필요하다.

CQ가 그 기준이다. 완성된 온톨로지가 답해야 하는 질문 목록을 먼저 쓰면, 그 질문에 답하는 데
필요한 개념만 남는다.

```
CQ  "어떤 모델 아키텍처를 사용했는가?"
      → 클래스 Model 이 필요하다
      → 관계 hasArchitecture 가 필요하다
      → 그 질문에 안 쓰이는 개념은 넣지 않는다
```

쓰임이 하나 더 있다. **구축이 끝난 뒤 검증 기준이 된다.** 만든 온톨로지로 40개 CQ에 다 답할 수
있으면 설계가 요구를 충족한 것이고, 못 답하는 질문이 있으면 빠진 관계를 찾아야 한다.

이 개념은 Ch.2의 OTKM·LOT 방법론에서 이미 나왔다. S24가 새로운 것은 그 질문 목록을 사람이
아니라 LLM이 초안으로 쓴다는 점이다.

## 2. RAG — 검색해서 붙여주고 답하게 하기

Retrieval-Augmented Generation이다. 모델에게 질문만 던지는 대신, **질문과 관련된 문서 조각을
찾아 함께 넣어주고** 답하게 한다.

```
질문  →  관련 청크 검색  →  [질문 + 청크]를 모델에 입력  →  답변
```

슬라이드가 오픈북 시험에 비유했다. 모델이 외워둔 것에 의존하지 않고 주어진 자료에서 답을 찾게
만든다. 논문 본문에 흩어진 재현성 정보를 뽑는 이 과제에 맞는 방식이다.

**청킹(chunking)**은 긴 문서를 조각으로 자르는 일이다. 모델 입력 길이에 한계가 있어서다.
이 논문은 2,500 토큰씩 자르고 **100 토큰을 겹치게** 했다. 겹치지 않으면 경계에 걸친 문장이
잘려 어느 쪽에서도 온전히 검색되지 않는다.

## 3. PROV-O와 재사용

PROV-O는 **출처(provenance)를 표현하는 W3C 표준 온톨로지**다. "누가/무엇이 이 결과를
만들었는가"를 기술한다. `Entity`(산출물), `Activity`(활동), `Agent`(행위자) 세 축이 기본이다.

딥러닝 재현성과 잘 맞는다. 데이터셋이 Entity, 학습이 Activity, 연구자나 소프트웨어가 Agent다.

**재사용을 지시한 이유**는 온톨로지의 기본 원칙이기 때문이다. 같은 뜻의 클래스를 각자 새로
만들면 서로 다른 KG가 연결되지 않는다. 표준을 상속하면 다른 시스템과 자동으로 이어진다.

이 논문의 결과가 그래서 뼈아프다. 지시했는데도 클래스 3개만 연결했고 객체 속성은 0건이다.

## 4. Mixtral 8x7B와 Mixture-of-Experts

**MoE(Mixture-of-Experts)**는 여러 개의 전문가 네트워크를 두고 입력에 따라 일부만 켜는 구조다.

```
Dense 모델   입력 하나에 전체 파라미터가 다 계산된다
MoE 모델     전문가 8개 중 2개만 켜진다 → 총 파라미터는 크지만 계산은 적다
```

Mixtral 8x7B는 7B 전문가 8개를 두고 토큰마다 2개를 쓴다. 총 파라미터는 약 47B인데 실제 계산은
13B 수준이다. **GPU 한 장에서 큰 모델의 품질을 내려는 선택**이고, 이 논문이 A100 한 장으로 전
파이프라인을 돌릴 수 있었던 이유다.

## 5. temperature와 결정적 출력

생성 모델이 다음 토큰을 고를 때 확률분포를 얼마나 평평하게 만들지를 정하는 값이다.

| temperature | 결과 |
|---|---|
| 높다 (1.0 이상) | 낮은 확률 토큰도 자주 뽑힌다. 다양하지만 불안정하다 |
| 낮다 (0에 가깝다) | 항상 최고 확률 토큰을 뽑는다. 사실상 결정적이다 |

이 논문은 1e-5를 썼다. **같은 입력에 같은 출력이 나오게 하려는 것**이고, 재현성을 다루는
논문이라 일관된 선택이다.

그런데도 프롬프트를 조금 바꾸면 결과가 크게 달라졌다(본편 15절). temperature를 낮춰도 프롬프트
민감성은 남는다는 뜻이다.

## 6. Judge LLM — LLM이 LLM을 채점한다

생성 결과를 사람이 다 볼 수 없을 때, **다른 LLM에게 채점을 시키는 방식**이다. LLM-as-a-judge라
부른다.

이 논문의 설계는 이렇다.

1. 사람 전문가가 논문 5편에 대한 정답을 작성한다
2. Judge LLM이 정답과 생성 답변의 일치도를 0~10점으로 매긴다
3. 6점 이상 Right, 3~6점 Partial, 3점 미만 Wrong으로 접는다

**핵심은 정답을 사람이 만든다는 것이다.** Judge는 채점만 한다. 그래도 사람과 21% 불일치가
났고, 대부분 사람이 `Partial`로 준 것을 Judge가 `Wrong`으로 깎은 경우였다.

## 7. Right / Partial / Wrong 세 단계 척도

이진(맞다/틀리다)이 아니라 셋으로 나눈 이유는 생성 답변이 대개 **부분적으로 맞기** 때문이다.
하이퍼파라미터 다섯 개 중 셋만 맞힌 답을 틀렸다고 하면 정보가 사라진다.

다만 세 단계는 경계가 흐리다. 6점과 3점이라는 절단선이 자의적이고, 사람과 Judge가 엇갈리는
지점도 대부분 `Partial` 근처였다.

## 8. RDF와 Turtle

**RDF**는 지식을 `주어–서술어–목적어` 트리플로 적는 W3C 표준 데이터 모델이다. **Turtle**은 그
RDF를 사람이 읽기 쉽게 적는 문법이다.

```turtle
dlprov:DataFormat_1   rdfs:label   'Audio Spectrogram' .
```

`접두사:이름` 형태는 긴 URI를 줄여 쓴 것이다. 문장 끝의 마침표가 트리플 하나의 끝이고,
세미콜론은 같은 주어를 이어 쓸 때, 쉼표는 같은 주어·서술어에 목적어를 여럿 붙일 때 쓴다.

본편 11절의 예시에서 `DeepLearningPipeline1`이 `hasDataFormat`으로 두 개의 값을 갖는 것이
쉼표로 표현돼 있다.

## 9. DLProv — 이 논문이 만든 온톨로지

이름이 DL(딥러닝) + Prov(provenance)다. 딥러닝 파이프라인의 출처 정보를 담는 온톨로지이고,
PROV-O를 상속하려 한 결과물이다.

규모는 클래스 45개, 객체 속성 41개, 공리 365개다. 공리 수가 클래스 수보다 훨씬 많은 것은
domain·range 선언이 관계마다 붙기 때문이다.

## 10. 재현성(reproducibility)이 왜 KG 문제인가

같은 논문을 읽고 같은 결과를 다시 만들려면 모델·아키텍처·하이퍼파라미터·데이터 출처·실행
환경을 알아야 한다. 이 정보가 논문 본문에 흩어져 있고 표기도 제각각이다.

구조화해서 KG로 넣으면 **검색·비교·검증이 질의 한 번**이 된다. "이 데이터셋을 쓴 논문들이
어떤 학습률을 썼나"를 물을 수 있다.

즉 이 논문의 KG는 지식 자체가 목적이 아니라 **연구 메타데이터의 색인**에 가깝다. 우리 실무
과제의 KG(설비·증상·부품)와는 성격이 다르다는 점을 감안하고 읽어야 한다.
