## 이 부록의 요지

강의는 두 논문을 **"온톨로지 활용의 양 극단"**으로 놓는다. 그런데 읽고 나면 축이 하나가 아니다.

- **MANUMATE는 온톨로지를 *만드는* 방법**이 구체적이다 — 참조 → 특수화 → 응용
- **Wikidata는 만들어진 그래프를 *굴리는* 방법**이 구체적이다 — 저장 · 공개 · 질의 · 로그

**즉 대립이 아니라 앞뒤다.** 이렇게 놓으면 우리 과제에 그대로 이어붙일 수 있다 —
**MANUMATE 구조로 만들고, Wikidata 방식으로 굴린다.** 4절이 그 흐름을 RDF 파이프라인으로 압축한다.

## 1. 비교표를 다시 놓기

[S05B 18절](S05B-MANUMATE-제조-상호운용성.md)의 종합 비교표는 일곱 행을 같은 축에 세운다.
그런데 **비교가 성립하는 행과 애초에 대상이 아닌 행이 섞여 있다.**

| 비교표의 행 | 실제로 | |
|---|---|---|
| 핵심 기술 (`RDF reification·SPARQL` vs `OWL+SWRL·Pellet`) | **비교 성립** | 같은 문제(표현력)에 다른 답 |
| 온톨로지 (넓고 얕음 vs 좁고 깊음) | **비교 성립** | 공리 밀도의 차이 |
| 생명주기 (영속 vs 일회성) | **층이 다름** | Wikidata는 그래프 전체, MANUMATE는 **응용 온톨로지 층만**. MANUMATE의 참조 온톨로지는 영속이다 |
| 설계 목적 (공유·질의 vs 시스템 통합) | **단계가 다름** | 하나는 굴리는 목적, 하나는 만드는 목적 |
| 거버넌스 (개방 대중 vs 폐쇄 전문가) | **비교 무의미** | 위키 프로젝트와 공장을 같은 축에 못 올린다 |
| 성숙도 (실서비스 vs PoC) | **비교 무의미** | 2018년 운영 보고서와 2022년 개념 증명 |

그래서 이렇게 다시 놓는 게 맞다.

| | **MANUMATE** | **Wikidata** |
|---|---|---|
| 답하는 질문 | **어떻게 만드나** | **어떻게 굴리나** |
| 다루는 구간 | 설계 → 인스턴스 생성 → 시스템 분배 | 저장 → 공개 → 질의 → 로그 분석 |
| 검증 수단 | Pellet 일관성 추론 (**만들 때**) | 타임아웃·쿼터·캐시 (**굴릴 때**) |
| 우리가 가져갈 것 | 2절 | 3절 |

## 2. MANUMATE에서 가져올 것 — 만드는 방법

### 2.1 참조와 응용을 2층으로 가른다

이게 이 논문에서 제일 실용적인 결정이다.

| 층 | 수명 | 유지보수 대상인가 |
|---|---|---|
| **참조 온톨로지** (Product · Process · Materials) | **영속** | **예** — 여기가 자산이다 |
| **응용 온톨로지** (제품/Lot 하나) | **일회용** | 아니오 — 만들고 버린다 |

원논문이 응용 온톨로지의 수명을 명시한다.

> "this application ontology is singular and should be created as soon as the necessity to make
> a product arises. … as soon as the product's manufacturing is done, **it should be destroyed**."

**`destroyed`** — 비활성이 아니라 파괴다. 여기에 실무 문제가 하나 걸린다.
**불량 분석은 사후에 일어난다.** 출하 3개월 뒤 클레임이 오면 그 Lot이 어떤 조건으로 만들어졌는지
되짚어야 하는데, 파괴됐으면 재구성해야 한다. 원논문은 이 문제를 다루지 않는다.

> **우리는 "파괴" 대신 "동결"로 간다.** 출하 시점에 활성 그래프에서 내리되 스냅샷은 남긴다.
> [S04 6.5절](S04-온톨로지-엔지니어링-방법론.md)의 진화 절차가 "새 버전으로 전환"이라고 한 것과 같은 발상이다.

### 2.2 검증을 만드는 시점에 건다

Pellet 일관성 추론이 걸리는 자리는 **응용 온톨로지가 만들어지는 순간**이다 — 적재 후가 아니다.
"부식방지 코팅인데 일반 PE 지정" 같은 모순을 **생산 지시가 내려가기 전에** 잡는다.

우리 파이프라인에는 SHACL이 이미 있는데, **둘은 하는 일이 다르다.**

| | 무엇을 보나 | 언제 |
|---|---|---|
| **Pellet** (추론기) | **논리적 모순** — 공리끼리 충돌하는가 | 응용 온톨로지 생성 직후 |
| **SHACL** | **형태 제약** — 필수 필드, 카디널리티, 값 범위 | RDF 적재 직전 |

둘 다 필요하다. SHACL은 "빠진 게 있나"를 보고, Pellet은 "말이 되나"를 본다.

### 2.3 다중 상속이 필요한 자리를 인정한다

`PrintedReel`은 **인쇄의 산물(Product)이면서 커팅의 원료(Material)**다.
제조에서 중간 산출물은 거의 항상 이렇다 — 증착 웨이퍼가 곧 다음 공정 투입물이다.

관계형 스키마라면 테이블을 쪼개거나 플래그 컬럼을 둬야 하는 자리이고,
**OWL을 쓸 실질적 이유 중 하나가 여기다.** 원논문의 구현 노트도 같은 말을 한다 —
Python 인스턴스는 한 클래스에만 속하지만 온톨로지 개체는 여러 클래스에 동시에 속한다.

### 2.4 다만 — "암묵지의 명시화"는 강의자의 프레이밍이다

[S05B 13절](S05B-MANUMATE-제조-상호운용성.md) 케이스 A에 붙은 **"핵심 — 암묵지의 명시화"**는
슬라이드의 표현이고, **원논문에는 'tacit knowledge'라는 말이 한 번도 나오지 않는다.**

원논문은 참조 온톨로지를 **어떻게 만들었는지도 쓰지 않는다.** 인터뷰·워크숍·전문가 도출 절차가 없고,
누가 모델링했는지도 밝히지 않는다. 참조 온톨로지에 대해 논문이 하는 말은 사실상 이것이다.

> "The reference ontologies are **the starting point** of the MANUMATE framework."

**출발점** — 그 앞은 범위 밖이라는 선언이다. 논문이 그 자리에서 실제로 쓴 문장은
"이 층의 기능은 전적으로 관리자와 작업자에게 맡겨져 있고, 이를 돕는 자동화나 지능이 없다"까지다.

> 프레이밍이 틀렸다는 게 아니다. 우리 도메인에 붙이기 좋게 만든 해석이고, 실제로 유용하다.
> 다만 **인용할 때 출처를 갈라야 한다** — 그리고 "그럼 그 명시화는 누가 하나"라는 질문은
> 이 논문에서 답을 못 얻는다.

## 3. Wikidata에서 가져올 것 — 굴리는 방법

### 3.1 값이 아니라 '문장'을 저장한다

MANUMATE의 값은 **단언**이다 — `has_offset: 5`, `has_pe_type: anti_corrosive`.
참이라고 전제된 값 하나가 슬롯에 들어간다. **설비 파라미터에는 이견이 없으니 이걸로 충분하다.**

사람의 판단은 다르다. 조건부이고, 출처가 있고, 서로 충돌한다.
Wikidata는 이걸 담는 장치를 데이터 모델에 이미 넣어뒀다.

| 장치 | 원논문의 정의 | 우리 쪽 쓸모 |
|---|---|---|
| **Qualifier** | 문장 자체를 주어로 삼는 보조 속성-값 쌍 (독일 속도제한 100 + `valid in place`) | 명장 지식은 거의 항상 조건부다 — "이 소리 나면 베어링"에 "**부하 80% 이상일 때**"가 숨어 있다 |
| **Reference** | 각 문장이 갖는 하나 이상의 출처 (문헌 속성 또는 URL) | **누가 말했나**. 30년차와 3년차의 판단은 무게가 다르다 |
| **Rank** | `normal`(기본) / `preferred` / `deprecated` — 한 속성에 문장이 여럿일 때의 필터 | 판단이 갈릴 때 하나를 preferred로. **틀린 것도 지우지 않고 deprecated로 남긴다** |

원논문의 rank 설명이 그대로 우리 상황이다 — *"도시는 시점별 인구 값이 여럿이고 최근 것이 preferred다.
`deprecated`는 틀렸거나 부적절한 문장을 **기록해두기 위해** 쓴다(명왕성은 행성)."*
**시점별로 값이 여럿이고 그중 하나를 고른다** — 공정 조건이 바뀌며 노하우가 갱신되는 것과 같은 구조다.

**단, 천장이 하나 있다.** 원논문이 한 줄로 못박는다.

> "**Nesting of annotations is not possible, i.e., qualifiers cannot be qualified further.**"

| 층 | 지식 | 표현 |
|---|---|---|
| 문장 | "이 소리가 나면 베어링 이상" | ✅ statement |
| 조건 1 | "부하 80% 이상일 때" | ✅ qualifier |
| **조건 2** | "단, 신품 교체 후 100시간 이내면 정상" | ❌ **qualifier에 qualifier를 못 단다** |

조건을 평평하게 펴서 나열하거나(조건 간 논리 관계가 사라짐) 문장을 쪼개야 한다. 어느 쪽이든 손실이 있다.

### 3.2 쉬운 경로와 정밀 경로를 함께 깐다 — 실제로 10%가 썼다

같은 사실에 두 경로를 낸다. `wdt:`로 값에 바로 닿거나, `p:`로 문장 노드를 거쳐 조건·출처까지 가거나.
중복이지만 의도된 중복이고, 원논문이 근거를 댄다.

> "this encoding … leads to graphs with many, sometimes redundant triples. This design is meant to
> simplify query answering, … **allowing queries to be as simple as possible and as complicated as needed**."

그리고 **그 설계가 실제로 쓰였다.**

> "**Almost 10% of the queries we analysed for 2018 are using an RDF property that is part of
> the more complex, reified statement encoding.**"

| | 비율 |
|---|---|
| 단순 경로(`wdt:`)로 끝나는 질의 | 약 90% |
| 정밀 경로(`p:`/`psv:`/`pq:`)까지 가는 질의 | **약 10%** |

> **판단 기준이 여기서 나온다** — 조건·출처가 필요한 지식이 전체의 10% 수준이어도 구조를 갖출 값어치가 있다.
> 단, **나머지 90%가 그 복잡도를 무시하고 지나갈 수 있어야 한다.** `wdt:`를 따로 둔 이유가 그것이다.

참고로 `wdt:`가 고르는 기준은 슬라이드보다 원문이 정확하다 —
*"the **highest rank among all statements for the same Wikidata property and subject**"*.
전역 기준이 아니라 **주어-속성 쌍 단위**로 최고 rank다.

### 3.3 로그를 봇/사람으로 가른다

Wikidata에서 사람 질의는 전체의 **0.6%**였다. 안 가르면 진짜 니즈가 봇 트래픽에 묻힌다.
논문의 분류 기준은 단순하다 — **소수 소스의 대량 트래픽 = 봇, 다수 소스의 소량 트래픽 = 사람.**

우리 쪽도 같다. **MES·SPARQL 조회 로그에서 자동 스크립트와 사람 조회를 분리해야**
"현장이 실제로 무엇을 궁금해하는지"가 보인다. 그게 다음 CQ의 원천이 된다.

### 3.4 운영 안전장치는 그대로 베낀다

6대 머신으로 월 1억 쿼리를 받은 구성이다. 규모는 다르지만 장치는 그대로 쓸 수 있다.

| 장치 | 값 |
|---|---|
| 쿼리 타임아웃 | 60초 |
| 클라이언트당 동시 쿼리 | 5개 |
| 자원 배분 | token bucket |
| 캐시 | 5분 (같은 요청 재처리 안 함) |

## 4. 합치면 — RDF 파이프라인 압축 요약

**MANUMATE 구조로 만들고, Wikidata 방식으로 굴린다.** 우리가 이미 가진 스택
(RML → SHACL → GraphDB → SPARQL) 위에 두 논문의 결정을 얹으면 이렇게 된다.

### 4.1 설계 시점 — 한 번 만들고 계속 고친다

| 단계 | 하는 일 | 도구 | 출처 |
|---|---|---|---|
| **① 참조 온톨로지** | 제품 · 공정 · 재료의 **틀**만. 구체값 없음 | OWL | MANUMATE |
| **①' 어휘 스킴** | 명장 어휘를 `prefLabel`/`altLabel`로 묶기 (웅웅거림 = 베어링 이상음) | SKOS | [S04-1 2.5절](S04-1-OTKM이-정하지-않은-것들.md) |
| **② 요구사항** | 공정 제약 · 품질 표준 · **가용 설비(MES 실시간)** · 제품군 · 고객 요구 | — | MANUMATE |

**여기까지가 영속 자산이다.** 유지보수 책임자가 붙는 곳도 여기다.

### 4.2 Lot 시점 — 매번 만들고 버린다

| 단계 | 하는 일 | 도구 |
|---|---|---|
| **③ 특수화** | 참조 + 요구사항 → **Lot 하나의 응용 온톨로지** 생성 | Owlready2 |
| **④ 일관성 검증** | 논리적 모순 사전 차단 (생산 지시 전) | **Pellet** |
| **⑤ RDF 적재** | 정형 소스 매핑 → 형태 검증 → 그래프 저장 | RML → **SHACL** → GraphDB |
| **⑥ 시스템 분배** | 응용 온톨로지를 각 시스템 언어로 번역 | split reasoning → ERP/MES/SCADA/PLC |

### 4.3 지식의 두 갈래 — 여기가 두 논문이 갈라지는 자리

같은 그래프에 들어가지만 **표현 방식이 달라야 한다.**

| 지식 | 표현 | 근거 |
|---|---|---|
| 설비 파라미터 · 공정 조건 | **단언** — `has_tool_thickness: 5` | MANUMATE |
| **사람의 판단 · 노하우** | **문장 + 주석** — qualifier(조건) · reference(출처) · rank(우선순위) | Wikidata |

### 4.4 운영 시점

| 단계 | 하는 일 |
|---|---|
| **⑦ 질의** | 단순 경로(`wdt:` 상당)와 정밀 경로(`p:` 상당)를 함께 제공 — 90%는 단순 경로로 끝난다 |
| **⑧ 로그 분리** | 봇/사람 구분 → 사람 질의에서 다음 CQ를 뽑는다 |
| **⑨ 동결** | 출하 시 응용 온톨로지를 활성에서 내리되 **스냅샷 보존** (사후 불량 분석용) |
| **⑩ 진화** | 현장 제안 → 지정 담당자 판정 → 참조 온톨로지 갱신 → ①로 |

### 4.5 한 줄로

```
[영속]  참조 온톨로지 + SKOS 어휘  ──┐
                                    ├─▶ ③ 응용 온톨로지(Lot) ─▶ ④ Pellet ─▶ ⑤ RML·SHACL·GraphDB
```
