## 1. 온톨로지 설계 패턴(ODP)이란

같은 상황을 모델링할 때 반복해서 쓰이는 검증된 틀이다. 소프트웨어의 디자인 패턴과 같은
발상이고, 이 회차의 평가 지표 하나가 여기에 걸려 있다.

이 논문이 드는 네 가지를 예로 풀면 이렇다.

| 패턴 | 문제 | 패턴을 쓰면 |
|---|---|---|
| Event Reification | `지급했다`를 속성 하나로 적으면 언제·왜·누구에게가 붙을 자리가 없다 | 사건을 객체(`PaymentEvent`)로 만들고 거기에 참여자·시점·금액을 건다 |
| Participation | 사람과 역할을 같은 것으로 보면 한 사람이 여러 역할을 못 가진다 | `Beneficiary`를 사람이 아니라 계약 안의 역할로 둔다 |
| Quantities | `50000`만 적으면 통화를 잃는다 | 값과 단위를 분리해 `MonetaryAmount(value, currency)`로 |
| Time Intervals | `2년간`을 문자열로 적으면 비교·계산이 안 된다 | 시작·끝이 있는 구간 객체로 |

본편 5절의 "문법은 맞는데 설계가 빈약한 온톨로지"가 이 패턴들을 안 쓴 결과다.

## 2. SRD와 TIP — 이 논문이 만든 두 산출물

이름은 논문이 붙인 것이고 표준 용어가 아니다.

| | 이름 | 무엇이 적히나 |
|---|---|---|
| SRD | Semantic Requirements Document | 이 페이지의 CQ에 답하려면 어떤 개념·관계·제약이 필요한지. 개념마다 Entity / Role / Event / State / Attribute / TimeInterval / MonetaryAmount 라벨을 붙인다 |
| TIP | Technical Implementation Plan | 코드를 쓰기 전에 확정하는 모델링 결정. 중심 개념 2~4개, 쓸 설계 패턴, 재사용할 기존 클래스 목록, CQ별 클래스 연결 |

둘의 차이가 이 논문의 핵심이다. SRD는 **무엇이 필요한가**(도메인 쪽 언어)이고 TIP은 **어떻게
만들 것인가**(온톨로지 쪽 언어)다. LLM이 둘을 섞어버리는 것이 문제라서 단계를 갈랐다.

## 3. HermiT와 OWL 추론기

HermiT는 OWL 온톨로지의 논리적 일관성을 검사하는 추론기다. 선언된 공리들이 서로 모순되는지
확인하고, 명시되지 않았지만 따라 나오는 사실을 도출한다.

여기서 하는 일은 좁다. **모순이 없는지만 본다.** 온톨로지가 쓸모 있는지, 설계가 좋은지는 판단하지
않는다. 본편 5절의 빈약한 Turtle이 문법 검사와 논리 검사를 모두 통과한다는 말이 이 뜻이다.

[S09-1](S09-1-제약처럼-보이는-공리들.md)에서 다룬 "공리는 무엇을 막고 무엇을 막지 않는가"와 같은
자리다.

## 4. RDFLib

파이썬의 RDF 처리 라이브러리다. 이 회차에서 세 곳에 쓰인다.

- Turtle 문법 검사 (파싱이 되는가)
- SPARQL 질의 실행
- 온톨로지를 방향 그래프로 바꿔 triple을 추출 (RAG 평가에서)

문법 검사와 논리 검사는 다른 층이다. 파싱이 된다고 논리가 맞는 것은 아니고, 논리가 맞다고 설계가
좋은 것도 아니다. 이 회차는 그 셋을 각각 다른 도구로 본다.

## 5. Krippendorff의 α

여러 심사자가 같은 대상을 평가했을 때 **얼마나 일치했는지**를 재는 값이다. 0이면 우연 수준이고
1이면 완전 일치다. 통상 .667 이상이면 잠정적으로 쓸 만하다고 본다.

이 회차에서는 LLM 5개를 심사자로 썼고 α가 Extensibility .784, ODP .706, Overall .755다. 다섯
모델이 대체로 같은 방향으로 채점했다는 뜻이라, 점수를 하나의 척도로 취급할 근거가 된다.

다만 α가 높다고 **채점이 옳다**는 뜻은 아니다. 다섯 모델이 같은 편향을 공유하면 일치도는 높게
나온다. 정답 온톨로지가 없다는 이 논문의 한계와 함께 읽어야 한다.

## 6. LLM-as-a-Judge를 두 번 쓴다

이 회차는 LLM 심사를 두 군데에 쓰는데 성격이 다르다.

| | 무엇을 채점하나 | 기준 |
|---|---|---|
| 설계 품질 심사 (5개 모델) | 온톨로지 구조가 좋은가 | 사람이 정한 척도 1~5점. 정답은 없다 |
| SPARQL Judge | 질의 실행 결과가 기대 정답과 맞는가 | CQ에 딸린 expected answer |

뒤쪽은 정답이 있어서 채점이 비교적 객관적이다. 앞쪽은 정답이 없고 "좋은 설계"에 대한 모델의
감각에 기댄다. 본편의 설계 품질 숫자(1.33 → 3.33)는 이 앞쪽에서 나온 값이다.

S24의 Judge LLM과 비교하면([S24-1 6절](S24-1-읽는-데-필요한-것들.md)), 거기서는 사람이 정답을
만들었고 여기서는 설계 품질 쪽에 정답이 없다.

## 7. SPARQL CQ coverage와 RAG CQ coverage

두 지표가 재는 것이 다르다.

| | 무엇을 보나 | 성격 |
|---|---|---|
| SPARQL coverage | 질의를 만들어 실행했을 때 기대 정답이 나오는가 | 엄격하다. URI와 속성 이름이 정확해야 한다 |
| RAG coverage | 필요한 노드와 연결이 검색되고 따라가지는가 | 관대하다. 이름이 조금 어긋나도 통과한다 |

본편 20절의 실패 사례가 둘의 차이를 보여준다. `hasAmount`와 `hasMonetaryAmount`를 헷갈리면
SPARQL은 빈 결과를 내지만, 임베딩 기반 검색은 두 이름을 가까운 것으로 보고 찾아낸다.

그래서 두 지표를 나란히 놓으면 **실패가 지식의 부재 때문인지 이름의 어긋남 때문인지**가
갈린다. 이것이 이 회차의 평가 설계에서 가장 잘 만든 부분이다.

## 8. BM25와 dense 검색, 그리고 하이브리드가 실패한 이유

| | 무엇으로 찾나 |
|---|---|
| BM25 | 단어가 얼마나 겹치는지. 희귀한 단어에 가중치를 준다 |
| dense (임베딩) | 의미가 얼마나 가까운지. 단어가 달라도 뜻이 비슷하면 가깝다 |

보통 문서 검색에서는 둘을 섞는 것이 낫다. 그런데 이 회차에서는 BM25를 섞을수록 나빠졌다.

이유는 검색 대상이 문서가 아니라 **온톨로지 식별자**이기 때문이다. `hasMonetaryAmount`,
`PaymentEvent` 같은 이름은 사람이 붙인 조어라 단어 빈도 통계가 의미를 담지 못한다. 흔한 접두사
`has`가 여기저기 붙어 있어 오히려 노이즈가 된다.

그래서 최종 설정은 임베딩만 쓴다. 검색 대상의 성질이 방법을 정한 사례다.

## 9. 2-hop 국소 탐색

CQ는 대개 여러 관계를 거쳐야 답이 나온다. `수익자가 받는 돈은?`에 답하려면
`PaymentEvent → hasMonetaryAmount → MonetaryAmount → hasValue`처럼 두세 단계를 따라가야 한다.

그래서 상위 k개 요소를 찾은 뒤 각 요소에서 2-hop까지 확장해 연결된 triple을 모은다. 이것을
컨텍스트 블록으로 만들어 답변 생성에 넣는다.

여기서 나오는 진단이 유용하다. **구조가 부실하면 탐색이 일찍 끝난다.** 끊긴 조각이나 얕은 별
모양(중심 노드에 속성만 잔뜩 달린 형태)이면 2-hop을 가도 새 정보가 없다. RAG 점수가 구조적
모델링의 완성도를 반영한다는 말이 이 뜻이다.

[S22 COMET의 2-hop](S22A-COMET-언어모델로-KG를-만든다.md)과 이름은 같지만 쓰임이 다르다. 거기서는
점수를 합산하는 경로였고 여기서는 컨텍스트를 모으는 범위다.

## 10. all-MiniLM-L6-v2

문장을 384차원 벡터로 바꾸는 작은 임베딩 모델이다. 6층짜리로 가볍고 빠르다.

이 회차에서는 노드와 엣지를 **각각 따로** 임베딩한다. 노드 이름(`PaymentEvent`)과 엣지
이름(`hasMonetaryAmount`)의 성격이 달라서다.

## 11. 합성 데이터를 쓴 이유

두 약관은 실제 보험사 문서가 아니라 공개된 합성 문서다. 실무 문서를 쓰면 저작권과 개인정보
문제가 걸리고, 무엇보다 **정답을 통제할 수 없다.**

대신 얻는 것이 통제다. 두 약관의 복잡성 종류를 다르게 설계해(법적 깊이 대 사건·제약의 수)
방식에 따라 어느 쪽이 유리한지를 볼 수 있다.

잃는 것도 분명하다. 합성 문서는 실제 약관보다 정돈돼 있을 가능성이 높다. 본편 23절이 "넓은
벤치마킹이 아니라 통제된 심층 진단"이라고 범위를 좁혀 적은 이유다.
