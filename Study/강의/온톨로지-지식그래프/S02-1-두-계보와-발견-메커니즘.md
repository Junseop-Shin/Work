# S02-1 — 온톨로지의 두 계보, 그리고 '발견'은 어디서 나오는가

> 2026-07-30 | 온톨로지, Palantir, Foundry, OWA/CWA, 링크예측, KG임베딩, 설계원칙

> 📖 [강의 목차/진행](README.md) · 본편: [S02 설계 원칙](S02-설계-원칙.md)

> **성격** — S02의 부록. 강의 자료에 없는 내용이며, S02 7.4절 트렌드 각주에서 갈라져 나와 대화로 정리했다.

## 왜 이 문서가 필요한가

S02 2.2절에 **Palantir**가 도입 사례로 나온다. 그리고 최근 트렌드(데이터 → 지식그래프 → LLM 연결 서비스들)도
대체로 그 계보다. 그런데 **강의가 가르치는 온톨로지는 RDF/OWL 계보**다.

같은 단어를 쓰지만 층위가 다르다. 겹쳐 읽으면 "온톨로지 지원"이라고 적힌 제품을 강의 내용대로 기대하게 되므로,
축을 먼저 분리해둔다. [S01 8.2절](S01-기본개념과-실사례.md)에서 Schema가 네 층위였던 것과 같은 성격의 정리다.

> **신뢰도 메모** — 아래 Palantir 관련 서술은 공개된 모델 구조(Object/Link/Action Type, 3계층) 기준이다.
> 내부 저장·실행 구현은 다루지 않는다.

---

## 1. Palantir Foundry 온톨로지의 구성물

| 요소 | 정체 |
|---|---|
| **Object Type** | 개체 타입. **뒷단 데이터셋(테이블)에 매핑**되고, 속성은 타입 있는 컬럼 |
| **Link Type** | 객체 타입 간 연결. FK나 조인 테이블에 가까움 |
| **Action Type** | 객체를 **변경하는 행위**. 권한 · 검증 · writeback이 붙음 |

강의가 말한 3계층(S02 2.2)이 이렇게 대응한다.

```
의미(semantic)  →  Object Type · Link Type
행동(kinetic)   →  Action Type
동적(dynamic)   →  Function · Model · Simulation
```

**핵심은 Object Type이 데이터셋에 매핑된다는 것이다.** 즉 Foundry 온톨로지는 관계형/테이블 데이터 위에 얹은
**의미 계층(semantic layer)**이다. BI 도구의 semantic layer나 DDD의 애그리게이트에 가깝고,
**논리 이론(logical theory)이 아니다.**

---

## 2. 다섯 축에서 갈린다

| | **W3C 계보** (RDF/OWL) | **Palantir 계보** |
|---|---|---|
| **정체성** | IRI — **전역 식별자** | Primary key — **인스턴스 내부** |
| **세계 가정** | OWA — 없는 건 *모르는* 것 | CWA — 없는 건 *없는* 것 |
| **새 사실의 출처** | **추론기** (선언적 axiom) | **함수 · 모델** (명령형 코드) |
| **재사용 단위** | 온톨로지 파일 import → 상속 | 자기 조직 데이터 위 자기 모델 |
| **행동** | 없음 | **있음** (Action Type) |

**1번 줄** — IRI는 "누가 발행했는지가 이름에 박혀 있다"는 뜻이다([S01 8.1](S01-기본개념과-실사례.md)).
그래서 조직을 넘어 데이터를 합칠 수 있다. PK는 그 인스턴스 안에서만 유효하다.

**2번 줄** — S01 8.2절 표와 같은 줄에 놓인다. **Palantir 온톨로지는 "제약" 쪽이고 "의미" 쪽이 아니다.**

**3번 줄이 가장 중요하다.** OWL은 선언만 하면 추론기가 도출하고 **무엇이 도출되는지는 논리가 결정**한다.
Foundry는 사람이 쓴 함수가 계산하고 **무엇이 나오는지는 코드가 결정**한다.

> 그래서 [S02 7.3절](S02-설계-원칙.md)의 **"상속한 axiom이 LLM 산출물의 채점 기준이 된다"가
> Foundry에서는 성립하지 않는다.** 채점이 추론기에서 코드 테스트로 내려간다.

**5번 줄** — 전통 온톨로지에 없던 층이다. 에이전트가 온톨로지를 쓰려면 필요해진다(→ 5절).

---

## 3. 왜 다른가 — 목적이 다르다

이게 전부다.

```
W3C 계보        목적 = 조직을 넘는 의미 공유
                → 그래서 IRI · OWA · 표준 형식 · 상속

Palantir 계보   목적 = 한 조직 안의 의사결정과 행동
                → 그래서 PK · CWA · 자체 형식 · 행동 계층
```

Gruber가 온톨로지의 목적을 **'지식 공유/재사용'**으로 뒀다([S02 4.3](S02-설계-원칙.md)).
Palantir 온톨로지의 목적은 그게 아니다. **남의 Foundry 온톨로지를 import하는 개념이 제품 구조상 없다.**

---

## 4. Gruber 5원칙으로 재보면 4 대 1로 갈린다

| 원칙 | Palantir 계보 |
|---|---|
| Clarity | 지킨다 |
| Coherence | 지킨다 |
| Extendibility | 지킨다 |
| Minimal ontological commitment | 지킨다 |
| **Minimal encoding bias** | **정면 위반** — 벤더 종속이 극단적 |

**5원칙 중 4개는 계보와 무관하게 유효하고, 최소 인코딩 편향만 갈린다.**

S02 4.8절 표의 그 칸이 "표준 형식(RDF/OWL)으로 작성 → 특정 벤더·툴에 종속되지 않고 시스템 간 그대로 주고받음"이라고
적혀 있다. 그게 정확히 Palantir가 포기한 항목이다.

**그리고 포기한 게 실책이 아니다.** 목적이 조직 밖 공유가 아니므로 그 원칙의 값이 낮다.
Gruber 자신의 기준("'참인가'가 아니라 '목적에 맞게 잘 만들었는가'", S02 4.1)을 **Gruber의 원칙 자체에 적용한** 셈이다.

### 4.1 Min encoding bias의 원래 뜻 — 흔히 혼동되는 지점

이 원칙은 **크기나 범위와 아무 상관이 없다.** 표기 방식이 개념 정의를 오염시키지 않게 하라는 뜻이다.

증거가 강의 자료 안에 있다. [S02 4.6절](S02-설계-원칙.md) **v1이 물리량의 크기를 `double-float`으로 못박은 것**,
그게 인코딩 편향 위반의 교과서적 예다. 개념(크기)을 정의하면서 구현 형식(부동소수점)을 끌고 들어왔다.

| 자주 섞이는 것 | 실제로 해당하는 원칙 |
|---|---|
| "어떻게 적을지가 개념을 정하면 안 된다" | **Minimal encoding bias** |
| "어떤 관계가 나올지 모르니 제약을 적게 걸고 열어둔다" | **Minimal ontological commitment** |

둘 다 "최소"로 시작해서 붙어 다니지만, 앞은 **표기 중립성**이고 뒤는 **정의 범위**다.

그리고 Palantir가 크게 만드는 목적도 **발견이 아니라 도달범위**다. 한 화면에서 판단하고 조치까지 하려면
ERP·CRM·SCM이 다 붙어 있어야 한다(S02 2.2). **크기는 목적이 아니라 결과다.**

## 5. LLM 가드레일에 대한 두 답

S02 3절이 "잘 정의된 온톨로지 = 의미 제어 계층 = 가드레일"이라고 했다. 두 계보의 메커니즘이 다르다.

| 계보 | 어떻게 막나 |
|---|---|
| **W3C** | axiom + 추론기. 모순되는 결론이 도출되면 잡힌다 → **의미로 막는다** |
| **Palantir** | Action Type의 권한 · 검증. 에이전트가 할 수 있는 **행위 자체를 열거**하고 그 밖은 막는다 → **행위로 막는다** |

Palantir의 AI 플랫폼이 LLM 에이전트에게 주는 도구가 곧 Action Type이다.

S02 1.3절의 "자율성이 높아질수록 리스크가 증폭된다"에 대해 두 계보가 서로 다른 답을 낸 것이고,
**둘은 배타적이지 않다.** 의미로 걸러진 다음 행위로 한 번 더 좁히는 게 자연스럽다.

## 6. '발견'은 세 층에서 나온다

"온톨로지/KG를 쓰면 생각지 못한 새 관계를 찾을 수 있다"는 말은 세 가지 서로 다른 메커니즘을 뭉갠 것이다.

| 메커니즘 | 어디서 | 나오는 것 | 성격 |
|---|---|---|---|
| **추론 (deduction)** | axiom + 추론기 (W3C) | 논리적으로 **이미 함축된** 것 | 엄밀함. 새롭지만 "생각지 못한" 건 아니다 |
| **링크 예측** | KG 임베딩 · GNN | **통계적으로 그럴듯한** 새 관계 | 틀릴 수 있음. 진짜 발견은 여기 |
| **탐색적 조회** | 사람이 그래프를 돌아다님 | 사람의 발견 | Palantir UI의 강점 |

**Palantir 계보에서는 첫 번째가 없다.** CWA + 명령형 함수이므로 **선언하지 않은 관계가 자동으로 도출되지 않는다.**
Link Type은 사람이 정의한다. 기계가 "이런 관계도 있네"를 내놓는 장치가 온톨로지 층에 없고,
발견은 세 번째(사람의 탐색)로 처리된다.

**"생각지 못했던 새 관계"는 두 번째다.** 그리고 그게 강의 **Ch.5(S13~S16)** 이다 —
TransE · DistMult(S13), R-GCN · CompGCN(S14). 37세션 중 4개가 배정돼 있고 S17에서 PyKEEN으로 실습한다.

> **목차가 발견을 별도 축으로 두고 있다는 게 정보다.** 설계(Ch.2)와 추론(OWL)으로는 안 되는 일이라서
> ML/DL 챕터가 따로 있는 것이다. 온톨로지 설계를 잘하면 발견이 딸려온다는 그림이 아니다.

## 7. 목적에 따라 원칙의 균형점이 이동한다

6절의 세 메커니즘 중 무엇을 노리느냐에 따라 설계가 반대 방향으로 간다.

```
발견이 목적   →  제약을 적게 (Min. commitment 강하게)
                 예측할 여지가 남아야 링크 예측이 값을 낸다

검증이 목적   →  axiom을 촘촘히
                 단, 촘촘하면 예측할 게 없어진다 (이미 다 함축돼 있으므로)
```

같은 그래프에 axiom을 다 걸어버리면 링크 예측 모델이 배울 여지가 줄어든다.
반대로 비워두면 [S02 7.3절](S02-설계-원칙.md)에서 말한 **채점 기준이 사라진다.**

**S02 4.5절의 "4 대 1 줄다리기"가, 목적에 따라 어디서 멈추느냐의 문제로 나타나는 셈이다.**

이건 자료에 없는 추론이므로 **Ch.5 회차에서 실제로 그런지 확인할 것.**

## 8. 실무 체크리스트

**1. [S02 7.1절](S02-설계-원칙.md)의 상속 논지는 W3C 계보에서만 성립한다.**

"대부분 분야엔 이미 온톨로지가 있어서 상속하면 싸다"는 BFO·IOF·SOSA를 import하는 얘기다.
Palantir 계보에는 import할 대상이 없다. 그쪽 비용 구조는 **데이터 통합 비용**이고 온톨로지 설계 비용이 아니다.

**2. 제품이 어느 계보인지는 세 개로 판별된다.**

| 확인할 것 | 아니라면 |
|---|---|
| 식별자가 **IRI**인가 | 조직 밖과 합칠 수 없다 |
| **추론기**가 있는가 | axiom은 문서용 주석에 그친다 |
| **표준 온톨로지를 import**할 수 있는가 | 상속으로 비용을 줄일 수 없다 |

셋 다 아니면 그건 온톨로지가 아니라 **그래프 모양의 데이터 모델**이다. 그것도 유용하지만 기대치를 조정해야 한다.
