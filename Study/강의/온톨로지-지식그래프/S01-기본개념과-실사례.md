## 한 줄 요약

온톨로지는 **"무엇이 존재하고 그것들이 어떤 관계인가"를 규정한 설계도**이고, 지식그래프는 그 설계도로 지은
구현물이다. 온톨로지 없이도 그래프는 만들 수 있지만, 온톨로지가 있어야 **개념과 용어가 통일된** 그래프가 된다.
DB·데이터 사전·분류 체계가 각각 못 하는 것 — 관계의 의미, 항목 간 연결, 영역 간 의미적 연결 — 을 채우는 게
온톨로지의 자리다.

## 1. 온톨로지란

**Ontology = Ontos(존재) + Logia(사고, 학문)**

- 객체가 세계관 속에서 **어떤 특성**을 갖고 **어떤 관계**를 맺으며 존재하는지를 파악하는 것
- 특정 분야에서 정의되는 **개념과 유형들의 속성과 관계를 나타내는 지도**

핵심은 "지도"다. 실제 데이터가 아니라, 데이터가 놓일 자리와 그 자리들 사이의 길을 미리 규정한다.

**연관 개념** — Semantic Web · Knowledge Graph · Schema · Taxonomy · Thesaurus

자료는 이 다섯 개를 나열하고 넘어간다. Knowledge Graph는 3절, Taxonomy·Thesaurus는 4절에서 다루고,
**Semantic Web과 Schema는 자료에 설명이 없어** 부록에서 자리를 세웠다 →
[S01-1 연관 개념의 층위](S01-1-연관-개념의-층위.md)

## 2. 기본 구성 요소

| 요소 | 영어 | 설명 |
|---|---|---|
| 개체 | Instance, Individual | 사물이나 개념의 구체물 또는 구현물 |
| 범주 | Class, Category | 사물이나 개념 등에 붙이는 이름 |
| 속성 | Attribute, Property | 범주나 객체의 특정한 성질 |
| 관계 | Relation | 범주–범주 또는 객체–객체 간 관계 |

범주와 개체의 구분이 헷갈리기 쉽다. `자동차`는 범주, `내 차(2020년식 아반떼 12가3456)`는 개체다.
**관계가 범주 수준에서도 객체 수준에서도 성립한다**는 점이 중요하다 — 범주 간 관계가 곧 설계 제약이 되고,
객체 간 관계가 실제 그래프의 엣지가 된다.

## 3. 온톨로지 ↔ 지식그래프

```
온톨로지  :  지식그래프
뼈대/설계도 :  구현물
```

**지식그래프의 구성 요소**

- **Entity (Node)** — 객체
- **Relation** — 관계
- **Triple** — `(Head Entity, Relation, Tail Entity)`

실제 DB를 구축할 때는 **각 노드별로 온톨로지에서 정의한 '속성'을 메타 정보로 저장**한다.
즉 온톨로지의 4요소 중 범주·관계는 그래프의 구조가 되고, 속성은 노드에 붙는 메타데이터가 된다.

**온톨로지가 있어야만 지식그래프를 구축할 수 있는 건 아니다.**
다만 온톨로지가 있으면 더 정교하고, 개념과 용어가 **통일된** 지식그래프를 만들 수 있다.

> 이 지점이 실무에서 갈린다. 온톨로지 없이 데이터를 밀어넣으면 그래프는 나오지만,
> 같은 것을 가리키는 노드가 여러 이름으로 흩어져 조회가 안 된다.
> → [`ontology-pipeline/docs/1.core-concepts.html`](../../../Projects/ontology-pipeline/docs/1.core-concepts.html)

## 4. Taxonomy & Thesaurus

둘 다 일종의 **'지식 체계'**다. 온톨로지의 부분집합 격으로 보면 된다.

| | Taxonomy | Thesaurus |
|---|---|---|
| 구조 | 주로 상/하위 분류 체계 → **트리** | 한 단어를 중심으로 **여러 관계**가 방사 |
| 관계 종류 | 사실상 상위–하위 하나 | 동의어 · 상위어 · 하위어 · 관련어 … |
| 예 | 동물 → 척추동물 → 포유류 → 개 | 자동차 ← 동의어 → 차 / 상위어 → 운송수단 / 하위어 → 승용차·트럭 / 관련어 → 도로 |

```
   Taxonomy (트리)                 Thesaurus (방사형)

       동물                              운송수단
      /    \                                ↑ 상위어
  척추동물  무척추동물          차 ←동의어— 자동차 —관련어→ 도로
   /   \        \                        ↙        ↘
포유류  조류     곤충                 승용차      트럭
 /  \                                    하위어
개  고양이
```

**차이의 핵심은 관계 종류의 수다.** Taxonomy는 관계가 한 종류라 트리가 되고, Thesaurus는 여러 종류라 그래프가 된다.

**그럼 온톨로지는** — Taxonomy의 **계층적 관계**와 Thesaurus의 **범위형·연관 관계**를 **모두 포함**한 것이
온톨로지다. 관계에 **의미(semantics)와 제약**까지 부여한 것이라고 볼 수 있다.

> 이 구분 기준을 표준(SKOS vs OWL) 층위에서 다시 세운 것과, Taxonomy가 실제로는 DAG인 이유는 부록으로 분리했다
> → [S01-1 1절](S01-1-연관-개념의-층위.md)

## 5. 왜 필요한가

> 참고: [wikidocs.net/336382](https://wikidocs.net/336382)

### 5.1 두 가지 실익

1. **같은 의미, 다른 용어** — 개념 및 용어의 통일
2. **특정 요소가 미치는 영향의 범위 파악** — 관계를 따라가며 파급을 추적

### 5.2 "우리 DB도 있고, 데이터 사전도 있고, 분류 체계도 있는데 이 정도면 AI/Agent 쓸 수 있는 거 아니야?"

강의가 정면으로 반박하는 질문이다.

| 구분 | 핵심 역할 | 연결/구성 기준 | 한계 |
|---|---|---|---|
| **데이터베이스** | 데이터 저장·조회·처리 | 키값(key) 중심 연결 | 단순 조인만으로는 **"왜 연결되는지", "어떤 관계인지"** 설명 못 함 |
| **데이터 사전** | 항목의 의미·정의 표준화 | 항목 단위 정의 | 항목 하나하나의 뜻은 분명해지지만 **항목들 간의 관계**를 보여주지 못함 |
| **분류 체계** | 대상을 나누고 묶기 | 위계(상위–하위)와 구분 | 서로 다른 분류 영역(제품 ↔ 공정 ↔ 품질) 간 **의미적 연결**을 설명 못 함 |

> **표를 세로로 읽으면** 세 가지 모두 **"관계"가 빈칸**이라는 게 공통점이다. DB는 관계가 있지만 의미가 없고
> (FK는 왜 연결되는지 안 말해준다), 데이터 사전은 의미가 있지만 관계가 없고, 분류 체계는 관계가 한 종류뿐이라
> 영역을 넘지 못한다. LLM/Agent가 데이터를 "이해"해서 추론하려면 이 빈칸이 채워져 있어야 한다.

## 6. 관계의 유형

관계는 **방향** × **출처(직접 보유 / 부모 상속)** 2축으로 4분면이 된다.

> 표기: Substance = 부모 / Children = 자식

| 방향 (Direction) | 내가(A) 직접 가진 관계 | 부모로부터 물려받은 관계 |
|---|---|---|
| **정방향** (A → B, A가 주체) | Relations | Inherited Relations |
| **역방향** (B → A, A가 대상) | Inverse Relations | Inverse Inherited Relations |

왜 구분하는가 — **조회할 때 어디까지 따라갈지가 달라진다.** 직접 관계만 보면 상속받은 제약을 놓치고,
역방향을 안 보면 "이 개체를 참조하는 것들"을 못 찾는다. 온톨로지 도구가 이 4가지를 별도로 보여주는 이유다.

## 7. 실사례

### 7.1 WordNet — 어휘 온톨로지

| | |
|---|---|
| 주체 | 프린스턴 대학교 인지과학연구소 |
| 시작 | 1985년, 첫 버전 배포 1991년 |
| 확산 | 1995년 *Communications of the ACM* 게재 후 컴퓨터 과학 분야에서 급격히 인기 |
| 정의 | 영어 단어를 의미 단위 **synset**으로 묶고, synset 간 의미 관계로 연결한 어휘 데이터베이스 |

**핵심 관계 4종**

| 관계 | 영어 | 예 |
|---|---|---|
| 동의어 | synonymy | car ↔ automobile |
| 반의어 | antonymy | hot ↔ cold |
| 상위어/하위어 | hypernymy / hyponymy | vehicle ⊃ car |
| 부분어/전체어 | meronymy / holonymy | wheel ⊂ car |

> **단위가 단어가 아니라 synset(동의어 집합)이라는 게 설계의 핵심이다.** `car`와 `automobile`을 각각 노드로 두면
> 관계를 두 번 써야 하지만, 같은 synset에 묶으면 관계는 한 번만 정의된다.
> 5.1의 "같은 의미, 다른 용어" 해법이 데이터 모델로 구현된 사례다.

**[visuwords.com](https://visuwords.com)** — 2005년 개정된 WordNet 기반 검색 결과 시각화 사이트.

### 7.2 UMLS (Unified Medical Language System) — 도메인 특화 온톨로지의 대표

> [uts.nlm.nih.gov/uts](https://uts.nlm.nih.gov/uts)

- 미국 **국립의학도서관(NLM)**이 **60개 이상의 생의학 어휘체계**를 하나로 통합한 의료 용어 시스템
- 같은 질병·유전자·약물이라도 SNOMED CT, MeSH, OMIM 등 **용어체계마다 다르게 표현되는 문제**를 해결하려고 만들어짐

**두 층으로 나뉘는 구조가 핵심이다.**

| 층 | 답하는 질문 | 구성 |
|---|---|---|
| **Metathesaurus** | "무엇이 **동일한 개념**인가" | 각 소스 어휘체계의 명칭이 의도한 의미를 파악하고, 같은 것을 의미하는 모든 명칭(동의어)을 연결 |
| **Semantic Network** | "그 개념이 **어떤 종류**인가, 그 종류들끼리 **어떻게 관계**되는가" | **Semantic Types** 127개 (카테고리/클래스) + **Semantic Relations** 54개. 관계 사이에도 트리 구조가 있다 |

```
Metathesaurus   "Myocardial Infarction" = "심근경색" = "MI" = ...   ← 동일 개념 묶기 (수평)
       ↓
Semantic Network   그 개념의 타입 = [Disease or Syndrome]           ← 종류 부여 (수직)
                   [Disease or Syndrome] --affects--> [Body Part]   ← 타입 간 관계
```

> **2층 분리가 이 사례의 배울 점이다.** "같은 것 묶기"(개체 정렬)와 "종류 체계 세우기"(범주 설계)는
> 성격이 다른 작업이므로, 층을 분리해야 각각을 독립적으로 늘릴 수 있다. 소스 어휘체계가 61개로 늘어도
> Semantic Network는 그대로다.

### 7.3 Schema.org — 웹의 공용 어휘

- 웹 사이트 내 콘텐츠의 **의미를 검색엔진·다른 사이트·프로그램과 공유**하기 위한 공통 표기법/어휘체계
- 문제의식: 사람은 HTML 코드를 보고 의미를 어느 정도 유추할 수 있지만, **컴퓨터는 그러지 못한다**
- **2011년** Bing · Google · Yahoo 등이 모여 사람·장소·이벤트·상품·오퍼 등 광범위한 주제를 아우르는 **단일 스키마** 제작 시작

**마크업 방식** — Microdata 속성으로 HTML에 의미를 얹는다.

```html
<div itemscope itemtype="https://schema.org/Person">
  <span itemprop="name">홍길동</span>
  <span itemprop="jobTitle">Frontend Engineer</span>
</div>
```

> **실무 메모** — 지금 웹에서는 Microdata(`itemscope`/`itemtype`/`itemprop`)보다 **JSON-LD**를 `<script type="application/ld+json">`에
> 넣는 방식이 사실상 표준이다. 마크업과 의미 정보가 분리돼 관리가 쉽고 Google도 이 방식을 권장한다.
> `profile` 프로젝트처럼 SEO가 걸린 사이트라면 여기서 바로 쓸 수 있는 내용.

> **부록 — 연관 개념의 층위** ([S01-1](S01-1-연관-개념의-층위.md))
> 1절이 연관 개념으로 던진 5개 중 자료가 설명하지 않고 넘어간 **Semantic Web**과 **Schema**의 자리,
> 그리고 위 세 사례를 겹쳐 읽은 정리를 부록으로 분리했다.
>
> - Semantic Web 스택 — 온톨로지가 왜 하필 RDF/OWL인가
> - Schema 네 층위 — DB 스키마는 **제약**, 온톨로지는 **의미**
> - schema.org를 온톨로지로 볼 수 있는지 (UMLS ↔ schema.org 스펙트럼)
> - 세 사례의 공통 해법 — 동의어 묶기 → 종류 부여 → 관계 정의
