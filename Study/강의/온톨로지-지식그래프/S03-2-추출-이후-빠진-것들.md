# S03-2 — 추출 다음에 남는 것들

> 2026-07-30 | 온톨로지, 상속, BFO, IOF, 온톨로지화, ODK, ROBOT, STT, 도구지형

> 📖 [강의 목차/진행](README.md) · 본편: [S03A](S03A-용어-추출-P-Mod.md) · [S03B](S03B-비분류-관계-학습.md) · [S03C](S03C-방법론-체계화와-도구-저장소.md) · 자매 부록: [S03-1 자동 구축의 천장](S03-1-자동구축의-천장.md)

> **성격** — S03의 부록. 강의 자료에 없는 내용이며 대화로 정리했다.
> S03-1이 "자동 구축이 어디서 멈추는가"라면, 이 문서는 **"멈춘 다음에 무엇이 필요한가"**다.

## 왜 이 문서가 필요한가

S03 세 편은 **개념과 관계의 목록**까지 만든다. 그 목록을 실제로 쓸 수 있는 온톨로지로 만들려면
네 가지가 더 필요한데, 자료는 이 중 어느 것도 다루지 않는다.

```
S03이 하는 것          개념 추출 → 관계 추출 → 목록
                                            │
                                            ▼
빠진 것                ① 무엇을 상속할지
                       ② 목록을 어떻게 온톨로지로 만들지
                       ③ 지금은 어떤 도구를 쓰는지
                       ④ 텍스트가 아닌 입력(음성)은 되는지
```

## 1. 어떤 common 온톨로지를 상속할지 — 자료가 정반대를 말한다

[S03B 8절](S03B-비분류-관계-학습.md)의 Contribution 세 번째 항목이 이렇다.

> **기존 ontology 없이 from scratch 구축**

**이걸 기여로 내세운다.** 그런데 [S02 7.1절](S02-설계-원칙.md)에서 정리한 현대 실무는 정반대다 —
대부분의 분야는 기성 온톨로지를 상속하고, 그래서 비용이 낮다.

### 왜 어긋나는가 — 연대 문제다

| 자원 | 사용 가능해진 시점 |
|---|---|
| BFO (상위 온톨로지) | 2000년대 초부터 존재하나 ISO 표준(21838)은 2021 |
| OBO Foundry (생의학 파운드리) | 2007 |
| SOSA / SSN (센서·관측, W3C) | 2017 |
| Brick (빌딩) | 2016 |
| IOF (제조 파운드리) | 2016 이후 |
| QUDT (단위) | 2010년대 |

S03의 논문들은 2000년대 중반 물건이다. **상속할 것이 거의 없던 시점이라 from scratch가 유일한 선택이었고,
그래서 기여로 쓸 수 있었다.** 지금 같은 문장을 논문에 쓰면 오히려 경고 신호다 — 왜 기성 것을 안 썼냐는 질문을 받는다.

> **자료를 읽을 때의 교정 지점이다.** "from scratch"를 방법론의 미덕으로 읽으면 안 된다. 시대 제약이다.

### 지금은 어떻게 고르나

**먼저 등록소에서 찾는다.** 새로 만들기 전에 있는지 본다.

| 등록소 | 범위 |
|---|---|
| **LOV** (Linked Open Vocabularies) | 범용 어휘 |
| **BioPortal** | 생의학 |
| **OBO Foundry** / Ontobee | 생물·의학 파운드리 (상호 정합성이 보장됨) |
| **prefix.cc** | prefix 중복 확인 ([S02 5.4](S02-설계-원칙.md)) |
| **FAIRsharing** | 표준·정책 범용 |

**층을 나눠서 고른다.**

```
상위(Upper)      BFO · DOLCE · SUMO       "존재하는 것의 종류" — 하나만 고른다
   ↓
중간(Mid)        IOF · CCO                도메인 공통 (제조·공통핵심)
   ↓
도메인           SNOMED CT · GO · FIBO    분야 특화
   ↓
주제별 모듈      SOSA/SSN · Time · QUDT · PROV-O   센서·시간·단위·출처
```

**판단 기준** — 커버리지만 보면 안 된다.

| 기준 | 확인할 것 |
|---|---|
| 유지 상태 | 최근 릴리스가 있는가. 죽은 온톨로지를 상속하면 같이 죽는다 |
| **IRI 영속성** | `w3id.org`/`purl.org` 같은 영구 주소를 쓰는가 ([S02 5.4](S02-설계-원칙.md)) |
| 라이선스 | 상업적 사용 가능한가 (SNOMED CT는 유료 라이선스가 있다) |
| 상위 온톨로지 정합성 | 여러 개를 상속할 때 상위가 서로 충돌하지 않는가 |
| axiom 강도 | 촘촘하면 검증에 좋고 예측 여지는 줄어든다 ([S02-1 7절](S02-1-두-계보와-발견-메커니즘.md)) |

**강의에서 이 자리** — Ch.10(S33~S34)이 SSN/SOSA·W3C Time을 배우고 Brick으로 적용하는 회차다.
Ch.2-2(S05~S06 도메인 구축 사례)도 후보다. **다만 "무엇을 고를지"의 기준을 다루는 회차는 목차에 없다.**

## 2. '온톨로지화'가 한 줄로 처리됐다

[S03B 2절](S03B-비분류-관계-학습.md) 파이프라인의 마지막 단계 서술이 이게 전부다.

> **Post-processing**: 중복 제거, 암묵적인 관계 정리하여 최종 OWL 온톨로지 구축

**한 줄이다.** 그런데 여기서 내려야 하는 결정이 적지 않고, 전부 뒤에 영향을 준다.

| 결정 | 문제 | 관련 원칙 |
|---|---|---|
| **클래스인가 인스턴스인가** | `leukaemia`는 Class인가 Individual인가. TBox/ABox 어디로 가나 | [S03C 16절](S03C-방법론-체계화와-도구-저장소.md) TBox/ABox |
| **관계 IRI 발행** | `is caused by` 문자열 → 어떤 ObjectProperty IRI로 | [S02 5.4](S02-설계-원칙.md) URI 설계 |
| **동의 표현 병합** | `is caused by` / `is induced by` / `results from` 을 하나로 볼 것인가 | [S01 5.1](S01-기본개념과-실사례.md) 같은 의미 다른 용어 |
| **domain / range** | 걸면 추론이 되고, 잘못 걸면 엉뚱한 타입이 추론된다 | [S01-1 3절](S01-1-연관-개념의-층위.md) 제약 vs 의미 |
| **axiom 강도** | 어디까지 제약을 걸까 | [S02 4.4](S02-설계-원칙.md) Min. commitment |
| **방향 처리** | S03B의 PRE/SUC를 `owl:inverseOf`로 묶을 것인가 | [S01 6절](S01-기본개념과-실사례.md) 관계 4분면 |

**마지막 줄이 특히 아깝다.** S03B는 PRE/SUC로 방향을 이미 구분해뒀는데
(`___ causes hypertension` vs `hypertension is caused by ___`), 그 정보를 `owl:inverseOf`로 옮기면
추론기가 양방향을 채워준다. 자료는 거기까지 가지 않는다.

**즉 [S03-1 1절](S03-1-자동구축의-천장.md)에서 "관계 이름이 `string`이라 추론이 안 된다"고 했던 것이,
온톨로지화 단계를 제대로 하면 부분적으로는 풀린다.** 문자열을 IRI로 승격시키고 inverse·transitive를 붙이는 일이
그 단계에서 일어난다. 자료가 한 줄로 넘긴 게 실은 Thesaurus를 Ontology로 올리는 단계였다.

**강의에서 이 자리** — 실습 ①(S09 OWL 온톨로지 설계 실습). 여기서 실제로 다뤄지는지 확인할 것.

## 3. 현재 도구 지형 — 21개는 대부분 죽었다

[S03C 13절](S03C-방법론-체계화와-도구-저장소.md)의 21개 목록(ASIUM · TERMINAE · Text-To-Onto · OntoLearn ·
Mo'K Workbench · CORPORUM-Ontobuilder …)은 **거의 전부 유지되지 않는 연구 프로토타입**이다.
목록의 값은 "지금 뭘 쓰나"가 아니라 **8기준·57지표라는 비교 축**에 있다.

### 지금 쓰이는 것 (2026-07 기준)

**★ = 지금 새로 시작한다면 이걸 기본값으로 잡는다.** 나머지는 조건이 맞을 때 갈아타는 선택지.

| 용도 | ★ 지금 고른다면 | 함께 보는 것 |
|---|---|---|
| **OWL 편집** | ★ **Protégé** — 20년째 사실상 표준 | WebProtégé(웹·협업) · TopBraid(상용) |
| **Python 조작** | ★ **RDFLib** | Java·추론 중심이면 OWL API |
| **프로젝트 툴체인** | ★ **ODK** (Ontology Development Kit) — git·Docker·CI·문서를 한 묶음으로 | 이 트랙과 겹침 → 아래 별도 항목 |
| **릴리스 · 변환 · 리포트** | ★ **ROBOT** | ODK가 내부에서 감싸 호출한다 |
| **텍스트 → KG (LLM 기반)** | ★ **OntoGPT / SPIRES** — 스키마를 고정해 추출 (강의 S37) | 검색 지향이면 Microsoft GraphRAG · LPG면 Neo4j LLM KG Builder · LangChain·LlamaIndex 그래프 빌더 |
| **텍스트 → KG (LLM 이전)** | — **지금 단독으로 고르지 않는다** | REBEL(강의 S28) · OpenIE · spaCy 커스텀. LLM 결과의 **비교 기준**으로 남는다 |
| **KG 임베딩** | ★ **PyKEEN** (강의 S17) | TorchKGE 등 |
| **온톨로지 · 개체 정렬** | ★ **DeepOnto** (강의 S18) | BERTMap이 이 안에 포함돼 있다 |
| **데이터 제약 검증** | ★ **pySHACL** | SHACL 자체가 W3C 표준 ([S01-1 3절](S01-1-연관-개념의-층위.md)) |
| **추론기** | ★ **ELK** — 대규모·EL 프로파일에서 빠르다 | 표현력 전체(OWL DL)가 필요하면 HermiT |
| **품질 · 안티패턴 점검** | ★ **OOPS!** | ROBOT report(파운드리 규칙 기반) |
| **문서 생성** | ★ **WIDOCO** | OnToology가 감싸서 자동화 |
| **저장 · 질의** | ★ **GraphDB** | 경량·임베디드는 Oxigraph(신흥) · 상용 Stardog · LPG면 Neo4j + n10s |

**표를 세로로 읽으면 지금의 기본 스택이 나온다.**

```
Protégé + RDFLib  →  ODK / ROBOT  →  pySHACL + ELK  →  WIDOCO
 (편집·조작)          (파이프라인)      (검증)            (문서)
                            ↑
              OntoGPT/SPIRES 로 초안 추출
```

> **확인 시점 메모** — 도구 지형은 빠르게 바뀐다. 이 표는 **2026-07 기준의 판단**이고,
> ★ 선정은 "가장 새것"이 아니라 **"지금 새로 시작하면 무엇을 잡을까"**로 골랐다.
> 실제로 채택할 때는 각 프로젝트의 최근 릴리스와 유지 상태를 다시 확인해야 한다 (1절의 판단 기준 참조).

### 강의는 사실 현재 도구를 다룬다 — 연결이 안 돼 있을 뿐

목차의 실습 회차들이 그대로 현재 도구다.

| 회차 | 도구 | 어느 층 |
|---|---|---|
| S09 · S10 | OWL 설계 · RDF 파이프라인 | 온톨로지화 · 적재 |
| S17 · S18 | PyKEEN · DeepOnto | 임베딩 · 정렬 |
| S37 | **OntoGPT / SPIRES** | LLM 기반 추출 |

**S03C의 서베이(21개 죽은 도구)와 이 실습 회차들을 이어주는 슬라이드가 없다.**
"과거엔 이랬고 지금은 이걸 쓴다"는 대응표가 있으면 좋았을 부분이다.

### 트랙 E와 겹치는 것 — ODK

**[트랙 E](../../../.claude/plans/트랙E-온톨로지-ADE.md)는 ODK를 먼저 봐야 한다.**
OBO 커뮤니티의 **Ontology Development Kit**이 트랙 E가 만들려는 것과 상당히 겹친다.

```
ODK가 이미 갖고 있는 것
  git 기반 레포 구조 · Docker로 재현 가능한 환경
  ROBOT으로 릴리스 파이프라인 (변환 · 모듈 추출 · 리포트)
  GitHub Actions CI 템플릿
  문서 생성
```

트랙 E 0단계("기존 도구로 한 바퀴 → 비어 있는 칸만 만든다")의 **첫 대상이 VoCol이 아니라 ODK**다.
겹치는 부분을 먼저 확인하지 않으면 이미 있는 것을 다시 만들게 된다.

## 4. 녹음본으로 온톨로지를 만들 수 있나

**먼저 용어** — 녹음 → 텍스트는 **STT / ASR**(Speech-to-Text, 음성 인식)이다.
TTS는 반대 방향(텍스트 → 음성)이라 여기선 쓰지 않는다.

### 파이프라인은 성립한다

```
음성 → [ASR] → 전사 텍스트 → [S03의 방법 또는 LLM 추출] → 개념·관계 → 온톨로지
```

전사만 되면 그 뒤는 텍스트 문제이므로 S03의 방법이 그대로 적용된다. **원리상 문제는 없다.**

### 그런데 S03의 방법이 무너지는 지점이 셋 있다

| 문제 | 왜 무너지나 |
|---|---|
| **구어체** | S03의 언어적 필터링은 **문서 문체를 전제**한다. 지시대명사("그거", "이렇게"), 미완결 문장, 반복·수정 발화에서는 `[NP] + [VP] + [NP]` 제약([S03B 4.1](S03B-비분류-관계-학습.md))이 거의 걸리지 않는다 |
| **도메인 용어 오인식** | ASR이 전문 용어를 틀리게 적으면 추출 자체가 어긋난다. 도메인 어휘 사전(bias list)을 ASR에 미리 넣어야 한다 |
| **화자** | 인터뷰라면 **누가 말했는지가 지식의 출처(provenance)**다. 화자 분리(diarization)를 안 하면 서로 다른 사람의 주장이 한 덩어리로 섞인다 |

세 번째가 특히 중요하다. **출처를 붙이려면 PROV-O 같은 어휘가 추가로 필요하고, 이건 추출 문제가 아니라
온톨로지화(2절) 문제다.** 발화 하나하나를 근거로 남길지, 아니면 합의된 결론만 남길지가 설계 결정이 된다.

### 근본 한계

**말로 표현되지 않은 것은 녹음에도 없다.** ASR은 발화를 텍스트로 바꿀 뿐이고,
발화되지 않은 판단 근거는 전사에도 나타나지 않는다. 이건 도구로 해결되는 문제가 아니라
질문을 어떻게 설계하느냐의 문제다 — CQ를 먼저 정하고 그 질문에 답하도록 인터뷰를 설계하는 쪽이 맞다
([S03-1 8.2절](S03-1-자동구축의-천장.md)의 "CQ는 구축보다 먼저").

**강의에서 이 자리 — 없다.** 멀티모달은 Ch.11(S35~S36)인데 **이미지**다. 음성은 목차에 없다.
가장 가까운 건 S24(CQ 기반 Human-in-the-loop 파이프라인)로, 인터뷰 설계와 엮일 여지가 있다.

## 정리 — 네 개가 어디에 있나

| 빠진 것 | 강의에서 | 상태 |
|---|---|---|
| ① 무엇을 상속할지 | Ch.10 (SSN/SOSA·Brick 적용) · Ch.2-2 (도메인 사례) | **적용은 나오나 선택 기준은 목차에 없음** |
| ② 온톨로지화 | 실습 ① (S09 OWL 설계) | 다뤄질 것으로 보임 — 확인 필요 |
| ③ 현재 도구 | 실습 S09·S10·S17·S18·S37 | 도구는 나오나 **서베이와 이어주는 대응표가 없음** |
