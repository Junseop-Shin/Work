## 1. 요약정리

### 요구사항 확인
- **요구사항 분류**: 기능적 요구사항(무엇을 해야 하는가) / 비기능적 요구사항(성능·보안·사용성 등 어떻게 동작해야 하는가)
- **요구사항 개발 프로세스**: 도출(Elicitation) → 분석(Analysis) → 명세(Specification) → 확인(Validation)
- **요구사항 검증(Validation) 기법 3가지**: 동료검토(Peer Review), 워크스루(Walkthrough), 인스펙션(Inspection) — 격식 수준은 워크스루 < 동료검토 < 인스펙션 순
- 인스펙션은 **정적(코드를 실행하지 않는) 기법**이며, CI에서 테스트케이스를 실행하는 것은 **동적 테스트**로 완전히 다른 카테고리

### 화면설계
- **UI 설계 4대 원칙**
  | 원칙 | 정의 |
  |---|---|
  | 직관성 | 누구나 쉽게 이해하고 사용할 수 있어야 한다 |
  | 유효성 | 인터랙션을 최소화하며 정확하게 목표를 달성할 수 있어야 한다 |
  | 학습성 | 초보자·숙련자 모두 쉽게 배우고 사용할 수 있어야 한다 |
  | 유연성 | 다양한 사용자 요구를 수용하고 오류를 최소화할 수 있어야 한다 |
- UI 설계 도구: 와이어프레임, 스토리보드, 목업, 프로토타입(저충실도/고충실도)

### 애플리케이션 설계 — UML
- **4대 다이어그램**
  | 종류 | 구분 | 핵심 |
  |---|---|---|
  | 클래스 다이어그램 | 정적 | 클래스 간 관계 |
  | 시퀀스 다이어그램 | 동적 | 객체 간 메시지 흐름(시간순) |
  | 유스케이스 다이어그램 | 정적(기능) | 액터-시스템 상호작용, Include/Extend |
  | 액티비티 다이어그램 | 동적 | 업무 흐름/조건 분기 |
  | (+) 상태 다이어그램 | 동적 | 이벤트에 따른 객체 상태 전이 |

- **클래스 다이어그램 관계 강도 순서**: 의존(Dependency) < 연관(Association) < 집합(Aggregation) < 합성(Composition) < 일반화(Generalization)
  - 의존: 매개변수 등으로 일시적 사용, 점선 화살표
  - 집합: 전체 소멸돼도 부분은 독립 존재, 빈 마름모(◇)
  - 합성: 전체 소멸 시 부분도 함께 소멸, 채워진 마름모(◆)
  - 일반화: 상속(is-a) 관계, 속이 빈 삼각형 화살표(▷). Java의 `extends`는 코드 키워드일 뿐 UML 정식 용어 아님

- **유스케이스 관계**: Include(`<<include>>`, 필수 실행) vs Extend(`<<extend>>`, 조건부 확장)

- **모듈 설계 척도**: 응집도(모듈 내부 요소 밀접도, 높을수록 좋음) / 결합도(모듈 간 의존도, 낮을수록 좋음) → "고응집 저결합"

- **아키텍처 스타일**: MSA(Micro Service Architecture) — 독립 배포·확장 가능한 서비스 단위로 분리, 모놀리식과 반대 개념

- **가용성 관련 용어 구분**: 로드밸런싱(부하 분산이 목적) vs 이중화/페일오버(장애 시 예비 시스템 자동 전환이 목적)

- **테스트 기법**: 블랙박스(입출력만으로 검증, 동치분할/경계값분석/결정테이블) vs 화이트박스(내부 코드 구조 검증, 구문/분기/조건 커버리지)

### GoF 디자인 패턴 (23개, 3분류)
- **생성(5)**: Singleton, Factory Method, Abstract Factory, Builder, Prototype
- **구조(7)**: Adapter, Bridge, Composite, Decorator, Facade, Flyweight, Proxy
- **행위(11)**: Observer, Strategy, Command, State, Template Method, Iterator, Visitor, Mediator, Memento, Chain of Responsibility, Interpreter

**목적이 다른 유사 패턴 쌍 (자주 헷갈림):**
| 패턴 | 목적 |
|---|---|
| Singleton | 인스턴스 1개만 생성 + 전역 접근 |
| Observer | 1:N 의존 관계, 상태 변화를 등록된 대상에 자동 통지 (Pub-Sub과는 결합도·동기방식에서 구별되는 별개 개념) |
| Strategy | 여러 알고리즘을 캡슐화해 런타임에 교체(클라이언트가 명시적으로 선택) |
| State | 객체 내부 상태에 따라 행동이 자동으로 달라짐(상태 전이가 내부에서 자동 처리) |
| Factory Method | 어떤 클래스의 인스턴스를 생성할지 서브클래스가 결정 |
| Abstract Factory | 관련된 여러 객체군(제품군)을 통째로 생성 |
| Builder | 복잡한 객체 하나를 여러 단계로 나눠 생성(메서드 체이닝) |
| Adapter | 호환 안 되는 인터페이스를 변환해 함께 동작하게 함 |
| Facade | 복잡한 서브시스템을 단순한 창구 하나로 감쌈 |
| Proxy | 원본과 동일한 인터페이스로 접근을 제어(권한체크/지연로딩/원격접근) |
| Decorator | 원본을 감싸 기능/책임을 추가(Proxy와 구조는 비슷, 목적이 다름) |

## 3. 해설

1. **정답: 유스케이스 다이어그램**. 액터-시스템 상호작용, Include(필수)/Extend(조건부 확장) 관계를 가짐.

2. **정답: 합성(Composition), 채워진 마름모(◆)**. 마름모 형태는 맞혔으나 관계 이름을 Include(유스케이스 관계 용어)로 잘못 답함. 반대로 전체 없이도 부분이 독립 존재 가능하면 집합(Aggregation, 빈 마름모).

3. **모범답안**: 한 객체(Subject)의 상태 변경 시 이를 구독하는 다수의 객체(Observer)에게 자동으로 통지되는 **1:N 의존 관계**를 정의하는 패턴. 이벤트 처리, MVC의 View 갱신 등에 사용. "상태 변화를 감시해서 전파"라는 방향은 맞았으나 "1:N 의존 관계 + 자동 통지"라는 공식 키워드가 빠짐. 또한 Pub-Sub은 발행자·구독자가 서로를 모르고 브로커를 통해 비동기로 동작한다는 점에서 Observer와는 결합도·동기방식이 다른 별개 패턴으로 구분해야 함(대표 예시로 쓰기엔 부정확).

4. **정답: 동료검토(Peer Review), 워크스루(Walkthrough), 인스펙션(Inspection)**. 인스펙션이 체크리스트 기반의 가장 공식적인 기법.

5. **정답: ① 직관성, ② 유효성**. "이해하기 쉬움=직관성", "배우기 쉬움=학습성"으로 구분해야 함. 유효성(인터랙션 최소화+정확한 목표달성)을 학습성과 혼동함.

6. **모범답안**: 동일한 목적의 여러 알고리즘을 각각의 클래스로 캡슐화해 런타임에 교체 가능하게 하는 행위 패턴. Observer는 "상태 변화를 알리는 것"이 목적(1:N 통지)이고, Strategy는 "여러 알고리즘 중 하나를 선택/교체하는 것"이 목적.

7. **정답: 의존(Dependency)**. UML 표기는 점선 화살표. 클래스 다이어그램 관계 중 가장 약한 관계.

8. **정답: Factory Method(팩토리 메서드)**. 상위 클래스는 생성 인터페이스만 정의하고, 실제 어떤 클래스를 생성할지는 서브클래스가 결정. Abstract Factory는 관련된 여러 객체군을 통째로 생성한다는 점에서 구분됨.

9. **정답: MSA(Micro Service Architecture)**. 독립 배포·확장 가능한 서비스 단위로 분리, 모놀리식과 반대 개념.

10. **정답: 응집도(Cohesion)**. 응집도는 높을수록, 결합도(모듈 간 의존도)는 낮을수록 좋은 설계("고응집 저결합"). 응집도 단계(강한 순): 기능적>순차적>교환적>절차적>시간적>논리적>우연적. 결합도 단계(약한 순): 자료<스탬프<제어<외부<공통<내용.

11. **정답: 상태 다이어그램(State Diagram)**. 상태(둥근 사각형), 전이(화살표, "이벤트[조건]/액션"), 시작(●)/종료(◉) 상태로 구성.

12. **모범답안**: 호환되지 않는 인터페이스를 가진 클래스들이 기존 코드 수정 없이 함께 동작할 수 있도록 인터페이스를 변환해주는 구조 패턴. "A-B 연결, 교체 가능"이라는 방향은 맞았으나 "인터페이스 호환/변환"이라는 핵심 키워드가 빠짐. Facade(복잡해서 단순화)와는 목적이 다름(Adapter는 인터페이스가 안 맞아서 변환).

13. **정답: 일반화(Generalization)**. `extends`는 Java 키워드일 뿐 UML 정식 용어가 아님. 표기는 속이 빈 삼각형 화살표(▷), "is-a" 관계, 클래스 다이어그램 관계 중 가장 강한 관계.

14. **정답: Facade(퍼사드)**. 서브시스템 자체는 변경하지 않고 클라이언트와의 결합도를 낮추는 창구 역할. Adapter와 짝지어 구분(Adapter=인터페이스 변환, Facade=복잡성 단순화).

15. **정답: 애자일(Agile)**. 스크럼(Scrum)은 애자일을 구현하는 구체적 프레임워크 중 하나(Sprint, Product Backlog 등 스크럼 고유 용어 사용). 애자일 ⊃ 스크럼 관계.

16. **정답: Builder(빌더)**. 점층적 생성자 문제(매개변수 과다)를 해결. 생성 과정을 여러 단계로 분리, 메서드 체이닝으로 구현. Factory Method(어떤 클래스인지 결정)/Abstract Factory(객체군 생성)/Singleton(1개만 생성)과 구분.

17. **정답: 블랙박스 테스트(Black Box Testing)**. 대표 기법: 동치분할, 경계값분석, 결정테이블. 반대 개념인 화이트박스 테스트(코드 구조 기반, 구문/분기/조건 커버리지)와 세트로 기억.

18. **모범답안**: 실제 객체(Real Subject)에 대한 접근을 제어하기 위해 동일한 인터페이스를 가진 대리 객체(Proxy)를 두는 구조 패턴. 유형: 가상 프록시(지연 로딩), 보호 프록시(권한 체크), 원격 프록시. "기존 코드 수정 없이 기능 추가"라는 답변은 오히려 Decorator의 정의에 가까움 — Proxy는 목적이 **접근 제어**, Decorator는 목적이 **기능/책임 추가**로 구분해야 함.

19. **정답: 이중화(Redundancy) / 페일오버(Failover)**. 예비 서버(Standby)가 주 서버 장애 시 자동으로 역할을 넘겨받는 Active-Standby 구조. 로드밸런싱은 부하 분산이 본래 목적으로, 결과적으로 가용성에 도움은 되지만 정확히 일치하는 답은 아님.

20. **모범답안**: 구조(인터페이스로 행위를 캡슐화, 런타임 교체 가능)는 비슷하지만, State는 객체의 **내부 상태에 따라 행동이 자동으로 달라지도록** 하는 것이 목적(상태 전이가 상태 객체 내부에서 자동 처리)이고, Strategy는 **클라이언트가 명시적으로** 알고리즘을 선택/주입하는 것이 목적(상태 전이 개념 없음).

## 4. 반복 오답 패턴 (D-2 최종 암기 시 재확인)

- 구조는 비슷한데 목적이 다른 패턴 쌍: **Adapter/Facade**, **Proxy/Decorator**, **State/Strategy**
- 용어 자체를 헷갈린 경우: **집합/합성**, **Include/Extend**, **extends(코드) vs 일반화(UML)**, **애자일(상위)/스크럼(하위)**
- 목적을 혼동한 경우: **로드밸런싱(부하분산) vs 이중화(장애대응)**, **응집도/결합도** 방향
