## 1. 요약정리

### 통합구현 — 연계 방식

**EAI(Enterprise Application Integration) 구축 유형**
| 유형 | 특징 |
|---|---|
| Point-to-Point | 1:1 직접 연결, 단순하지만 시스템 많아지면 유지보수 폭증(N²) |
| Hub & Spoke | 중앙 허브가 각 시스템과 연결, 허브 장애 시 전체 영향(단일 장애점) |
| Message Bus(ESB) | 미들웨어 버스를 통해 표준화된 방식으로 연계, 확장성 가장 좋음 |
| Hybrid | 그룹 내부는 Hub&Spoke + 그룹 간은 Message Bus 혼합 |

- **ESB(Enterprise Service Bus)**: 개방형 표준(SOAP, REST 등) 기반 서비스 중심 통합 미들웨어. 일반 EAI보다 유연하고 특정 벤더 종속성이 낮음
- **연계 기술 방식**: DB Link(DBMS 직접 접속, 결합도 높고 보안 이슈), DB Connection(JDBC/ODBC), API/Open API, 소켓(Socket), 웹서비스(SOAP/REST), 화면 연계(Screen Scraping)
- **SOAP vs REST**: SOAP은 XML 기반 엄격한 표준 프로토콜(WSDL, 보안·트랜잭션 내장) / REST는 HTTP 메서드+URI로 자원을 표현하는 아키텍처 스타일(Stateless, Cacheable, Uniform Interface, Client-Server)

### 통합구현 — 형상관리

- **형상관리(SCM) 4단계**: 형상식별(Identification) → 형상통제(Control, 변경 요청의 타당성 검토·승인) → 형상감사(Audit, 승인된 변경이 기준선에 제대로 반영됐는지 검증) → 형상기록(Status Accounting, 상태 보고)
  - **통제 vs 감사 자주 헷갈림**: 통제="변경을 승인할지" 결정 / 감사="승인된 변경이 제대로 반영됐는지" 사후 검증
- **버전관리 도구 3세대**
  | 세대 | 방식 | 예시 |
  |---|---|---|
  | 공유 폴더 방식 | 로컬 저장소를 공유폴더로 공유 | RCS, SCCS |
  | 클라이언트/서버 방식 | 중앙 서버 1곳에만 저장소 존재, 커밋이 네트워크에 의존 | CVS, **SVN** |
  | 분산 저장소 방식 | 로컬+원격 저장소 모두 존재, 로컬 커밋 후 push로 원격 반영, 오프라인 커밋 가능 | **Git** |
- 형상관리 도구 사용 목적: 변경 이력 추적, 여러 개발자의 동시 개발 지원(협업), 이전 버전으로의 롤백, 산출물 전체의 일관성 유지

### 통합구현 — 단위 테스트

- **IEEE 829 표준 문서 작성 순서**: 테스트 계획서 → 테스트 케이스 → 테스트 시나리오 → 테스트 결과서
- **xUnit 프레임워크**: 단위 테스트 자동화 프레임워크 계열의 통칭(JUnit-Java, NUnit-.NET, CppUnit-C++) — assert 구문으로 예상값/실제값 비교

### 서버구현 — 프레임워크 & 배치

- **프레임워크 vs 라이브러리 (IoC 관점)**: 라이브러리는 개발자 코드가 능동적으로 라이브러리를 호출(제어권이 개발자 코드에 있음). 프레임워크는 반대로 프레임워크가 전체 흐름을 쥐고, 개발자가 작성한 코드(콜백/오버라이드)를 프레임워크가 호출(제어권이 프레임워크에 있음 = **IoC, Inversion of Control**)
- **배치 프로그램 3대 필수 요소**: 대용량 데이터 처리 / 자동화(무인화) / 견고성(Robustness, 예외 상황에도 시스템이 멈추지 않고 견뎌야 함)
- **배치 스케줄링 유형**
  | 유형 | 설명 |
  |---|---|
  | Event-driven | 시스템 내부/외부 이벤트 발생 시 실행 |
  | Time-driven(정기 배치) | 정해진 시각/주기에 자동 실행(가장 일반적, 예: Quartz) |
  | On-demand | 사용자(또는 다른 시스템)의 명시적 요청 시 즉시 실행 |

### 서버구현 — IPC(프로세스 간 통신)

- **IPC(Inter-Process Communication)**: 서로 다른 프로세스(또는 컴퓨터) 간 데이터 교환/동기화 방법의 통칭
- **종류**: 공유 메모리(Shared Memory), 소켓(Socket, 네트워크 경계를 넘어 통신 가능하다는 점이 다른 방식과의 핵심 차이), 세마포어(Semaphore), 파이프(Pipe), 메시지 큐(Message Queueing), 원격 프로시저 호출(RPC — 원격 함수를 로컬처럼 호출)
- **세마포어 vs 뮤텍스**: "공유 가능/불가능"이 아니라 **동시 접근 허용 개수**의 차이. 세마포어는 카운터 기반으로 N개까지 동시 접근 허용, 뮤텍스는 상호배제(Mutual Exclusion)로 오직 1개만 동시 접근 허용

## 3. 해설

1. **정답: Hub & Spoke**. 중앙 허브가 모든 시스템과 1:N으로 연결되는 구조라 허브가 단일 장애점(SPOF)이 됨. Point-to-Point는 허브 없이 시스템끼리 직접 1:1 연결이라 시스템이 늘어날수록 연결 수가 N²로 폭증.

2. **정답: 개방형 표준(SOAP, REST 등) 기반의 서비스 중심 미들웨어라 특정 벤더에 종속되지 않고 유연하게 대응 가능**.

3. **정답: 형상식별 → 형상통제 → 형상감사 → 형상기록**. 순서는 맞혔으나 첫 단계 이름을 "형상파악"으로 잘못 답함(정확히는 "식별"). 형상 항목에 이름과 버전을 부여해 식별하는 단계.

4. **정답: 분산 저장소 방식, Git**. 클라이언트/서버 방식(SVN)은 중앙 서버 1곳에만 저장소가 있어 커밋 자체가 네트워크에 의존적이라는 게 Git과의 핵심 차이.

5. **정답: 테스트 계획서 → 테스트 케이스 → 테스트 시나리오 → 테스트 결과서**. 계획(무엇을 테스트할지) → 케이스(구체적 입력/기대값) → 시나리오(케이스를 실행 순서로 묶음) → 결과서(실제 실행 결과) 흐름으로 암기.

6. **정답: IoC(Inversion of Control, 제어의 역흐름)**. 일반 라이브러리는 개발자 코드가 능동적으로 호출하지만, 프레임워크는 반대로 흐름을 쥐고 개발자 코드(콜백 등)를 호출. Spring의 DI도 IoC의 구현 방식.

7. **정답: 대용량 데이터 처리 / 자동화(무인화) / 견고성(Robustness)**. "자율성", "에러처리"로 답했으나 정확히는 "무인화(사람 개입 없이 실행)"와 "견고성(예외 상황에도 견뎌내는 능력)"이라는 용어로 답해야 함.

8. **정답: Time-driven(정기 배치)**. "크론잡"은 이 방식을 구현하는 대표 도구/기법 예시로는 맞지만, 유형 이름 자체는 Time-driven(Schedule 방식). Event-driven(이벤트 발생 시), On-demand(요청 시 즉시)와 세트로 암기.

9. **정답: 세마포어는 카운터 기반으로 N개까지 동시 접근 허용, 뮤텍스는 상호배제로 오직 1개만 동시 접근 허용**. "공유 가능/불가능"이 아니라 "동시 접근 허용 개수(N개 vs 1개)"로 답해야 정확.

10. **정답: DB Link**. 상대 DB에 직접 접속 계정으로 연계하는 방식. 구현은 간단하지만 결합도가 높고(스키마 변경에 취약) DB 계정 노출 등 보안 이슈가 있음.

11. **정답: xUnit**. assert 구문으로 예상값과 실제값을 비교해 테스트를 자동화하는 프레임워크 계열의 통칭.

12. **정답: Hub & Spoke + Message Bus**. 그룹(부서) 내부에서는 Hub & Spoke, 그룹 간에는 Message Bus로 연결하는 혼합 형태. Point-to-Point는 Hybrid 구성 요소로 보통 등장하지 않음.

13. **정답: 원격 프로시저 호출**. 네트워크상의 다른 프로세스에 있는 함수를 로컬 호출처럼 실행하게 해주는 IPC 방식. 클라이언트의 스텁(Stub)이 요청을 직렬화해 네트워크로 전달, 서버가 실행 후 결과 반환.

14. **정답: SVN은 중앙 서버(원격)에만 저장소가 존재(커밋에 네트워크 필요) vs Git은 로컬에도 완전한 저장소가 있어 오프라인 커밋 가능, 이후 push로 원격 반영**.

15. **모범답안**: SOAP은 XML 기반 엄격한 표준 프로토콜(WSDL, 보안·트랜잭션 내장), REST는 HTTP 메서드+URI로 자원을 표현하는 아키텍처 스타일로 더 가볍고 유연. REST의 핵심 특성(Stateless, Cacheable, Uniform Interface, Client-Server) 중 "Stateless"만 답함 — SOAP 쪽 설명이 통째로 빠짐.

16. **정답: 승인된 변경이 기준선(Baseline)에 요구사항대로 제대로 반영되었는지 사후 검증하는 단계**. "변경이 적절한지 판단"은 형상통제(변경관리)의 정의라 혼동함. 통제=변경을 "승인할지" 결정 / 감사=승인된 변경이 "제대로 반영됐는지" 검증.

17. **정답: 사용자(또는 다른 시스템)의 요청이 발생하는 즉시 실행**. Event-driven(시스템 내부/외부 이벤트가 트리거)과 구분: On-demand는 "명시적 요청"이 트리거.

18. **정답: 네트워크를 통해 서로 다른 컴퓨터(또는 같은 컴퓨터의 다른 프로세스) 간 통신 가능, IP 주소+포트로 대상 지정**. "3-way handshake"는 TCP 연결 설정 과정 개념이라 방향이 다름. 공유메모리·파이프·세마포어는 같은 시스템 내부에 국한되지만 소켓은 네트워크 경계를 넘을 수 있다는 게 핵심 차이.

19. **정답: 변경 이력 추적, 여러 개발자의 동시 개발 지원, 이전 버전 롤백, 산출물 전체의 일관성 유지**.

20. **모범답안**: 라이브러리는 개발자 코드가 능동적으로 라이브러리를 호출(제어권이 개발자 코드에 있음). 프레임워크는 반대로 프레임워크가 전체 흐름을 쥐고, 개발자가 작성한 코드(콜백/오버라이드)를 프레임워크가 필요한 시점에 호출(제어권이 프레임워크에 있음 = IoC). "누가 호출의 주체인가"라는 핵심 문장이 빠짐.

## 4. 반복 오답 패턴 (D-2 최종 암기 시 재확인)

- 뮤텍스/세마포어 차이: "공유 가능/불가능"이 아니라 **동시 접근 허용 개수(1개 vs N개)**로 기억
- 형상통제 vs 형상감사: 통제="승인할지" 결정 / 감사="제대로 반영됐는지" 사후 검증
- 프레임워크/라이브러리 IoC 서술: **"누가 누구를 호출하는가"**가 채점 포인트(개발자 코드가 호출 vs 프레임워크가 호출)
- 유형/방식 이름을 실제 구현 예시(크론잡, 3-way handshake 등)로 대체해서 답하는 습관 — 시험은 정확한 공식 용어(Time-driven, IP+포트 기반 네트워크 통신 등)를 요구
- Hybrid EAI = Hub&Spoke + Message Bus (Point-to-Point 아님)
