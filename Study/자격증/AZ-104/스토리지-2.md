# 스토리지 2

시험 영역 중 스토리지 구현·관리(15~20%)에 해당하는 내용이다. 2편은 접근 제어, Azure Files, AzCopy를 다룬다. 계정, 계층, 이중화는 [1편](스토리지-1.md)에 있다.

## 스토리지 계정 메뉴별 역할

포털의 스토리지 계정 메뉴 이름이 보기로 그대로 나온다.

| 메뉴 | 정하는 것 |
|---|---|
| 네트워킹 | 어디서 들어올 수 있나. 인터넷, 특정 VNet, 특정 IP |
| 액세스 키 | 누가 들어올 수 있나. 계정 전체 권한을 가진 키 두 개 |
| 데이터 보호 | 지운 걸 되살릴 수 있나. 일시 삭제, 버전 관리, 특정 시점 복원 |
| 암호화 | 저장된 데이터를 어떤 키로 암호화하나. Microsoft 관리 키 또는 고객 관리 키 |

인터넷에서 들어오는 접근을 막으라는 문제는 네트워킹이다. 키를 바꿔도 인터넷에서 들어오는 길은 그대로 열려 있다.

네트워킹 메뉴의 공용 네트워크 액세스 설정은 세 가지다.

| 설정 | 동작 |
|---|---|
| 모든 네트워크에서 사용 | 인터넷 어디서든 들어온다. 인증은 따로 필요하다 |
| 선택한 가상 네트워크와 IP 주소에서 사용 | 허용한 VNet 서브넷과 공용 IP만 들어온다 |
| 사용 안 함 | 프라이빗 엔드포인트로만 들어온다 |

요청은 네트워크 규칙과 인증을 둘 다 통과해야 데이터에 닿는다. 공용 액세스를 꺼 두면 유효한 SAS URL로도 인터넷에서는 접속하지 못한다.

```mermaid
flowchart LR
    R["요청"] --> N{"네트워크 규칙 · 어디서"}
    N -->|"거부"| X["차단"]
    N -->|"통과"| A{"인증 · SAS · 키 · Entra"}
    A -->|"실패"| X
    A -->|"성공"| D["데이터"]
```

### ExpressRoute로 들어오는 온프레미스만 허용

ExpressRoute의 Microsoft 피어링으로 스토리지 공용 엔드포인트에 붙으면, 스토리지에는 온프레미스의 NAT 공용 IP가 출발지로 보인다. 그래서 온프레미스 연결만 허용하라는 문제는 스토리지 계정 네트워킹 메뉴에서 그 공용 IP 범위만 허용하는 것이 답이다.

ExpressRoute 경로 필터는 Microsoft 피어링에서 어떤 Microsoft 서비스의 경로를 온프레미스로 알려 줄지 고르는 기능이다. 스토리지에 누가 들어오는지는 정하지 못한다. 경로 테이블과 SAS도 접근 출발지를 제한하지 않는다.

## SAS

SAS(Shared Access Signature, 공유 액세스 서명)는 URL 뒤에 붙는 서명된 토큰이다. 권한(읽기, 쓰기, 삭제, 목록), 만료 시각, 허용 IP, HTTPS 전용 여부를 담는다.

```
https://storage1.blob.core.windows.net/data/report.csv?sp=r&se=2026-11-03T09:00Z&sig=...
```

| 종류 | 범위 | 서명 |
|---|---|---|
| 계정 SAS | 계정 전체. 여러 서비스를 한 번에 | 계정 액세스 키 |
| 서비스 SAS | 서비스 하나 안의 리소스. 컨테이너, Blob 하나, 파일 공유 등 | 계정 액세스 키 |
| 사용자 위임 SAS | Blob 컨테이너나 Blob | Entra ID 자격 증명. 키를 쓰지 않아 권장된다 |

외부 조직에 일정 시간만 접근을 주라는 문제는 SAS다. 액세스 키는 계정 전체 권한에 만료가 없어서 외부에 주지 않는다. CDN은 콘텐츠 전달, 수명 주기 관리는 계층 이동이라 권한과 관계없다.

만료 전에 SAS를 취소하는 방법은 종류마다 다르다.

| 상황 | 취소 방법 |
|---|---|
| 키로 서명한 계정 SAS, 서비스 SAS | 서명에 쓴 액세스 키를 교체한다. 그 키로 만든 SAS가 전부 무효가 된다 |
| 저장된 액세스 정책을 연결한 서비스 SAS | 정책을 수정하거나 삭제한다 |
| 사용자 위임 SAS | 사용자 위임 키를 취소한다 |

## Azure Files

### 도메인 서버에서 AD 계정으로 접근

| 접근 방식 | 프로토콜 | 인증 |
|---|---|---|
| 드라이브로 연결(`net use Z: \\storage1.file.core.windows.net\share1`) | SMB, 포트 445 | 액세스 키나 Kerberos(AD 계정). SAS는 안 된다 |
| 앱이 HTTPS로 파일 올리고 받기 | REST API | SAS, 키, Entra |

AD DS 도메인 서버의 사용자가 자기 계정으로 파일 공유를 쓰게 하는 순서다.

1. 스토리지 계정의 파일 공유 설정에서 ID 기반 액세스(AD DS)를 켠다. 스토리지 계정이 AD에 컴퓨터 계정처럼 등록된다
2. 공유 단위 권한을 RBAC로 준다. 예: `Storage File Data SMB Share Contributor`
3. 폴더·파일 단위 권한은 NTFS 권한으로 준다
4. 서버에서 `net use`로 연결한다

첫 번째로 할 일을 묻는 문제는 1번이다. 서버의 로컬 그룹은 Azure 권한과 관계없고, 보안 파일 공유 설정은 SMB 버전과 암호화 수준을 정하는 것이다.

사용자가 Entra 계정으로 인증해 SMB로 붙게 하라는 문제도 같은 설정이다. ID 기반 액세스의 원본으로 Microsoft Entra Kerberos를 고른다. SAS와 연결 문자열은 SMB에서 쓰지 않고, 액세스 키를 다시 만드는 건 인증 방식과 관계없다.

### 대용량 파일 공유

표준 파일 공유는 기본 최대 5TiB이고, 대용량 파일 공유를 켜면 100TiB까지 된다. 켜면 끌 수 없다. 시험 기준으로 대용량 파일 공유는 LRS와 ZRS에서 된다.

```powershell
Set-AzStorageAccount -ResourceGroupName RG1 -Name storage1 -EnableLargeFileShare
Update-AzRmStorageShare -ResourceGroupName RG1 -StorageAccountName storage1 -Name share1 -QuotaGiB 102400
```

할당량은 GiB 단위라 100TiB는 102,400이다. 이미 있는 공유라서 `New-AzRmStorageShare`가 아니라 `Update-AzRmStorageShare`다. 이름의 Rm은 옛 AzureRM 모듈이 아니라 Resource Manager를 거쳐 공유를 다룬다는 뜻이고 현재 Az 모듈 명령이다.

## AzCopy

AzCopy v10은 Blob(ADLS Gen2 포함)과 Files를 복사한다. Queue와 Table은 대상이 아니다. 인증은 `azcopy login`(Entra)이나 SAS 토큰으로 한다. Table 데이터는 Storage Explorer나 Data Factory로 옮긴다.

| 명령 | 동작 | 용도 |
|---|---|---|
| `azcopy copy` | 지정한 파일을 비교 없이 복사한다 | 한 번에 옮기는 마이그레이션 |
| `azcopy sync` | 원본과 대상 목록을 이름과 수정 시간으로 비교해서 바뀐 것만 올린다. `--delete-destination=true`를 주면 원본에 없는 대상 파일도 지운다 | 주기적으로 다시 돌려서 맞추기 |

sync도 실행하면 비교하고 끝나는 일회성 명령이다. 계속 맞추려면 스케줄러로 반복 실행한다. 온프레미스 파일 서버를 Azure Files와 계속 동기화하는 건 Azure File Sync다. 서버에 에이전트를 설치하면 서비스로 돌면서 맞춘다.

공유 폴더 전체를 Blob으로 옮기라는 문제에서 시험은 `azcopy copy ... --recursive`와 PowerShell 조합을 답으로 본다. `Set-AzStorageBlobContent`는 파일 하나만 올리므로 `-File`에 폴더를 넣으면 안 되고, `Get-ChildItem -Recurse`로 파일 목록을 만들어 파이프로 넘긴다.

```powershell
Get-ChildItem -Path \\server1\images -Recurse -File |
  Set-AzStorageBlobContent -Container "images" -Context $ctx
```
