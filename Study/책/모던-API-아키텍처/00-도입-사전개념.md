## 한 줄 요약

0장은 본격적인 API 설계 논의에 앞서 **공통 어휘를 세팅**하는 도입부다. ① API가 프로세스 경계를 넘느냐(in/out-of-process), ② 아키텍처를 어떤 추상화 레벨로 그리느냐(C4), ③ 어떤 방향의 트래픽이냐(수직/수평), ④ 결정을 어떻게 기록하느냐(ADR) — 이후 장들의 전제가 되는 4가지 기초 개념을 정리한다.

## 1. API 정의 + In-process vs Out-of-process

**API** = 시스템 기능을 외부에 노출하는 **계약(contract)·경계**. 핵심 구분은 호출이 **프로세스 경계를 넘느냐**다.

| | In-process | Out-of-process |
|---|---|---|
| 호출 | 같은 프로세스 내 함수/메서드 | 프로세스 경계를 넘음(네트워크/IPC) |
| 예 | 라이브러리·모듈 API | **REST, gRPC, 메시지 큐, DB 호출** |
| 메모리 | 주소공간 공유, 직접 참조 | **직렬화/역직렬화 필요** |
| 속도 | 나노초 | **밀리초**(네트워크 비용) |
| 실패 | 거의 없음 | **부분 실패·지연·타임아웃 고려** |

> out-of-process는 경계를 넘기에 **직렬화·네트워크 오류·지연·버전 호환**을 설계에서 다뤄야 한다(분산 시스템의 근본 난이도). 이 책이 다루는 건 주로 **out-of-process(네트워크) API**다.

## 2. C4 다이어그램 — Context / Container / Component

**C4 모델**(Simon Brown) = 아키텍처를 **"지도의 줌 레벨"**처럼 4단계 추상화로 그리는 방법. 위에서 아래로 줌인:

```
Level 1: System Context  ── 시스템 1개 + 사용자 + 외부 시스템 (숲)
Level 2: Container       ── 시스템 내부를 "실행/배포 단위"로 분해
Level 3: Component       ── 한 컨테이너 내부를 구조 블록으로 분해
Level 4: Code            ── 클래스 수준 (보통 생략)
```

| 레벨 | 보여주는 것 | 청중 |
|------|------------|------|
| **System Context** | 시스템 박스 + actor(사용자) + 외부 시스템과의 관계 | 경영진·이해관계자 |
| **Container** | 시스템 내부의 **실행/배포 단위**(웹앱, 모바일앱, API 서버, DB, 브로커) + 기술스택·통신 | 아키텍트·개발자 |
| **Component** | **한 컨테이너 내부**의 주요 구조 블록(컨트롤러/서비스/리포지토리 그룹) | 개발자 |

> **⚠️ 함정: C4의 "Container"는 Docker 컨테이너가 아니다.** "독립적으로 실행/배포되는 단위"(SPA, API 서버, DB 등)를 뜻한다.

**차이의 본질 = 추상화 레벨(줌 정도).** Context(시스템↔외부) → Container(실행 단위) → Component(컨테이너 내부)로 줌인. 청중에 맞춰 적절한 레벨을 고른다.

## 3. 수직(Vertical) vs 수평(Horizontal) 트래픽

흔히 **North-South / East-West**로도 불린다.

| | 수직(Vertical / North-South) | 수평(Horizontal / East-West) |
|---|---|---|
| 방향 | **외부 ↔ 시스템**(클라이언트↔서버) | **시스템 내부 서비스 ↔ 서비스** |
| 통과 지점 | API 게이트웨이·로드밸런서 | 서비스 간 직접/메시·서비스 메시 |
| 예 | 브라우저→API, 외부 클라이언트 | 마이크로서비스 간 호출 |

> **설계 관점:** 외부에 노출하는 수직 API와 내부 수평 API는 고려사항이 다르다 — 보안(수직=OAuth/공개 인증, 수평=mTLS), 버전 관리, 성능 기대치. "어느 트래픽의 API인가"에 따라 원칙이 달라진다.
> *(※ 책 고유 정의가 위와 다르면 보정 필요 — 일반 통용 정의로 정리함)*

## 4. ADR (Architecture Decision Record)

**ADR** = 중요한 **아키텍처 결정을 기록**하는 경량 문서. "왜 이 결정을 했는지"를 미래의 팀과 자신에게 남긴다.

널리 쓰이는 **Michael Nygard 템플릿**:

| 항목 | 내용 |
|------|------|
| **Title** | 결정 요약 제목 (예: "API 인증에 JWT 사용") |
| **Status** | Proposed / Accepted / Deprecated / Superseded |
| **Context** | **왜** 필요한가 — 배경·제약·문제 상황 |
| **Decision** | **무엇을** 하기로 했나 |
| **Consequences** | **결과** — 긍정/부정 영향, 트레이드오프 |

> 시간이 지나면 "왜 이렇게 했지?"를 잊는다. 결정의 **맥락·대안·이유**를 박제해 나중에 그 결정을 뒤집을지 판단하는 근거로 삼는다. 특히 `Consequences`에 트레이드오프를 적는 게 핵심.
> *(※ 책이 추가 항목(Alternatives/Date/Deciders 등)을 제시했다면 보정 필요)*

## 핵심 정리

- **In/Out-of-process** — 경계를 넘느냐가 직렬화·실패·버전 문제를 결정. 이 책은 out-of-process 대상.
- **C4** — Context→Container→Component 줌인. Container는 Docker 아닌 "실행 단위".
- **수직/수평 트래픽** — 외부↔시스템(수직) vs 서비스 간(수평), 설계 고려가 다름.
- **ADR** — Context·Decision·Consequences로 "왜"를 기록.

## 주의사항

- C4 "Container" ≠ Docker 컨테이너 (가장 흔한 오해)
- 다이어그램은 청중에 맞는 레벨로 — Context를 개발자에게, Code를 경영진에게 들이밀지 말 것
- ADR의 `Consequences`(트레이드오프)를 비우지 말 것 — 결정의 핵심은 "무엇을 포기했나"
