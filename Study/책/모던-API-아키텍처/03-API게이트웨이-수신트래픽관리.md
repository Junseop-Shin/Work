# 3장. API 게이트웨이 — 수신 트래픽 관리

> 2026-06-10 | API Gateway, 서비스 메시, 사이드카, gRPC, SSL Termination, Rate Limiting, Build vs Buy

## 한 줄 요약

외부 트래픽이 내부 서비스에 닿기 전에 인증·라우팅·변환·제어를 일괄 처리하는 경계 레이어. 각 서비스가 중복 구현하던 횡단 관심사를 한 곳으로 뽑아낸다.

---

## 책 원문 구조

### API 게이트웨이가 유일한 해법인가?

책은 "외부 요청을 내부 백엔드로 라우팅하는 방법은 다양하다"는 전제로 시작한다.
API 게이트웨이 없이도 nginx 리버스 프록시 + 앱 내 인증으로 충분한 케이스가 있고,
MSA 규모가 커질수록 전용 게이트웨이의 필요성이 올라간다.

### API 게이트웨이란?

소비자(클라이언트)와 백엔드 서비스 사이 **네트워크 엣지에 위치**하는 중개 컴포넌트.

핵심 기능:
- 요청/응답 변환
- 백엔드 서비스 집계(Aggregation)
- 인증 및 인가
- 트래픽 제어 및 Rate Limiting

### API 게이트웨이를 쓰는 이유 (책 6가지)

| 이유 | 설명 |
|-----|-----|
| **결합도 감소** | 프론트-백엔드 간 어댑터/퍼사드 역할, 변경 영향 범위 제한 |
| **소비 간소화** | 여러 백엔드 서비스 집계, 데이터 형식 통합 |
| **과다 사용 방지** | 위협 탐지, Rate Limiting, 접근 제어 |
| **사용 패턴 이해** | 관찰성(Observability) 제공, 로깅·분석 |
| **API 제품화** | 라이프사이클 관리, 버전 관리 |
| **수익화** | 계정 관리, 청구, 결제 처리 |

### API 게이트웨이의 역사적 진화

| 시대 | 기술 | 특징 |
|-----|-----|-----|
| 1990년대~ | 하드웨어 로드밸런서 | 기본 트래픽 분산 |
| 2000년대~ | 소프트웨어 로드밸런서 | 유연성 증가 |
| 2000년대 중반 | ADC(애플리케이션 전달 컨트롤러) | 애플리케이션 인식 기능 |
| 2010년대 초 | 1세대 API Gateway | API 관리 기능 도입 |
| 2015년~ | 2세대 API Gateway | 마이크로서비스 친화적, 경량화 |

### 현대적 API 게이트웨이 유형

**전통적 엔터프라이즈 게이트웨이**
- 중앙 집중식 배포, 강력한 관리 기능
- 모놀리식·레거시 아키텍처 대상

**마이크로서비스 게이트웨이**
- 경량화, 컨테이너 환경 최적화
- 책 실습 예시: Ambassador Edge Stack (Kubernetes)
  - URL 경로 기반 매핑
  - 호스트 기반 라우팅

**서비스 메시**
- 서비스 간 트래픽 관리 (East-West)
- 사이드카 프록시 패턴
- 네트워크 계층에서 투명하게 관리

### 케이스 스터디: Conference System

책이 Ambassador Edge Stack으로 Kubernetes에 게이트웨이를 붙이는 흐름을 실습으로 보여준다:
- Attendee Service를 외부 소비자에게 노출
- URL 경로 기반 매핑 → 호스트 기반 라우팅 → 백엔드 자동 연결

### 배포 시 실패 관리

**단일 장애점(SPOF) 대응**
- 게이트웨이 다운 = 전체 서비스 중단
- 다중화·이중화 + 자동 페일오버 필수

**문제 감지 및 소유권**
- 모니터링·알림 구성
- 팀별 역할 명확히 정의

**위험 완화 패턴**
- Rate Limiting, 서킷 브레이커, Graceful Shutdown

### 흔한 구현 함정 (책 경고)

| 함정 | 설명 |
|-----|-----|
| **API Gateway Loopback** | 게이트웨이가 다른 게이트웨이를 통해 요청 → 성능 저하 + 복잡성 |
| **ESB처럼 사용** | 비즈니스 로직을 게이트웨이에 구현 → 관리 복잡도 폭발 |
| **계층 과잉 (Turtles All the Way Down)** | 네트워킹 레이어를 과도하게 쌓음 → 운영 복잡성 급증 |

### API 게이트웨이 선택 가이드 (Build vs Buy)

**요구사항 식별 항목**
- 트래픽 규모
- 기능 요구사항 (인증, rate limit, 집계 등)
- 배포 모델 (클라우드/온프레미스/하이브리드)
- 조직의 운영 능력
- 예산 제약

| | Buy (관리형) | Build (자체 호스팅) |
|--|------------|-----------------|
| 장점 | 빠른 배포, 유지보수 용이, 표준화 | 맞춤화 가능, 내부 정책 완전 제어 |
| 단점 | 커스터마이징 한계, 벤더 종속 | 높은 초기 비용, 지속적 운영 부담 |

책은 선택 근거를 **ADR(Architecture Decision Record)** 로 문서화하도록 권장한다.

## 심화 개념 (대화 기반 확장)

### 인프라 계층 전체 비교

```
클라이언트
    ↓
[로드밸런서]       L4 — IP/포트 레벨 트래픽 분산
    ↓
[리버스 프록시]    L7 — SSL 종료, 캐싱, 정적파일 (nginx 등)
    ↓
[API 게이트웨이]   비즈니스 레벨 — 인증, 인가, rate limit, 변환
    ↓
서비스들
```

### 어댑터 vs 퍼사드 패턴

| 패턴 | 역할 | 게이트웨이 적용 예 |
|-----|-----|----------------|
| **어댑터** | 호환 안 되는 인터페이스 변환 | REST↔gRPC, REST↔SOAP |
| **퍼사드** | 여러 서브시스템을 단일 인터페이스로 | BFF — 주문+재고+배송 API를 하나로 묶어 반환 |

### SSL Termination

```
클라이언트 → [HTTPS] → 게이트웨이 (인증서 관리)
                            ↓ 내부망 [HTTP]
                       서비스들
```

외부 CA 인증서 import(BYO Certificate) 가능. 와일드카드 인증서(`*.company.com`)로 도메인 통일이 가장 깔끔하다.

### 인증 구조 — 게이트웨이 vs Auth 서버

```
로그인 시:  사용자 → Auth 서버 → JWT 발급
이후 요청:  사용자 → 게이트웨이 → JWT 서명 검증 (Auth 서버 불필요)
                                 ↓ 강제 무효화 필요 시만
                              [Redis 블랙리스트 or Auth 서버 조회]
```

> Auth 서버는 "발급소", 게이트웨이는 "검문소".

경로별 다른 인증 정책 (선언적 설정):

```
/api/public/*   → 인증 없음
/api/user/*     → JWT 검증
/api/admin/*    → JWT + Role 체크
/api/partner/*  → API Key (B2B)
```

### Rate Limiting + Redis

게이트웨이를 스케일아웃하면 인스턴스마다 카운터가 분리된다. Redis에 카운터 공유로 해결.

```
GW1 ─┐
GW2 ─┼─→ [Redis]  user:123:count = 247  (TTL 60s)
GW3 ─┘
```

Redis의 추가 용도:

| 용도 | 내용 |
|-----|-----|
| Rate limit 카운터 | 인스턴스 간 공유 |
| 토큰 블랙리스트 | 강제 만료된 JWT 저장 |
| Auth 서버 응답 캐싱 | 동일 토큰 재검증 비용 절감 |

### 스케일아웃 전략

```
[로드밸런서]
   ↙   ↓   ↘
GW1  GW2  GW3   ← 무상태(stateless) 필수
      ↓
   [Redis]
      ↓
   서비스들
```

무상태 설계 원칙:
- 세션을 인스턴스 메모리에 두지 않음 → JWT 사용
- rate limit 카운터를 로컬에 두지 않음 → Redis 공유

### 프로토콜 변환 (REST → gRPC)

**`.proto` 스키마 등록이 전제다. 설정 한 줄로 자동 변환되지 않는다.**

```protobuf
service OrderService {
  rpc GetOrder (OrderRequest) returns (OrderResponse) {
    option (google.api.http) = {
      get: "/orders/{order_id}"   // REST 매핑 명시
    };
  }
}
```

`protoc-gen-openapiv2`로 `.proto` → OpenAPI 스펙 자동 생성 가능 → 단일 소스로 내외부 문서 관리.

내부에 gRPC를 쓰는 이유:

| | REST (외부) | gRPC (내부) |
|--|------------|------------|
| 형식 | JSON (텍스트) | Protobuf (바이너리) |
| 속도 | 상대적으로 느림 | 빠름 |
| 스키마 | 느슨함 | 강타입 강제 |
| 스트리밍 | 어색함 | 네이티브 지원 |

### 서비스 메시 — 사이드카 패턴

서비스 메시는 중앙 허브가 아니다. **각 서비스 옆에 사이드카가 분산 배치**된다.

```
[컨트롤 플레인] × 1  ← 설정/정책 중앙 관리, 라우팅 테이블 배포
        ↓ 자동 배포
[주문] + [사이드카]
[재고] + [사이드카]   ← 서비스 수 n개
[배송] + [사이드카]
```

Kubernetes + Istio: 네임스페이스 라벨(`istio-injection: enabled`) 하나로 사이드카 자동 주입.
정책 변경 → 컨트롤 플레인에서 한 번 → 전체 전파.

오버헤드: 사이드카 1개당 메모리 ~50–100MB, 레이턴시 ~1ms 추가.

서비스 메시 도입 기준:

| 상황 | 판단 |
|-----|-----|
| 서비스 3~5개 | 직접 통신으로 충분 |
| 서비스 20개+ | 메시 적합 |
| 다국어 환경 | 언어 무관하게 사이드카가 처리 |

### 다중 프로토콜 수신 패턴 (IoT)

```
IoT 기기     → MQTT  ┐
웹 클라이언트 → HTTP  ┼→ [프로토콜 게이트웨이] → [API 게이트웨이] → 서비스들
레거시 시스템 → SOAP ┘
```

IoT + AI 파이프라인 구조:

```
[프로토콜 게이트웨이]
        ↓
   [Kafka]   ← IoT 데이터 버퍼 (폭발적 수신량 흡수, 재처리 가능)
     ↓              ↓
[AI 분석]      [일반 백엔드]
              [API 게이트웨이 + 서비스 메시]
```

## 핵심 질의응답

**Q. API 게이트웨이는 MSA에서만 필요한가?**
A. 꼭 그렇지 않다. 모놀리식 + 외부 API 노출 상황에서도 쓰지만, 모놀리식이면 nginx + 앱 내 인증으로 충분한 경우가 많다. MSA에서 필요성이 가장 높다.

**Q. 인증 로직을 게이트웨이 자체에 심는가, 별도 Auth 서버에 두는가?**
A. 둘 다 쓴다. JWT 서명 검증처럼 매 요청마다 빠르게 처리해야 하는 건 게이트웨이가 자체 처리. 로그인·토큰 발급·권한 정책 관리는 Auth 서버가 담당. 강제 무효화 때만 Redis나 Auth 서버를 조회한다.

**Q. REST → gRPC 변환이 설정값 한 줄로 자동 되는가?**
A. 아니다. `.proto` 스키마 등록 + HTTP 매핑 어노테이션이 선행되어야 한다. 게이트웨이(Envoy 등)는 그 스키마를 보고 변환한다.

**Q. 서비스 메시에서 사이드카가 n개인데 관리 부담이 크지 않은가?**
A. 컨트롤 플레인 1개가 전체 사이드카에 설정을 자동 배포하므로 개별 관리 불필요. Kubernetes에선 사이드카 주입도 자동이다. 단, 메모리·레이턴시 오버헤드는 실재한다.

**Q. 서비스 메시는 중앙 게이트웨이 1개인가?**
A. 아니다. 각 서비스 옆에 사이드카가 n개 분산 배치된다. 컨트롤 플레인은 두뇌(설정 배포)이고, 실제 트래픽은 사이드카끼리 직접 통신한다.

## 주의사항 / 자주 하는 실수

- **Gateway Loopback**: 게이트웨이가 다른 게이트웨이를 통해 요청하는 순환 구조 — 성능 저하, 추적 어려움
- **ESB화**: 비즈니스 로직을 게이트웨이에 넣으면 관리 복잡도 폭발 — 게이트웨이는 횡단 관심사만
- **레이어 과잉**: 필요 없는 계층 추가는 운영 복잡성만 늘림 — 필요한 레이어만
- **무상태 설계 누락**: 인스턴스 로컬에 세션·카운터 두면 스케일아웃 의미 없음
- **서비스 메시 조기 도입**: 서비스 5개 미만에선 오버엔지니어링
