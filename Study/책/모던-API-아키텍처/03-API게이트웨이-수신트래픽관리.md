# 3장. API 게이트웨이 — 수신 트래픽 관리

> 2026-06-10 | API Gateway, 서비스 메시, 사이드카, gRPC, SSL Termination, Rate Limiting

## 한 줄 요약

외부 트래픽이 내부 서비스에 닿기 전에 인증·라우팅·변환·제어를 일괄 처리하는 경계 레이어. 각 서비스가 중복 구현하던 횡단 관심사를 한 곳으로 뽑아낸다.

---

## 핵심 개념

### API 게이트웨이란

외부 클라이언트와 내부 마이크로서비스 사이에 위치해 모든 인바운드 요청을 한 번 통과시키는 레이어.

```
클라이언트
    ↓
[API 게이트웨이]  ← 인증, 인가, SSL, rate limit, 라우팅, 변환
    ↓
마이크로서비스들  ← 비즈니스 로직만
```

### 게이트웨이가 해결하는 문제

게이트웨이 없이 각 서비스가 모두 구현해야 하는 것들:

- 인증 / 인가
- Rate Limiting
- SSL 처리
- 프로토콜 변환
- 로깅 / 트레이싱

서비스가 10개면 10번 중복. 게이트웨이가 이를 한 곳으로 집중시킨다.

### 어댑터 패턴 vs 퍼사드 패턴

게이트웨이가 두 패턴 모두 구현한다.

| 패턴 | 역할 | 게이트웨이 적용 예 |
|-----|-----|----------------|
| **어댑터** | 호환 안 되는 인터페이스 변환 | REST↔gRPC, REST↔SOAP 프로토콜 변환 |
| **퍼사드** | 여러 서브시스템을 단일 인터페이스로 | BFF — 주문+재고+배송 API를 하나로 묶어 반환 |

핵심 차이: **어댑터는 형식 변환, 퍼사드는 복잡도 은닉.**

## 인프라 계층 비교

트래픽 흐름 순서:

```
클라이언트
    ↓
[로드밸런서]       IP/포트 레벨 — 트래픽 분산만
    ↓
[리버스 프록시]    HTTP 이해 — SSL 종료, 캐싱, 정적파일 (nginx 등)
    ↓
[API 게이트웨이]   비즈니스 레벨 — 인증, 인가, rate limit, 변환
    ↓
[서비스들]
```

| 컴포넌트 | 인식 레벨 | 핵심 역할 |
|---------|---------|---------|
| 로드밸런서 | L4 (IP/포트) | 트래픽 분산 |
| 프록시 | 클라이언트 앞 | 클라이언트 신원 대리 |
| 리버스 프록시 | L7 (HTTP) | 서버 구조 은닉, SSL, 캐싱 |
| API 게이트웨이 | 비즈니스 로직 | 인증·인가·rate limit·변환 |

nginx로 API 게이트웨이를 흉내 낼 수 있지만, 인증·모니터링·변환 기능은 전부 직접 구현해야 해서 한계가 있다.

---

## 주요 기능

### SSL Termination

게이트웨이가 인증서를 소유하고 HTTPS를 끊는다. 내부는 HTTP로 통신.

```
클라이언트 → [HTTPS] → 게이트웨이 (인증서 관리)
                            ↓
                      내부망 [HTTP] → 서비스들
```

외부 CA(DigiCert, 사내 PKI 등)의 인증서도 가져와서 쓸 수 있다(BYO Certificate).
와일드카드 인증서(`*.company.com`)를 게이트웨이에 올리면 도메인 통일이 가장 깔끔하다.

### 인증 / 인가 처리 구조

게이트웨이가 모든 인증을 직접 하는 게 아니라 **역할을 분리**한다.

| 주체 | 하는 일 |
|-----|--------|
| **게이트웨이** | JWT 서명 검증, 만료 확인 — 매 요청마다 빠르게 |
| **Auth 서버** | 로그인, 토큰 발급, 권한 정책 관리 |

JWT는 서명 자체로 위변조 검증이 가능해서 게이트웨이가 Auth 서버에 매번 묻지 않아도 된다.
강제 로그아웃·계정 정지처럼 토큰을 무효화해야 할 때만 Auth 서버(또는 Redis 블랙리스트)를 조회한다.

> Auth 서버는 "발급소", 게이트웨이는 "검문소".

경로별로 다른 인증 정책을 선언적으로 적용할 수 있다:

```
/api/public/*    → 인증 없음
/api/user/*      → JWT 검증
/api/admin/*     → JWT + Role 체크
/api/partner/*   → API Key (B2B)
/api/payment/*   → JWT + IP 화이트리스트
```

### Rate Limiting + Redis 조합

게이트웨이를 스케일아웃하면 인스턴스끼리 카운터가 분리되는 문제가 생긴다.
Redis에 카운터를 공유하면 해결된다.

```
GW1 ─┐
GW2 ─┼─→ [Redis] ← 카운터 공유 (TTL 60s)
GW3 ─┘
```

Redis는 rate limit 외에도 다음 용도로 자주 쓰인다:

| 용도 | 내용 |
|-----|-----|
| Rate limit 카운터 | 인스턴스 간 공유 |
| 토큰 블랙리스트 | 강제 만료된 JWT 저장 |
| Auth 서버 응답 캐싱 | 동일 토큰 재검증 비용 절감 |

### 프로토콜 변환 (REST → gRPC)

게이트웨이가 외부는 REST로 받고 내부는 gRPC로 전달할 수 있다.

```
외부 클라이언트 (REST/HTTP)
        ↓
[API 게이트웨이: 프로토콜 변환]
        ↓
  서비스 (gRPC / Protobuf)
```

**변환은 단순 설정값이 아니다. `.proto` 스키마가 반드시 필요하다.**

```protobuf
service OrderService {
  rpc GetOrder (OrderRequest) returns (OrderResponse) {
    option (google.api.http) = {
      get: "/orders/{order_id}"   // REST 매핑 명시
    };
  }
}
```

`protoc-gen-openapiv2`로 `.proto` → OpenAPI 스펙 자동 생성도 가능해서,
단일 소스(.proto)로 내부 계약과 외부 문서를 함께 관리할 수 있다.

내부에 gRPC를 쓰는 이유:

| | REST (외부) | gRPC (내부) |
|--|------------|------------|
| 형식 | JSON (텍스트) | Protobuf (바이너리) |
| 속도 | 상대적으로 느림 | 빠름 |
| 스키마 | 느슨함 | 강타입 강제 |
| 스트리밍 | 어색함 | 네이티브 지원 |

## 스케일아웃 전략

모든 요청이 게이트웨이를 거치므로 병목이 될 수 있다. 표준 해법은 **스케일아웃 + 로드밸런서**다.

```
클라이언트
      ↓
[로드밸런서]
   ↙   ↓   ↘
GW1  GW2  GW3
      ↓
[Redis]   ← 공유 상태
      ↓
서비스들
```

스케일아웃이 잘 되려면 게이트웨이가 **무상태(stateless)** 여야 한다:

- 세션을 인스턴스 메모리에 두지 않는다 → JWT 사용
- rate limit 카운터를 로컬에 두지 않는다 → Redis 공유

## API 게이트웨이 유형

### 마이크로서비스 게이트웨이 vs 서비스 메시 게이트웨이

| | 마이크로서비스 게이트웨이 | 서비스 메시 게이트웨이 |
|--|----------------------|-------------------|
| 방향 | 외부→내부 (North-South) | 내부↔내부 (East-West) |
| 역할 | 인증, SSL, rate limit, 라우팅 | 재시도, mTLS, 서킷브레이커, 트레이싱 |
| 대표 | Kong, AWS API GW | Istio Ingress, Consul |

Envoy 기반 도구(Istio 등)는 두 역할을 하나의 기술 스택으로 처리할 수 있다.
단, **설정과 정책은 외부/내부를 분리 관리하는 게 권장된다**.

### 서비스 메시 동작 방식

서비스 메시는 중앙 허브가 아니다. **사이드카 프록시가 각 서비스 옆에 분산 배치**된다.

```
[컨트롤 플레인] × 1  ← 라우팅 테이블·정책 배포
        ↓
[주문] + [사이드카]
[재고] + [사이드카]   ← 서비스 수 n개
[배송] + [사이드카]
```

- Kubernetes + Istio 환경에서는 네임스페이스 라벨 하나(`istio-injection: enabled`)로 사이드카 자동 주입
- 정책 변경은 컨트롤 플레인에서 한 번 → 전체 사이드카에 자동 전파
- 사이드카 1개당 메모리 약 50~100MB, 레이턴시 약 1ms 추가

서비스 메시 도입 기준:

| 상황 | 판단 |
|-----|-----|
| 서비스 3~5개 | 직접 통신으로 충분 |
| 서비스 20개+ | 서비스 메시 적합 |
| 다국어 환경 | 언어 무관하게 사이드카가 처리 |
| 규모 작은 팀 | 오버엔지니어링 가능성 높음 |

## 관리형 vs 자체 호스팅

| | 관리형 (AWS/Cloudflare) | 자체 호스팅 (Kong/KrakenD) |
|--|------------------------|--------------------------|
| 커스터마이징 | 플러그인/함수 범위 내 | 거의 무제한 |
| 인프라 관리 | 불필요 | 직접 운영 |
| 비용 | 트래픽 기반 과금 | 서버 고정 비용 |

관리형도 커스텀 로직 주입이 가능하다. "코드 직접 배포"가 아니라 "함수/플러그인 주입" 방식이다:

| 서비스 | 방식 |
|-------|------|
| AWS API Gateway | Lambda Authorizer |
| Cloudflare | Workers (JS 엣지 실행) |
| Kong | Lua 플러그인 |

## API 문서화 전략

프로토콜 변환이 있으면 외부 인터페이스와 내부 구현이 달라진다.

| 대상 | 문서 형식 | 기준 |
|-----|---------|-----|
| 외부 REST API | OpenAPI/Swagger | 게이트웨이 노출 엔드포인트 기준 |
| 내부 gRPC | `.proto` 파일 | 서비스 계약 |
| 통합 | `protoc-gen-openapiv2` | `.proto` → OpenAPI 자동 생성 |

프론트엔드는 게이트웨이 Swagger만 보면 된다. 내부가 gRPC로 바뀌어도 외부 계약만 유지되면 무관하다.

## 다중 프로토콜 수신 패턴 (IoT/이벤트)

IoT 또는 다양한 소스가 있는 환경에서는 게이트웨이 앞에 **프로토콜 게이트웨이** 레이어를 추가한다.

```
IoT 기기     → [MQTT]
웹 클라이언트 → [HTTP/REST]  → [프로토콜 게이트웨이] → [API 게이트웨이] → 서비스들
레거시 시스템 → [SOAP]
파트너사     → [AMQP]
```

IoT + AI 파이프라인이 있으면 Kafka 레이어도 추가된다:

```
[프로토콜 게이트웨이]
        ↓
  [Kafka]  ← 데이터 파이프라인 버퍼 (폭발적 IoT 데이터 흡수, 재처리 가능)
        ↓              ↓
[AI 분석 서비스]  [일반 백엔드 서비스]
        ↓              ↓
  [API 게이트웨이] + [서비스 메시]
```

## 핵심 질의응답

**Q. API 게이트웨이는 MSA에서만 필요한가?**
A. 반드시 그렇지 않다. 모놀리식 + 외부 API 노출 상황에도 쓰지만, MSA에서 가장 필요성이 높다. 모놀리식이면 nginx + 앱 내 인증으로 충분한 경우가 많다.

**Q. 인증 로직을 게이트웨이 자체에 심는가, 별도 Auth 서버에 두는가?**
A. 둘 다 쓴다. JWT 서명 검증·만료 확인처럼 매 요청마다 빠르게 처리해야 하는 것은 게이트웨이가 자체 처리. 로그인·토큰 발급·권한 정책 관리는 Auth 서버가 담당. 강제 무효화가 필요할 때만 Redis 블랙리스트나 Auth 서버를 조회한다.

**Q. REST → gRPC 변환이 설정값 하나로 자동 되는가?**
A. 아니다. `.proto` 스키마 등록이 전제다. `google.api.http` 어노테이션으로 REST 매핑을 proto에 명시해두면 게이트웨이(Envoy 등)가 자동 변환한다.

**Q. 서비스 메시에서 사이드카가 n개인데 관리가 어렵지 않은가?**
A. 컨트롤 플레인 1개가 모든 사이드카에 설정을 자동 배포하므로 개별 관리 불필요. Kubernetes에서는 사이드카 주입도 자동이다. 대신 사이드카당 메모리·레이턴시 오버헤드는 실재한다.

**Q. 서비스 메시는 중앙 게이트웨이 1개인가?**
A. 아니다. 각 서비스 옆에 사이드카 프록시가 n개 붙어 분산 동작한다. 중앙 컨트롤 플레인은 설정을 배포하는 두뇌 역할이고, 실제 트래픽은 사이드카끼리 직접 통신한다.

## 주의사항 / 자주 하는 실수

- **게이트웨이 = 단일 실패점(SPOF)**: 반드시 스케일아웃 + 로드밸런서 구성 필요. Redis도 클러스터로 운영.
- **무상태 설계 전제**: 인스턴스 로컬에 세션·카운터 두면 스케일아웃 의미 없음.
- **서비스 메시를 소규모에 도입**: 서비스 5개 미만에선 사이드카 오버헤드가 이점보다 크다.
- **gRPC 변환 = 설정 한 줄 착각**: proto 스키마 + HTTP 매핑 설계가 선행되어야 함.
- **외부/내부 정책 혼재**: 하나의 게이트웨이가 두 역할을 할 수 있어도, 설정은 반드시 분리 관리.
