# 패치해둔 라이브러리가 어느 날 다시 취약 버전으로 돌아가 있었던 사건

> 2025.12 · 보안 · React · Next.js · AI 코딩 · 사고

- **기간** · 2025.12
- **팀 / 역할** · 사고 분석 + 사후 조치
- **스택** · React, Next.js (서버 컴포넌트), GitHub Rulesets
- **핵심** · 서버 컴포넌트 XSS 패치 후 동료가 AI 코드 검증 없이 머지 → 의존성 다운그레이드로 패치 무력화 → GitHub Rulesets로 동료 동선 레포 전반에 PR 리뷰 1+ 강제

---

작년에 React/Next.js의 서버 컴포넌트 관련 XSS 취약점이 알려졌고, 우리는
빠르게 최신 버전으로 패치를 깔았다. 그게 끝인 줄 알았다. 그런데 시간이
좀 지난 어느 시점에 운영 VM에서 이상한 현상이 생겼고, 한참 디버깅한
끝에 **사실은 그 사이에 누군가가 우리 의존성을 다시 취약 버전으로
되돌려놨다**는 걸 알게 됐다. 패치가 한 번 무력화됐다 다시 깔린 사이에
공격이 들어와 있었다.

## 어떻게 시작됐나

작년 어느 시점에 React 쪽에서 서버 컴포넌트 관련 XSS 보안 취약점이
공개됐다. 정확한 표면적 영향이야 환경마다 다르지만, 우리 서비스는
영향권 안에 있었다. 그래서 보안팀과 협의한 뒤, **취약점이 패치된 최신
버전으로 의존성을 올리는 작업을 빠르게 마무리**했다. 배포까지 들어가고
나서, 적어도 이 사안에 대해서는 이제 안전하다고 생각하고 다음 일로
넘어갔다.

## VM이 이상하다는 알림에서 시작된 추적

시간이 좀 지난 뒤 운영 VM에서 의심스러운 현상이 보고됐다. 응답이 평소와
다르거나, 의도하지 않은 동작이 보이거나, 모니터링 지표가 미묘하게
어긋나는 종류였다. 처음엔 인프라 이슈를 의심했다. 그쪽이 정상이면
배포된 코드 변경을 의심했고, 그것도 별 이상이 없어 보이면 외부 의존성을
의심했다. 한참을 헤맸다.

결국 **공격받은 흔적**이 보였다. 하필 우리가 한참 전에 패치를 깔아둔,
바로 그 서버 컴포넌트 XSS 취약점을 노린 공격이었다. 그제야 머릿속이
복잡해졌다. **"우린 분명히 패치 깔았는데 왜?"** 그게 그날 가장 풀리지
않는 질문이었다.

## 알고 보니 패치가 한 번 무력화돼 있었다

`package.json`과 lockfile, 최근 머지된 PR을 거슬러 올라가다가 진짜 원인을
찾았다. 그 사이에 머지된 어느 PR에서 **문제의 라이브러리 버전이 다시
취약 버전 쪽으로 내려가** 있었다. 패치를 깔아둔 우리 운영 환경에는
그 PR이 머지·배포되는 순간 **다시 취약 상태가 되돌아간 시점이 분명히
존재**했고, 공격은 그 창문을 그대로 노렸다.

문제의 PR을 들여다보니 패턴이 명확했다. **동료가 AI에게 받은 코드를
별도 검증 없이 그대로 머지한 것**이었다. AI가 만든 코드 자체가 의도적
악성은 당연히 아니지만, 같이 따라온 의존성 변경이나 lockfile 업데이트가
**기존에 우리가 명시적으로 올려뒀던 패치 버전을 덮어쓰면서 다운그레이드**
시켰다. 머지하는 사람이 그걸 한 번도 들여다보지 않았다는 것이 그날의
진짜 사고였다.

코드 리뷰만 정상적으로 돌았어도 잡혔을 변경이었다. 그런데 그 PR은
**리뷰 없이 빠르게 통과**됐고, CI에도 의존성 다운그레이드를 잡아낼
게이트가 없었다. 우리가 깔아둔 패치가 한 번의 머지로 한순간에 깔끔하게
사라진 셈이다.

## 그래서 무엇을 배웠나

이 사건을 정리하면서 가장 무거웠던 깨달음은, **"AI가 짠 코드라는
이유로 검증 부담을 사람이 더 가져가야 한다"** 는 것이었다. AI가 의도적
악성 코드를 짜는 건 아니지만, AI는 보통 **현재 우리 환경의 보안 컨텍스트를
모른다**. "이 라이브러리는 우리가 보안 패치 때문에 명시적으로 올린
버전이다" 같은 사정이 모델한테는 안 보인다. 그래서 AI가 만든 패치/업그레이드
제안엔 **사람이 더 꼼꼼히** 의존성과 lockfile 변경을 들여다봐야 한다.
체감적으론 AI 시대 들어 오히려 코드 리뷰의 가치가 올라갔다. 빠르게
짤 수 있다는 것의 반대편에 빠르게 사고 칠 수 있다는 게 늘 같이 있다.

두 번째로, **CI에 의존성 보안 게이트가 없었다는 게 사고를 키운 결정적
구멍**이었다. 사람이 리뷰를 빼먹어도, 자동화가 한 번 더 잡아주는
게이트가 있었으면 이 사고는 안 났다. 머지 시점에 의존성 취약점 스캔과
"패치 버전 이하로 내려가는 변경"을 막는 정책이 필요하다는 결론이
명확해졌다. 메인 브랜치 보호와 필수 리뷰어 정책도 같이.

세 번째는 **공격 흔적이 코드 변경 이력으로 거꾸로 검증 가능하다**는
점이었다. "왜 패치 깔았는데 공격이 들어왔지?" 라는 질문에 답하려면
**그 사이의 모든 의존성 변경 이력**을 다시 봐야 한다. 평소엔 잘 안
보는 lockfile diff가 그날 가장 중요한 자료였다.

사후 조치로 가장 먼저 한 일은, **그 직원이 같이 일하는 레포 전반에
GitHub Rulesets으로 "PR 머지 시 최소 1명 이상 리뷰 승인 필수"** 룰을
걸어둔 것이었다. 응급 처치 성격이긴 했지만, 같은 패턴(검증 없이 그대로
머지)이 다시 나오는 길을 그 사람 동선 전체에서 일단 막은 셈이다.

다만 이건 응급 처치고, 더 본질적으로는 두 가지가 더 따라가야 한다.
하나는 **알려진 취약 버전으로의 다운그레이드를 머지 시점에 차단하는
CI 게이트**. 사람이 리뷰를 빼먹어도 자동화가 잡아줘야 한다. 다른 하나는
**AI가 만든 코드를 머지할 때 따라야 할 팀 차원의 체크리스트** — 적어도
의존성·환경 변수·시크릿·권한 변경은 사람이 한 번 눈으로 따라가는 흐름이
정해져 있어야 한다. 도구가 빨라질수록 사람이 챙겨야 할 검증의 결이
달라진다는 걸, 이 사건이 가장 비싸게 가르쳐줬다.
