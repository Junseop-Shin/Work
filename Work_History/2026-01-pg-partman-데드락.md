# 매일 09시 30분에 도는 cron이 데드락을 만드는 줄도 모르고

> 2026.01 · PostgreSQL · pg_partman · 데드락

- **기간** · 2026.01
- **팀 / 역할** · 본인 주도 분석·수정
- **규모** · 매장 IoT 정기보고 4개 테이블 / 일별 파티션 / 1차 적재는 Azure Table Storage (이중화)
- **스택** · PostgreSQL, pg_partman, pg_cron, advisory lock, ctid 배치 DELETE
- **핵심** · run_maintenance retention drop의 ACCESS EXCLUSIVE LOCK 데드락 분석 → 책임 분리(생성 / 정리) + DELETE 배치 → DROP TABLE 두 단계로 해결, 분리 후 재발 0건

---

PostgreSQL로 옮긴 직후, 파티셔닝까지 같이 손대야 하는 테이블이 **4개**
있었다. 매장 IoT가 게이트웨이로 보내는 정기보고 데이터인데, 게이트웨이가
요구하는 보존 기간은 **딱 2일치**였다. 그 이상은 의미 없는 데이터가 쌓이는
것뿐이고, 한 번에 DELETE를 돌리면 WAL이 폭주하는 종류의 테이블이라 뭔가
정리가 필요했다.

## 어떻게 시작됐나

대상이 된 테이블은 4개였다. 채널별 전력 사용량, 센서 측정값, 원격 디바이스
상태, 그리고 사인(상태) 로그. 모두 시간이 지날수록 부푸는 종류였고, 인덱스
관리·VACUUM 부담·일괄 삭제 비용이 모두 부담스러운 테이블이었다.

`pg_partman`을 쓰기로 했다. PostgreSQL native declarative partitioning을 운영
자동화해주는 익스텐션이고, 미래 파티션 자동 premake (`run_maintenance`)와
retention 기간 지난 파티션의 자동 detach / drop을 둘 다 해준다. 우리 기준에
맞춰서 **일별 파티셔닝, premake 3, retention 2** 로 구성했다. 즉 매일
−2일에서 +3일까지 파티션이 살아 있게 유지하는 그림이었다.

여기서 한 가지 신경 써야 했던 게 **시간대**였다. DB가 UTC로 돌고 있었고,
"오늘 날짜" 파티션은 UTC 기준으로 잘린다. KST 자정에 maintenance를 돌리면
UTC로는 아직 어제고, 그러면 오늘 파티션이 제대로 안 붙는 사고가 난다. 그래서
스케줄을 **KST 09:30 (UTC 00:30)** 에 맞췄다. UTC 자정을 막 넘긴 시점에
돌아야 의도한 대로 다음날 파티션이 premake되기 때문이다. `pg_cron`으로 매일
이 시각에 `pg_partman.run_maintenance()`를 돌리는 식으로 깔았다.

여기까지는 깔끔했다. 문제는 그 다음이었다.

## 서비스가 느려지기 시작한다

처음 깔아둘 때는 멀쩡했다. 한동안 아무 문제 없이 돌았다. 진짜 골치 아픈
건 그 다음에 시작됐는데, **마이그레이션 작업이 진척되면서 PostgreSQL 쪽
트래픽과 데이터 양이 점점 늘어나기 시작한 시점**부터였다. 어느 날부터
서비스 응답이 묘하게 느려진다는 얘기가 나오기 시작했고, 원인이 딱
떨어지지가 않았다. 모니터링 대시보드를 한참을 들여다보다가 데드락
카운트가 유의미하게 올라가고 있는 걸 보고서야 감이 잡혔다.

`pg_partman.run_maintenance()`가 매일 retention 단계에서 노후 파티션을
DROP / detach 한다. 이 작업은 부모 테이블에 **`ACCESS EXCLUSIVE LOCK`** 을
요구한다. 우리 시스템은 매장 게이트웨이가 늘 INSERT/SELECT를 때리는 종류라,
maintenance 윈도우라는 게 따로 존재하지 않는다. 그러니 매일 한 번씩,
maintenance가 락을 잡으려는 순간 운영 트래픽과 순환 대기에 빠져 데드락이
검출되고, PostgreSQL이 victim 트랜잭션을 abort 시키고 있었던 것이다.

다행이라면, 정기보고 데이터의 **1차 저장은 Azure Table Storage로 분리되어
있었다**는 점이었다. PostgreSQL의 4개 파티션 테이블은 게이트웨이의 2일 조회
SLA를 위한 보조 저장소였고, 데이터 유실은 없었다. 영향은 게이트웨이 측 조회
지연과 일부 트랜잭션 abort 정도로 격리됐다. 이 이중화 설계가 결과적으로
안전망 노릇을 해줬다는 게, 사고를 본 뒤의 솔직한 감상이다.

## 책임을 분리하기로 했다

원인이 명확해지고 나서 수정 방향을 잡는 건 어렵지 않았다. **maintenance와
retention drop을 분리**하기로 했다.

`pg_partman` 측 `part_config`에서 retention 옵션을 끄고, run_maintenance는
**미래 파티션 생성과 정합성 점검만** 담당하게 했다. ACCESS EXCLUSIVE LOCK이
걸리는 DROP 동작 자체를 maintenance에서 빼버린 셈이다.

대신 노후 데이터 정리는 별도 프로시저를 만들어 처리했다. **DELETE 배치를
먼저 돌리고, 비워진 파티션을 그 뒤에 DROP TABLE 하는** 두 단계 흐름이다.
데이터가 차 있는 상태에서 DROP을 바로 들어가면 ACCESS EXCLUSIVE LOCK 보유
시간과 WAL 부담이 그대로 쌓이는데, DELETE를 작은 배치로 먼저 비워둔 뒤
빈 파티션을 DROP 하면 락 시간이 짧아져서 운영 트래픽과의 충돌 위험이
훨씬 작아진다.

DELETE 단의 핵심은 세 가지였다. 첫째, **`ctid` + `LIMIT 50000` 배치
DELETE**로 한 트랜잭션이 쥐는 락 시간과 WAL 양을 작게 유지했다. 인덱스
조건만으로 큰 DELETE를 한 번에 돌리면 락 보유 시간이 길어진다. ctid는
물리 위치라서 LIMIT과 자연스럽게 결합되고, 페이지 단위 핀포인트 삭제가
가능하다. 둘째, 배치 사이에 **`pg_sleep(100ms)`** 를 끼워서 운영 워크로드에
숨통을 줬다. 셋째, **`pg_try_advisory_lock`** 으로 cron 중첩이나 수동
재실행 시 동시 실행을 막았다. 이 프로시저는 ROW_COUNT가 0이 될 때까지
루프하면서 idempotent하게 마무리되도록 짰고, **다 비워진 뒤에야 빈
파티션을 DROP TABLE로 정리**한다.

이 분리를 적용한 뒤 데드락은 재발하지 않았다.

## 그래서 무엇을 배웠나

이 사건을 복기하면 핵심은 한 줄이다. **익스텐션의 자동화에 모든 책임을 다
맡기지 말 것.** 특히 우리처럼 트래픽이 끊기지 않는 시스템에서는 더 그렇다.
편한 도구일수록 어디서 락을 잡는지, 어떤 트랜잭션 경계를 가지는지 들여다봐야
한다. `pg_partman`은 좋은 도구지만, retention drop이 운영 워크로드와 같은
시점에 같은 락을 두고 경합한다는 사실을 모른 채로 그냥 켜두면 우리처럼 된다.

두 번째로, **`ACCESS EXCLUSIVE LOCK`이 필요한 작업은 시간과 빈도 둘 다 줄여야
한다**는 걸 새삼 배웠다. 큰 한방 DELETE보다 작은 배치 + sleep이 운영에는
훨씬 안전하다는, 어찌 보면 당연한 원칙을 사고로 다시 확인한 셈이다.

세 번째는 **타임존**이다. DB가 UTC로 돌고 비즈니스가 KST면, 파티션 운영의
시각 결정은 신중해야 한다. KST 자정에 돌렸으면 사고가 더 일찍 났을 것이다.
이건 처음 설계할 때 잘 잡고 갔던 한 가지였다.

마지막으로, **cron 작업은 advisory lock을 깔아두는 게 거의 공짜로 얻는
보험**이라는 것. 스케줄 중첩, 수동 재실행, 백업 시점 겹침 같은 시나리오에서
idempotency를 보장해준다. 처음부터 넣어두는 게 사후 조치보다 훨씬 싸다.

다시 한다면 처음부터 생성과 정리를 분리한 구조로 설계할 것 같고,
`pg_stat_database.deadlocks` 변화나 retention 누락 같은 지표를 모니터링에
연결해두고 시작할 것 같다. 우리는 이미 `pg_notify` Slack 파이프라인이
있으니 거기에 연결하면 큰 비용 없이 얹을 수 있는 일이었다. 사고가 나고
나서야 보이는 것들이지만, 다음 사이클부터는 미리 깔아두려고 한다.
