# 18,000개 매장 시스템의 DB를 6개월에 걸쳐 옮긴 이야기

> 2025.08 ~ 2026.01 · PostgreSQL · 마이그레이션 · 무중단

- **기간** · 2025.08 ~ 2026.01 (약 6개월)
- **팀 / 역할** · 5명 / DB 이관 + 배치 + 일부 백엔드 풀스택 (자진 영역 확장)
- **규모** · 220 테이블 · 약 200GB · 18,000개 매장 실시간 거래 시스템
- **스택** · MariaDB → PostgreSQL (Azure Database for PostgreSQL), DBeaver
- **핵심** · SQL 방언 360건 직접 변환, 1개월 무중단 점진 이관, 2주 안정화

---

회사가 어느 날 결정을 내렸다. Azure를 표준 클라우드로 가져가면서, MariaDB를
PostgreSQL로 옮기겠다는 것이었다. 처음엔 "DB 한 번 갈아끼우는 정도지" 했는데,
그게 **220개 테이블, 약 200GB, 18,000개 매장**이 실시간으로 달려 있는
시스템이라는 걸 본격적으로 들여다보면서부터는 이야기가 달라졌다. 결과적으로
**5명이 약 6개월(2025년 8월 ~ 2026년 1월)** 을 들여서 끝낸 작업이었다.

## 어떻게 시작됐나

회사가 클라우드 표준을 Azure 쪽으로 정리하던 시기였다. 그 흐름에서 매니지드
PostgreSQL을 적극 쓰자는 결정이 내려졌고, 마침 Azure가 자체 MariaDB 매니지드
서비스를 EOL 시킨다고 발표한 시점이라 명분도 충분했다. 트랜잭셔널 DDL이라든가
여러 운영적 장점도 거론됐지만, 솔직히 진짜 동기는 **클라우드 표준화와 EOL
대응**이었다.

내 원래 할당은 백엔드 서버 이관이었다. 그런데 프로젝트가 굴러가기 시작하면서
**남들이 손대기 꺼리는 영역에 공백이 생기는 게 보였다**. 배치도 그랬고,
무엇보다 DB 이관 자체가 그랬다. 이대로 두면 마이그레이션 자체가 막힐 것
같다는 판단이 들어서, 자진해서 그쪽으로 영역을 옮겼다. 결과적으로 이관 작업의
중심에 DB가 들어가게 됐고, 220개 테이블 / 200GB / SQL 방언 변환까지 내가
직접 책임지는 모양이 됐다.

## DBeaver로 한 땀 한 땀

이관 도구를 처음엔 자동화 쪽으로 알아봤다. 하지만 막상 들여다보니 **마스터
테이블들이 신규로 다시 설계된 상태**였다. 단순 복사로 끝낼 수 있는 테이블이
아니었고, 컬럼 매핑·타입 변환을 사람이 일일이 맞춰줘야 했다. 결국 마스터는
DBeaver로 한 테이블씩 손으로 옮겼다.

뒤늦게 후회되는 게 여기다. 마스터 외 나머지 테이블은 사실 단순 이관이었는데,
그쪽까지 같은 결로 처리해버렸다. 그건 pgloader 같은 도구를 썼어야 했다.
"마스터 어차피 손으로 해야 하니까" 라는 관성에 끌려서 단순 이관 테이블에도
같은 노력을 쏟아부은 게, 다시 보면 가장 큰 시간 낭비였다.

## 한 달짜리 무중단 이관

가장 골치 아팠던 건 컷오버였다. 게이트웨이가 매장별 IP에 묶여 있고, 그 IP를
바꾸려면 협력사 쪽 방화벽까지 새로 열어야 했다. **18,000개 매장**을 한
번에 전환한다는 건 비현실적이었다. 그래서 결정한 게 **약 1개월에 걸친
무중단 점진 이관**이었다.

양쪽 DB를 동시에 운영하면서 데이터를 계속 동기화하고, 도메인별로 메인
서비스를 바꾼 다음 그 시점의 차이만큼 다시 보정해주는 식이었다. 글로 쓰면
깔끔해 보이는데, 실제로는 **실시간으로 변동하는 데이터와 아직 안 옮겨진
데이터 사이의 갭**이 사고로 튀어나왔다. 어느 매장에선 분명히 발생한 거래가
새 DB에는 안 들어가 있다든가, 그런 식의 클레임이 한참 들어왔다. 이걸 수동으로
보정하는 데 들어간 시간이 생각보다 컸다.

거기에 또 한 가지, **220개 테이블** 이 너무 많아서 5명이서 도메인별로 나눠
작업했는데, 그 과정에서 한 번 매핑 오류가 나서 일부 테이블 재이관까지
들어갔다. 이쯤 되니 "이걸 무중단으로 한 게 맞나" 싶은 자기 회의가 슬슬
들기 시작했다.

## SQL 방언이 360번씩 부딪힌다

코드 쪽 이슈도 만만치 않았다. 우리 코드베이스 안에 800~900개 정도의 쿼리가
있었는데, 그중 **약 360개를 수정**해야 했다. 단순 함수 이름 차이는 큰일이
아니었다. 진짜 발목을 잡은 건 두 가지였다.

하나는 **GROUP BY 표준 엄격성**이었다. PostgreSQL은 SQL 표준대로 SELECT 절의
모든 비집계 컬럼을 GROUP BY에 명시해야 한다. MariaDB에서 한참을 자유롭게
적어왔던 쿼리들이 이 한 가지 룰 하나에 줄줄이 깨졌다. 이건 단순 치환이
아니라 쿼리 의도를 다시 확인해야 하는 작업이었다.

다른 하나는 **identifier quoting**이었다. PostgreSQL은 큰따옴표로 감싸지
않으면 식별자를 자동으로 lowercase로 바꾼다. MariaDB는 그런 짓을 안 한다.
그래서 `userId` 같은 camelCase alias를 그대로 쓴 쿼리들이 PostgreSQL에선
`userid`가 돼버려서 매칭이 깨졌다. 이건 한 번 패턴을 알면 빠르게 바꿀 수
있었지만, 처음엔 정말 황당했다.

그 외에 `IFNULL` → `COALESCE`, `DATE_FORMAT` → `TO_CHAR`, `TINYINT(1)` →
`BOOLEAN`, `0000-00-00` 같은 비정상 날짜의 strict 거부 같은 것들이 잔뜩
딸려나왔다. 한참을 코드 베이스 안에서 뒤지고 다녔다.

## 안정화 2주, 그리고 회고

DB가 다 옮겨가고 나서도 **약 2주간 자잘한 이슈가 끝없이 나왔다**. 웹과 모바일
양쪽에서 날아오는 핫픽스 이슈들. QA가 충분히 돌아가지 못한 상태로 들어간 게
컸다. 안정화 기간이 그만큼 길어졌다.

이 프로젝트를 다시 한다면 가장 먼저 바꿀 건 **컷오버 전략**이다. 무중단
점진 이관은 듣기에는 멋있지만, 실시간 데이터 갭을 보정하는 비용이 다운타임
비용보다 훨씬 컸다. 차라리 점검 시간을 짧게 잡고 한 번에 전환하는 게 총
비용이 작다는 결론이다.

두 번째는 **자동화 툴을 더 적극적으로 썼어야 한다**는 것. 마스터 테이블
때문에 처음부터 손으로 가던 흐름이 끝까지 발목을 잡았다. 단순 이관 테이블은
처음부터 도구로 분리해서 처리했어야 했다.

세 번째는 **자동 검증 파이프라인**. row count + 체크섬 + 핵심 비즈니스 쿼리
결과 비교를 자동으로 돌렸어야 했다. 우리는 사고를 한 번 겪고 나서야 그
검증을 강화했는데, 처음부터 깔고 시작했으면 데이터 꼬임 자체를 훨씬 일찍
잡아낼 수 있었을 것이다.

PostgreSQL 자체의 큰 장점들 — JSONB, TimescaleDB, PostGIS 같은 익스텐션
생태계 — 은 솔직히 마이그레이션 직후엔 거의 활용을 못 했다. 운영하면서
`pg_notify`로 알림 파이프라인을 깔고, `pg_stat_statements`로 슬로우 쿼리를
잡고, 암묵적 타입 캐스팅으로 인덱스를 못 타는 케이스를 정리하는 정도까지는
왔다. 진짜 PG의 힘을 빌리는 일은 아직 더 남아 있다.
