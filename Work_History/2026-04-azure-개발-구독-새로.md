# 협업사와 갈라지면서 클라우드 구독을 처음부터 다시 깔았다

> 2026.04 · Azure · DevOps · OIDC

- **기간** · 2026.04
- **팀 / 역할** · 본인 / 플랫폼 개발환경 셋업 담당
- **규모** · 신규 Azure 구독 1개, 두 도메인(플랫폼 / CCTV) 환경 분리
- **스택** · Azure (VM, Function App, Service Bus, TableStorage, LogAnalytics, VNet), GitHub Actions OIDC, Self-hosted Runner, EMQX (Docker)
- **핵심** · 협업사 분리 후 새 구독 셋업, 공통 리소스 통합, OIDC 일관 이식, GitHub Actions environment로 새 환경 배포 자동화

---

회사가 협업하던 곳과 결별하기로 했다. 같이 쓰던 Azure 테넌트도 갈라야 했고,
운영 구독은 외주 회사 쪽으로 통째로 넘기는 그림이었다. 우리한테 남은 숙제는
**개발 환경을 처음부터 새로 깔아야 한다**는 것이었다. 그리고 마침 그
김에, 오랫동안 정리해야지 하고 미뤄왔던 일을 같이 처리하기로 했다.

## 어떻게 시작됐나

기존 개발 환경엔 오랜 골칫거리가 있었다. **하나의 구독 안에 플랫폼 서비스와
CCTV 서비스가 같이 들어 있었던** 것이다. 도메인이 다른 두 프로덕트가 같은
구독에서 굴러가니 권한 관리, 비용 추적, 리소스 식별이 다 어지러웠다. 정리해야
한다는 얘긴 늘 있었지만 우선순위에 늘 밀려 있었는데, 테넌트가 갈라지는 김에
같이 분리하기로 했다.

내 몫은 **플랫폼 개발 환경**이었다. 새 Azure 구독을 받아서 처음부터 리소스를
구성하고, 파이프라인까지 다 깔아야 했다.

## 다행이라면 사이징은 이미 있었다

처음부터 사이징을 다시 추산했다면 굉장히 오래 걸렸을 텐데, 운영에서 사용량을
기반으로 이미 최적화해둔 자료가 있었다. 그걸 그대로 가져다 쓰는 식으로 새
구독에 리소스를 다시 만들었다. 처음부터 다시 짜는 부담이 한 단계 줄었다.

리소스를 새로 까는 김에 손볼 만한 것도 같이 정리했다. 기존 환경에선 Function
App마다 별도로 TableStorage와 LogAnalytics 워크스페이스를 만들어 붙여 쓰고
있었는데, 갯수만 늘고 비용·관리 부담만 커지는 구조였다. 이참에 **공통
리소스를 하나로 통일**해서 모든 Function App이 같은 곳을 참조하게 했다.
로그도 한 곳으로 모이니 분석할 때도 편해졌다. 굳이 분리할 이유가 없는 건
처음부터 분리할 필요가 없다.

## OIDC와 self-hosted runner

GitHub Actions의 인증은 OIDC(federated identity) 패턴이 **이전 환경에 일부
이미 적용**되어 있었다. service principal 시크릿을 깔지 않고 federated
identity로 배포하는 그 방식이다. 새 구독에도 일관되게 그대로 이식했다.
시크릿 만료나 유출 리스크를 신경 안 써도 되는 게, 새 환경 깔면서 가장 마음
편한 부분 중 하나였다.

self-hosted runner를 깐 이유는 좀 다른 결이었다. 우리 배포 워크플로 일부가
**SSH 기반**이고, target 서버 쪽 네트워크 화이트리스트에 등록할 **고정
IP**가 필요했다. GitHub-hosted runner는 IP 풀이 변동되니 화이트리스트가
사실상 의미가 없다. self-hosted runner를 우리 쪽 환경 안에 두고, 그 고정
IP를 target에 등록하는 방식으로 풀었다. 화려한 의사결정은 아니지만 현실적인
제약이 결정한 구조였다.

MQTT 서비스는 단순했다. **EMQX를 도커 컨테이너**로 그냥 올렸다. 매니지드
Web PubSub 같은 걸 굳이 안 썼다. 개발 환경이고, 어차피 운영에서도 EMQX를
쓰던 패턴이라 굳이 클라우드 매니지드로 갈 이유가 없었다.

마지막으로 **외부 앱용 별도 서비스**가 하나 들어갔는데, 이건 사실 CCTV
플랫폼 쪽이 외부 서비스로 호출하는 인터페이스였다. 분리 작업의 흐름상
잠정적으로 새 플랫폼 구독에 같이 둔 거고, 나중에 정리·이관될 가능성이 있는
영역이다. "잠정"이 결국 영구화되는 케이스를 많이 봤기 때문에, 이건 명문화된
정리 일정과 함께 두는 게 맞다고 본다.

GitHub Actions 측에선 environment를 추가해서 새 구독에 대한 배포가 자동으로
흐르도록 워크플로를 다듬었다. 이건 비교적 정해진 작업이었다.

## VNet에서 한참을 헤맸다

가장 까다로웠던 건 **VNet 통합**이었다. 모든 리소스가 공유해야 하는 네트워크
설정 — 공통 서브넷, 라우팅, NSG 베이스 — 과 개별 리소스만의 설정 — 전용
서브넷, NIC 옵션, private endpoint — 이 머리에서는 잘 분리되는데 코드/구성
파일로 옮기면 막상 잘 안 나뉘었다. 어디까지 공통이고 어디부터가 개별인지의
경계가 자꾸 모호해져서, 결국 사후 조정으로 메꾸는 일이 많았다.

다시 한다면 이 부분은 처음부터 **공통 base layer + per-resource layer로
명시적으로 분리한 IaC 모듈 구조**로 짤 것 같다. 사후에 합치는 것보다 처음에
나누는 게 훨씬 싸다는 것을 이 작업으로 다시 확인했다.

## 그래서 무엇을 배웠나

이번 작업의 핵심 가치는, 사실 도구 선택이 아니라 **분리** 자체에 있었다.
한 구독에 두 도메인이 섞여 있던 게 권한·비용·리소스 추적·장애 영향 격리를
모두 흐리고 있었고, 분리하고 나니 그 모든 게 깔끔해졌다. "지금 잘 돌아가니까
나중에"가 운영 부담을 매일매일 누적시키고 있었다는 걸, 환경을 한 번 갈라보니
체감했다.

기술적으론 OIDC 같은 좋은 패턴은 한 번 잡으면 새 환경에 일관되게 옮기는 게
어렵지 않다는 것, self-hosted runner처럼 화려하진 않지만 현실 제약을 풀어주는
도구는 그것대로 의미가 있다는 것 정도가 남았다. 그리고 "잠정"이라는 단어를
조심해야 한다는 것 — 외부 앱용 서비스가 새 환경에 잠시 끼어들었는데, 정리
일정을 명문화해두지 않으면 그게 영구 자산이 돼버린다.

다음에 새 환경을 깔 일이 또 있다면, 사이징 자료처럼 재사용 가능한 자산은
빠르게 쓰고, VNet 같은 네트워크 구성은 처음부터 모듈로 나누고, "잠정"은
종료 시점을 명시한 다음에 들어가게 할 것 같다.
