# 서비스 하나를 배포했더니, 전혀 다른 서비스가 죽었다

> 2026.06 ~ · 아키텍처 설계 · Azure · Go

- **기간** · 2026.06 ~ (진행 중)
- **팀 / 역할** · 전체 아키텍처 정리·세부 설계(본인) + 프론트엔드·이벤트 파이프라인 구현 담당
- **규모** · 여러 서비스가 한 서버에 얹혀 있던 SEMS 플랫폼을 서비스별 분리 구조로 전면 재설계
- **스택** · Next.js, TypeScript, Go, Azure (Event Hubs, API Management, Function Apps, Table/Blob Storage), Kafka, PostgreSQL, MongoDB, Docker
- **핵심** · "플랫폼이지만 사실은 서비스마다 로컬화가 필요한 SI"라는 전제 위에서, 공통 구조 + 분리 빌드/배포 + 기본앱 제공 체계로 재설계

---

플랫폼이라고 부르긴 했는데, 나는 SEMS가 진짜 플랫폼 역할을 하고 있다고 느낀 적이
별로 없었다. v2를 하게 된 건 결국 그 위화감에서 출발했다.

## '플랫폼'인데 플랫폼이 아니었다

지금 쓰는 v1은 처음부터 구조가 그리 좋지 않았다. 게다가 나도, 팀도 이 플랫폼을
잘 모르고 그 위에 올라가는 서비스도 잘 모르는 상태에서 이관을 진행했다. 그러다
보니 필요할 때마다 테이블을 어거지로 고치고 새로 만들면서, **플랫폼도 서비스도
아닌 애매한 혼종** 같은 게 만들어졌다.

가장 큰 문제는 프론트, 백엔드 서버, DB를 전부 하나에 몰아서 서비스를 올려둔
구조였다는 거다. 그래서 어느 서비스 하나를 고쳐서 배포하면, 전혀 상관없는 다른
서비스에까지 영향이 갔다. 유지보수를 하려고 붙였는데 오히려 더 어려워졌고, 새
서비스를 하나 올리는 것도 결코 쉽지 않았다.

한 번은 별개의 근태관리 서비스 서버를 업데이트하는데, 그 과정에서 패키지가
바뀌면서 **같은 서버에 얹혀 있던 전혀 다른 서비스의 컨트롤러**가 영향을 받았다.
결국 그 서비스의 외부 연동에서 오류가 터졌고, 롤백을 해야 했다. 서로 아무 관계도
없는 두 서비스가 같은 서버에 산다는 이유만으로 엮여서 무너진 거다.

여기에 하나가 더 있다. 주 고객사가 "로그인을 이런 식으로 처리해달라"고 요구하면,
그게 특정 서비스만이 아니라 사실상 전 서비스에 반영돼야 하는 구조였다. 이쯤에서
확실해졌다. **말은 플랫폼이지만, 실제로는 서비스마다 로컬화가 필요한 SI다.** 이걸
잊으면 안 된다는 게 v2 설계 내내 나를 붙잡은 전제가 됐다.

## 논의가 한 달째 멈춰서, 방향을 잡았다

처음엔 아키텍처 설계를 팀이 다같이 진행하려고 했다. 그런데 유스케이스 논의만
한 달 정도 이어지면서 진도가 거의 나가지 않았다. 누군가는 방향을 잡아야 했고,
결국 내가 나서서 전체 플랜을 짜기로 했다.

요구사항 자체는 몇 가지로 정리돼 있었다. 매니지드 서비스를 최대한 활용할 것,
새 서비스를 쉽게 추가할 수 있을 것(단, SI라는 전제를 잊지 말 것), 그리고 IoT
장비에서 올라오는 수집 데이터는 메인 DB가 죽더라도 계속 쌓일 수 있게 수집 경로를
분리할 것. 나는 전체 설계를 먼저 잡은 다음 파트를 쪼개 미팅을 돌렸고, 팀원들에게
하고 싶은 파트를 자원받아 하나씩 매칭해줬다. 그렇게 남은 두 파트가 **프론트엔드와
이벤트 파이프라인**이었고, 그 둘을 내가 맡았다.

Event Hubs나 API Management 같은 매니지드 서비스는 주변에서 조사해서 넘겨줬지만,
API 서버를 어떻게 설계할지는 내가 따로 공부해야 했다. 『모던 API 아키텍처 설계
전략』을 읽으면서 그쪽 감을 잡고 적용했다. 그리고 한 달쯤 지난 지금도 나는 꽤
주체적으로 굴러가고 있다. 프론트에 목업으로 기능을 먼저 넣어보고 거기서 필요한
API를 요청하는 식으로 기획을 이어가고, 프론트에는 디자인 시스템과 디자인 문서까지
적용해뒀다.

## 제일 비쌌던 건, 데이터를 받는 입구였다

수집 데이터 쪽에서 재밌는 걸 하나 발견했다. 게이트웨이에서 올라오는 보고를 단순
HTTP로 받으려고 앞단에 Function Apps를 붙여놨는데, 이게 사용량 기반 과금이라
**비용이 플랫폼 전체의 1/5쯤**을 잡아먹고 있었다. 데이터를 '받기만' 하는 입구가
제일 비싼 셈이었다.

그래서 이 입구를 Kafka로 바꾸는 게 낫겠다고 판단했는데, 사실 비용은 부차적인
이유였다. Kafka를 쓰는 가장 큰 이유는 원래 그게 존재하는 이유 그대로다. **이벤트를
유실 없이 처리**하는 것, 그리고 **비즈니스별로 컨슈머를 분리**할 수 있다는 것.
컨슈머를 나누면 같은 문서 DB를 쓰더라도 비즈니스별로 내부 DB를 분리하는 구성이
가능해지고, 수집 경로가 메인 DB와 분리되니 DB가 죽어도 데이터는 유실 없이 계속
쌓인다(원래 요구사항이기도 했다).

여기에 부수적인 이점이 더 붙는다. 하나는 앞서 말한 비용 절감이고, 다른 하나는
Azure 매니지드인 Event Hubs의 **Capture 기능**이다. Capture는 올라온 메시지를
알아서 Blob에 압축된 형태로 적재해준다. 덕분에 Table Storage에 쌓았다가 별도의
Azure Data Factory 마이그레이션 파이프라인으로 Blob에 옮기는 과정 없이, 아카이빙이
그 자체로 해결된다. Table Storage를 대체하기에 딱이었다.

물론 여기까지가 전체 설계에서 내가 방향을 잡은 부분이고, 이 정기보고 파이프라인의
세부 설계와 구현은 그 파트를 맡은 팀원이 진행한다. 내가 맡은 이벤트 파이프라인은
같은 Event Hubs 네임스페이스를 공유하되 별도 토픽으로 굴러가는, 반대편의 흐름이다.

## 어디까지 공통이고 어디까지 비즈니스인가

내가 직접 세부 설계를 파고든 건 내 담당인 **프론트엔드와 이벤트 파이프라인**이었다.
플랫폼이니 여러 서비스를 올릴 수 있어야 하고, 그러려면 공통 구조가 필요했다. 대신
나는 조건을 하나 걸었다. **분리해서 빌드·배포할 수 있어야 한다.** 그래야 서비스 간
분리가 쉬워지니까. 물론 분리하지 않고 통으로도 빌드·배포할 수 있게 열어뒀다. 이건
지금 다시 봐도 좋은 결정이었다고 생각한다.

프론트엔드에서는 관리자 앱과 비즈니스 기본 앱(웹·모바일)을 만들어, 새 서비스가
들어오면 이 기본 앱을 제공하고 각 서비스에 맞게 고쳐 쓰는 구조로 잡았다. 구현하면서
가장 손이 많이 간 건 기능이 아니라 경계였다. **어디까지를 공통으로 두고 어디까지를
비즈니스로 뺄 것인가** — 이걸 정하는 데 변경이 제일 많았다. 그래도 결과적으로는 꽤
깔끔하게 정리됐다. 프론트엔드 쪽은 다행히 v1이 굉장히 잘 되어 있는 편이라, 그걸 잘
참고하면서 개선하는 방향으로 갔다.

## 처음 써보는 Go, 그리고 배운 것

이벤트 파이프라인은 한 번도 써본 적 없는 Go로 구현하고 있다. Go를 고른 이유는
두 가지였다. 첫째, **동시성 하나하나가 가볍다.** v1에서 파이썬 + 멀티프로세스로
VMSS를 돌려가며 처리했던 근본 원인이 결국 GIL이었는데, Go는 그 우회 자체가 필요
없어서 같은 일을 단일 프로세스로 감당할 수 있다. 그러고도 모자라면 쿠버네티스
컨테이너로 인스턴스를 늘리면 된다. 둘째, **정적 컴파일된 단일 바이너리**라
컨테이너 이미지가 아주 작다. 파이썬 이미지는 인터프리터에 의존성까지 수백 MB인데,
Go는 수십 MB로 떨어진다. 주 판단 근거는 아니었지만 쓰다 보니 따라온 장점도 있다 —
배포 아티팩트가 바이너리 하나로 끝나 런타임 의존성 꼬임이 없고, 쿠버네티스·Kafka·
CloudEvents·OpenTelemetry 같은 클라우드 네이티브 생태계가 전부 Go를 1급으로
지원해서 라이브러리 궁합이 좋았다.

구조는 수신 어댑터 → 판단 코어 → 실행기로 이어지고, 이벤트가 유실되지 않도록
멱등 처리와 DLQ를 바닥에 깔았다. 언어가 낯설어서 분명 어렵게 가고 있는데, 그래도 AI를
쓰면서 생각보다는 수월하게 진행 중이다. 이번에 확실히 느낀 건, **설계만 제대로
해두면 구현은 꽤 잘 나온다**는 거다. 낯선 언어라는 장벽이 예전만큼 크지 않았다.

아직 진행 중이라 다 끝난 이야기는 아니다. 유스케이스를 기반으로 기본 앱의 제공
기능을 정의해서 구현해뒀는데, 이 기능 정의 부분은 앞으로도 수정이 꽤 있을 것 같다.
그래도 큰 방향 — 공통과 비즈니스를 나누고, 분리 빌드·배포를 열어두고, 기본 앱을
제공해 서비스를 얹는 구조 — 은 지금도 맞게 가고 있다고 본다. 무엇보다 "플랫폼이라
불러도 결국 SI"라는 전제를 놓지 않은 게, v1에서 겪은 그 뒤엉킴을 되풀이하지 않게
해준 것 같다.
