[Java 베이스 클래스와 단일 진입 프로시저로 SP 표준화](./2025-09-java-pg-공통-프레임워크.md)
를 깔고 나니, **DB 안에서 일어난 일이 어떻게 외부로 빠져나가야 하는가**
라는 질문이 같이 따라왔다. 프로시저 실패도 슬랙으로 알려야 하고, 파티션
백업도 누군가는 실행해줘야 하는데, 그걸 stored procedure 안에서 직접 외부
시스템 호출하게 두면 트랜잭션 경계도 흐릿해지고 SP가 외부 의존성을 줄줄이
끌어안게 된다. 이걸 깔끔하게 풀자고 같이 만든 게 **`pg_notify` 기반
알림·백업 파이프** 였다.

## 어떻게 시작됐나

상황은 이랬다. SP 진입 프로시저가 자리 잡으면서 **SP 실패 = 슬랙 알림**
이라는 흐름을 자연스럽게 깔 필요가 생겼다. 동시에 운영팀 쪽에서는
**파티션 백업**을 정기적으로 돌리는 작업이 따로 있었는데, 그쪽도 트리거가
SQL 단에서 와야 하는 구조였다. 둘 다 "DB 내부 이벤트가 외부로 나가는
통로"가 필요하다는 점에서 같았다.

처음에는 SP 안에서 직접 슬랙 webhook을 호출하는 방법도 검토했는데, 이건
빠르게 기각했다. SP가 외부 네트워크에 의존하면 트랜잭션이 외부 응답에 묶이고,
실패 시 처리도 까다로워지고, 무엇보다 **DB 사용자에게 외부 통신 권한을
주는 것 자체가 보안 측면에서 불편**했다. 그래서 결정한 게 LISTEN/NOTIFY
패턴이었다. SP는 채널에 메시지를 던지기만 하고, 채널을 듣는 별도 서비스가
실제 외부 통신을 담당하는 그림이다.

## 두 채널로 나눴다

채널은 두 개를 깔았다. **슬랙 알림용 채널**과 **백업 요청용 채널**.
한 채널에 다 몰아 넣을 수도 있었지만, 둘은 **소비 패턴이 다르다**.

슬랙 알림은 받는 즉시 webhook을 한 번 때리면 끝나는 짧고 잦은 메시지고,
백업은 한 건이 수십 분 걸리기도 하는 무거운 작업이다. 같은 리스너가 둘
다 처리하면 백업 도는 동안 슬랙 알림이 막힐 수 있다. 그래서 채널을
나누고, 각 채널을 **독립된 psycopg2 연결로 LISTEN**하게 분리했다. 한쪽이
끊겨도 다른 쪽이 영향받지 않는 구조다.

PostgreSQL 단에는 슬랙 메시지 송출용 헬퍼 함수를 세 가지로 갈라뒀다.
일반 알림용, 에러용, 그리고 SP 실패 전용. 이 함수들이 결국 다 **같은
채널에 type 필드를 박은 JSON을 발행**한다. 백업 쪽은 백업 요청 채널에
단일 또는 배치 요청 페이로드를 직접 발행하는 방식이다.

## 채널을 듣는 작은 데몬

이 두 채널을 듣는 별도 리스너 서비스를 띄웠다. 하는 일은 단순하다. 두
개의 LISTEN 스레드를 들고 있다가, 알림이 오면 type 필드를 보고 적절한
핸들러로 라우팅한다. 슬랙 쪽은 webhook으로 던지고, 백업 쪽은 `pg_dump` →
`gzip` → 정해진 백업 디렉토리로 옮기는 일을 한다.

연결 관리는 의도적으로 단순하게 잡았다. 두 채널은 **각자 독립 연결**을
쓰고, 끊기면 5초 후 자동 재연결한다. AUTOCOMMIT 모드에서 LISTEN을 걸고,
0.1초마다 polling 하면서 `notifies` 큐를 비우는 흔한 패턴이다. 굳이 더
정교한 큐를 들이지 않은 이유는, 우리 부하 수준에선 이 단순한 polling
loop로 충분했기 때문이다.

배치 백업 요청은 한 번에 여러 파티션이 들어올 수 있어서, 그 부분만
**ThreadPoolExecutor (max 3 workers)** 로 처리한다. 동시 백업이 너무 많이
돌면 디스크 I/O가 병목이 되니까, 동시성은 의도적으로 작게 잡았다.
실패한 요청은 카운트해서 따로 추적하고, 일정 횟수를 넘으면 **별도 type의
메시지를 다시 슬랙 채널로 발행**한다. 즉, **알림 시스템이 백업 시스템의
사고도 같이 알려주는** 구조다.

## type 필드 하나로 다 라우팅한다

슬랙 채널 위에 흐르는 메시지는 한 종류가 아니다. 일반 알림, 에러,
SP 실패, 재시도 초과, 파티션 삭제·유지보수·상태·경보 같은 **여러 type을
같은 채널이 공유한다**. 리스너 측은 type 필드를 키로 쓰는 dispatch table
한 장으로 이 모든 경우를 한 곳에서 라우팅한다. 새 type 추가가 사실상 한
줄짜리 작업이 된다.

채널을 더 잘게 쪼갤 수도 있었지만, 슬랙으로 흘려보내는 메시지는 결국 같은
webhook을 타고 가니까 같은 채널에 두고 type으로 나누는 게 운영상 더
편했다. **한 LISTEN으로 모든 슬랙 트래픽을 잡는다**는 단순함이 핵심이다.

슬랙으로 나갈 때는 type별로 출력 형식도 조금씩 다르다. SP 실패는 우리
`SEMS` 포맷(`Error occurred at`, `Exception`, `Message`, `At` 라인)을 그대로
재사용해서 SP 쪽도 다른 언어 배치들과 같은 모양으로 알림이 찍히게 했다.
`field_titles` 라는 작은 매핑 테이블이 한자리에 정의돼 있어서, 어떤 키가
들어오든 이모지 + 라벨 + short 여부가 일관되게 박힌다.

## 그래서 무엇을 배웠나

이 시스템을 깔고 나서 가장 명확하게 좋아진 건, **SP가 외부에 뭘 알리는
방식이 단 한 줄로 통일**됐다는 점이었다. SP 어디에서 슬랙을 보내고
싶으면 헬퍼 함수 한 줄을 호출하면 끝이다. 직접 webhook을 호출하지도,
트랜잭션 경계를 신경 쓰지도, 타임아웃을 걱정하지도 않는다. 같은 원칙이
백업 요청에도 적용돼서, **백업 워커를 호출한다는 게 결국 채널에 메시지
한 장 던지는 일**로 단순해졌다.

가장 크게 배운 건 **DB 내부와 외부의 경계를 명확히 그어주는 것의
가치**였다. SP는 자기 트랜잭션 안에서 일을 끝내고, 외부 세계와의 통신은
오로지 채널을 통해서만 흐른다. 이렇게 그어두면 SP 단위 테스트가 외부
의존성을 갖지 않게 되고, 슬랙 webhook이 죽어도 SP는 멀쩡히 도는 등
**한쪽 시스템의 사고가 다른 쪽으로 번지지 않는다**.

다시 한다면 보강할 건 두 가지다. 하나는 **메시지 영속화**. 지금
`pg_notify`는 휘발성이라 리스너가 죽어 있는 동안 발행된 알림은 그대로
사라진다. 중요한 알림은 실패한 트랜잭션이라도 따로 테이블에 남기고,
리스너가 살아나면 따라잡을 수 있는 보강이 필요하다. 다른 하나는 **폴링
주기와 동시성 튜닝**. 0.1초 polling은 단순하긴 한데, 알림이 폭주하는
시점엔 약간의 지연이 누적될 수 있다. 큐 갯수와 처리 시간 메트릭을
내보내서, 임계치 넘으면 워커 수를 늘리는 식의 자가 조정이 필요한 시점이
언젠간 올 것이다.

작은 시스템이지만 이 파이프 하나가 깔린 뒤로 운영팀의 "어디서 뭐가
터졌지?" 질문에 거의 항상 슬랙 한 장으로 답이 나온다. 그게 이 작업의
가장 솔직한 가치였다.
