# 3개 언어로 흩어진 배치 레포를 한 호흡으로 정리한 시간

> 2026.02 · Python · Java · Node.js · 리팩토링 · 운영 표준화

- **기간** · 2026.02 (며칠 안에 일괄)
- **팀 / 역할** · 본인 주도 / 다언어 배치 레포 3트랙 운영 표준화
- **스택** · Python · Java · Node.js · systemd · FastAPI · Uvicorn · MyBatis 패턴
- **핵심** · Slack 메시지 포맷 통일 · graceful shutdown 표준화 · 7개 Python 서비스 FastAPI 통일 · 14개 SQL Mapper 분리 · 단일 yaml 정의 + systemd 템플릿 자동 생성

---

배치 레포를 처음 열어보면 늘 비슷한 인상을 받는다. **언어가 섞여 있고**,
**운영 패턴이 제각각**이다. 우리도 그랬다. **Python·Java·Node.js 3개
언어**로 짜인 배치들이 한 레포에 모여 있었는데, 같은 운영팀이 보기에
알림 모양도 다르고, 종료 처리도 다르고, 의존성 관리도 달랐다. 신규 배치
하나 추가하려면 매번 보일러플레이트를 다시 짜야 했고, 장애가 나면 언어별로
다른 디버깅 패턴을 타야 했다. 어느 시점부터 이걸 그대로 두면 운영 비용이
계속 누적되겠다는 판단이 들어, 한 번에 정리하기로 했다.

## 무엇을 정리했나

크게 세 트랙이었다. 로깅과 알림과 종료 처리, Python 쪽 FastAPI 통합
아키텍처, 그리고 Java SQL을 코드에서 분리하는 일. 기간으로는 며칠 안에
일괄로 굴렸다. (베이스 클래스 차원의 추상화 — Java `CommonTask`나
PostgreSQL 단일 진입 프로시저 같은 것 — 은 시간을 두고 그 해 후반에
별도로 한 번 더 정리했다. 그 이야기는 따로 적어뒀다.)

## 알림과 로그를 한 모양으로

먼저 손댄 건 **Slack 메시지 포맷**이었다. 같은 사고가 나도 Python은 Python
대로, Java는 Java대로, Node는 Node대로 모양이 달랐다. on-call 입장에서 보면
인지 부하가 그냥 컸다. 그래서 SEMS 라는 이름의 공통 포맷을 정해놓고 세
언어가 다 그 포맷으로 보내게 했다.

핵심은 한 장만 보면 어떤 환경의 어떤 언어의 어떤 태스크가 어디서 터졌는지
알 수 있게 만드는 것이었다. 환경 이모지(`:factory:` / `:construction:`),
환경 prefix(`[PRODUCTION]` / `[STAGING]`), 언어 표시, 태스크명, 그리고 본문에
환경·시간·예외·메시지·발생 위치를 박았다. 환경 구분은 `ENVIRONMENT`
환경변수가 1차고, 누락되면 `PG_DB_HOST` 호스트명에서 추론하도록 fallback을
깔아뒀다. 환경변수 누락이 있어도 안전한 기본 동작을 하게 하기 위함이다.

로그 쪽은 자체 `TimeSizeRotatingFileHandler`를 만들어 **매일 자정 + 파일당
10MB 초과** 시 롤링하고 **10일치까지만 보존**하는 복합 롤링으로 바꿨다.
그리고 한 가지 사소하지만 효과가 컸던 게, **Java Logback 패턴을 한 곳에
정의해두고 Python이 그걸 자기 포맷으로 자동 변환하게 한 것**이었다.
`logging.properties` 파일 하나만 보면 양쪽 언어 로그가 같은 모양으로
찍힌다. Logback의 `%d{yyyy-MM-dd HH:mm:ss.SSS} [%thread] %-5level
%logger{36} - %msg%n` 같은 토큰을 Python format으로 변환하는 작은 매퍼만
있으면 됐다.

종료 처리는 의외로 단순하게 풀었다. 별도의 파이썬 시그널 핸들러를 만들지
않고, **systemd + Uvicorn 옵션 조합**으로 끝냈다. systemd가 SIGTERM을 보내고,
Uvicorn이 `--timeout-graceful-shutdown 60`으로 진행 중 요청을 **최대 60초**
까지 마무리하고, 그 안에 안 끝나면 systemd가 SIGKILL로 정리한다. 코드를
안 만지고도 모든 파이썬 서비스에 일괄 적용할 수 있는 게 이 방식의
장점이었다.

## Flask와 FastAPI가 섞여 있던 걸 통일

Python 쪽은 더 큰 손질이 필요했다. **Flask와 FastAPI가 같이 굴러가고 있었고**,
서비스마다 자기 venv가 따로 있고, 코드 구조도 서비스마다 자유롭게 흩어져
있었다. 미들웨어, 검증, lifespan 처리 같은 게 거의 다 중복이었다.

이걸 정리하는 방향은 단순했다. **FastAPI로 통일**하고, **공통 인프라를
common/ 모듈에 모으고**, 각 도메인 서비스를 server/ 아래로 정리하는 것.
앱 팩토리, 요청 로깅·인증 미들웨어, 로거, graceful shutdown
유틸, 실행 로깅, Azure Monitor 통합까지 모두 common 한 곳으로 모았다.
**venv는 서비스별 7개에서 공통 `requirements.txt` 1개로** 묶었다. server
아래에는 token, weather, regular_data, herit_dr, ems_server, daemon, postgres
이렇게 **7개 모듈**이 들어갔다.

여기에 작은 조각 하나가 더 들어갔다. **단일 yaml 정의 파일**에 모든
서비스 정의를 적어두고, 작은 generate 스크립트가 그걸 보고 systemd unit
파일을 자동 생성하게 한 것이다. 신규 서비스 추가가 **yaml 한 줄 +
generate 실행** 으로 끝나게 됐다. 정책을 한 군데서 바꿀 수 있다는 게,
이런 종류의 자동화에서 가장 큰 가치였다.

## Java SQL을 XML로 빼냈다

Java 배치는 또 다른 결의 문제였다. 쿼리들이 전부 **Java 코드 안에 String
상수**로 박혀 있어서, 쿼리 한 줄을 고치려고 해도 빌드/배포 사이클을
타야 했다. 운영에서 쿼리 튜닝이 잦은 배치엔 이 비용이 작지 않았다.

MyBatis 스타일을 흉내 내서, **14개 mapper XML 파일**을 만들고 쿼리를
거기로 옮겼다. 파라미터는 PreparedStatement index 대신 named parameter
(`#{paramName}`) 로 바꿨다. 가독성도 같이 올라갔다. 공통으로 **XML 파싱·
쿼리 로드 클래스**와 **named parameter를 PreparedStatement로 풀어주는
실행기**를 만들었고, 컴파일·런타임 스크립트에서 mapper 디렉토리를
classpath와 시스템 프로퍼티로 노출하는 정도가 부수 작업이었다.

이렇게 옮기면 trade-off가 하나 따라온다. **컴파일 타임 검증이 약해진다는
것**이다. SQL 오타가 있어도 빌드가 통과한다. 이걸 보완하기 위해 mapper 로딩
단계에서 syntax 검증을 강하게 두는 식으로 처리했다. 완벽하진 않지만, 빌드
없는 쿼리 수정이 주는 가치가 그 트레이드오프보다 컸다고 본다.

## 그래서 무엇을 배웠나

이번 리팩토링을 끝내고 가장 크게 남은 건 **선언적 정의의 가치**였다.
단일 yaml 정의 파일이 신규 서비스 추가의 진입 장벽을 거의 zero로 만들었고,
정책 변경(예: graceful timeout 시간)을 한 곳에서 처리할 수 있게 했다. IaC와
같은 사고 방식을 작은 운영 도구에 적용한 셈인데, 효과는 IaC만큼 컸다.

두 번째로 느낀 건, **표준화는 결국 인지 부하 비용을 줄이는 작업**이라는 것.
Slack 알림 한 장만 봐도 어느 환경의 어떤 언어의 어떤 태스크가 어디서 터졌는지
알 수 있게 된 것, 모든 파이썬 서비스가 같은 graceful shutdown 패턴으로
도는 것, 로그 포맷이 한 곳에서 정의되는 것 — 하나하나는 작아 보이지만
운영팀의 매일 비용을 갉아먹던 자잘한 결정 비용이 다 한 번에 사라졌다.

다시 한다면 보강할 건 두 가지다. 하나는 **테스트 자동화 게이트를 같이
묶어** 진행하는 것. 공통 인프라 단위 테스트와 yaml 정의 변경 시 회귀
테스트가 같이 돌아가는 구조가 있었어야 안전했다. 다른 하나는 **graceful
shutdown을 systemd에 의존하지 않게** 한 번 더 추상화하는 것. 지금은 K8s
같은 다른 오케스트레이터로 갈 때 그 부분을 다시 짜야 한다. lifecycle을 한
번 더 추상화해두면 이식성이 올라갈 것이다.

세 트랙 다 한 호흡에 굴린 게 결과적으론 잘한 선택이었다. 따로따로 했으면
공통 인프라 위에 새 패턴이 얹어지는 그림이 한참 미뤄졌을 것이다. 큰 정리는
한꺼번에 하는 게, 운영 표준화라는 종류의 작업엔 잘 맞는다.

이 작업이 며칠 안에 일괄로 굴러갈 수 있었던 것 자체가, 사실 [그 전에
미리 깔아둔 베이스 클래스와 SP 단일 진입 프로시저](./2025-09-java-pg-공통-프레임워크.md)
덕분이기도 했다. 자식이 보일러플레이트를 직접 들고 있었으면 로그 포맷이나
Slack 양식 같은 운영 인터페이스를 일제히 바꾸는 게 결코 며칠 안에
끝날 일이 아니었다. 부모/감싸는 층이 단단히 잡혀 있었기 때문에 한 군데만
손봐도 모든 자식에 자동 반영되는 구조였고, 이번 작업의 속도는 거기서
나왔다.
