---

배치 코드를 한참 만지다 보면 자연스럽게 보이는 게 있다. **같은 모양의
보일러플레이트가 매 배치마다 반복**되고 있다는 사실. 시작 로그 INSERT,
끝 로그 UPDATE, 실패 시 슬랙 알림 호출. Java 배치도 그랬고, PostgreSQL
의 stored procedure도 그랬다. 새 배치 하나를 추가할 때마다 비슷한 wrapper
를 또 적고 있는 게 거슬렸다. 이 한 층을 한 번에 묶어내자고 결심했던 게
이 작업의 시작이었다.

## Java 쪽 — 추상 베이스 클래스 하나로

Java 배치 클래스들은 형태가 거의 비슷했다. **시작 시점에 공통 변수
세팅, 끝나면 실행 로그 저장, 실패하면 알림** — 매번 똑같은 흐름이
배치 클래스마다 손으로 적혀 있었다. 비즈니스 로직보다 wrapper 코드가
양적으로 더 많은 배치도 있었고, 새 배치 추가할 때마다 이 쳇바퀴를 또
돌리는 게 진짜 거슬렸다.

추상 베이스 클래스 하나를 만들었다. 자식 클래스는 **비즈니스 로직과
메타 정보(태스크 ID·이름·결과 요약 정도)** 만 override 한다. 부모 쪽이
SQL Mapper 초기화, 공용 날짜 변수 세팅, 실행 로그 INSERT, 실패 시 슬랙
알림 발사까지 다 알아서 처리한다. 자식이 신경 쓸 일은 "어떤 일을 할
것인가" 한 가지로 줄어든다.

결과적으로 **신규 Java 배치 추가가 비즈니스 로직 + 시그니처 몇 개 +
실행 스크립트로 수렴**했다. 이전엔 100줄짜리 배치를 적으면서 절반은
wrapper였는데, 그게 다 부모로 빠지면서 새 배치는 그냥 하던 일만 적으면
끝나게 됐다.

다 만들고 보니 한 가지 호기심이 남았다. 이걸 굳이 직접 만들었어야
하는가, **Spring Batch**와 비교하면 우리 베이스 클래스는 어디쯤 와
있는가. 체감으론 우리 패턴이 의외로 잘 자리 잡힌 것 같은데, Spring
Batch가 가진 chunk-oriented processing, restart-at-failure, skip
policy, JobRepository 같은 더 무거운 정공법 기능이 우리한텐 어떤
의미가 있는지 — 그리고 그 정도 정교함이 우리 배치 워크로드에 정말
필요한지 — 는 따로 한 번 정리해보고 싶은 주제다. 우리 배치는 거의
다 one-shot 단순 잡이라 Spring Batch를 끌어 들이는 비용이 오히려
클 수 있다는 게 현재 가설이지만, 그 가설을 진짜로 확인하려면 양쪽을
같은 잣대로 한번 비교해 봐야 한다. 추후 공부 거리로 메모해 둔다.

## PostgreSQL 쪽 — 단일 진입 프로시저로 같은 결을

Java를 그렇게 묶고 보니, **PostgreSQL의 stored procedure도 정확히 같은
모양의 문제**를 안고 있었다. 시스템엔 SP로 도는 배치가 10여 개 있었는데,
모든 SP에 시작/완료/실패 로그 INSERT·UPDATE와 실패 시 슬랙 알림 호출이
중복으로 깔려 있었다. SP 수정할 때마다 비슷한 wrapper를 같이 만지고
있었다.

해결 방향은 Java와 같은 결이었다. **단일 진입 프로시저** 를 하나 만들고,
그 프로시저가 시작 로그 → 비즈니스 함수 동적 실행 → 성공 로그 또는
실패 로그·알림 흐름을 감싸게 했다. 실제 비즈니스 함수는 시그니처를
표준화해서 — `(배치 ID, 시작 시각)` 을 받고 결과 요약 텍스트를 RETURN
하는 형태로 — **로깅·예외 처리·알림은 한 줄도 자기가 직접 안 한다**.
그냥 일을 하고 결과만 돌려주면 끝이다.

스케줄러(`pg_cron`) 등록도 단순해졌다. 매번 SP 호출을 직접 적는 대신,
**진입 프로시저를 호출하면서 인자로 비즈니스 함수 이름과 배치 식별자를
넘기는** 한 패턴으로 통일됐다. 새 SP 배치 추가가 사실상 "함수 작성 +
스케줄 한 줄" 두 단계로 끝난다.

10여 개 함수를 모두 이 모양으로 바꿔놓고 보니, **Java 배치와 SP 배치의
운영 인터페이스가 같은 모양으로 수렴**했다. 어디서 도는 배치든 시작·종료·
실패 로그가 같은 테이블에 같은 포맷으로 남고, 실패 알림이 같은 채널로
흘러간다. 운영하는 쪽에선 "배치가 도는 곳이 어디든 패턴은 한 가지" 라는
단순함을 얻은 셈이다.

이 SQL 단 표준화는 곧바로 짝이 되는 작업으로 이어졌다 — SP의 실패 알림이
외부 슬랙으로 흘러나갈 통로가 같이 필요해진 것이다. 같은 시기에 깔린
[`pg_notify` 기반 알림·백업 파이프](./2025-09-pg-notify-슬랙-백업-시스템.md)
가 그 통로 역할을 한다.

## 그래서 무엇을 배웠나

이번 작업으로 가장 분명해진 건 **언어를 가리지 않고 같은 패턴이 이식
가능하다**는 점이었다. Java의 베이스 클래스로 풀었던 보일러플레이트
문제가 PostgreSQL에서도 거의 같은 구조로 풀렸다. 도구는 달라도 "공통
보일러플레이트를 부모/감싸는 층으로 빼고, 자식은 비즈니스 로직만 적는다"
는 원칙이 양쪽에서 그대로 통했다. 표준화가 결국 아키텍처 패턴 얘기라는
걸 새삼 느꼈다.

두 번째로, **이 한 층이 자리 잡으면 그 다음 표준화가 굉장히 쉬워진다**
는 것. 부모/감싸는 층이 단단히 잡히면, 그 위에서 로그 포맷이나 슬랙
메시지 양식 같은 운영 인터페이스 통일은 나중에 한 곳만 손봐도 모든
자식에 자동 반영된다. 실제로 이 베이스 위에서 운영 인터페이스 표준화는
한참 뒤에 한 번 더 굴렸는데, 그 작업이 며칠 만에 끝날 수 있었던 건
이 베이스 층 덕이었다 →
[`2026-02-배치-레포-리팩토링.md`](./2026-02-배치-레포-리팩토링.md).

세 번째는, **직접 만든 프레임워크와 기성품(Spring Batch)을 진지하게
비교해 두는 게 다음 단계에서 늘 도움이 된다**는 것. 우리 워크로드는
지금 단순 one-shot 위주여서 가벼운 베이스 클래스로 충분하지만, 워크로드가
복잡해지면(예: chunk reader/processor/writer가 정말 필요한 경우) Spring
Batch 쪽으로 옮기는 비용 vs 우리 베이스 클래스를 그 방향으로 키우는
비용을 비교해야 한다. 그 비교 작업은 추후 과제로 남겨둔다.

다시 한다면 보강할 건 두 가지다. 하나는 **베이스 클래스와 SP 진입
프로시저에 대한 단위 테스트 자산화**. 같은 패턴을 쓰는 자식이 늘어날수록
부모/감싸는 층의 회귀 위험도 같이 커진다. 다른 하나는 **SP 비즈니스
함수의 시그니처 검증을 정적으로** 잡는 것. 지금은 런타임에 시그니처가
어긋나면 동적 실행에서 터지는데, 진입 프로시저 등록 시점에 시그니처를
검증하도록 한 번 더 막아두면 사고가 줄어든다.
