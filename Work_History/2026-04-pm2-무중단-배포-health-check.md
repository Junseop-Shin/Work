# 내가 고친 줄 알았던 ecosystem 설정이 사실은 한 번도 안 먹혔다는 이야기

> 2026.04 · Next.js · PM2 · 무중단 배포 · 트러블슈팅

- **기간** · 2026.04
- **팀 / 역할** · 본인 주도 트러블슈팅
- **스택** · Next.js 14.2.30, PM2 (cluster mode, 2 instances), GitHub Actions self-hosted runner, Ubuntu
- **핵심** · pm2 reload가 ecosystem 정의(script/args/instances) 변경을 안 먹는다는 사실 발견 → pm2 delete + start로 등록 정보 재초기화 흐름 정립

---

수동 배포에서 SSL 인증서 덮어쓰기로 한 시간을 날린 뒤, 무중단 배포로
올라가야겠다는 결심이 머리에 박혔다. 그래서 어느 프론트 서비스에 PM2 기반
무중단 배포를 깔아보기로 했는데, 이게 의외로 한참을 발목 잡았다. 결국
원인을 찾고 보니, **내가 고친다고 생각한 부분이 사실 한 번도 안 고쳐지고
있었다**는, 좀 어이없는 결말이었다.

## 어떻게 시작됐나

대상 서비스는 **Next.js 14.2.30** 기반 SSR 앱이고, target 서버는 Ubuntu
VM이다. 배포는 **self-hosted GitHub Actions runner**가 SSH로 들어가서
처리하는 흐름이고, 프로세스 매니저는 **PM2 cluster mode (인스턴스 2개)**.

처음 잡은 그림은 아주 단순했다. 빌드 산출물을 새 폴더로 받아놓고, 운영
경로의 폴더를 새 빌드로 교체한 다음, `pm2 reload`로 워커를 한 번 돌린다.
PM2의 reload는 워커를 한 번에 다 죽이지 않고 한 명씩 갈아끼우니까,
이론적으로는 다운타임이 없어야 한다.

로컬에서 같은 절차를 손으로 돌려보면 잘 된다. 워커가 순차로 새 코드로
교체되고, 그동안 트래픽도 잘 받는다. 이거면 끝났다고 생각했다.

## CI에서 처음 막혔다

GitHub Actions가 같은 절차를 도는 순간 막혔다. PM2 reload 단계까지는
나가는데, **마지막 health check 단계에서 실패**한다. 로컬에선 잘 되는데
CI에서만 실패하니, 처음엔 SSH 세션이나 권한 문제인가 의심했다. 그쪽은
딱히 문제가 없었다.

검색해 보니 익숙한 패턴이 보였다. **PM2 cluster mode + npm / yarn
script**의 조합이 잘 안 동작한다는 얘기였다. PM2는 cluster mode에서
node 프로세스를 직접 fork 해서 워커를 띄우는데, 우리 ecosystem 정의가
`yarn start` 비슷하게 npm script를 한 번 거치는 모양이라, **PM2가 추적해야
할 진짜 워커 프로세스가 npm/yarn child의 child** 가 되어버린다. 그래서
reload 시점에 워커가 의도대로 한 명씩 갈아끼워지지 않거나, 새로 뜬
프로세스가 PM2 입장에선 정상 ready 상태로 안 잡히는 경우가 있다는 거였다.

## .next 직접 실행으로 가도 또 막힌다

여기까지 정리하고 나니 해법은 명확해 보였다. **npm/yarn을 한 단계 빼고,
PM2가 node로 빌드 산출물을 직접 실행**하게 만들자. Next.js 빌드 결과물을
직접 물려서 PM2 cluster의 워커가 곧바로 그 프로세스가 되도록 ecosystem을
바꿨다.

그런데 이렇게 바꿔놓고 다시 돌려도 **health check 단계에서 또 실패**한다.
정확히 어디서 실패하는지가 모호한데, 워커는 일단 뜬 것 같고, 응답이 안
나오거나 응답이 나오기 전에 health check 타임아웃이 끊는 것 같은 모양으로
보인다.

이쯤 되니 PM2 cluster + Next.js 14의 조합 자체에 우리가 모르는 함정이
하나 더 있는 게 아닌가 싶어졌다.

## 진짜 원인은 reload가 ecosystem을 안 본다는 거였다

가설이 잔뜩 쌓이고 나서야, 한 번도 제대로 안 한 일을 그제야 했다.
**PM2가 실제로 무슨 명령으로 워커를 띄우고 있는지 직접 확인**하는 거였다.
`pm2 show <서비스명>` 으로 실행 중인 워커의 script와 args를 들여다봤다.

그제야 보였다. **PM2는 여전히 yarn을 실행하고 있었다.** ecosystem.config.js에는
이미 yarn을 빼고 node로 직접 next를 호출하도록 바꿔뒀는데도, PM2 안에서
도는 워커는 옛날 등록 그대로 `yarn start`였다. PM2 로그를 다시 까보니
`yarn run v1.22.22 / $ next start -p ...` 가 그대로 찍히고 있었다. 즉,
**내가 고친 ecosystem 변경이 PM2에 한 번도 반영된 적이 없었다**.

이유는 단순했다. **`pm2 reload`는 코드(워커가 실행하는 파일)를 새로
로드시키는 명령이지, ecosystem 정의 자체(script / args / instances /
env 같은 등록 정보)를 다시 읽어들이는 명령이 아니다**. ecosystem을
바꿨으면 reload가 아니라 **`pm2 delete` 후 `pm2 start ecosystem.config.js`로
다시 등록**해야 한다. 등록 정보는 PM2 내부의 process list에 박혀 있어서,
파일 수정만으로는 그쪽이 갱신되지 않는다.

내가 그동안 "ecosystem을 yarn에서 node 직접 실행으로 바꿨다"고 생각하면서
계속 시도했던 건, 실제로는 **계속 옛날 yarn 실행을 그대로 reload하고
있었던 것**이었다. 처음 의심했던 cluster + npm/yarn 호환성 가설은 사실
검증조차 해본 적이 없었던 셈이다.

수정은 단순했다. 한 번 process 목록에서 깨끗하게 지우고 ecosystem.config.js로
다시 등록한 다음 `pm2 save`로 보존한다. 그 뒤로는 배포 스크립트의
`pm2 reload`가 의도대로 동작한다.

## 그래서 무엇을 배웠나

이 사건에서 가장 크게 남은 건, **"내가 고쳤다고 생각한 게 정말 적용된
상태인지 도구한테 직접 물어봐야 한다"** 는 것이었다. 설정 파일을 바꿨다고
도구의 런타임 상태가 자동으로 같이 바뀌는 건 아니다. PM2의 reload는
코드 갱신이지 등록 정보 갱신이 아니고, Kubernetes의 manifest apply도
어떤 필드는 즉시 적용되지만 어떤 필드는 pod 재생성을 요구한다. 도구마다
"무엇을 reload 하고 무엇을 reload 하지 않는지"의 경계가 다르다는 걸,
이 사건이 아주 비싼 방식으로 가르쳐줬다.

그리고 그 위에 또 한 가지. **가설을 검증하기 전에 현재 상태부터 먼저
확인해야 한다**. 나는 cluster + yarn 호환성을 의심하면서 ecosystem을
node 직접 실행으로 바꾸는 가설 검증으로 바로 넘어갔는데, 사실 그 변경이
적용됐는지 자체를 확인 안 했다. `pm2 show` 한 줄이면 30초 만에 끝났을
일을, 며칠짜리 미스테리로 늘려놓았다.

다시 한다면 두 가지를 미리 깔아둘 것 같다. 하나는 **배포 스크립트에
"PM2가 지금 무슨 명령으로 워커를 띄우는지" 출력하는 단계**를 명시적으로
넣는 것. 등록 정보와 실제 실행 명령이 어긋나는 순간 즉시 보이게 만든다.
다른 하나는 **ecosystem 변경이 들어가는 PR에는 reload가 아니라 delete →
start 흐름이 들어가도록** 배포 절차를 분리하는 것. reload는 코드 변경
전용으로, 등록 정보 변경은 별도 절차로 명시해두면 같은 실수가 반복되지
않는다.

cluster + yarn 호환성 얘기 자체는 여전히 유효한 함정이지만, 우리 경우엔
그 함정이 문제가 아니라 **그 함정을 피하려고 한 변경이 안 들어가 있었던
것**이 문제였다. 가설이 맞았어도 검증 환경이 틀려 있으면 답을 얻을 수
없다는 게, 이번에 가장 비싸게 배운 한 줄이다.
