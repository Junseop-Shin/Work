# 메모리 스케줄러로 도는 데몬을 systemd 배치로 다시 짠 이야기

> 2026.02 · Python · MongoDB · 마이그레이션 · 스케줄링

- **기간** · 2026.02
- **팀 / 역할** · 본인 주도
- **규모** · 기존 12개 작업 → 8개 systemd 배치 (5분 3 / 1시간 3 / 1일 2)
- **스택** · Python (motor, asyncpg, azure-data-tables, asyncio), MongoDB, PostgreSQL, systemd, pg_cron, Supervisor (이전 환경)
- **핵심** · 메모리 데몬 → DB 스케줄러 + systemd 개별 배치, per_site 타임존 처리로 다지역 사이트 통합 집계

---

기존에 데이터 수집을 담당하던 작은 레포가 하나 있었다. Supervisor가 띄운
**단일 파이썬 데몬**이 안에서 메모리 기반 스케줄러로 **12개**의 작업을
돌리는 구조였다. 작은 회사에서는 흔히 보는 모양이고, 처음엔 이게 깔끔해
보이지만 시간이 지나면 운영이 거의 항상 어딘가에서 막힌다. 이걸 우리 표준
배치 레포 위로 옮겨, **12개 → 8개 systemd 배치 서비스로 통합·분리**하는
작업을 맡았다.

## 어떻게 시작됐나

사실 이건 단순한 이관이 아니라, **운영 모델 자체를 갈아끼우는 작업** 이었다.
기존엔 모든 작업이 한 데몬 안에서 도니까 어디 한 곳이 죽으면 전체가 멈췄고,
재실행 단위도 모호했다. 스케줄도 메모리 안에서 관리되니 무엇이 언제 돌았고
다음에 언제 돌아야 하는지가 사람의 머릿속에만 있었다.

새 구조에서는 **각 작업을 개별 systemd 배치 서비스로 분리**하고, **스케줄을
DB 테이블로 옮기고**, 로깅·실행 기록·슬랙 알림 같은 공통 인프라는 표준
배치 레포 쪽에 깔아둔 common 모듈을 그대로 쓰는 그림을 잡았다. one-shot
으로 실행되고 끝나는 단순한 배치들이고, 스케줄링은 별도 데몬 서비스가
DB의 스케줄 테이블을 보고 시간이 되면 해당 배치 서비스에 start 명령을
던지는 식이다.

## 언어를 다시 정해야 했다

옮기는 김에 언어를 바꿀까 하는 얘기가 잠깐 나왔다. Node.js나 Java도 후보에
있었다. 결론은 **Python을 유지하는 것**이었고, 이유는 단순했다. 기존
data-collector가 Python으로 짜여 있고 핵심 라이브러리(motor, asyncpg,
azure-data-tables)가 다 같다. 집계 쿼리 로직을 거의 그대로 이식할 수
있다는 게 가장 큰 가치였다. 언어를 바꾸면 타임존 처리나 MongoDB 쿼리 같은
미묘한 곳에서 버그가 새로 들어올 위험이 있는데, 그 위험을 굳이 안고 갈
이유가 없었다.

운영 일관성도 컸다. 표준 배치 레포에는 이미 Python 배치용 템플릿이
있었고, **단일 yaml 정의 파일에 한 줄 추가하는 것만으로 systemd 서비스가
자동 생성되는** 환경이 깔려 있었다. Python으로 가면 그 모든 인프라를 그대로
탈 수 있었다. 언어 선택에서 화려함보다 **기존 자산을 최대로 재활용하는 게
가장 보수적이면서 가장 확실한 선택**이었다.

## 12개를 8개로 묶었다

작업 분류부터 다시 했다. 기존 12개 작업을 들여다보니 비슷한 결의 작업들이
같이 묶이는 패턴이 보였다. Azure Table → MongoDB 복사 두 개, 게이트웨이
집계 두 개, 시간/분기/일별 전력 사용량 세 개. 매번 따로 굴릴 이유가 없는
것들이었다.

최종적으로 **5분 단위 3개, 1시간 단위 3개, 1일 단위 2개의 8개 배치 서비스**로
정리됐다. 작업 갯수를 줄이는 게 목적이라기보다, **장애 격리 단위와 스케줄
주기가 같은 것끼리 묶고, 다른 것끼리는 분리한다**는 원칙이 결과적으로 12 →
8을 만들어냈다. 예를 들어 장치 상태 일별 집계는 hourly 작업과 데이터 의존성도
없고 주기도 다르니까 따로 빼서, 한쪽이 실패해도 다른 쪽 재실행이 자유롭게
했다.

## 타임존이 또 등장한다

가장 신경 쓴 부분 중 하나가 **타임존**이었다. 우리 사이트는 한국에만 있는
게 아니라 여러 지역에 흩어져 있고, "그 지역의 정시 직후"를 기준으로 시간별
집계가 돌아야 하는 작업들이 있었다. 이걸 사이트별로 배치를 따로 띄우면
관리가 폭발한다. 그래서 단일 배치가 매시 10분에 돌면서 **그 시점에 "로컬
시간 기준 정각을 막 지난 사이트들"** 만 골라서 집계하도록 짰다.

UTC 01:10에 배치가 돌면 Asia/Seoul은 로컬 10:10이고, America/New_York은
20:10(전날), Europe/London은 01:10이다. 각 사이트별로 로컬 시간 기준 정시를
막 지난 첫 실행을 잡는 패턴이라, 사이트가 어느 지역에 있든 자기 로컬 시간으로
"매시 10분"에 집계가 도는 효과가 난다. `timezone_utils` 라는 작은 헬퍼
모듈에 이 로직을 모아뒀고, hourly 배치 중 `per_site` 모드인 것들이 이걸
공유한다.

## 배치 한 개가 어떻게 생겼나

각 배치는 크지 않다. one-shot 실행 패턴이라, **시작 시점에 처리할 시간
윈도우를 계산하고, MongoDB·PostgreSQL 커넥션을 async context manager로
잡고, 집계 로직을 한 번 돌리고, 결과를 기록하고 끝난다**. 실패하면 공통
실행 로거가 슬랙 알림까지 같이 발사한다. 시작·종료·실패 로그가 어느
배치든 같은 테이블에 같은 포맷으로 남기 때문에, 운영 시점에서는 어디서
무슨 일이 일어났는지 한 곳에서만 보면 된다.

스케줄링은 자기가 안 한다. cron 표현식과 timezone 모드가 DB의 스케줄
테이블에 들어가 있고, 5분/1시간/1일 단위 스케줄이 거기서 관리된다. 별도의
스케줄러 서비스가 이 테이블을 보고 시간이 되면 해당 배치 서비스에 start
명령을 던지는 식이다.

## 그래서 무엇을 배웠나

이 작업을 끝내고 가장 명확하게 느낀 건, **운영 모델을 갈아끼울 때 가장
큰 비용은 코드가 아니라 사람의 머릿속을 갈아끼우는 것**이라는 점이었다.
"이 작업이 지금 돌고 있나?", "다음 실행은 언제지?", "한 번 실패하면 어떻게
재실행하지?" 같은 질문에 답이 명확하게 떨어지는지 — 그게 실제로 운영
부담의 대부분을 결정한다. 메모리 스케줄러에서 DB 스케줄러로 가고, 단일
데몬에서 개별 systemd로 가고, Supervisor에서 systemd로 간 것 모두 같은
방향이었다. **상태와 결정을 사람의 기억이 아니라 시스템의 기록으로 옮기는
일.**

언어를 그대로 둔 것도 같은 결의 결정이었다. 화려한 선택이 아니라 가장 잘
알고 가장 잘 옮길 수 있는 도구를 고르는 게 마이그레이션이라는 종류의 작업엔
거의 항상 옳다.

다시 한다면 **테스트 데이터셋과 검증 자동화**를 더 일찍 깔고 들어갈 것
같다. 12개를 8개로 묶는 과정에서 의도치 않게 누락된 케이스가 있을 수
있으니, 기존 data-collector와 새 배치를 같은 입력으로 돌려서 출력을 비교하는
diff 스위트가 있었다면 이관 검증이 훨씬 안전했을 것이다. 다음 비슷한 작업이
있다면 그 부분을 먼저 만들고 시작하려 한다.
