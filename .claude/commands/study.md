# /study — 기술 학습 정리

기술 스택, 개념, 도구를 대화로 깊이 정리하고 `Study/기타/<카테고리>/<주제>.md`에 저장한다.

아래 Phase 1·2는 이 대화형 흐름을 다룬다. 강의·논문 자료를 정리하는
`Study/강의/`·`Study/책/`·`Study/아티클/` 노트는 [자료 기반 노트 규칙](#자료-기반-노트-규칙)을 따른다.

문체·도형 표기는 한글 문서 공통이라 CLAUDE.md의 Language Policy 절에 있다.

## Steps

### Phase 1: 대화

1. 안내 메시지로 시작:
   > 학습 정리를 시작합니다. 어떤 기술이나 개념을 공부하셨나요?
   > 알고 있는 것, 헷갈리는 것, 궁금한 것 자유롭게 이야기해주세요.
   > 마무리하려면 `정리해줘` 라고 말씀해주세요.

2. 주제가 정해지면 **항목을 먼저 나열**해서 사용자가 어디부터 깊게 갈지 선택하게 한다 (대주제일수록 효과적):
   - 예: "React 19" → 주요 항목 10개+ 나열 → 사용자가 깊게 보고 싶은 것 표시
   - 예: "Zustand" → 핵심 개념 5개 나열 → 비교 대상(Redux/Jotai) 같이 거론

3. **심층 질문**으로 대화를 이끈다:
   - 핵심 원리(어떻게/왜 동작하나) — 피상적 답변 금지
   - 실제 사용 시나리오 / 안 쓰는 경우
   - 비슷한 개념과의 차이 + 트레이드오프
   - 자주 틀리는 부분 / 함정
   - 본인 프로젝트와의 연결

4. 사용자가 "잘 이해 안돼", "그게 뭔데" 등으로 되물으면 **풀어서 다시 설명**. 비유/배경/단계별 흐름을 활용. 빽빽하지만 친절하게.

5. 외부 라이브러리/프레임워크 사실 확인이 필요하면 **context7 MCP 사용** (`mcp__context7__query-docs`). 추측 금지.

6. 사용자가 `정리해줘` 입력 시 Phase 2로 전환.

### Phase 2: 문서화

#### 1. 주제·분량 확정

- 주제명 확인: "주제명 이렇게 가도 될까요? 또는 '알아서 해봐'"
- **분량이 큰 주제는 문서 분리 제안**:
  - 예: "기본 / 버전별 변경사항"
  - 예: "라이브러리 사용법 / 내부 동작"
  - 사용자에게 "한 문서 vs 분리" 묻고 진행

#### 2. 카테고리 확정 + 파일 경로

`Study/기타/README.md`의 17개 카테고리 중 하나를 선택. 카테고리 폴더가 없으면 생성.

```
Study/기타/<카테고리>/<주제>.md
```

**규칙:**
- 파일명에 **날짜 포함 X** (변경 이력은 git이 관리)
- 폴더명: README의 카테고리명 그대로 (예: `언어/`, `프론트엔드/`, `모바일/`)
- 주제명 한글/영문 자유 (검색 잘 되는 형태로)
- 예: `Study/기타/프론트엔드/Next.js-기본.md`, `Study/기타/언어/TypeScript-종합정리.md`

#### 3. 문서 작성 — 템플릿

```markdown
# <주제>

> <YYYY-MM-DD> | <태그 3-5개 (쉼표 구분)>

## 한 줄 요약

<이 기술/개념의 본질을 한 문장으로. "빠르다/편하다" 같은 피상적 표현 금지.>

## 핵심 개념

### 왜 <이 기술>을 쓰는가
<해결하는 문제, 기존 방식의 한계, 비교 대상>

### <핵심 개념 1>
<원리/동작 방식. 코드 예제 + 설명.>

### <핵심 개념 2>
...

## <섹션 — 주제에 맞춰 자유롭게 분할>

### <세부 항목>
- 동작 원리
- 코드 예제
- 함정

## 핵심 질의응답

**Q. <대화에서 실제 나온 질문>**
A. <답변 — 1-3문장>

(대화에서 나온 인사이트 수만큼 추가. 만들어내지 말 것)

## 주의사항 / 자주 하는 실수

- <함정 1 — 왜 함정인지 한 줄로>
- <함정 2>

## 참고

- [공식 문서](URL)
- [관련 문서](상대 경로) ← 같은 Study 안의 다른 문서 상호 링크
```

**문서 작성 톤 가이드:**
- 빽빽하지만 읽기 좋게 (적당한 빈 줄, 표/리스트/코드 적극 사용)
- 코드 예제는 짧고 핵심만
- "왜 그렇게 설계됐나" 같은 본질 짚기
- 표는 **실질적인 차이가 있을 때만** 사용
- 같은 시리즈 문서들끼리 **상호 링크** (예: 기본 ↔ 변경사항)

#### 4. 초안 확인

작성 후 사용자에게 **구조 요약** 보여주고 확인:
- 어떤 섹션 들어갔는지
- 어떤 깊이/범위로 다뤘는지
- 수정할 부분 묻기

#### 5. README 업데이트

문서 작성 후 **반드시 두 README 업데이트**:

1. **`Study/기타/README.md`** — 해당 카테고리 행에 링크 추가, 상태 (`✅` 또는 `🟨`)
2. **`README.md` (루트)** — `기술 학습` 표의 해당 카테고리 행에 `(✅ 주제명)` 표기

#### 6. 커밋 / PR / 머지

```bash
git checkout main && git pull origin main
git checkout -b docs/study-<주제-슬러그>
git add Study/기타/<카테고리>/<파일명>.md Study/기타/README.md README.md
git commit -m "$(cat <<'EOF'
docs(study): <주제 1-2문장 요약>

Co-Authored-By: Claude Opus 4.7 (1M context) <noreply@anthropic.com>
EOF
)"
git push -u origin docs/study-<주제-슬러그>
gh pr create --title "docs(study): <주제>" --body "<문서 구성 + 핵심 포인트 요약>"
```

**머지는 사용자 승인 후에만 진행** (CLAUDE.md 룰). "머지해줘" 명시 시:
```bash
gh pr merge --squash --delete-branch
git checkout main && git pull origin main
```

여러 PR을 동시에 머지할 때 conflict 발생 가능 — 후속 PR을 main에 rebase하거나 cherry-pick 필요.

## 자료 기반 노트 규칙

강의·책·논문처럼 **원자료가 있는** 학습을 정리할 때 지킨다
(`Study/강의/<강의명>/S<nn>-주제.md`, `Study/책/<책명>/`, `Study/아티클/`).
`/study`의 대화형 흐름으로 만드는 `Study/기타/` 문서에는 해당하지 않는다.

### 본편과 부록을 나눈다

한 문서에 자료 요약과 추가 인사이트를 섞지 않는다.

| | 담는 것 |
|---|---|
| 본편 `SNN-주제.md` | 자료에 있는 내용만. 절 구성도 자료의 흐름을 따른다 |
| 부록 `SNN-N-주제.md` | 대화로 도출한 인사이트, 다른 개념·계보와의 비교, 검증할 가설 |

- 부록은 상단에 `성격` 메모로 어느 절에서 갈라져 나왔는지 적고, 본편에서 링크를 건다
- 본편에 자료 밖 내용을 넣어야 하면 인용 블록(`>`)으로 짧게만 표시한다
- 사용자가 질의로 파고든 결과는 기본적으로 부록 대상이다
- 한 회차가 크면 `SNNA`·`SNNB`로 쪼갠다. 여러 회차를 묶는 부록은 `S05-06-1` 형태
- 부록 제목은 짧고 건조한 명사구로. 콜론·괄호로 부제를 달지 않는다.
  기존 결: `자동구축의 천장`, `추출 이후 빠진 것들`, `OTKM이 정하지 않은 것들`

학습 방식이 "자료 요약 + 질의를 통한 추가 인사이트"인데 둘이 한 문서에 섞이면 나중에 다시 볼 때
어디까지가 자료 내용이고 어디부터가 우리 해석인지 구분되지 않는다.

### 자료가 갈리면 판정하지 말고 병기한다

논문·자료가 서로 다른 결정을 내리면 어느 쪽이 옳은지 결론짓지 말고 "여기서 갈린다"고 적는다.
노트는 나중에 판단 근거로 다시 보는 물건이라, 내가 내린 판정이 자료의 사실처럼 굳으면 위험하다.
도메인·목적이 달라 애초에 비교 대상이 아닌 경우도 섞여 있다.

- 부록에 "충돌하는 지점" 절을 따로 세우고 각 쟁점을 `A ↔ B` 형태로 병기한다
- 한 논문 안에서 용어가 두 뜻으로 쓰이는 경우도 같은 취급
- 정리표는 합의하는 것 / 갈리는 것 / 미해결로 남은 것으로 나눈다
- 우리 요건에 맞춰 한쪽을 골라야 하면 골랐다는 사실과 버린 쪽을 명시한다 —
  "이 조합은 충돌에서 한쪽을 고른 결과이고 논문들이 합의한 그림이 아니다"처럼

### 사례 자료로 원론을 펴지 않는다

technical report·use case 성격의 논문을 다룰 때 추상적 담론(분야 전체의 공백, 20년 계보론)으로
끌고 가지 않는다. 가져다 쓸 구체적 설계 결정을 뽑는다. 소절을 잘게 나누는 것도 피한다 —
원론이라 나눌 게 없어서 억지로 쪼갠 티가 난다.

## Rules

- **피상적 설명 금지** — "편리하다/빠르다" 수준 X. 동작 원리, 트레이드오프, 함정까지.
- **핵심 질의응답은 대화 기반** — 만들어내지 말 것
- **외부 라이브러리/프레임워크 사실은 context7로 검증**
- **문서 초안은 반드시 사용자 확인 후 커밋** (CLAUDE.md 룰)
- **README 두 개 (루트 + Study) 모두 업데이트**
- **파일명 날짜 X** — 폴더 분류 + git history로 충분
- **분량이 길면 분리 제안** — 기본/변경사항, 사용법/내부동작 등
- **항상 `Work` 레포의 `Study/기타/<카테고리>/`에 저장**
- **시리즈 문서끼리 상호 링크**
