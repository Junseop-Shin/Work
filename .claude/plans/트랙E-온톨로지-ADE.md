# 트랙 E — 온톨로지 ADE (Protégé 대체)

> **상태: 개념 스케치.** 구체화는 나중에. 여기서는 "무엇을 만드는 것이고 왜인가"까지만 정한다.

## Context

온톨로지 편집의 표준 도구가 **Protégé**(2000년대 Java 데스크톱 앱)다. 20년째 사실상 표준이지만
데스크톱 앱이고, 그 주변(버전 관리 · CI · 문서 생성 · 배포 · LLM)이 통째로 비어 있어 도구를 여러 개 갈아타며 써야 한다.

[트랙 A](../../Study/강의/온톨로지-지식그래프/README.md)의 S02에서 정리한 **FAIR 논문의 출판 4단계**(URI 설계 →
문서화 → Web 공개 → 통합 프레임워크)가 사실상 이 도구의 요구사항 명세다. 그리고 그 4단계를 묶으려는 기존
시도(ODK · OnToology · VoCol · PoolParty)가 있지만 전부 **CLI·파이프라인 도구**이고 에이전트를 전제하지 않는다.

**목표** — **Protégé를 대체하는 단일 end-to-end 온톨로지 개발 환경.**
편집부터 검증 · 문서 · 배포까지 하나의 도구 안에서 하고, **GUI로 온톨로지를 직접 다룰 수 있게** 만든다.
그리고 에이전트가 초안을 쓰고 사람이 GUI에서 감독하는 구조(**ADE**, Agentic Development Environment).

## 왜 온톨로지가 에이전트에게 유리한 작업인가

이게 이 트랙의 존재 이유다.

> **온톨로지는 산출물이 기계 검증 가능하다.** 추론기가 모순을 잡고, SHACL이 제약 위반을 잡는다.
> 즉 **에이전트 루프에 필요한 채점 함수가 이미 도메인에 존재한다.**

코드에서 테스트가 하는 역할을 온톨로지에서는 추론기가 한다. 대부분의 에이전트 적용이 "채점을 어떻게 하나"에서
막히는데, 여기는 그 문제가 처음부터 풀려 있다. (S02 7.3절)

채점 기준이 없는 새 도메인에서는 **CQ(Competency Question)가 테스트 역할**을 한다 —
CQ를 SPARQL로 적어두면 그게 곧 테스트 스위트가 된다. (S02 7.4절)

## GUI 우선 — 무엇을 개선하는가

Protégé의 기능 목록을 베끼는 게 아니라, **Protégé에서 불편한 지점**을 GUI로 푼다.

| Protégé에서 | 이 도구에서 |
|---|---|
| 데스크톱 Java 앱, 협업은 WebProtégé로 갈아타야 함 | **웹 기반 단일 환경** |
| 추론기를 수동 실행 → 결과를 별도 창에서 확인 | **편집 중 실시간 추론·검증 피드백** (상속·모순이 즉시 보임) |
| 계층 트리 · 관계 · 추론 결과가 창마다 흩어짐 | **그래프 뷰에서 직접 조작** (드래그로 관계 연결) |
| 기성 온톨로지 상속이 URL 직접 입력 수준 | **등록소 검색 + 임포트 마법사** (BioPortal · LOV · OBO Foundry) |
| 저장하면 RDF/XML — diff가 안 읽힘 | **정규화 Turtle로 저장 → PR 리뷰 가능** |
| 문서·배포는 별도 도구(WIDOCO · OnToology) | **같은 화면에서 문서 생성·배포** |

**임포트 마법사가 특히 값이 있다.** [S03-2 1절](../../Study/강의/온톨로지-지식그래프/S03-2-추출-이후-빠진-것들.md)에서
정리한 상속 선택 기준(유지 상태 · IRI 영속성 · 라이선스 · 상위 정합성)은 강의에도 없고 Protégé도 돕지 않는다.
등록소를 검색해 후보를 비교하고 모듈만 잘라 임포트하는 흐름은 GUI가 실제로 유리한 자리다.

> **한 가지 위험은 미리 적어둔다.** 편집 UI는 Protégé의 20년치 기능 폭과 비교당한다.
> 그래서 초기 범위를 **자주 쓰는 편집 동작**(클래스·속성 추가, 계층 재배치, 관계 연결, 임포트)으로
> 좁게 잡고, 희귀 기능은 Protégé로 열 수 있게 **파일 호환만 유지**하는 게 현실적이다.

## 단계 (개념)

| 단계 | 내용 | 얻는 것 |
|---|---|---|
| **0** | 기존 스택으로 수동 한 바퀴 (Protégé → SHACL → WIDOCO) · **ODK 확인** · 병목 측정 | 무엇을 통합할지 확정 |
| **1** | **코어** — 온톨로지 읽기/쓰기 층 + **Turtle 정규화 직렬화** | GUI가 얹힐 기반, diff 보존 |
| **2** | **GUI 편집** — 클래스·속성·개체 편집, 계층 트리, 관계 그래프 뷰, 임포트 마법사 | Protégé 대체의 본체 |
| **3** | **검증 통합** — 추론기 + SHACL을 **편집 중 실시간 피드백**으로 | 모순·위반을 저장 전에 잡음 |
| **4** | **CQ = 테스트** — CQ 관리 UI + SPARQL/DL 질의 실행 + 통과율 | axiom 없는 도메인의 채점 기준 |
| **5** | **에이전트** — LLM이 초안·수정 제안, 2~4가 채점, 사람이 GUI에서 승인 | 구축 비용 절감 |
| **6** | **FAIR 공개** — URI · 문서 · 버전 · 배포 자동화 (ROBOT · WIDOCO 호출) | 만든 것이 실제로 쓰임 |

**1단계가 2단계의 전제다.** GUI로 편집해도 결과는 파일로 저장되고, **RDF/XML은 diff가 안 읽힌다.**
직렬화를 정규화해 텍스트 diff를 복구해두지 않으면 GUI 편집이 곧 리뷰 불가능한 커밋이 된다.
git · CI · 에이전트 편집이 전부 여기에 걸려 있다.

## 검증

단계마다 기준을 하나씩 쓴다.

| 단계 | 기준 |
|---|---|
| 1 | 온톨로지 변경 PR의 **diff를 사람이 읽을 수 있는가** |
| 2 | **Protégé로 하던 작업을 더 적은 단계로 끝내는가** (클래스 추가 · 관계 연결 · 임포트로 측정) |
| 3 | 모순·제약 위반이 **저장 전에** 잡히는가 |
| 4 | CQ 통과율이 나오는가 |
| 5 | **에이전트 제안의 수락률** |
| 6 | 공개된 온톨로지가 사람·기계 양쪽에서 열리는가 |

## 기존 도구와의 관계

**대체 대상과 통합 대상을 나눈다.**

| 도구 | 관계 |
|---|---|
| **Protégé / WebProtégé** | **대체 대상.** 단, 파일 호환을 유지해 희귀 기능은 Protégé로 열 수 있게 한다 |
| **ODK** (Ontology Development Kit) | **가장 크게 겹친다.** git 레포 구조 · Docker 환경 · ROBOT 릴리스 파이프라인 · GitHub Actions CI · 문서 생성을 이미 갖고 있다. **0단계의 첫 대상** — 겹치는 부분은 감싸고 GUI만 얹는 쪽이 빠를 수 있다 |
| **ROBOT** | **통합 대상.** 변환 · 모듈 추출 · report를 6단계에서 그대로 호출 |
| **pySHACL · ELK · HermiT** | **통합 대상.** 3단계의 검증 엔진 |
| **WIDOCO · OnToology** | **통합 대상.** 6단계 문서·공개 |
| **VoCol** | 선행 연구 (git 기반 + 문법 피드백). 무엇이 부족했는지 확인 |
| **OOPS! · Themis** | 안티패턴 검사 · CQ 기반 테스트. 3·4단계의 선행 연구 |

**바퀴를 다시 만들지 않는다.** 엔진은 대부분 이미 있다. 없는 것은 **그것들을 하나로 묶은 GUI 환경**이다.

**0단계 재료가 이미 있다.** 강의 S03C의 논문 ②가 **텍스트 기반 OL 도구 21개를 8기준·57개 하위 지표로
정리**해뒀다. 그중 ④ 사용자·전문가 개입(자동화 수준)과 ⑥ 상호운용성이 이 트랙의 판정에 바로 쓰인다.
그리고 그 21개는 전부 **추출** 도구여서, 이 트랙이 겨냥한 범위(편집 통합 · 버전 관리 · CI · 문서 · 배포)는
목록에도 기준에도 없다 — **비어 있는 칸이 실제로 비어 있다는 확인**이다.
→ [S03-1 8.4절](../../Study/강의/온톨로지-지식그래프/S03-1-자동구축의-천장.md)

**4단계의 실질적 난점은 CQ → 질의 변환이다.** S03C 논문들은 CQ를 DL 질의로 옮기는 일을 **수동으로** 했다.
채점(추론기)은 이미 기계화돼 있고 **채점 문항을 기계가 읽을 형식으로 옮기는 일만 사람 몫으로 남아 있다.**
LLM이 값을 내는 자리가 여기다 — 자연어 CQ → DL/SPARQL 번역, 검증은 추론기.
그리고 **CQ는 구축보다 먼저 고정돼야 한다** (사후에 지으면 답할 수 있는 질문만 고르게 된다).

## 순서 제약

```
강의 S02 (FAIR)  ──→  E(개념)      ✅ 완료 — 요구사항 명세 확보
강의 S09~S10 실습 ──→  E(0~1단계)   실제 병목을 알아야 착수 가능
Projects/ontology-pipeline  ──→  E(0단계)   이미 한 바퀴 돈 파이프라인이 재료
```

**강의 3주차(S09~S10) 이후 착수.** 그 전에는 무엇이 아픈지 추측으로 정하게 된다.
이미 [`Projects/ontology-pipeline`](../../Projects/ontology-pipeline/)에 정제 → RML → SHACL → GraphDB → SPARQL을
한 바퀴 돈 결과가 있어서 0단계 재료로 쓸 수 있다.

## 미해결

- **"Orca처럼"의 정확한 참조점** — ADE를 Agentic Development Environment(에이전트가 주 작업자,
  사람이 리뷰·감독)로 읽었다. Orca의 어떤 부분을 가져올지는 확인 필요.
  (관찰: 작업 디렉터리에 `.orca/drops/`를 만들어 스크린샷을 떨어뜨린다 — 워크스페이스를 인식하는
  로컬 도구로 보인다. 설정 파일은 레포에 없다)
- **배포 형태** — 웹앱 / 데스크톱(Electron · Tauri) / VS Code 확장.
  로컬 파일과 git을 다뤄야 하므로 순수 웹은 제약이 있다. GUI 우선 방향에서 가장 먼저 정해야 할 것
- **그래프 뷰의 규모 한계** — 클래스가 수천 개일 때 직접 조작이 성립하는지
- 대상 사용자 — 나 혼자 쓰는 도구인가, 팀 도구인가. 협업 기능의 우선순위가 갈린다
- Turtle 정규화를 직접 구현할지, 기존 도구(`rdfpipe` · `rapper` · ROBOT)로 되는지
- LPG(Neo4j) 계열도 대상에 넣을지 — 넣으면 검증 층(SHACL · 추론기)이 통째로 달라진다
