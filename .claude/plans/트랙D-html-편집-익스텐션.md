# 트랙 D — HTML 편집 크롬 익스텐션

## Context

AI로 HTML 문서를 만드는 일이 잦아졌다. 그런데 만들어진 결과물을 조금 고치려면 다시 프롬프트를 쓰거나 에디터를 열어야 한다. **브라우저에서 열어둔 그 HTML을 그 자리에서 고치고 저장**할 수 있으면 왕복이 사라진다.

백지에서 시작하는 Notion형 에디터가 아니다. **이미 존재하는 HTML을 대상으로 하는 편집기**다. 이 차이가 설계 전체를 결정한다 — 만드는 게 아니라 고치는 것이므로, 성공 기준은 "얼마나 잘 만드는가"가 아니라 **"안 건드린 부분을 얼마나 안 건드리는가"** 가 된다.

**목표**: 브라우저에 열린 HTML 문서를 편집하고, 편집 결과를 원본 마크업 구조를 보존한 채 저장한다.

## 핵심 난제 — 마크업 오염

이 프로젝트의 난이도는 UI에 있지 않다. **직렬화에 있다.**

`contenteditable`은 브라우저가 알아서 마크업을 생성한다. 붙여넣기 · 엔터 · 서식 지우기 같은 흔한 동작에서 `<div><br></div>`, `<font>`, `<span style="...">` 같은 쓰레기가 끼어든다. AI가 만든 깔끔한 HTML을 열어 몇 글자 고쳤을 뿐인데 저장하면 diff가 수백 줄이 되는 상황이 기본값이다.

그래서 설계 원칙 하나로 수렴한다:

> **새 마크업을 생성하는 순간을 최대한 뒤로 미룬다.**

기존 노드의 텍스트만 바꾸거나 기존 노드를 재배치하는 조작은 마크업 오염이 **구조적으로 불가능**하다. 새 노드를 만드는 기능만 오염 위험을 갖는다. 단계 순서를 이 기준으로 짠다.

## 두 번째 난제 — 저장

크롬 익스텐션은 로컬 파일을 직접 덮어쓸 수 없다.

- `chrome.downloads` — 새 파일로 내려받기. 가장 확실하고 제약 없음. **1차 선택.**
- File System Access API — 사용자가 핸들을 승인하면 원본 덮어쓰기 가능하나 확장 컨텍스트에서 제약이 있다. 필요해지면 그때.
- 클립보드 복사 — 폴백.

`file://` URL을 편집 대상으로 하려면 설치 후 **"파일 URL에 대한 액세스 허용"을 사용자가 수동으로 켜야 한다.** 이건 코드로 해결할 수 없으므로 README에 설치 절차로 명시한다.

## 단계

각 단계는 그 자체로 쓸 수 있는 물건이고, 다음 단계로 안 가도 손해가 아니다.

**1단계 — 읽기 전용 스파이크**
현재 페이지의 HTML을 읽어 사이드 패널에 구조 트리로 표시. 편집 기능 없음.
→ 검증하는 것: 권한 모델, content script 주입, CSP 충돌 여부, `file://` 접근. **기술 리스크를 편집 기능 없이 먼저 털어낸다.**

**2단계 — 텍스트 편집만**
요소를 선택해 `textContent`만 교체. `contenteditable`을 쓰지 않는다.
→ 마크업 오염 확률 0. 실제로 AI 생성 HTML을 고칠 때 필요한 작업의 상당수가 여기서 끝난다.

**3단계 — 블록 조작**
이동 · 삭제 · 복제. 기존 노드를 재배치할 뿐 새로 만들지 않는다.
→ 오염 확률 여전히 0.

**4단계 — 스니펫 삽입**
my-ui-lib 카탈로그에서 정적 HTML 조각 삽입. **여기서 처음으로 새 마크업이 생긴다.** 단, 삽입되는 마크업은 우리가 통제하는 고정 문자열이므로 브라우저가 생성하는 쓰레기와는 성격이 다르다.

**5단계 — 저장**
편집된 DOM을 직렬화해 다운로드.

## my-ui-lib 연결 (4단계)

**React 런타임은 넘어갈 수 없다.** 편집 대상이 정적 HTML이므로 React 컴포넌트를 삽입할 방법이 없다. 이식 가능한 것은 두 가지뿐이다:

1. **디자인 토큰** — Tailwind v4 테마를 CSS 변수로 추출 (`tokens.css`)
2. **마크업 패턴** — 각 컴포넌트가 렌더한 정적 HTML + 필요한 클래스 조합 (`snippets.json`)

이를 위해 my-ui-lib에 **새 빌드 타겟을 추가**해야 한다. Storybook이 이미 모든 컴포넌트를 격리 렌더하고 있으므로, 스토리를 정적 HTML로 뽑는 경로가 가장 짧다.

**순서 제약: [트랙 C](./트랙C-base-ui-전환.md)가 먼저다.** Base UI 전환은 컴포넌트가 렌더하는 DOM 구조를 바꾼다. 전환 전에 스니펫을 뽑으면 전환 후 전부 다시 뽑아야 한다.

[트랙 B](./트랙B-디자인-지식그래프.md)와는 엮지 않는다. 나중에 익스텐션이 `design_check`를 호출해 편집 중인 HTML을 검증하는 그림이 가능하지만, 그건 B가 실제로 쓸모 있다고 판정된 다음 이야기다. 지금 엮으면 D가 B에 종속돼 순서가 강제된다.

## 검증

단계마다 동일한 기준 하나를 쓴다:

> **편집 전 HTML과 편집 후 HTML의 diff가, 의도적으로 편집한 부분과 정확히 일치하는가.**

문서를 열어 한 글자만 고치고 저장했을 때 diff가 한 줄이어야 한다. 이게 이 프로젝트의 유일한 진짜 성공 기준이고, 1~3단계는 이 기준을 구조적으로 보장하도록 설계돼 있다. 4단계부터는 실제로 측정해야 한다.

테스트는 AI로 생성한 HTML 문서 몇 개를 픽스처로 두고 자동화한다 — 열기 → 편집 → 저장 → diff.

## 기술 결정

| 항목 | 선택 | 이유 |
|---|---|---|
| Manifest | V3 | 현행 표준 |
| 편집 UI | content script 주입 + `chrome.sidePanel` | 페이지 레이아웃을 건드리지 않음 |
| 저장 | `chrome.downloads` | 제약 없음. FS Access는 필요해지면 |
| 편집 방식 | `contenteditable` **사용 안 함** (2·3단계) | 마크업 오염 원천 차단 |
